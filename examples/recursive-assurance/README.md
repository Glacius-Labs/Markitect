# Recursive assurance fixture

This is a source- and target-owned example for recursive projection assurance. It defines four project-owned behavioral contracts: independent Orders and Billing leaf operations, Checkout glue that composes both, and Commerce glue that invokes Checkout twice and applies the shared Billing rule once to both checkout totals plus prior amounts. Four nonoverlapping .NET Projection roots mirror those scopes. The parent Projections explicitly select their own intent Definition and every descendant Definition; their own checks compile the explicit descendant roots as well as parent-owned source.

The configured check projects have closed compile inputs. They do not search for hidden implementation sources. Their literal commands are in `canonical.yaml`, with one exact required check per Projection Module. Each check uses the installed .NET SDK and framework references only; there are no package dependencies. Implementations remain candidate-owned files selected by an Executor within the declared target roots. Policies explicitly name the public classes, namespaces, operations and exception behavior consumed by these fixed checks. They constrain public APIs and semantics, not source filenames or templates; the checker does not silently supply an omitted target naming contract.

The bounded leaf checks cover invalid inputs, normal arithmetic and overflow. The Checkout check is independently parent-owned: it detects dropped order amounts and bypass of invalid Orders input even when both children pass. The Commerce check independently detects omission of either Checkout and failure to apply Billing's shared overflow rule. The recursive hierarchy is therefore not satisfied by leaf evidence alone.

`recursive_assurance_test.go` fixes canonical loading to full Git HEAD and checks exact pins, typed composition, selected scopes, policies, target roots and check bindings through actual `PrepareCanonicalProjection`. These fixture and structural compiler tests are not an Executor, Verifier or agent-behavior result. The frozen protocol requires fresh real Executor and independent Verifier runs; no new C9 success is claimed here. The historical C9 absence/failure remains unchanged.

No adopter data is included, and no check output implies human approval. A real adoption would require owner-selected source, review and authorization outside this public synthetic fixture.
