# Apply trial cases

Prepared cases for later real Apply runs, each answering one question about where Apply works reliably and which kinds of error it detects, repairs or correctly escalates. This directory is preparation for [#523](https://github.com/Glacius-Labs/Markitect/issues/523): fixtures, an answer key, independent checks and small helpers. It starts no Agent or provider, changes no Apply behavior and records no Apply result. Its self-check shows that the fixtures are consistent and that the checks discriminate; it does not show how Apply behaves.

**Everything here is operator material.** The models, realizations and faults are deliberate trial material, not product definitions. Agents receive only a packet: a fresh Git repository built by `materialize.py` with the case's model, the shared dependencies, the execution settings and, where the case has one, a realization and registry. The answer key, the checks, the validation overlays and this guide never enter a packet, and `materialize.py` refuses a packet that names them.

## Two projects, two levels

Complexity is set by rules, dependencies and responsibility boundaries, not by size.

- **stockroom (level 1):** one Package and Root, 11 Definitions, four commands. Rules: SKU normalization, quantity and name limits, stock limits, list order, one atomic data file. No rule crosses a responsibility boundary. Python 3.13 standard library, `python -B app.py --db PATH COMMAND`, layout exception `realization` → `stockroom` as in Roombook and Readinglog.
- **depot (level 2):** five Packages and Root (six Managers), 19 Definitions, eight commands. The SKU rule of `catalog` is used by `stock`, `orders` and `reports`; the availability rule of `orders` (on hand minus open reservations) is used by order admission and both reports; the stock limit of `stock` must hold under fulfilment; every command commits all parts' changes in one atomic file write owned by `depot`. Each domain Package owns `realization/<package>/` with its tests; `depot` owns `app.py`, the README, the end-to-end tests and the shared foundations.

Both share the Core and Software dependency inputs of [Library r2](../test-projects/library-r2/README.md) byte for byte; `materialize.py` copies them from there.

## The cases

Each failure class is first tested alone on stockroom; D-M combines several classes across depot's boundaries. [answer-key.md](answer-key.md) holds the exact edits and expectations.

| Case | Question | Start | Expected |
| --- | --- | --- | --- |
| S-N | A conforming stand stays unchanged? | reference | Verified, `no_change` |
| S-D | Two code faults under the unchanged model, one caught by the project tests and one only by the model, repaired with nothing else changed? | reference with faults | Verified, applied, both repaired |
| S-A | Code, tests, README and configuration contradict each other, including a passing test of wrong behavior: resolved toward the model? | reference with faults | Verified, applied, all four repaired, the wrong test corrected |
| S-G | Model-only Apply: built from the model alone, internal choices decided without escalation? | model only | Verified, applied, no `model_defect` |
| S-Q | A gap that changes boundary behavior (what `issue` does beyond the stock) reported instead of decided? Minimal pair of S-G. | model only | `model_defect`, nothing published |
| S-X | Two Definitions contradict each other (SKU case) while the artifacts follow one: reported? | reference | `model_defect`, nothing published |
| S-O | Three valid but unnecessary restrictions (fixed error text, fixed file format, prescribed limits module) realized without relaxing or escalating them? | reference | Verified, applied, all restrictions met |
| S-C | The model change 0.1.0 → 0.2.0 (limit 500, reorder points, `list --low`, old data stays usable) realized on the actual result of S-G? | previous result | Verified, applied |
| S-F | A second Apply on a Verified, committed result changes nothing? | previous result | Verified, `no_change` |
| D-N | The conforming six-Manager stand stays unchanged? | reference | Verified, `no_change` |
| D-M | Six faults in five areas (behavior, a passing wrong test, a README error, a rule rebuilt outside its owner, a registration in the wrong shard, a fault the tests catch) repaired by their owners? | reference with faults | Verified, applied, all six repaired |
| D-G | Model-only Apply of the six-Manager project, shared rules realized once by their owners? | model only | Verified, applied |
| D-F | Follow-up no-change on a Verified depot result? | previous result | Verified, `no_change` |

Expectation rules, as stated by DEC-063 and the trial assignment: a conforming stand stays unchanged; repairable artifact drift is repaired against the unchanged model; internal design freedom is decided within the model; a behavior-relevant gap or a contradiction in the model ends the run through Root's `model_defect` without publication; a valid overspecified statement is realized and not relaxed, and its usefulness is a separate modeling question.

## Self-check

From the repository root, with Python 3.13 and Git:

```text
python -B experiments/apply-trials/selfcheck.py [--project stockroom|depot] [--markitect PATH/TO/markitect]
```

It shows that every cited Definition exists; that each reference passes its profile and its own tests and each validation overlay passes its changed profile; that degenerate command lines fail; that each fault alone fails exactly its declared checks (and the reference tests exactly when declared) and a case's faults together fail exactly their union; that the reference fails exactly the declared checks of the `s2` and `o` profiles; that every case materializes and passes the leak audit and, with `--markitect`, `markitect check` and `context` at `HEAD` (D-M fails strict accounting with exactly its `registry.outside_area` finding, which Apply treats as start-stand drift under DEC-062); that the assessor judges unrepaired, partly and fully repaired starts, unchanged stands and model-defect reports correctly; that S-G → S-C → S-F and D-G → D-F chain through `--from-repo`; and that `answer-key.md` is current. A full run takes about eight minutes.

The checks execute the realization they assess. Run them on the trial host, not on a machine whose files the realization must not reach.

## Run a case later

Real runs need the owner's grant, credentials and a selected order; the commands below were not executed in this preparation. They reuse the [demonstration harness](../recursive-apply-demo/README.md) in WSL Ubuntu with Docker; `SRC` is the harness's source checkout of the build commit and `TAG` its first twelve characters.

```text
experiments/recursive-apply-demo/ra_build.sh SHA BUILD
docker build -f packaging/runtime/examples/python/Dockerfile --build-arg BASE=markitect-runtime:ra-TAG -t markitect-runtime-python:ra-TAG SRC
MARKITECT_STORE=trial-CASE experiments/recursive-apply-demo/ra_bind.sh BUILD ATTEMPT
python3 experiments/apply-trials/bind_profiles.py ATTEMPT "$(docker image inspect --format '{{.Id}}' markitect-runtime-python:ra-TAG)"
python3 -B experiments/apply-trials/materialize.py CASE ATTEMPT/repo [--from-repo EARLIER_ATTEMPT/repo]
python3 ATTEMPT/frozen/ra_runconfig.py ATTEMPT LABEL SHA DEADLINE "Apply the committed model."
ATTEMPT/markitect apply --repo ATTEMPT/repo --model .markitect/model.yaml \
  --dependency .markitect/dependencies/core/model.yaml --dependency .markitect/dependencies/software/model.yaml \
  --host-profile ATTEMPT/host/host.yaml --run-config ATTEMPT/run-config-LABEL.json > ATTEMPT/out/apply-LABEL.json
bash ATTEMPT/frozen/ra_cleanup.sh ATTEMPT
python3 -B experiments/apply-trials/assess.py CASE --repo ATTEMPT/repo --report ATTEMPT/out/apply-LABEL.json --output ATTEMPT/out/assess-LABEL.json
```

Pass the neutral owner request `Apply the committed model.` explicitly: the harness default names the Library. Give the deadline the project's `executionTime` (20 minutes for stockroom, 30 for depot) plus a margin. `--from-repo` copies the earlier repository with its uncommitted publication, commits that publication as accepted, then applies the case's model; the earlier repository stays untouched. For S-F and D-F with an `s2` model, pass `--previous` with a 0.1.0 realization to `assess.py` so the upgrade check runs.

## What to record

`assess.py` reports per run: whether the expected outcome was met; the oracle result; per fault whether it is repaired and whether a test now fails when the fault returns (required for a test that asserted the wrong behavior); the artifact checks; every changed path grouped by owner, with protected inputs and changes outside the fault files and allowed paths listed separately; rounds with their checks, turns, engine seconds and cost; and every finding with owner, raiser and text. The evaluator then decides which findings were false, whether a model-defect report names the right defect and nothing else, which repairs were made through the owner's realization, and records human interventions and wall time. Keep each run's evidence outside the repository, as the demonstration harness does.

## Recommended order

1. **S-N first:** the smallest complete run. It checks the trial wiring (Python image, profile names, check command, publication) against a known-good stand and gives the baseline of unnecessary changes. A failure here invalidates the other cases' setup, not Apply.
2. **S-D, then S-A:** isolated drift classes with exact expectations.
3. **S-X, then S-G with S-Q:** escalation; S-X and S-Q end within minutes when Apply behaves as intended.
4. **S-O, then S-C on S-G's result, then S-F.**
5. **D-N, D-M, then D-G and D-F:** the complex level only after the isolated classes are understood.

## Limits

- The checks execute agent-written code on the trial host; they are black-box, so an internal choice is judged only where the model binds it (`limits-module` in S-O).
- Detecting false findings and judging a model-defect report stay manual; `assess.py` lists the material and matches defect terms as an aid only.
- A regression test counts as present only when the repaired text of the fault is found unchanged; a restructured repair reports `not-applicable` and needs reading.
- The S-Q gap and the S-O restrictions encode the expectations of DEC-063 and this assignment; a real run may show that the owner reads a case differently, which is a finding about the case.
- `bind_profiles.py` was tested on the Host profile text that `ra_bind.sh` writes, not with Docker; the run commands above were not executed.
