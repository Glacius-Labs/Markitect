# Prospective Design comparison and migration questions

This addendum responds to the four public migration concerns in the Overseer's evaluation.md. It changes neither v3 requirements nor the closed rubric. It starts no trial and allocates none of the remaining eight-full-trial ceiling. The two research questions and maximum six matching cells proposed in prospective-repeat-proposal.md remain the proposed scope.

Design must first hand off a clean source/binary/configuration pin, executable public path, exact runtime/tool dependencies, native role contract and known limitations. Active WIP and a Luna High development smoke do not provide that freeze or comparative evidence. Keep the held Classic candidate distinct from Classic main; accepting a newer Classic version requires an explicit prospective pin decision. Use the same actual model/reasoning/tools and cumulative finite resources across Design, Classic and strong Conventional. Serving-identity uncertainty stays visible.

| Public migration concern | Shared observable outcome to declare before a future freeze | Method-specific assessment kept separate |
|---|---|---|
| Canonical model authority and maintenance | Released intent changes have one identifiable accepted source; a requested change preserves unchanged obligations and exposes unresolved authority/conflicts | Design/Classic model schema, acceptance and reconciliation receipts; Conventional may use its own clear engineering records without Design artifacts |
| Durable file ownership and coverage | Required changes and generated files have identifiable responsibility; no omitted required output or conflicting writer silently overwrites valid work | Product ownership/coverage declarations and stale checks where supported; Conventional uses its own explicit task/change review and tests |
| Usable Run/Resume/Repair/Verify/Apply | A bounded task can be interrupted and resumed, a stale/failed candidate is rejected, and accepted changes have current verification and a clear apply decision | Actual product commands/role state versus conventional branch/test/review workflow; no command or artifact parity imposed on Conventional |
| Brownfield conflict resolution and selective adoption | Existing released contracts and unrelated valid files survive a deliberate conflict and selective adoption; migration preserves attributable accepted evidence | Product-specific adoption/conflict/evidence migration semantics, separated from shared application behavior |

Before additional actual trials, translate only necessary common outcomes into public requirement wording and independent acceptance evidence. Review that wording for equal information and implementation freedom. A task designed to exercise a product-specific feature belongs in separately labeled method/readiness assessment unless an equivalent shared observable requirement can be declared for every arm. Do not silently expand the old order-service cards or score Conventional against a schema it does not use.

A six-cell proposal can address readiness/usable completion and then result-quality/intervention tradeoffs under the same two start conditions. It cannot establish reliability, variance or broad economic superiority. Any remaining two trial places require a finding-based separate grant, not automatic retries. Classic replacement additionally needs an explicit reviewed migration/compatibility path and integration decision; winning an exploratory case alone does not authorize main replacement.
