## Independent source review

The bounded source review found no remaining material blocker after two pre-test correction batches. The first aligned final-agent classification with the pinned `.162` `MessagePhase` value `final_answer`; the second latches the sanitized command receipt only after a validated successful command-completion event, preventing a later stale in-progress snapshot from replacing that proof. The source then passed one focused synthetic invocation: 12 test groups, 0.480 seconds, all passing. No test launched the native runner or app-server.

The client keeps the existing thread-only admission and response gates, startup-status observer, protocol-failure helper, stderr handling, and Job cleanup. It adds only `turn/start` to the fixed RPC sequence; `turn/interrupt` can be constructed once for stopping an owned active turn after its response has been validated. The unchanged three thread notifications still pass through both the original `ThreadGate` and collector. The ten fixed actor lifecycle notifications are admitted only after the turn request is sent; the separately schema-validated `error` notification is terminal. Unknown methods and server requests remain fail-closed.

The collector reconciles bounded early events against the returned thread and turn IDs, then requires exact thread/turn/item correlation, a single exact public read command, a successful completion event and the expected public sentinel. It rejects plugin/script-backed command items and a second command item. It uses the pinned `.162` final-answer phase, retains only the public sentinel, fixed command metadata, IDs, and allowlisted numeric usage counters, discards arbitrary message/reasoning/error text, and compares cumulative usage snapshots without summing them. The configured 10,000-token threshold is retrospective; it is not an in-flight cap.

The focused tests cover success and strict identity/policy gates, error and interrupt handling, early event correlation, foreign IDs, exact-command and second-command rejection, latest usage and threshold stop, stale command snapshots, malformed envelopes, and request/freeze binding. They use synthetic session frames; the passing cases establish client behavior against those fixtures, not a live server response, tool execution, provider behavior, billing, OS isolation, or broader S1 readiness. The actual `.162` schemas and exact method set are source-pinned, but schema validation alone does not establish event ordering. The independent request/freeze binding review and any live outcome remain separate evidence.
