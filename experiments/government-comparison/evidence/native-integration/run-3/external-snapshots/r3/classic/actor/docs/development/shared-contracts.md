# Shared contracts for parallel implementation

The [constitution](../engineering-constitution.md) owns invariants; this document records final technical ownership and stable contracts. A freeze holds inspected behavior constant during a dispatched wave; it is not a promise of indefinite binary or schema compatibility. Version labels remain the actual `v1alpha1` source labels. The dated [baseline](baseline.md) and [release receipt](../production-assessment.md#v0130-published-release) preserve historical evidence. The [consolidation decision](../design/clean-architecture-consolidation.md) owns the boundary rationale. The published v0.13.0 release remains unchanged by this source architecture. The accepted canonical reset is a separate source-only alpha; this table records historical v0.13 contracts unless explicitly marked as reset direction.

## External command seam

Project entries use `name`, `type: command`, `version` and `config`. Configuration requires exact `inputs` and `observe`, `plan`, `verify` argv. Apply is optional: `apply` argv and `allowApply` are declared together and require a non-secret `target`. There is no self-registration or independent `consumes`/capability manifest. The runner passes `adapter-request/v1alpha1`; responses use `adapter-result/v1alpha1`; saved envelopes use `adapter-plan/v1alpha1`, all under `markitect.example.org/`. Names select configured executables through a generic branch; adding a command implementation needs no provider switch in Core.

The saved command plan separately binds resolved executable bytes, declared version/configuration and the other reviewed inputs. The executable digest is not a field of the typed adapter identity. This binding is not a release attestation, trust certification, process sandbox or guarantee about remote state. Declared read-only actions remain a contract with the executable running under caller authority. Apply requires the existing explicit boundary and must reject altered/stale plans. A new remote provider adapter must define observed-state concurrency/precondition behavior and credential handling in its own design before writes are enabled.

Cross-command external-target exclusivity is **not enforced by a shared registry**. The target string binds a plan/response; it does not establish uniqueness or resolve aliases across adapters. Independent read-only adapters and deliberately disjoint isolated targets can start. Shared/overlapping writes wait for reviewed target ownership and concurrency semantics. Native renderer collision checks do not solve remote ownership. Do not invent an enforced registry in documentation or add a broad runtime to avoid this decision.

## Coordinator-owned changes

The coordinator owns shared Core contracts, Host composition/runtime seams, source identity, adapter DTOs/lifecycle/trust boundaries, package activation and controlled writes. Module implementers propose concrete changes with consumers, alternatives, compatibility/determinism/evidence tests and a focused design before editing shared contracts. One generic limitation needs repeated independent engineering evidence; a provider convenience does not justify Core expansion. See [Modules and static composition](modules.md) for the dependency law and Core request format.

The shared handoff is included in v0.13.0 outside Core and is documented in the [selective adoption contract](../design/selective-adoption-handoff.md). `prepare` owns explicit selection and capture; `copy-me` validates externally supplied records over the captured bytes. Their adoption boundary is shared, but no automatic root scan, content-driven scope expansion, reviewer authentication, conflict resolution, Project mutation or candidate adoption is introduced. Published v0.13.0 remains unchanged by the architecture work. See [adoption boundaries](adoption-boundaries.md).

## Canonical reset candidate contracts

The [reset design](../design/canonical-projection-reset.md) is authoritative for the new Core migration. Its Core model is a pure structural compilation result over Schema, Kind, Property and Definition; the historical Domain/policy kernel and consumers preserve their behavior behind Host compatibility. The old IR is not a shared contract for new Definitions, and no lowering creates a second canonical model.

Installable manifest type is closed: Schema-only (schemas, no projectors) or Projection-only (projectors, no schemas). Bundles are installation convenience. Go packages under internal/modules implement capabilities but are not themselves installable manifests. Canonical Projection contains spec.representation (initially dotnet or markdown), exact semantic scope, target and policies, not a concrete Module/projector. Runtime source configuration projectionBindings pairs full Projection identity in projection with exact installed Module name in module; Host resolves installed version pin and one unique internal entrypoint. Missing/ambiguous resolution fails. Compatible binding changes do not alter canonical semantic digest but stale request-bound plans and records. Module installation/configuration alone creates no Projection and materializes nothing.

The source alpha exposes explicit `controller-propose`, `controller-execute`, `controller-apply` and `controller-verify` actions; these do not create a background service or replace a future aggregate `plan`/`apply` workflow. The controller loads only the exact canonical source paths named by the selected config at the full source commits. It inventories metadata beneath configured target roots and reads content only for explicit affected/owned paths and required dependency evidence. Projection Modules own their independent proposal DTOs and decide work, no-op or escalation; Host validates and composes proposals, scope, file ownership and collisions. Execution follows the explicit finite assurance DAG child-first. Parent preparation gets child candidate bytes or selected observed active bytes, then all outputs remain staged for one guarded reviewed Apply. No Core traversal or composition language is added. No-op is not semantic PASS, and skipped evidence is not fresh. See the [proof-readiness decision](../design/proof-readiness-capabilities.md) and [candidate dependency design](../design/candidate-dependency-execution.md) for the accepted boundaries.

The operational markitect.example.org/projection-record/v1alpha1 contract (see [Module ownership](modules.md#operational-projection-evidence)) is distinct from canonical Projection intent. It binds exact Projection, full source revision, model digest, reviewed plan digest, pre-apply input snapshot digest, opaque Host binder request digest, Module/projector, scope/policies and materialized artifacts. Its target snapshot is derived from exact portable paths, byte digests and regular-file modes. Initial materialization changes are created, modified or retained; deletion is rejected. Record states are materialized-unverified, partial-failure or escalated. `materialized-unverified` means only that the candidate was materialized; verification runs later against immutable evidence. Record IDs bind deterministic normalized payloads, including the optional prior-record identity supplied by Host. Host supplies the request digest; records validate its format and bind it without reconstructing or claiming correctness of request composition. A predecessor link does not establish chronology unless the caller supplies and verifies that history.

markitect.example.org/verification-result/v1alpha1 is separate from the record. It binds record ID, canonical revision/model, post-target digest, verifier identity and exact declared check identities/outcomes. A passed result, when validated against expected Freshness, requires nonempty verifier/check digests, exactly all expected checks with no undeclared checks, and every outcome passed. These are caller-supplied facts: binding and validation do not authenticate the verifier or prove semantic independence or sufficiency.

markitect.example.org/artifact-ownership-index/v1alpha1 is a derived view over caller-selected active records and explicit inventory facts, never an append-history oracle. It indexes scope↔artifact ownership and rejects duplicate active owners. Unknown, excluded and ignored inventory roles remain visible. Freshness is checked against caller-supplied expected revision/model/plan/input/request digests, exact target inventory and declared checks. The controller Host persists attempts and verification results in an external append-only event ledger and updates the complete active record set through expected-head compare-and-swap. A materialized-unverified attempt may be retained in history, but active selection admits only complete ownership records. The ledger and active set do not establish authorization, human review or semantic acceptance; the index cannot claim missing history or infer full repository inventory.
