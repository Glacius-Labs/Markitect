# Codex projection workstream

## Context

Start from the full verified preparation integration SHA supplied in the assignment, as defined by [Baseline](../development/baseline.md). PR 59's `e9550f5` is the source audit base only; it omits these preparation contracts and is not the dispatch baseline.

At the PR 59 integrated baseline (`e9550f5c91430c6a65cbbd4ffcdbb49b48272537`), Codex files are generated by Markitect's built-in provider renderer. They consume the validated graph and captured files directly, not the external command `SemanticModel` DTO. Shared assumptions are owned by [the shared adapter contracts](../development/shared-contracts.md).

## Objective

Maintain or prepare bounded changes to the built-in Codex projection with explicit Project target selection, canonical resource ownership, deterministic output, and clear evidence limits.

## Scope

Codex-native Skill and Agent outputs under `.agents/skills/` and `.codex/agents/`, Codex Agent settings, and their focused tests. A separate integration with an external Codex-related service must be treated as a command adapter workstream with its own target and lifecycle design.

## Current implementation

`internal/render/render.go` selects the `codex` target and dispatches supported resources. `internal/render/agents.go` and related provider helpers produce provider files that route to canonical YAML or explicitly configured text. Project mappings and strict inventory are validated in `internal/app/outputs_provider.go`. The shared `markitect-render` reconciliation flow handles local generated-file drift and writes.

## Owned subsystem

Codex-specific templates, format helpers and tests can be separately owned in provider-specific files. `render.go`, shared path/collision/ownership helpers, shared Agent behavior, `provider_adapters.go`, CLI reconciliation, and common inventory are co-owned by the renderer coordinator.

## Allowed changes

- Make Codex-specific content or encoding changes in owned provider files with isolated tests.
- Add explicit Codex-specific fixtures and verify generated bytes against canonical sources.
- Propose new Codex paths/settings with one-owner-per-output, strict inventory and collision behavior specified.
- Explore external Codex system synchronization through a separate command adapter, defaulting to read-only observation and a disjoint target.

## Forbidden changes

- Do not interpret generated Claude or Markdown output as canonical input.
- Do not add provider-specific fields to generic Core solely for Codex integration.
- Do not change shared dispatch, Agent contract links, output inventory, or reconciliation without coordinator review.
- Do not add remote mutation or call external services from local `render`, `check`, `observe`, `plan`, or `verify`.

## Dependencies

Depends on existing Agent/Skill Domain data, `Project.spec.targets`, provider mapping settings, renderer ownership and output collision behavior. Shared changes require the [shared adapter contract](../development/shared-contracts.md) owner and Claude/docs renderer coordination.

## Design questions

- Is the work changing a local Codex file projection or integrating a remote Codex-related target?
- Which canonical Agent/Skill and fields own each output?
- Does a desired behavior exist in current Domain data, or would the proposal require a Domain contract decision?
- Are path/settings differences provider-specific and isolated, or changing shared Agent behavior?
- What does the output prove: configured content, not runtime behavior, tool access, or user acceptance?

## Required tests

Test Codex target gating, deterministic format/content, source links, explicit settings, per-file ownership, case-insensitive output collisions, and strict inventory as relevant to the change. A remote command adapter requires its own observe/plan/verify protocol and scope tests; remote writes need separate approval/design gates.

## Required evidence

Record source revision, Codex target/configuration, canonical resource/source digests, generated file paths and hashes, inventory findings, and test commands. For remote targets record adapter executable byte digest and version string separately, exact target/scope, and observation limitations; a binary hash is not signed provenance.

## Exit criteria

Codex output is deterministic, explicitly selected, owned by canonical resources, isolated from other provider outputs, and covered by focused tests. Any shared renderer edits are reviewed by the coordinator.

## Completion questions

- Are all changed outputs Codex-owned and derived directly from canonical model content?
- Is the behavior claim limited to generated/configured files?
- Did any shared renderer, path, ownership, or inventory hotspot change without coordination?
