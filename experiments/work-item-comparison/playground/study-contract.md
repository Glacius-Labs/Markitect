# Study contract: ordinary CLI user experience

Prospective clarification from the direct user, 2026-10-09. Preparation continues; actual study execution remains stopped. This contract owns the research question and interpretation of later data. Historical attempts and judgments are unchanged.

## Question and comparison

For an ordinary user working through Codex CLI, what benefits and disadvantages does Markitect add compared with strong conventional agentic coding on the same engineering work? Examine delivered behavior, intent/rule consistency, regression, changeability, recovery and the total work needed to achieve them. The transport is a controlled implementation detail, not the main treatment or a quality criterion.

The Markitect treatment is its actual usable installation: explicit canonical intent/model, dependencies/rules, genuine generated guidance/tools and its normal engineering workflow, including product-managed roles where applicable. Conventional gets ordinary clear project instructions, planning, testing, native helpers, review and self-directed repair. Do not weaken Conventional or make it reproduce Markitect's artifacts. Do not handcraft a Scientist workflow that substitutes for either method.

Possible benefits are fewer remaining rule/regression/rename inconsistencies and easier continuation or repair. Possible disadvantages are initial modeling/installation effort, ongoing model/view upkeep, coordination overhead, latency, extra model usage and product failures. Record evidence for either direction. A correct canonical model alone is not evidence of correct software; method artifact volume earns no outcome credit.

## User reference and control transport

The primary reference is a normal Codex CLI session: installed project instructions/Skills, the same short backlog request, ordinary shell/Git/tests/native helpers, and continuity of the project and conversation across released work. Use a fresh initial actor context per method/case/repetition; do not reset its context at every wave or inherit another arm's solution. Fixed wave boundaries represent incoming batches of user work, not Scientist coaching at each internal step.

The installed Codex CLI user flow is preferred for direct reference observations. A non-interactive CLI/SDK or App Server controller may automate the same work when it preserves the relevant semantics. Equality is a hypothesis, not established by sharing an executable. Before interpreting an automated run as a CLI approximation, bind the executable/model/effort, loaded instructions/context, project cwd, configuration, tools/MCP/Skills, permissions/approval behavior, session continuation, native helpers and available resources. Record differences and the approximation's evidence; unobserved parity stays unknown. Do not construct a separate readiness laboratory or run transport trials under this preparation scope.

Within each method pair, keep the same outer runtime/control path and general tool/resource baseline. Markitect's product MCP/CLI surface, generated guidance, model and internally scheduled roles are legitimate parts of its treatment, with their cost included. Product-internal App Server use does not require changing Conventional's outer controller. The harness does not schedule semantic implementation roles for either arm. MCP is an agent-to-product tool interface; App Server is a Codex execution-control interface. They need not compete for one slot.

Official [CLI reference](https://learn.chatgpt.com/docs/cli/reference) distinguishes interactive `codex` from non-interactive `codex exec`; [non-interactive guidance](https://learn.chatgpt.com/docs/non-interactive-mode) describes scripted operation. These documents explain interfaces, not behavioral equality in this study. No native runtime was probed or launched for this clarification.

Codex Luna High is the primary stratum for the requested CLI question. Claude Code Latest Sonnet is a separate secondary extension of the same question to its own ordinary user workflow, subject to genuine product provider support. Never pool the two runtimes as a method effect or substitute a mixed Claude/Luna Markitect run. No extra model or transport matrix is introduced.

## Fixed conditions and ordinary behavior

Use the existing GF/BF cases and public 1/3/7/1 work-item trajectory, shared requirements, dependency scope and assessment. Agents select architecture, decomposition, native helper prompts/branches and repairs themselves. The controller introduces no new hidden requirements, success instructions, response DTO lessons or candidate fixes. Existing case history is accessible; old study solutions, other arms and private evaluation data are excluded.

Use equal finite resource opportunity per pair, counting method-internal managers/helpers and Conventional's own helpers within the declared scope. Equal opportunity does not mean forcing identical helper counts or forbidding Markitect's actual mechanisms. Record enforcement versus observation versus unknown. Normal failures and agent-owned repairs remain part of execution and cost. Product failures affecting a normal user remain findings; do not retrospectively discard them to improve an outcome.

Before an authorized run, freeze pair inputs, implementation/evaluator versions, public criteria, allowed interventions, deadline/end rule, order and any repetitions. Counterbalance/randomize order where a finite design permits and retain the actual schedule. Fresh independent actors and checkouts prevent solution carryover. The existing four possible scenario/runtime pairs are preparation coverage, not a sample-size justification; repetition count remains a later finite design input, with no grant implied.

## Outcomes, effort and interpretation

| Evidence | Interpretation |
|---|---|
| Required behavior, regression, durable state, rule/rename consistency, maintainability | Common outcome quality, independent of method artifacts |
| Canonical model/view/check/realization agreement | Markitect conformance; explains mechanisms, not business success by itself |
| Setup, model authoring/upkeep, implementation, repairs, reviews, integration | Actual method work, including owner/Scientist/manual setup contributions; no free initial model |
| Wall time, agent activity, user/manual interventions, scoped usage/cost | Separate burdens; preserve overlap and unknowns, never substitute one metric for another |
| Loaded context/tools/rights, session/transport differences, resource exhaustion, infrastructure errors | Validity/context of an observation, with raw failures and reasons retained |

Use the same functional assessment and severity/scope rubric for both methods. Freeze independent evaluator inputs and any additional public-spec test cases before execution; they add cases, not secret requirements. Hide arm labels and transcripts from functional checking where possible, but do not claim full blinding when repository artifacts reveal the method. Review method conformance separately, without repairing the candidate or teaching later actors from previous results.

Compare observed outcomes and effort at the same scope/budget/end rule; incomplete work and time to completion are both recorded. Keep setup and steady-state work visible separately, and show total observed effort as well. Do not invent a weighted winner, statistical confidence or economic benefit from one small pair. Four stages of one project are dependent observations. These small synthetic projects approximate a bounded user workflow; they do not establish effects on all real repositories or human acceptance. Evidence must distinguish mechanism observations, outcome observations, plausible explanations and untested hypotheses.
