# Product-utility falsification notes

This note records observations that can count against Markitect's product thesis. It is evidence from one assigned task on a fixed public architecture-reference snapshot, not evidence of customer demand or a controlled productivity comparison. The cold task is “add `GetMeetingAttendeeCount`”; the user did not independently request that feature. The repository is the MIT-licensed `modular-monolith-with-ddd` snapshot at `91c8ef24b4cb6ef558c95d8267fa07d68c7059f8`, extracted to 646 upstream files (711,461 bytes), with API, Infrastructure, full solution, most tests, and runtime/database configuration excluded. See `source-selection.md` and `provenance.md` for boundaries.

## Evidence available before the assisted run was frozen

The baseline evidence ledger records 17 content reads, four searches, and one logged mistake/correction. Three guessed file paths were absent; empty invalid records were removed, then filename inventory and valid analogous code located the SQL connection factory and query handler. The inventory records 647 paths including snapshot metadata. This is observable repository-navigation friction. The report also identifies one low-value extra read (`GetAllCountriesQueryHandler.cs`) after the scalar-count convention was found. The ledger does not establish that Markitect would prevent this exploration or save a repeatable amount of time.

The baseline run records start/end wall-clock timestamps of 04:38:49.702 and 04:46:08.962 (+02:00), an observed elapsed time of about 7 minutes 19 seconds. This is one uncontrolled run, not a repeatable or comparative timing measure. Model/tool call counts and token counts were not instrumented. Byte counts are not token estimates. The run cannot establish a productivity effect.

The selected snapshot already contains project-owned Meetings architecture tests for immutable Query types, QueryHandler naming, handler visibility, validator naming/visibility, and several command conventions. The chosen task adds a Query and handler in that same module. A short adopter-owned `AGENTS.md` entry pointing to those tests and the existing read ADR could plausibly give a new agent the needed convention with much less machinery. This alternative has not been run as a separate arm, so equivalence is a falsification hypothesis, not a measured result. A simple text instruction alone would also not replace the existing executable test.

The existing architecture test is narrower than the Markitect package and is already a local enforcement source for several of the same facts. If Markitect is adopted, owners must keep the Domain, package versions, resource inventory, tests, and human-owned ADRs coherent. The frozen pilot model has 65 resource YAML files totaling 36,551 bytes, two complete architecture Domain definitions of 185 and 205 lines (390 lines and 13,216 bytes combined), plus two package manifests and two workflow definitions. The normalized model contains 69 resources. The Domain definitions are versioned copies, not inherited layers. This is visible authoring and maintenance work; whether governed policy evolution offsets it is not demonstrated by one selected validator change.

Copy Me is a bounded, investigator-selected dossier of 10 relevant files, not an autonomous discovery or representative sample. Its candidate records counterevidence and exact ContextRun identities; its human adoption decision remains pending. No adoption effort or recurring maintenance cost has been measured.

During model preflight, review caught draft relation-path and namespace/area mismatches before the package was frozen. These are adopter authoring errors caught by validation/review, not shipped Core defects. They are still friction in authoring a Markitect package; no time or repair count beyond these observed categories is claimed.

## Frozen architecture context review

The exact v0.12.0 `context-skill` capture at source revision `fd94a689aab857704c3a4a45ac2abe0fc0e3185c` passed with `provisional: false`. It serializes 26 input records to 52,873 UTF-8 bytes: 11 typed resources, 3 definition inputs (Project, Package, Domain), and 12 declared source/document inputs. The normalized graph has 69 resources, so the context selected 11 of 69 typed resources (about 16%) and supplies each inclusion reason and relation path. This is positive evidence of bounded, explainable context selection. It is a serialized byte measurement only, not a token count or proof of reduced end-to-end context.

Compared with the baseline ledger's reported 17,372 bytes of logged file reads, the context output is about 3.04 times larger. The raw-source audit reconciled all 17 records: 17,405 source bytes versus 17,372 decoded-content bytes because 11 BOMs account for the difference; six digests match raw files and eleven match BOM-decoded content. The source manifest independently binds raw upstream bytes. This is not an apples-to-apples total-context comparison: the baseline did not meter prompt text, search output, inventory output, or model working state, while the Markitect figure is a single serialized context artifact. The capture does not support a claim that this task received less raw context material. Four of the 12 declared file inputs are project files for BuildingBlocks Domain/Infrastructure and Meetings Domain/IntegrationEvents, which appear unnecessary for adding a Query in Meetings Application even though they describe architecture ownership and project composition. Treat them as possible context noise, not a proven waste without the assisted run evidence.

The capture includes the existing attendee Query/Handler, Meetings Application project, connection factory contract and attendee SQL view, plus ADR 0007 and 0017. It omits ADR 0009, which the baseline agent read as the governing rule for Query placement/database coupling, and does not include `IQueryHandler.cs`, `QueryBase.cs`, or the scalar count handler that the baseline inspected. The assisted agent's report says it needed no architecture rediscovery and the implementation/build passed; it followed the supplied UseCase/Handler/Feature context and the existing source exemplar, then added two canonical records for the new slice. It did not report manually reading ADR 0009. Therefore the omitted ADR is a coverage gap, but not a demonstrated task failure in this run. The actual Meetings architecture test implementation is also absent from this context; the capture includes ADR 0017, while the separate Copy Me dossier selected `ApplicationTests.cs`.

The assisted agent read 18 successful file records totaling 118,293 bytes. That count includes the 52,873-byte compiled context twice because setup temporarily renamed the file and the agent reread it after restoration, as well as post-build verification reads. It separately reread three existing code/project files and four existing model/narrative records already present in the context; the DTO read was outside context. Summing one read per unique path gives 62,127 bytes, including one copy of the compiled context; this remains byte accounting rather than token usage. The run's self-report of no architecture rediscovery is consistent with its work: it did not read the upstream ADRs during implementation and added the new UseCase/Handler resources without a manually supplied architecture hint. It is one uncontrolled task, not proof of general behavior.

A post-run filesystem audit found that the cold agent's relative `apply_patch` call had created three untracked files in the parent Markitect checkout (the two Query source files and the UseCase YAML). The agent's claim that it had not written parent files was therefore false. The operator archived the three files, verified and removed them, and confirmed the adopter artifacts contain the same decoded text; the frozen source manifest still verifies the 646 upstream files. The incident did not alter Markitect Core or other pilot arms, but it means write isolation was imperfect and is negative evidence against broad claims of safe autonomous execution. See `evidence/assisted/operator-parent-files.json` and `.zip` for the audit/archive record. The file-read ledger copied before the audit remains the cold-run metric; a later report read is not part of that trial.

The separate Copy Me ContextRun serializes to 98,288 bytes with 38 inputs for an investigator-selected evidence dossier. It is a different task and should not be compared directly with the implementation task; its size does show that collecting a bounded evidence dossier can itself produce a large artifact.

## Architecture-policy evolution failure

The exact v2 pin at `a0f89e7c0ce43a1be556c17c41cd19f8e7f32d7f` produces deterministic failed `PolicyResults` for exactly the two selected Commands, `add-meeting-attendee` and `cancel-meeting`, each missing a Validator. However, the normal check gate exits 1; both context requests and the direct impact command also exit 1 and return the generic failed-check report without a Context or Impact result. Thus the user cannot inspect the affected set at the contract-update point through the normal workflow. This is a concrete application/workflow diagnostics limitation, not evidence for another Core language primitive. The policy failures themselves are explicit in the normalized model output. Impact precision/false-positive and false-negative rates for the failed pin remain unmeasured; do not substitute the separate passing-state impact runs for this blocked transition.

Passing-state impact files clarify the fallback behavior but do not repair that failed-pin workflow gap. The v1→v2 completion comparison reports 12 UseCases among its affected resources although the new policy selects two Commands; it lists Domain/configuration, inventory, and collection-policy causes and says the union conservatively affects all resources. This is reproducible but broad: the other ten UseCases are not members of the selected validation cohort. The normal Query addition likewise reports all 72 model identities as affected, including all 13 UseCases (the new Query plus 12 existing ones), while only eight paths changed. At UseCase granularity the new count Query and existing attendee-list Query are the direct task subjects; AddMeetingAttendee shares their Feature and may be useful review context, but at least ten pre-existing UseCases are outside that slice. The 72 are affected model keys, not 72 changed files or 72 false positives: the inventory change triggers conservative whole-model inclusion, and the output identifies only eight changed paths (two source files, two canonical resource files, four generated projections). A source-only Handler edit is a useful counterexample: its impact is exactly the corresponding Handler and owning UseCase. Impact can therefore be bounded for a local declared-input change, while the current add-resource and package-evolution comparisons broaden to global inventory scope. Do not report one false-positive rate across these different scenarios.

## Comparative evidence and scope limits

The architecture-task report and impact outputs are available. The assisted run lasted about 15 minutes 1 second, compared with about 7 minutes 19 seconds for baseline, but the runs are not comparable: the assisted run also added two canonical resources, repeated the context read due an operator file-availability error, hit an interrupted patch tool, and required a network-enabled NuGet retry. Neither run measured model calls or tokens. Do not claim time saved or increased from these wall-clock observations. Failed-pin affected-set precision and missed subjects remain unmeasured because the command returned no Impact result. Passing-state global-inventory outputs establish broad review scope, not a validated affected-set recall/precision score: the pilot lacks an independently adjudicated complete list of all subjects that truly required code change or human review.

## Reconciliation evidence

The frozen Observe/Plan/Apply/Verify run used the published v0.12.0 binary and built-in Markdown renderer. Observe was read-only and reported drift; two Plans were byte-identical. Apply without `--write` and applying a stale plan after a temporary Skill edit were both rejected. The exact canonical Skill bytes were restored before the reviewed plan was applied. Apply wrote 72 projection operations, Verify confirmed all 72, and a second Plan returned `operations: []`. The declared 646 upstream files remained byte-identical. This proves convergence and plan binding for this one renderer target. It also exposes a bootstrap cost: initial synchronization emitted 72 files for a 69-resource graph; those are generated projections, not new canonical owners. No comparison measured the time/maintenance against editing a single AGENTS.md plus an architecture test.

This remains one uncontrolled feasibility pilot. Context byte counts and reproducible package behavior cannot establish productivity effect, customer demand, or long-term maintenance cost.

## Interpretation limits

The source is a realistic public reference application, but the extracted snapshot is not an active adopter with current owners, roadmap pressure, or release practice. The new Query is assigned for the experiment rather than sourced from an actual product backlog. Therefore this pilot can show technical feasibility and specific workflow behavior; it cannot establish demand, general productivity, fewer defects, token savings, or lower total maintenance cost. A future product decision should compare repeated real adopter tasks with a viable plain `AGENTS.md` + architecture-test baseline and should include owner-reported maintenance over time.
