# Projection-first bounded materialization proof

The synthetic Dispatch proof uses a custom Domain unknown to Core. The independent checker and fixtures were fixed before candidate generation. It is not an adopter-benefit experiment.

Two fresh Codex CLI sessions returned candidate bytes from identical supplied context, plan and explicit project inputs. Agents did not apply candidates or declare acceptance. The coordinator reviewed all four files, rebuilt an explicit plan with the reviewed current binary, and used Apply with the exact raw candidate digest. At fixed synthetic commits both variants passed independent checker tests, implementation tests and the finite contract check. The executable example retains variant A; variant B is separate replay input, not canonical meaning.

The initial input binary was frozen separately (b16e04d949d4154975a6e2a9c9b3ebb8714ac2528c49d82d198034d53160de3f). Review fixed opaque CI loading and Domain fan-out before Apply, so both candidates were explicitly replanned with the same new binary (d41885bd9a6e762922fa337684316dfa9f7f195a95fb125ac36f2368ec728b81). Old input reports were retained rather than relabeled. Result JSON identifies actual applied tool, plan, intent, candidate and commit digests. These local synthetic commits are receipts, not published product commits.

Earlier failed attempts remain excluded from successful materializations: the subagent dispatch reached a thread limit; two CLI configuration forms failed before execution; then two agent sessions were unexpectedly read-only and wrote nothing. Their final messages and actual check refusals were preserved locally. A separate read-only candidate-generation workflow then succeeded. Automatic review initially withheld the external candidate request pending payload/provider evidence; it permitted the unchanged action after exact synthetic payload inspection. No rule or sandbox bypass was used.

Candidate A uses a short lexical ordering implementation; B adds timestamp/identity validation and rejects duplicate selected IDs. Both agree on the predeclared finite cases, and their code/test hashes differ. Extra behavior beyond those cases is unproven, including whether B's extra rejection is appropriate for a real adopter. CI and hook contents are identical. The check establishes command literals, not provider execution, hook installation or arbitrary shell correctness. Checks run with local authority, not an OS sandbox.

Actual token telemetry exists for the two successful read-only sessions, but there is no matched productivity comparison, token-savings claim, winner, generalized obedience or safety claim. Candidate-generation sessions used the same installed Codex CLI (0.130.0) and ignored incompatible user configuration; resolved model identity was not independently established. Materializer identity is supplied provenance, not authentication.

Private Konfyra content was never part of these inputs. Historical gauntlet evidence remains separate, paused, without a final winner; holdout stays unopened. Published v0.13.0 is unchanged.


Six exact drift trials first verified a byte-identical converged clone, then changed one code/document/Codex/Claude/CI/hook target. Each returned drift at the fixed negative commit. Explicit Apply repaired exactly that target without changing intent, and fixed Verify returned converged. Earlier clones had inherited Windows line-ending conversion; those six confounded runs remain locally preserved and excluded, not substituted into this result set.

Materialization changed two actual representations (CI and Process documentation); unchanged targets remained review/evidence inputs. Independent checker bytes remained identical, and final Verify converged.

That counterexample is preserved separately; no test was edited to manufacture a pass. It exposes checker/model duplication and maintenance pressure. Its first report also exposed a product status bug: an earlier required Project gate failure, outside contract-selected checks, was classified incomplete.
