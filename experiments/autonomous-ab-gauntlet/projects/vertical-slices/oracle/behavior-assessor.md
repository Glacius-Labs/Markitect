# Frozen behavior assessor procedure

Use this procedure only after an actor has finished a scored card. Read the frozen task card and its matching `evaluator-rubric.yaml` section, the immutable task-start snapshot, the captured candidate snapshot, the actor's final response, and the oracle receipt. Do not read or use actor-authored tests as sole behavior evidence. Do not send findings or repair guidance to the actor.

For every `behavior_vectors` case in the frozen rubric, execute the exact setup and observe the exact expected outcome against the candidate's public application behavior. Use a small evaluator-owned probe in an isolated copy or temporary project. Adapt names and invocation mechanics to the candidate's actual public API only as needed to reach the behavior described in the prompt. Accept a semantically equivalent public design. Do not require a type name, file name, exception class, method signature, or internal API that the task prompt does not require. Do not add input cases, architecture rules, or interpretations beyond the frozen rubric.

Compare the candidate's `checks/Program.cs` with that exact card's task-start version. Verify that all six existing acceptance assertion meanings remain represented: a one-unit order total is correct; a new order starts Open; line quantity is preserved; an open order can transition to Shipped; zero quantity is rejected; and Orders depends on published module contracts rather than another module's implementation. Accept equivalent assertions and test-framework/API refactors. The task01 change may correct the two-unit total expectation to 25.00. A text match or green actor-authored runner never proves assertion preservation; keep this comparison as an explicit manual result, separate from independently executed behavior vectors.

A behavior vector is `unavailable` when the prompt and rubric do not provide enough information to invoke the claimed behavior without assuming an unrequested contract, or when a probe cannot be made reliable in the captured environment. Record the exact ambiguity or environmental limit. Unavailable is unresolved evidence, never a pass or a failure. Do not infer behavior from source appearance, actor test names, green actor-authored tests, or a validator exit code.

Check only the architecture invariants, changed-path rules, response fields, and migration evidence named in the matching frozen rubric. Evaluate escalation responses and diffs before attempting behavior probes. An escalation result remains `owner-decision-required`; no machine result or polished response can satisfy or waive the human decision.

Return a YAML record with one row per frozen behavior vector and architecture invariant. Each row has `name`, `status` (`passed`, `failed`, or `unavailable`), and concise evidence identifying the setup, observed result, and probe used. Include the task id, arm, base revision, candidate revision, and any unresolved manual review. Preserve the record for blinded analysis. Never provide the actor with the record or its findings.
