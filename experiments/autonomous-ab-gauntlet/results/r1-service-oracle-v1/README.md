# Service oracle correction boundary

This is a separate benchmark revision, defined by [protocol-service-oracle-v1.yaml](../../protocol-service-oracle-v1.yaml). The original `r1-paths-v3` freeze and raw results remain unchanged. Both original service trial-1 arms are excluded together by the [exact oracle exclusion record](../r1-paths-v3/oracle-run-exclusions.yaml); their actual public-check failures remain evidence.

The original task-03 oracle required a literal header, fixed column order and narrower wording than the task requested. The replacement recognizes the three named module rows, their bounded ownership statements, exact package paths and Core/Contracts dependencies. Column order and header names are immaterial; path annotations are optional and checked when supplied. Extra dependencies, wrong ownership and missing rows still fail. Eighteen focused positive/negative cases exercise this contract. This is literal recognition of the stated fixture facts, not general semantic understanding of Markdown.

The original task-02 vector required the word `conflict` in an error message although the task prescribed no error spelling or type. The replacement retains the existing runtime sequence: issue an invoice, retry the same amount, reject a different amount and verify the original invoice is unchanged. The frozen API returns a comparable `Invoice` value, so the pre-conflict value comparison does not alias a mutable returned pointer. A non-nil error in that bounded conflict scenario is evidence of rejection; it does not establish an error taxonomy or correctness outside those vectors.

There is no product-binary, seed, task-intent, model, effort or budget change. There are no new behavior vectors. A new external arena must preserve the predecessor input identities, replace only the declared oracle/protocol bytes, and freeze its own exact input manifest after the corrected source passes normal Windows/Linux gates. No new actor may use the correction before that gate. The fresh symmetric trial-1 pair and trials 2/3 belong to the new cohort; the excluded original pair is not rescored as a comparative success. Holdouts remain sealed until the development assessment and explicit fix/no-fix decision.

Results are identified by arena plus run ID. An oracle correction is a measurement correction, not a Markitect improvement, and cannot support a before/after product claim.
