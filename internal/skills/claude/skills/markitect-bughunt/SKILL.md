---
name: markitect-bughunt
description: Hunt for bugs beyond what markitect status lists. In a worktree of its own, the markitect-builder agent has the markitect-reviewer agent hunt and record each bug, repairs them, and has the reviewer verify again; a bug the spec does not cover becomes a spec-problem for the owner. A large project is hunted in parallel, per Package. The work comes back to this branch when it leaves nothing worse. Use when the user asks for a bug hunt on a Markitect project.
disable-model-invocation: true
allowed-tools: Bash(markitect status), Bash(markitect status *), Bash(markitect config strategy.bughunt)
---
Run `markitect status` and keep the Definitions it lists. Run `markitect config strategy.bughunt` for how to hunt: `sequential`, `parallel`, `auto` or the name of a custom workflow. With `auto`, choose: parallel when this is a Git repository and the spec has more than about 30 Definitions in at least two Packages (`markitect status --json` counts them per Package), otherwise sequential. Parallel and custom workflows need Git: in a folder that is not a Git repository, work sequentially. Tell the user in a line how you work and why. Change no file and record no verdict yourself.

In a Git repository the work starts from the last commit of this branch, so it holds no uncommitted change: if `git status` shows any, tell the user they are not part of the hunt and ask whether to commit them first.

**Sequential.** Start the markitect-builder agent with the message "Hunt bugs.", and add what the user asked to focus on, if anything. In a Git repository, start it in a worktree of its own (the Agent tool's worktree isolation), and in the background where the Agent tool can, so that the user can go on designing, here or in another session. In a folder that is not a Git repository, start it here and ask the user to leave the folder alone until it ends. The builder starts the reviewer to hunt; the reviewer records each bug it finds as `fail` on the Definition it breaks, and a bug the spec does not cover as `spec-problem` on the nearest Definition. The builder repairs what failed and has the reviewer verify again, until nothing it can settle is left, or the list has not got shorter for three rounds. Wait for it to end. It ends by naming its folder and branch.

**Parallel, or a custom workflow.** Note the current branch (`git branch --show-current`): the run comes back to it. Then enter a worktree of your own with the EnterWorktree tool, named `markitect-bughunt` with the date and time: the run works on its branch, and Claude Code branches every builder's worktree from it. Then start the workflow with the Workflow tool, `markitect-parallel` for parallel or the custom workflow by its name, with the args `{"mode": "bughunt", "into": "<the branch you noted>", "focus": "<what the user asked to focus on, or empty>"}`. It has one reviewer per Package hunt and record, commits the record, then runs one builder per Package that has something to repair, each in a worktree of its own with its own reviewer, in waves along the spec's dependencies, Root last, and merges each strand into your worktree's branch. Tell the user that it runs, and stay in the worktree until the workflow has ended. Then leave the worktree with ExitWorktree and keep it: its folder and branch hold the work.

**When the work has ended,** run `markitect status --repo <its folder>`. If its worktree is gone, because nothing changed, run `markitect status` here instead, skip the commit and the merge, and report. Commit everything in its folder in one commit on its branch, `.markitect/review.sum` included. Then:

- **If status there lists no Definition that was not listed here before,** merge its branch into the current branch here, then remove its worktree and branch. If Git refuses, because of uncommitted changes in the way or a conflict, abort the merge, leave the branch as it is and tell the user.
- **Otherwise,** leave the work on its branch, tell the user what the hunt left open, and ask whether to merge it as it stands, so that its spec-problems reach the spec here.

Push nothing. In a folder that is not a Git repository, commit nothing and say that the work is ready to commit.

Then tell the user in a line or two what the hunt found and repaired, whether it was merged, and which spec-problems wait for the owner, each with its question. A workflow returns the strands it could not merge, each with its branch: name them.
