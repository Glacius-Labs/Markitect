---
name: markitect-audit
description: Audit the spec itself. Fresh markitect-auditor agents read the spec as newcomers, one per Package that holds Operations or Reactions and one for the rest, and report contradictions, gaps, unclear and duplicated statements, missing links and the topics of the coverage list the spec neither states nor rules out to the owner, triaging the unlinked mentions markitect vet finds. It changes nothing and records nothing. Use before a spec is built, after a large change of it, or when the user asks to check the spec rather than the code.
allowed-tools: Bash(markitect status --json), Bash(markitect config strategy.audit), Bash(markitect list)
---
Run `markitect config strategy.audit` for how to audit: `sequential`, `parallel`, `auto` or the name of a custom workflow. With `auto`, audit as with `sequential` for now. Change no file yourself.

- **Sequential:** run `markitect list`, which names each Package with its Definitions and their Kinds. Start, in one message with the Agent tool, one markitect-auditor for each Package but Root that holds a Definition of kind `std/Operation` or `std/Reaction`, with the message "Audit Package PACKAGE: read markitect doc --read PACKAGE --bound first, and triage the unlinked mentions markitect vet --strict lists in it.", and one more with "Audit the rest of the spec: Root's own folders, the Packages ALL OTHERS, and the edges between Packages; walk the coverage list, and triage the unlinked mentions markitect vet --strict lists there.", ALL OTHERS being the Packages that have no auditor of their own. Add to each message the Packages or Definitions the user asked to focus on or to leave alone, if any.
- **Parallel, or a custom workflow:** start the workflow with the Workflow tool, `markitect-parallel` for parallel or the custom workflow by its name, with the args `{"mode": "audit", "focus": "<what the user asked to focus on or to leave alone, or empty>"}`. It returns the auditors' reports.

When the audit has ended, merge the auditors' reports into one: their findings, the most serious first, in plain words, each with its place and its question, a finding that several report once. Say how many Operations and Reactions the auditors walked, and name any that a Package's auditor left without its line. The missing links found come as one list, each with the Definition to link: the owner adds them, in their session with the markitect-architect skill, or by hand. The topics of the coverage list the spec neither states nor rules out come as one list too: the owner states each, or rules it out as the list says. The findings are for the owner to settle in the spec, with the markitect-architect skill or by hand: nothing is recorded and nothing is committed. When the audit runs as the step of starting a project in the markitect-architect skill, give the user none of them: that skill settles them and hands over.
