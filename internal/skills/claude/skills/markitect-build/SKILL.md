---
name: markitect-build
description: Build the spec as it stands. The markitect-builder agent works in a worktree of its own, makes the project match the spec for what markitect status lists, and starts the markitect-reviewer agent, which verifies each item and records it; a long list is built slice by slice, what others rely on first, or in parallel, per Package. The work comes back to this branch when nothing is left to verify but spec-problems, which wait for the owner. Use when the user says the spec is ready to build or apply.
disable-model-invocation: true
allowed-tools: Bash(markitect status), Bash(markitect status *), Bash(markitect config strategy.build)
---
Run `markitect config strategy.build` for how to build: `sequential`, `parallel`, `auto` or the name of a custom workflow. With `auto`, build sequentially for now. Parallel and custom workflows need Git: in a folder that is not a Git repository, build sequentially. Tell the user in a line how you build. Change no file and record no verdict yourself.

In a Git repository the work starts from the last commit of this branch, so it holds no uncommitted change: if `git status` shows any, tell the user they are not part of the build and ask whether to commit them first.

**Sequential.** Run `markitect status --slices`, with `--size N` if the user named a size for the slices. It prints the slices the list is built in, each with the command that lists it: a short list is one slice, and a long one goes Package by Package, what others rely on first, and ends with `markitect status` for what is verified on the whole project and whatever is left. If it prints errors in the spec, build nothing and offer to fix them with the user; if it prints no slice, because nothing is to verify or only spec-problems are left, say so and end. With several slices, tell the user how many there are and that each one is merged into this branch as it ends, so they leave this branch alone until the build has ended. Then take the slices in the order printed, one at a time: do everything from here down to the merge for one slice before you start the next, so that each builder starts from the work of the slices before it. Start each printed slice once, and no further builder.

For a slice that is not the last, first run its command and note how many items it lists. Start the markitect-builder agent. With one slice, and for the last of several, the message is "Build what markitect status lists."; for any other slice it is "Build the slice that `COMMAND` lists.", with the command printed for that slice. Add what the user asked to focus on or to leave alone, if anything. In a Git repository, start it in a worktree of its own (the Agent tool's worktree isolation), and in the background where the Agent tool can, so that the user can go on architecting in another session. In a folder that is not a Git repository, start it here and ask the user to leave the folder alone until it ends. Wait for it to end. It ends by naming its folder and branch.

**Parallel, or a custom workflow.** Note the current branch (`git branch --show-current`): the run comes back to it. Then enter a worktree of your own with the EnterWorktree tool, named `markitect-build` with the date and time. The run works on its branch, and Claude Code branches every builder's worktree from it. Then start the workflow with the Workflow tool, `markitect-parallel` for parallel or the custom workflow by its name, with the args `{"mode": "build", "into": "<the branch you noted>", "focus": "<what the user asked to focus on or to leave alone, or empty>"}`. Tell the user that it runs and that they can go on architecting in another session meanwhile, and stay in the worktree until the workflow has ended. Then leave the worktree with ExitWorktree and keep it: its folder and branch hold the work. The workflow returns the strands' worktrees: remove each one it marks merged, with `git worktree remove --force <folder>` and then `git branch -D <branch>`, and leave what is already gone; the others hold work that is left. If Git or Claude Code refuses to remove one, tell the user which folders and branches are left to remove.

**When a builder or a workflow has ended,** look at its list: `markitect status --repo <its folder>`, or, for a slice that is not the last, the slice's command with `--repo <its folder>`. If its worktree is gone, because nothing changed, run the command here instead and skip the commit, the review below and the merge: report, or after a slice that is not the last go on with the next when its list is empty, and stop and ask the user when it is not. Commit what is uncommitted in its folder in one commit on its branch, `.markitect/review.sum` included; a parallel run has committed its work already.

If the work was sequential and its list names a Definition as `changed` or with `no record yet`, the builder ended with something no reviewer has seen, such as an edit after its last review. Have it verified once, in the builder's folder: enter that folder with the EnterWorktree tool (`path`: its folder), start the markitect-reviewer agent with the message "Verify what markitect status lists.", or "Verify the slice that `COMMAND` lists." for a slice that is not the last, and add what the user asked to focus on or to leave alone, if anything. Wait for it, commit its record there, run the list again, and leave with ExitWorktree, keeping the worktree. In a folder that is not a Git repository the builder worked here, so start the reviewer here. After a parallel run or a custom workflow, skip this: a workflow holds its own review, and names what it left. Then:

- **If its list is empty there, or says that only spec-problems are left,** merge its branch into the current branch here, then remove its worktree and branch: a spec-problem waits for the owner, no builder settles it, and it stays on the list here. If Git refuses, because of uncommitted changes in the way or a conflict, abort the merge, leave the branch as it is, tell the user and start no further slice. After a slice that is not the last, say in a line how it ended and go on with the next.
- **Otherwise,** something is left that the builder did not settle. With one slice, and after the last of several: leave the work on its branch and ask the user whether to merge it as it stands; `markitect status` here then lists what remains. After a slice that is not the last: if its list is shorter than the number you noted, merge its branch all the same, say in a line what is left, and go on, since the next slice's command lists the Packages before its own too and its builder takes up what is left. If its list is no shorter, the slice settled nothing: leave the work on its branch, start no further slice, say what the builder reported and ask the user.

Push nothing. In a folder that is not a Git repository, commit nothing and say that the work is ready to commit.

Then tell the user in a line or two how it ended: whether status lists nothing, and if not, what is left and which spec-problems wait for the owner, each with its question. A workflow returns how it stopped and the strands it could not merge, each with its branch: name them. If status lists errors in the spec, offer to fix them with the user.
