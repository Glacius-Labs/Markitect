---
name: markitect-build
description: Build the spec as it stands. The markitect-builder agent works in a worktree of its own, makes the project match the spec for what markitect status lists, and starts the markitect-reviewer agent, which verifies each item and records it; a long list is built in parallel, per Package. The work comes back to this branch when nothing is left to verify. Use when the user says the spec is ready to build or apply.
disable-model-invocation: true
allowed-tools: Bash(markitect status), Bash(markitect status *), Bash(markitect config strategy.build)
---
Run `markitect config strategy.build` for how to build: `sequential`, `parallel`, `auto` or the name of a custom workflow. With `auto`, build sequentially: the parallel strategy has passed only a small real run so far, so `auto` does not choose it yet. Parallel and custom workflows need Git: in a folder that is not a Git repository, build sequentially. Tell the user in a line how you build and why. Change no file and record no verdict yourself.

In a Git repository the work starts from the last commit of this branch, so it holds no uncommitted change: if `git status` shows any, tell the user they are not part of the build and ask whether to commit them first.

**Sequential.** Start the markitect-builder agent with the message "Build what markitect status lists.", and add what the user asked to focus on, if anything. In a Git repository, start it in a worktree of its own (the Agent tool's worktree isolation), and in the background where the Agent tool can, so that the user can go on designing, here or in another session. In a folder that is not a Git repository, start it here and ask the user to leave the folder alone until it ends. The builder works until markitect status lists nothing, or only spec-problems, or the list has not got shorter for three rounds; it starts the reviewer itself. Wait for it to end. It ends by naming its folder and branch.

**Parallel, or a custom workflow.** Note the current branch (`git branch --show-current`): the run comes back to it. Then enter a worktree of your own with the EnterWorktree tool, named `markitect-build` with the date and time. The run works on its branch, and Claude Code branches every builder's worktree from it, so a later wave starts from what the earlier ones merged there. Then start the workflow with the Workflow tool, `markitect-parallel` for parallel or the custom workflow by its name, with the args `{"mode": "build", "into": "<the branch you noted>", "focus": "<what the user asked to focus on, or empty>"}`. It runs one builder per Package, each in a worktree of its own where it commits its work, in waves along the spec's dependencies, Root last; it merges each strand's branch into your worktree's branch and has a reviewer verify the Package there. Tell the user that it runs and that they can go on designing in another session meanwhile, and stay in the worktree until the workflow has ended. Then leave the worktree with ExitWorktree and keep it: its folder and branch hold the work. The workflow returns the strands' worktrees: remove each one it marks merged, with `git worktree remove --force <folder>` and then `git branch -D <branch>`, and leave what is already gone; the others hold work that is left. If Git or Claude Code refuses to remove one, tell the user which folders and branches are left to remove.

**When the work has ended,** run `markitect status --repo <its folder>`. If its worktree is gone, because nothing changed, run `markitect status` here instead, skip the commit and the merge, and report. Commit what is uncommitted in its folder in one commit on its branch, `.markitect/review.sum` included; a parallel run has committed its work already. Then:

- **If status lists nothing there,** merge its branch into the current branch here, then remove its worktree and branch. If Git refuses, because of uncommitted changes in the way or a conflict, abort the merge, leave the branch as it is and tell the user.
- **Otherwise,** leave the work on its branch and ask the user whether to merge it as it stands; `markitect status` here then lists what remains.

Push nothing. In a folder that is not a Git repository, commit nothing and say that the work is ready to commit.

Then tell the user in a line or two how it ended: whether status lists nothing, and if not, what is left and which spec-problems wait for the owner. A workflow returns how it stopped and the strands it could not merge, each with its branch: name them. If status lists errors in the spec, offer to fix them with the user.
