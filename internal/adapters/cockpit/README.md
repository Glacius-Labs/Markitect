# Cockpit adapter

`markitect cockpit` serves a local web view of the runs recorded in one or more state directories. It implements the [cockpit concept](../../../docs/design/cockpit.md) in six slices: the inspector of a recorded Apply Run with organization, causal waits, exchanges, timeline, step details, candidates, evidence and replay; live observation of a running Apply through the same projections; the cockpit entry with the project, running runs and run history; proposals for the execution settings; model sessions in which an Agent proposes model changes on the owner's prompts ([working through the cockpit](../../../docs/design/cockpit.md#working-through-the-cockpit)), the start and stop of the one Apply the cockpit runs ([starting and stopping](#starting-and-stopping-a-run)), and the per-user project list with the guided setup ([projects](#projects-and-guided-setup)). The [runtime contract](../../../docs/design/canonical-model/manager-apply-runtime.md#evidence-and-state) owns the evidence it reads.

```text
markitect cockpit [--listen 127.0.0.1:7341] [--no-open]
markitect cockpit --state DIR [--state DIR ...] [--repo .] [--model PATH] [--dependency PATH ...] [--listen 127.0.0.1:7341] [--no-open]
markitect cockpit --run-config PATH [--runtime-profile PATH] [--repo .] [--model PATH] [--dependency PATH ...] [--no-open]
```

**Two ways to open it.** Without any of `--state`, `--run-config`, `--runtime-profile`, `--repo`, `--model` and `--dependency`, the cockpit opens in project mode: the project used last if it is still in the list, otherwise the project list ([below](#projects-and-guided-setup)). Giving any of these flags, even with its default value, opens that project directly as before and saves nothing; the page then offers *Keep in the project list*. `--listen` and `--no-open` work in both modes. A project flag without `--state` or `--run-config` is still refused.

The command prints the address it serves and opens it in its own window ([below](#app-window-notifications-and-background)); `--no-open` only suppresses the opening.

`--model` and `--dependency` select the repository's model and its dependency models as `markitect check` and `markitect apply` select them; a project whose model imports dependency models needs them for its observation, its proposals and its model sessions.

## Read boundary

The cockpit reads `<state>/runs/<runID>/events.jsonl`, `report.json` and `transcripts/<turn>.jsonl` and `current-run`. Its writes are an accepted proposal, a model session's Agent turns, workspace and evidence, the start and stop of the one run this cockpit started, and the project list and a project's setup files (all below). Every other route accepts only `GET`; no request repairs a run, stops one that was started elsewhere or answers a question of a run.

- **Consistent prefix.** Only complete lines are records. A trailing partial line is reported as a tail. A line that does not decode keeps its line number (its `seq`) and shows as unreadable, so later sequence numbers never shift. An append is read incrementally when the file keeps its identity and length and continues its last 64 consumed bytes; otherwise the file is read again from its start and, if it no longer begins with the consumed history, counted as replaced. An in-place rewrite of earlier bytes that keeps the identity and the last consumed bytes is not detected; the producer only appends.
- **Boundary.** A view is the projection of the first `seq` records (`/api/runs/{run}/view?at=N`). Nothing after record N reaches it: a later verdict, outcome or report stays hidden. The report appears only at the final boundary. Details (`/detail?ref=...&at=N`) and transcripts (`/transcript?turn=...&at=N`, cut at the boundary's recorded time) obey the same boundary. `/entries` lists the whole record for navigation; the page shows its entries only up to the boundary.
- **Local only.** The server listens on a loopback address and admits only requests addressed to it, so another site cannot read evidence through a rebound host name. Pages load no external resources.

## Live observation

`/api/runs/{run}/stream` sends server-sent events over the same projections: `entries` with the records appended after the client's last one (the event id is that record's `seq` and its mark, a digest prefix of its line), `health` every two seconds, and `replaced` when the events file no longer holds the client's history, after which the stream ends. A reconnecting browser sends `Last-Event-ID` and receives exactly the records after it; a different record at that position, also from a replacement while the browser was away, ends the stream as replaced. The page applies deliveries one at a time, trims an overlap and refills a gap through `/entries`, so it always holds one complete prefix.

Health is the current observation, kept apart from the recorded boundary. A written report means the run ended. Otherwise bootstrap's state lock probe and `current-run` decide: this run holds the directory (running, or finishing once its outcome is recorded), another run holds it, or nobody does (ended without a report). A failed probe is unknown. The probe takes the lock for an instant when nobody holds it, which the brief retries of a starting Apply and of `markitect setup` absorb, and runs at most once per two seconds and state directory. Health can be briefly behind: within the probe interval after a run starts, or while a crashed run's `current-run` remains and another process holds the lock. A written report is announced by health, not by a record, so the page reads its final view again when the run state changes; the stream closes once the report is written.

The page follows new records while the boundary is at the latest record. Pausing, selecting, scrubbing or stepping back pins the boundary; the page then counts newer records and offers an explicit return to live. Playing from a pinned boundary replays the record at the chosen speed and follows the run once it reaches the latest record. A lost link, its reconnection and a stale link (no contact for longer than the health interval) are shown with the run state of the last contact; changes of the link and of the run state are announced to assistive technology, the running seconds are not. Following a run starts, stops or answers nothing: a Run is closed.

## Hub and areas

The cockpit is one application built as a hub and four areas the owner enters and leaves: Model, Runs, Decisions and Settings. The hub shows the project as its last observation saw it (model, source head, canonical model digest, the check, *Observe again*), the one next step that needs the owner — a proposal to decide, the open session, a running run or a failed check, in that order — and a tile per area with its live state. A tile glows while its area waits for the owner. The digits 1 to 4 enter the areas from the hub; Escape leads one level up: from a run to the Runs area, from a Definition to its Package and on to all Definitions, from an area or an open decision to the hub. The top bar names where the owner is (the way back, the area, its tabs, the open item) and carries what waits for the owner, the running runs, the check and the notification bell; on narrow windows it keeps one status chip with its word shortened, so the project name, the way back, the area emblem, the tabs, the chip and the bell fit at 390 px. One poll every four seconds while the page is visible (project, runs, proposals, sessions) serves the top bar, the hub and the pages.

- **Model:** two tabs. *Browse* is a browser of the checked model the project observation prepared (`GET /api/model`): Packages on the left, their Definitions in the middle (`/` filters by id, title, body or Package), the chosen Definition on the right with its body (each `[[link]]` opens its target), its fields, the registered files that realize it and the Definitions that link to it. A newer observation, after *Observe again* or an accepted proposal, is read again. The model is read only; it changes through a model session or by hand. *Session* is the model session: the conversation on the left and the session's latest proposal with its decision on the right (below).
- **Runs:** a card to start and stop a run ([below](#starting-and-stopping-a-run)), the runs that run now and the run history; a run opens in the inspector inside the area.
- **Decisions:** this cockpit's proposals in one list, waiting ones first, beside the chosen one with its check, difference and decision. Without a choice, the first waiting proposal opens.
- **Settings:** the execution settings form.

Every page of its own has the same header: a title, one short sentence and, where more must stay reachable, a collapsed *How this works* (what writes, what spends provider usage, that nothing is committed); empty states are a short title and one line. Without a model session the session page is one inviting column: a sentence, a four-step stepper, the composer and the provider-usage note at the start action. Small windows stack the split views and the tiles. The presentation uses modern cards in the Glacius Labs colors: an ink ground, ice as the accent of intent, quiet status colors and an accent per area; DM Sans and JetBrains Mono are used where installed, and the page loads nothing from elsewhere. Motion (the entry of a place, the glow of a waiting area) stops with reduced motion.

## Cockpit entry and closed Runs

The hub shows the project as structural preparation of the repository (`--repo`, default `.`) observes it in the background, bounded to two minutes: model, canonical model digest, source head, Packages, Definitions and the check status. Observing again is a POST with the cockpit's own request header. The run history shows the provider steps and cost a report states; without a report, usage is unknown. The Runs area also offers the start and stop of a run when the cockpit is configured for it.

A Run is closed: no question or answer crosses Root to the user during a Run, so the cockpit has no route that lists or answers an owner question and no preloaded owner decision exists. Older runs may still record a question to the user. Their evidence is read only: the inspector shows such a question, its lapse and its exchange as recorded, and offers no answer.

## Proposals for the execution settings

With a repository, the settings page (`#/settings`) reads `.markitect/execution.yaml` of the committed source through [authoring](../../authoring/README.md) and offers the budget, the role profiles, per-Package profile overrides and the team as a form. Proposing posts the edited settings as JSON with the cockpit's own request header (`/api/proposals/settings`); the service makes the changed file, runs the structural check on the proposed tree and keeps the proposal. Reading the settings captures and prepares the repository as `markitect check` does, which takes seconds on a large model; a proposal made from the settings read at a head reuses that capture. Settings read from an earlier head are refused, because applying them could undo what was committed since; the page asks to read them again. The form refuses number fields that are not whole numbers.

A proposal in Decisions (`#/proposal/{id}`) shows the check with every finding, the line difference and the decision. Accepting takes two steps and is offered only for a passed check; discarding writes nothing. Accepting posts to `/api/proposals/{id}/accept`. Bootstrap's fence takes the lock of every observed state directory, so an Apply that holds one refuses the acceptance and the proposal stays open. The publication runs to its receipt even when the page goes away, and a stopping cockpit waits for it. While it runs, the cockpit holds the state locks: the cockpit's own health view does not take that for a running Apply, but an Apply started in those seconds refuses as if another Apply held its directory. A page that finds a proposal being written reads it again until it has its receipt. The page shows the receipt with every path's read-back state; only an applied publication is shown as accepted, a stale source asks for a new proposal, and a partial or unknown outcome asks the owner to inspect the working tree. Nothing is committed and no Apply starts. Proposals live in the cockpit process; a working tree with uncommitted changes, including an accepted but uncommitted proposal, refuses the next one. The repository adapter keeps each distinct captured source in memory for its publication guard, so a cockpit that runs across many commits grows; restarting it releases them.

## Model sessions

With `--run-config` and `--runtime-profile`, the session page (`#/session`) opens a model session through [authoring](../../authoring/README.md#model-sessions). Starting takes two steps, because it captures the committed source with the Runtime profile, starts a container and spends one Agent turn; every further prompt is one more turn. The preparation runs to its end, within ten minutes, when the page goes away. The page shows the session's state, its Agent profile, its limits (turns used of the execution budget's Agent turns, the turn timeout), the usage each turn reported, every tool use with the cockpit's answer, the proposals with links, the Agent's answers and final text as its own text, and whether the end of each turn's container was observed. A halted session takes no prompt and offers only closing. A working session is read again every two seconds; the composer keeps its draft. Closing stops a working turn and releases the workspace. At most one session is open; a stopping cockpit closes it, also while it prepares. Sessions write only below the state directory's `sessions/`: they hold no state lock and touch neither `runs/` nor the owner channel. A run configuration's deadline does not bound them; the execution budget's limits do. The routes are `GET /api/sessions`, `POST /api/sessions` (start), `GET /api/sessions/{id}`, `POST /api/sessions/{id}/prompt` and `POST /api/sessions/{id}/close`; the writes need the cockpit's own request header, the prompts a JSON body.

A model proposal's page shows the Agent's summary as the Agent's text, apart from the difference and the check the cockpit observed.

## Starting and stopping a run

With `--run-config`, `--runtime-profile` and `--repo`, the Runs area offers *Start a run*. The cockpit then runs the same execution function as `markitect apply` (`executionService.Execute`) in its own process, with the repository, model and dependency selection it was started with, the Runtime profile and the run configuration; the run's budget, checks, evidence and publication are Apply's. Without them the card says how to enable starting; for a project of the project list it says that the project is not set up and links to *Set up runs for this project* ([below](#projects-and-guided-setup)).

- **Confirmation.** Starting takes two steps. The second shows what the run will use, read when the confirmation opens and not on the four-second polls: the execution budget of the committed `.markitect/execution.yaml` (execution time, turn timeout, Agent turns, Passes), the run configuration's deadline, Root's Execute profile with the model its Runtime profile states (or that it states none) and, when per-Package overrides make other Managers use other Execute profiles, each of those with its Managers. They come from the captured settings and the profile decoders `markitect apply` uses, so a working tree with uncommitted changes shows the refusal instead of the facts. Concurrent reads share one capture. The page says that a run spends provider usage and that ending the cockpit stops it.
- **Stale confirmation.** The start request names the committed head the confirmation was read from. The cockpit reads HEAD again through the repository adapter (`ResolveRevision`) and refuses a start when it differs ("the committed source changed since the confirmation; review it again"); the page then reads the facts again. A commit between that check and `Execute`'s own capture remains possible, and `Execute` then runs the newer committed source.
- **One run.** At most one run started by this cockpit is active. A start is refused while that run is active, while an Apply or a publishing proposal holds the state directory (probed first; `Execute`'s own lock remains the guard), and once the cockpit ends. Whatever `Execute` refuses, such as uncommitted changes, shows as the ended run's error with the outcome `refused`.
- **Run handle.** The run's context derives from the cockpit's. The handle states `starting`, `running` once the run is known, `stopping` after a stop, and `ended` with the outcome, the error and the report path once `Execute` returned; the result stays until the next start. The run is named from the state directory's `current-run` only after `Execute`'s lock wait has passed with `Execute` still running, because an Apply that won the lock between the probe and `Execute` also writes `current-run` while `Execute` is still refusing; an ended run is named only from its evidence directory. Until then the card offers the stop of the cockpit's own run but shows no run link, and the inspector offers no stop for any run. The assumption is that `Execute` obtains the lock or refuses within that wait; a process that is slower than the wait could still name a foreign run.
- **Stop.** Stopping takes two steps and cancels the run's context: the run ends incomplete with its report and evidence, as an interrupted `markitect apply`; nothing is restored. A stop before the run created evidence (during preparation) ends incomplete with the statement that nothing ran and no evidence exists; it is not shown as a refusal. Stop is offered on the card and in the inspector's head for the run the cockpit started and for no other. A run started elsewhere is stopped where it was started.
- **Cockpit ends.** When the cockpit's context ends it cancels its run and waits until `Execute` returned, so the report is written before the process exits; no run starts after that. A hung `Execute` therefore keeps the cockpit from exiting after the first interrupt; a second interrupt ends the process without the run's report. Closing the window does not end the cockpit or its run.
- **After a start** the focus moves to the card's heading, which then names the run.

The routes are `GET /api/run-control` (whether starting is available and why not, the run this cockpit started, and with `?facts=1` the confirmation facts or why they cannot be read), `POST /api/run-control/start` (a JSON body with the confirmed `head`) and `POST /api/run-control/stop`. The writes need the cockpit's own request header with the purposes `start-run` and `stop-run`; a foreign `Origin` or host is refused. `Execute` prints its own account to the cockpit process's standard error, as it does for `markitect apply`.

## Projects and guided setup

**The list.** The per-user project list is one file, `<user configuration directory>/markitect/cockpit/projects.json` (`os.UserConfigDir`, so `%AppData%` on Windows, `~/.config` on Linux, `~/Library/Application Support` on macOS):

```json
{"formatVersion": 1, "projects": [{"name": "library", "repository": "/abs/library", "model": ".markitect/model.yaml", "dependencies": [], "runtime": "/abs/runtime/library"}], "last": "library"}
```

A project is a repository with the model and dependency models `markitect check` selects and, once set up, the runtime directory that `markitect setup --runtime` fills: `<runtime>/run.json` is its run configuration, `<runtime>/runtime.yaml` its Runtime profile and `<runtime>/state/` its state directory. Names are unique and default to the repository's directory name. The file is replaced atomically (temporary file next to it, then rename), with mode 0600 where the platform has modes, and its directories are created as needed. A file with another `formatVersion`, malformed or unknown content, repeated names or relative paths is shown as an error on the project page and is never overwritten; the owner fixes or removes it. Every change reads the file again first and replaces it atomically; there is no lock between processes, so two cockpits changing the list at the same instant can still lose one change. A cockpit opened by flags that cannot determine the user configuration directory still serves its project and says the list is unavailable.

**One listener, one project at a time.** A `Host` owns the HTTP handler: it serves the page and the `/api/projects` routes and gives every other API route to the current project's `Server`, which stays a single-project server. Without a current project those routes answer 409 ("No project is open") and the page shows the project list. A project's `Server` is built by bootstrap from its entry exactly as the flags would build it: repository, model and dependencies, the run configuration and Runtime profile of its runtime directory, the run controller, sessions and proposals. A project without a runtime is observed (model, check, proposals, settings) but starts no run and no model session.

**Switching.** Opening another project, and removing the open project's entry, is refused while the current project is busy: a run this cockpit started is active, a model session prepares, works or closes, or an accepted proposal is being written (`Server.Busy`). Otherwise the new project is built first, so a project that cannot be built leaves the current one open; then the host swaps them under its lock and closes the old one as a stopping cockpit would (idle model sessions end, nothing else is running). A write to the current project is admitted and counted under the host's lock. A switch marks the project draining under that lock, so no write is admitted after the busy state was read (a write then answers 409 "The cockpit is switching projects"), reads the busy state, waits for the writes already admitted and reads it again; one that started work in the meantime refuses the switch and the project takes writes again. Reads and streams are not drained. A switch and a setup under way are joined by a stopping cockpit, which then closes the project that is current. The project opened last is remembered in the list. When the project used last cannot be opened at start, the list opens with the reason.

**Routes.** Writes are POST with the cockpit's request header (purposes below), a JSON body where one is read, and the same origin and host checks as the other writes.

- `GET /api/projects`: the list, the open project (`current`, with whether it is `saved` in the list and `setUp`), `last`, why the last project did not open, whether the open project is busy and why, the suggested runtime base and setup's defaults, and an error when the file is unusable.
- `POST /api/projects` (`project-add`): `name` (optional), `repository`, `runtime` (optional), `model` and `dependencies` (optional). The repository and the runtime directory must be absolute; the repository needs its model file and dependency models; a runtime directory needs `run.json` and `runtime.yaml`.
- `POST /api/projects/{name}/open` (`project-open`), `POST /api/projects/{name}/remove` (`project-remove`; the entry only, never the repository or the runtime directory), `POST /api/projects/keep` (`project-keep`; saves the project opened by flags, optionally under another `name`), `POST /api/projects/{name}/setup` (`project-setup`).

**Guided setup.** The form of a project (`#/projects?setup=NAME`) asks for the inputs of `markitect setup`: the runtime directory (suggested under `<user configuration directory>/markitect/runtimes/<name>`; setup requires it outside the repository), the workspace image, the credential file, the Agent model, the effort, the container engine (setup's default), the check profiles as PROFILE and EXECUTABLE rows, and optionally a store label and a deadline. The first step reviews them ("Writes runtime.yaml and run.json in DIR"); the second calls bootstrap's setup function, the one behind `markitect setup`, with the project's repository, model and dependencies and no owner request. It writes exactly what `markitect setup` writes and refuses where it refuses, for example while an Apply holds the state directory; setup's report (its status, error text, the identities it bound and the files with their actions) is shown as it is. The form never sees credential bytes, only the path. On success the runtime is stored in the list and the project is reopened with runs enabled; if it cannot reopen yet (the open project is busy) the answer says so and the runtime stays stored. Setup is refused while the project it would rewrite is open and busy. While it runs, the open project is itself busy ("a setup is writing its runtime files"): no run and no model session starts, and it is not switched or removed. One setup runs at a time; a started setup runs to its end even when the page goes away, and a stopping cockpit waits for it.

**Browser.** `#/projects` is a page in the card language of the hub: a card per project with its name, repository, runtime or "Not set up", the open one marked, *Open*, *Set up runs* and *Remove…* (two steps); a card to add a project; and, for a project opened by flags, the card to keep it. With no open project every place leads to the project list. The top bar shows the open project's name as a link to it (inside an area it is hidden below 760 px, where the bar has no room; the hub and the list show it at every width, shortened to 14 characters below 760 px). The cards redraw only when the list changes, and the add and setup forms are never redrawn by the four-second poll, so focus and typed values stay.

## App window, notifications and background

**Window.** Once the cockpit listens, `markitect cockpit` opens its address in an app window of an installed Chromium browser (`--app=URL`: no tabs, no address bar), unless `--no-open` is given. The address is printed either way. `WindowLaunches` chooses, as a pure function of the platform, the environment and the installed programs, an ordered list of ways to open it, and `OpenWindow` starts the first that works, detached and without waiting for it:

- Windows: Microsoft Edge (`msedge.exe` in `Program Files`, `Program Files (x86)` or the user's local application directory, or on the path), then Google Chrome in the same places, then the default browser.
- macOS: Google Chrome, then Microsoft Edge, installed as an application (`open -na APP --args --app=URL`), then `open URL`.
- Linux: `google-chrome`, `chromium` or `microsoft-edge` (and their stable or packaged names) with `--app`, then `xdg-open`.
- WSL (`WSL_DISTRO_NAME` set): the Windows side first. Edge and Chrome are probed in their standard `Program Files` places through the `/mnt/c` mount and the one found is run directly with `--app`; without one, `cmd.exe /c start "" URL` opens the default browser; then the Linux candidates. Starting through `cmd.exe` is not used for the browsers because it would succeed without one.

Opening is best effort. A failure, or the absence of any browser, is reported on stderr with the address to open by hand, and the cockpit keeps serving. A browser that starts but then fails cannot be noticed, because it is never waited for; the printed address is the fallback. Nothing is bundled; installer and updates belong to the pinned pilot build.

**Notifications.** The page compares each observation of the four-second poll with the previous one and, with the owner's permission, raises a desktop notification through the Web Notifications API when:

- a run that was running or finishing is no longer, naming its outcome when the run list has one (a click opens the run);
- the open model session leaves working or preparing and waits for the next prompt, or halts (a click opens the session);
- a proposal newly waits for a decision (a click opens the proposal).

Each part of the observation (runs, sessions, proposals) takes its baseline when it first arrives, so opening the cockpit, or a part that failed to load at first, raises no burst for what was already there. The permission is asked only from the bell in the top bar, an icon with a status dot whose accessible name and tooltip read "Notifications off", "Notifications on" or "Notifications blocked" (blocked stays focusable and explains itself; the browser's site settings change it); the browser keeps the permission and the cockpit remembers nothing. Without it nothing is notified and everything else works as before. No notification is raised while the window is visible and has focus, because the page shows the change itself. A minimized or covered window keeps polling once notifications are allowed and still notifies, with the delay of the browser's throttling of hidden pages; a closed window cannot notify, because only the open page watches.

**Window title.** The document title is prefixed with the count of proposals that wait for a decision, `(2) Hub – Markitect cockpit`, and carries no prefix when none waits. One module (`web/js/notify.js`) owns the prefix; the places only name themselves.

**Background.** The window is only a view. Nothing in the page or the server ties the cockpit's life to it: the server ends when the `markitect cockpit` process is interrupted, a closed window only ends its own requests and event streams, and model sessions, accepted proposals and anything else the cockpit runs continue. Closing the window therefore leaves the cockpit working, and reopening its address (or `markitect cockpit` again, if it ended) shows the same state.

## Projection

`Project` folds records into the view the browser shows: the Run's binding (strategy, build, work Passes, budget and each Manager's model context); Passes with gates, candidates, checks, seals and the turns and cost of their turns; Managers in the organization the run's Package paths define, with state, active turn, helpers, submissions and open findings; turns with their mode and how they received their context, state spans, proposals, findings, questions, problems, probes, lookups and dependency bindings; a short factual account; and the limitations of the record (`gaps`). `Entries` labels every record for the timeline and marks exchanges with their direction and channel: Agent communication, a submission to the decider, an Orchestrator control or acceptance event, or the owner channel of an earlier run.

**Binding.** `run.start` records what the caller bound the run to. The view decodes the strategy (`direct` or `staged`), the build, the source head, the work Passes, the budget durations and, per Manager, the context the run bound: the Brief's digest, the Definitions supplied in full and those supplied by reference only. A `lookup.definition` or `lookup.brief` record shows which reference-only Definitions a Manager looked up, Pass by Pass. Binding a context says what was selected for the Manager, not what the Agent understood.

**Model assessment.** The first Pass of a Run is the Model assessment. Its Pass page is a verdict: the submissions' obligation coverage per Definition (status, note, and each evidence item's claim, source, location and reasoning) and the findings with their class (`model_error`, `model_gap` or `unclassified`, which the engine carries in the correction field). An assessment that Root confirmed as a material model problem reads as the closed ending *Model problem confirmed — nothing published; correct the model and start a new run* (`status.ending`), recognized from the engine's failed-outcome reason; an assessment that sealed unclean only because of disputes or open suspicions confirms no problem and is not shown as one. The assessment's summaries and its reason are shown whole.

**Observation kinds.** A finding's kind (`deviation`, `suspected`, `model`, `suggestion`) decides its label and its effect (`effect`): an open confirmed deviation or model problem names a correction and blocks; an open suspicion is shown as one, holds the Pass back until a fresh review decides it and names no correction; a suggestion never blocks. A correction Pass addresses only findings that name a correction. A review of the very candidate an earlier review of the same purpose judged is a re-Verify of an unchanged candidate (`unchanged`), not a review of a corrected candidate.

**Probes.** `probe.requested` records the claim and the expectation before the probe runs, `probe.receipt` the outcome (passed, failed or error with its exit code and uncertainty) and `probe.disposed` the accepted disposition of an adverse receipt or its withdrawal. The view keeps one probe per receipt; the probe's bytes and output stay in the record (`probe:ID`). A finding and a coverage evidence item link to the receipts they cite.

**Report.** The view presents the Run's own status (`report.run.status`) with the publication beside the report's outcome pill, reads `report.run.problems`, `turns` and `probes` as counts and lists, and maps the outcome from the command status for a report of an earlier build that lacks it, without listing that as a gap. A no-change publication reads *no change — nothing to write*.

Waits keep the Orchestrator's wording. The known forms (a decision on a proposal, the results of children or helpers, the parent's basis, a declared dependency, the accepted basis or result of a Manager the waiting Manager itself named, an answer, a contact) name the participants that must act next and the records involved; the cause follows those participants through the same view, and the Manager's own `report.wait` (with its `stage`) supplies its reason. Before a Manager's productive work starts, the Orchestrator does not record a changed wait that leaves the Manager Waiting (after its release, or after one of several declared dependencies is met). A recorded parent-basis or dependency wait whose condition the record shows fulfilled is therefore marked outdated, and the view names the still unaccepted dependencies of the accepted plan instead of guessing a reason.

What the record does not establish stays visible: delivery and reading of exchanges, the candidate's file differences, the publication's candidate digest when something was written, a missing outcome or report, unknown record kinds and unreadable lines. Only kinds the cockpit does not know are listed as unknown; bookkeeping kinds (`listedOnly`) and the historical working-environment records of earlier builds are listed as entries and are no gap. `TestEveryRecordedKindIsProjectedOrListedOnly` reads the run engine's and Apply's source and fails when a recorded kind is neither projected nor listed; a listed kind need not still be produced.

## Project organization

`GET /api/organization` serves `declared` from the same structural project
observation as the model browser. Bootstrap uses the product's topology and
ownership layout, including its more-specific exclusions. Root has no local
Definitions. Profiles retain their declaration source; absent team/profile
values remain absent. The response includes defaults, exact Package overrides,
the project-wide helper team, run-wide strategy and declared checks.

With a configured Runtime profile and run configuration, `?resolve=1` explicitly
starts a bounded background capture through the run confirmation's `runFacts`
path. Ordinary reads poll `resolving` and receive `resolved` or the refusal in
`error`. Concurrent resolution requests share the active capture. A later
explicit request refreshes it. The resolved observation names its committed
head and model digest separately from the draft declaration observation; it
is a snapshot, not a guarantee about a later start. It applies product defaults,
binds Execute, Verify and helper profiles and decodes their provider models.
Neither operation starts a Run, Agent, container or project check. Tests use
fake metadata readers; production metadata preparation may inspect the selected
Runtime image as run confirmation does.

## Browser

The page is plain HTML, CSS and JavaScript modules without a build step, embedded in the binary and packaged with the source. Replay moves the boundary through the record with play, pause, speed, record and exchange steps; recorded gaps are compressed and bookkeeping records take no playback time. Selecting anything pauses the presentation; pausing never affects a run. Arrows illustrate recorded sends along the tree, pause with the replay and open their record; with reduced motion they are drawn still. Keyboard: Space, arrows, Shift with arrows, Home, End, `[` `]`, Esc and `?`. Narrow windows show the organization as a list.

**Inspector header and rail.** The header holds the run identity, the strategy, the start and duration at the boundary, the outcome pill (*Verified · no change*, *Incomplete*, *Model problem confirmed*, in progress) and a small *Live* or *Replay* chip whose tooltip holds the link details (connection, last contact, run state, following or pinned). The rail names each Pass (*Model assessment p1*, *Verify p5*) with its seal, whether it is a correction round or a re-Verify of an unchanged candidate, and its turns and reported cost, which its tooltip completes with the output tokens. The owner is drawn in the organization, and named in the legend, only when the record holds owner-channel records of an earlier run.

**Detail pages.** A Pass page shows the assessment's verdict and coverage, the probes of the Pass with their outcome, stand, exit code, uncertainty and disposition, the observations it raised and closed and its turns and cost. A Manager page adds its model context (counts, the Definitions in full, the reference-only ones looked up in each Pass), its probes, the findings it owns by kind, its bound dependencies and its turns with mode and context. A probe page shows claim, expectation, receipt, disposition and, from the record, the probe's bytes and output. Findings carry a kind label in a quiet color and are never told apart by color alone. *What this record does not establish* is a collapsed section.

Pass labels in the timeline are shortened to the Pass identity, or left out, where they would overlap; the band's tooltip and a click always name the Pass.
