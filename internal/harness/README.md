# Native harness inputs

This pure package constructs complete checked instructions without I/O, provider calls or Run dependencies. The native adapter actually consumes `Document.Base` and `Document.Developer`; a builder or digest alone does not prove provider loading.

The five layers are versioned Markitect working rules; bound checked Project and complete Manager hierarchy; exact Manager, selected canonical Definitions, typed fields, source digests and inclusion reasons; mandate, Findings and selected Manager instructions; and the provider's actual rendering, loader controls and offered Run tools. The first four are built here. The last is owned by each native adapter.

`Rules` holds the Manager's role, the organization rules (hierarchy, questions along the tree, authority, Notes, workspace) and the answer format (`judge`, `check`, `review`). It does not explain how the host runs the hierarchy: message continuation, fixing handoffs and similar host states are not working rules. Tasks arrive as Run messages.

`Build` requires the exact Manager from a valid `project.Prepared`, retains all selected Definitions and original body/explicit instruction bytes, and refuses missing or invalid UTF-8 instruction inputs. There is no truncation or file acquisition. The adapter projects Run's mandate, Findings and bound input into these pure inputs and supplies runtime-profile instruction sources separately.

Each Initial Finding names the Definition it affects; Run hands Implement no other Finding ([DEC-073](../../docs/concepts/register.md#dec-073-change-minimality-on-an-unchanged-model)). `Origin` is the command's bound input. When the host states it, `Origin.Verified` names the stored Verify Run that already approved exactly that input under the same basis, and the document says so; it does not say the code or tests are correct. Verify's duties carry the concept's tiers for judging the changes against that input.

`Document.Digest` binds the exact length-prefixed native base/developer strings after native rendering adds profile instructions. It is an observation of supplied bytes, not a claim about the provider's effective load order or semantic acceptance. Native controlled loading, conflicting-file and background-command proofs remain concrete adapter evidence.
