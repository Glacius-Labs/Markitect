# The Run engine

`internal/run` runs one Run per change ([concept 2.0](../../docs/concepts/v2-concept.md) §6, §7) for `markitect apply` and `markitect verify`. It decides who works, starts a maker and a fresh checker per working Manager through the [agent port](../agentport/README.md), reads their handoffs from the Run's [remote](../runremote/README.md), writes the Result and lands it as in a merge queue. This page is the canonical description of the engine and of the Result page's layout, which §14 left to the build. It is step T4 of the [delivery plan](../../docs/implementation-plan.md#concept-20-build).

| Package | Role |
| --- | --- |
| `internal/run` | The engine: gate, impact, plan, schedule, host tools, Result and landing. It starts no process itself; its ports do. |
| `internal/adapters/rungit` | The host's own Git work in a private bare repository (below). |
| `internal/agentport` | How the engine starts agents; provider adapters implement it. |
| `internal/bootstrap` | Builds the engine for the command line with the host's Git, the Run remote in a container and the provider adapters. |

## A Run

1. **Start and base.** The Run starts from the tip of the target branch. The base is `--base`, or by default the work Markitect last landed there: the newest commit that adds a Result page under `.markitect/results/` names it in its `Run-Work` trailer (below). A landing on a moved target merges in commits the Run did not realize, so the base is the approved work, not the merge, and those commits stay in the next Run's impact. With no landed Run yet, `--base` or `--full` is needed.
2. **Initial gate.** The project at the start commit is compiled; with a compile error the Run ends as `check-failed` and no agent and no remote start.
3. **Who works.** Impact from the base to the start commit (model and files, with `--findings` and `--full`) gives the working Managers and their checklists ([impact and checklists](../../docs/guides/model-language.md#impact-and-checklists)). Untouched Packages do not start and are listed as not taking part; with no working Manager the Run ends as `nothing-to-do`.
4. **Queue.** In `apply` the Run takes its place in the target branch's lock (below) and waits while a Run whose impact overlaps its own works on the branch. When the target moved while it waited, it starts again from step 1 at the new tip. `verify` changes nothing and takes no place.
5. **Remote.** `runremote.PlanFor` builds the plan; the engine gives every agent its own user and random token, puts only the tokens' hashes in the plan and starts the remote from a bundle of the start commit.
6. **Schedule** (below), then the Result and landing.

## The target branch's lock

Runs whose impact overlaps take turns on one branch; others work side by side ([concept 2.0 §6.5](../../docs/concepts/v2-concept.md#65-landing)). The lock lives in the target repository, so it holds for every host that lands there, not only for one machine: the ref `refs/markitect/lock/<branch>`, which no clone fetches by default, points at a commit without parents whose one file `lock.json` lists the Runs of `apply` that work on the branch, each with its impact, a random nonce and a time after which its entry no longer counts, the Run's deadline plus twice the cleanup bound. A Run reads the record, drops entries past their time, and enters its own entry with a push that names the record's commit as the expected old value, so two hosts never both enter on the same record. While an entry overlaps its own impact, it reads the record again every `LockPoll` (15 seconds) until its deadline, and the Result's queue says whom it waited for and how long. A Run that waits past its deadline ends as `incomplete` and starts nothing. A second Run of a name that already works on the branch is refused; a write that reported a failure but took effect is recognized by the Run's own nonce. When the target moved while the Run waited, it leaves the lock and starts again from the new tip, until its deadline. The Run removes its entry, by its nonce, on every way it ends, on its own cleanup deadline; a host that dies leaves its entry until its time passes, or until someone deletes the ref. Waiting Runs have no order: whoever reads the record first after a holder left enters first, so a Run can wait until its deadline while others pass. Entries expire by the clock of the host that reads them, so clock skew between hosts shortens or lengthens them. Pushing the lock ref has been exercised against local bare repositories only, not yet against a hosted one.

Impact here is what landing reads as the Run's impact: the Definitions the change changes or reaches, Findings' and stale entries' Definitions and files, and the files it reaches. Landing stays the final check: a Run whose lock entry did not overlap can still be kept when the other Run's landing changed something it then touches, for example a working Manager's registry page.

## Schedule

One goroutine decides; every agent runs in its own goroutine, and the engine reads the remote (an export bundle imported into the host's repository) each time an agent ends. In `apply`:

- Parent first ([concept 2.0 §6.2](../../docs/concepts/v2-concept.md#62-one-run-maker-and-checker)): a parent with checklist items starts its maker at once and submits its own files; its children start only after its approval, and the host first moves each child's branch, still at the base, to that approved commit on the remote, so shared files such as a module file exist before the children's required checks run. That first submission covers the parent's own area, and the maker's and the checker's tasks say so; the parts its children realize come with its later submission that integrates them. A parent without items lets its children start at once, from where it started itself, and its maker starts once all its working children are approved. Leaves start side by side. No agent waits for a message: the order is the host's, by when it starts whom.
- A Manager's work starts from that commit: its task names it, and its checker's diff is from it (`Git.Base` of the [agent port](../agentport/README.md)).
- A maker's start ends with a submission at its branch tip, a message, or nothing. A submission goes to a fresh checker only when it contains every working child's latest approval; otherwise the maker gets a host message naming what to merge. A submission made before all children are approved is not reviewed, except a parent's first submission of its own files before its children start. A child counts as approved for its parent only when its whole subtree is.
- A checker's review commit on the submission approves or rejects it. A rejection goes back to the maker as a `review` message with every disputed item. An approval finishes the Manager. Whenever all of a parent's children are approved and their approvals differ from those its maker last got, the parent's maker gets them in a host message and merges them.
- An approved Manager that starts again, for example for an answer, and leaves its branch unchanged stays approved.
- An approved submission that holds a `model-problem` verdict escalates to the parent automatically; at Root it is a model defect.
- A Manager that escalates, with the tool or by such a verdict, is not started again until its parent has dealt with the matter (§6.2): the parent settles it, if the model allows, and children wait only for their parent's approved commit (§6.3). The parent's maker gets the escalation; while a child waits for it, the parent's submissions are reviewed without its children's approvals, as a first submission of its own area is, and a parent that ends such a start without a submission is told to submit, even when it sent a message. The child starts again after a maker start of its parent's that began after the escalation: when that start's submission is approved, or when it ended without a change and answered the escalation. It continues from its parent's newest approved work since the escalation, if there is one: a host message names it, a submission the child made before is not reviewed, and a submission that does not contain the commit its work continues from is answered with a host message instead of a review. The parent then integrates the child's approved work as any child's. Without this, a child that needs a file of its parent's starts again on the answer without the parent's change, and the parent's change waits for the child's approval, so neither converges (the T7 arm smoke's [launch 3](../../docs/validation/t7-arm-smoke-20261029.md)). An answer without a change thus reaches the child once the parent's start has ended rather than at once; no agent waits for it meanwhile.
- Root's checker is the final check: the Run's work is approved when Root is, no message waits and every Manager is approved.

In `verify` every working Manager's checker starts at once and pushes its verdicts as one commit without file changes; there are no makers and no merges.

Every start gets the task in the host's words, its checklist, its inbox, its Git access, its tools and its deadline. The harness says how to work; the engine says what to achieve (concept 1.0 §3.7).

### Messages

Messages run along the tree only and no agent waits for one: a start that sends a question ends, and the answer starts the asker again; an escalation starts the asker again once the parent has dealt with it (above). A parent whose start ends with a question still open is reminded once; a Run where nobody can go on names the open questions. The host tools are `ask` and `escalate` (to the parent), `answer` (a child's question or escalation), `assign` (work for a working child, which then needs a new approval), and `note` and `notes`. Makers in `apply` get all that fit their place in the tree. A checker, the only role in `verify`, gets only `note`: it is fresh and sees the model, the repository at the submission and its diff, and nothing its maker wrote besides the commit, so it does not read the Shared Notes (concept 2.0 §6.2). A refused call says why and what to do next. No message reaches the owner during a Run: Root's escalation is a model defect, which ends the Run without landing and becomes a decision for the owner with the escalation's `Recommendation:`.

### Limits and honest stops

`Limits` bound the Run: a deadline for the whole Run, a number of agent starts that corrections share, a number of maker and of checker starts per Manager, and a deadline per start. The deadline reaches every agent start and every Git and remote operation through its context. A start that leaves nothing behind (no submission, review or message) gets one host message; two such starts in a row stop the Run as making no progress. Every stop ends as `incomplete` (or `model-defect`), cancels the running agents, waits until they have ended, reads the remote one last time and keeps Root's newest state on the Run branch. A stopped Run lands nothing; a checker approval that happened is still reported as that checker's approval, and approved work of other Managers that the Run branch does not hold is listed as not kept. Writing that Result and removing the remote run on their own short deadline after the Run's has passed, and anything that may remain is listed under cleanup.

### Shared Notes

Notes are side observations with their origin (Manager and role) and no authority. Makers write and read them; checkers only write them. A Note holds at most 16 KiB; `notes` reads pages of at most 100 Notes and 128 KiB, oldest first, with a cursor. Every Note appears on the Result page.

## The Result

The host writes the Result from commits, verdicts and checks, never an agent. `markitect apply --json` prints it as JSON, the evaluation suite's Result contract; otherwise it prints the Result page, which is also committed under `.markitect/results/<run>.md`.

| State | Outcome | Means |
| --- | --- | --- |
| `landed` | landed | the approved work is on the target branch |
| `nothing-to-do` | not-landed | the change reaches no Manager; nothing started |
| `check-failed` | not-landed | the initial gate failed; nothing started |
| `verified`, `findings` | not-landed | `verify` found every item conforming and the required checks passing, or Findings, owner decisions or failing required checks |
| `model-defect` | not-landed | Root ended the Run on a model defect |
| `kept` | not-landed | approved work that may not land; it stays on its Run branch |
| `incomplete` | not-landed | a budget, a deadline, no progress or a technical failure |

The page has, in this order: the state and why; the command, outcome, target, base, start, Run branch, times and tokens; the checklist, one row per item with its verdict, evidence, approving checker and the checker's own evidence; where the required checks ran and their results; decisions for the owner with recommendations; Findings; the Packages not taking part and why; how long the Run waited in the target's lock and for whom; the kept Run branches a landing replaces; every agent start with how it ended; every message; side observations (impact notes and Shared Notes); and what cleanup left. `verify --findings-out FILE` writes the Findings as a Findings page, the input of `apply --findings`. A `verify` Finding is a `deviates` verdict; its evidence may say `Observed:` and `Expected:`.

**Required checks.** The hooks compile every submission and run the checks on its full repository state, so in `apply` the Result names the checked push of Root's approved submission from the remote's decision log. When the target moved, the checks also run on the merged state before landing, and the Result names that run instead, or says that no merged state was checked. In `verify` the hooks run the checks once, on Root's verdicts, whose tree is the start commit's, and the Result names the start commit; failing checks make the Run's state `findings`, never `verified`. The page says what ran: passed, ran and did not pass, or did not run, with why.

## Landing

Landing works as a merge queue (concept 2.0 §6.5):

1. Root's approved commit must contain every working Manager's latest approval, no commit of the work, message or change, may hold one of the Run's Git tokens or touch a provider login file (`.credentials.json`, `auth.json`), since landing pushes the whole history, and it must compile; otherwise it is kept. The host compiles every state it lands (concept 2.0 §6.3).
2. The approved work is pushed to `markitect/runs/<run>` first, so nothing is lost if landing fails half-way.
3. If the target branch has not moved, the Result commit on top of the approved work lands as a fast-forward.
4. If it moved, it must still contain the start commit (a rewritten branch keeps the work), and the incoming commits must not touch the Run's impact: no changed or reached Definition of the Run or of its Findings and stale entries, no file the Run reached or changed, no change to the manifest, the lock, the required checks or a working Manager's registry page, and a state that compiles. Then the host merges them; the merge must be clean, the merged state must compile and the required checks must pass on it, and the Result commit on top of the merge lands.
5. Every push to the target names the tip it expects. If the target moved again meanwhile, landing starts over, at most three times. A failed push is checked by reading the target again on a fresh deadline: it may have landed, and when the target cannot be read the Result says the landing state is uncertain.
6. A landed Run's branch is deleted, and so is every kept Run branch the landing covers: the kept Run started from a state that the landing Run's start holds, and the landing Run's impact holds the kept Run's impact, or the landing Run was `--full`. The landed Result page lists them under "Replaced Run branches". Only kept Runs of the same target branch count, and only a branch whose tip is the host's Result commit, which adds nothing but that Run's Result page; a Run branch whose tip someone else moved, and a Run that still holds an entry in the lock, are never deleted. A deleted kept Run's Result page, with any decisions for the owner on it, goes with its branch; the landing's Result names the branch. A Run that does not land keeps its Result commit on its Run branch, on top of Root's newest state (in `verify`, of the start commit), and says why; it stays until a later landing covers it or the owner deletes it.

Result commits carry trailers the host reads back. A landing commit names the approved work it lands (`Run-Work`), the next Run's default base. When two Runs landed side by side, the second's work holds the first's landing only through the merge, so the next Run's impact holds the first Run's changes again and its Managers check them once more; that costs a Run's work but misses nothing. A Result commit on a Run branch names the Run (`Run-Name`), its target branch (`Run-Target`), its start (`Run-Start`), `Run-Full: true` for a full Run and one `Run-Impact` line per entry of its impact, from which a later landing reads whether it covers that Run. They are ordinary Git trailers, not the agents' `Markitect-` trailers of the [Run remote](../runremote/README.md), whose parser refuses an unknown `Markitect-` key on a branch tip, and every Run starts from a landing commit.

`verify` never lands: it changes nothing, and its Result stays on its Run branch.

## Host Git

`internal/adapters/rungit` is the host's own Git work: it reads the target branch and its lock record, makes the start bundle, imports the remote's export, reads commits, merges with `git merge-tree` and writes the Result commit through a private index, all in a private bare repository. The user's repository is only a Git remote to it, so Markitect never touches the user's working tree. The target is `--remote` and `--branch`: by default the current branch's upstream remote and branch, else `origin`, else the repository itself. The adapter never pushes to a branch that is checked out in a working tree of a local target, whatever `receive.denyCurrentBranch` says, so with no remote a Run keeps its work on its Run branch; landing is meant for a remote the user pulls from, like any colleague's push. Merges use Git's own text merge, whatever merge drivers attributes or configuration name.
