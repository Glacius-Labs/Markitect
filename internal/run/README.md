# Closed hierarchical Run

`Executor.Execute` executes one Assessment, Implement or Verify with the complete checked Project hierarchy. It opens every Manager environment before ordinary work, gives each its own Git copy, and uses direct child delegation, asynchronous questions, exact child review and upward Git integration. Completed Managers remain reachable in their ordinary conversation.

## Collaboration contract

Run keeps one explicit assignment state per Manager (`assignment.go`). Each change follows a named event: a parent assigns a task, the Manager receives it, judges it, its handoff is fixed, the parent reviews it, a correction reopens it, or a late finding changes it. A judgment binds the received task (with its mandatory Findings) and the assessed state: the Implement working-copy commit at the time of the judgment, otherwise the fixed input candidate.

The Manager tool set is fixed: `delegate`, `await`, `review`, `ask`, `reply`, `judge`, `check`, `read_notes` and `append_note`. Run sets the acting Manager and the origin of every Finding. A refused call returns its concrete reason and the possible next step.

## Shared Notes

`runstore.Store` gives every Note an ID that starts with its creation time, so Notes sort in creation order and concurrent processes need no lock. `read_notes` returns one page, oldest first, as `notes` and `next`; passing `next` as `after` reads the following page and an empty `next` marks the last one. A page holds at most `NotePageCount` (100) Notes and `NotePageBytes` (128 KiB) of encoded Notes, and at least one. A Note has at most `MaxNoteText` (16 KiB) of text and `MaxNoteContext` (1 KiB) of context, so even a Note of bytes that need the longest JSON escape fits a page and every page fits the 1 MiB tool frame. An oversized append is refused with the limit and the next step; nothing is truncated, cut or deleted. Notes stored before IDs carried a time keep their random IDs: they stay complete and in a stable position, but not in creation order. A Note appended while a reader pages, whose ID sorts before the reader's cursor (a slow append, clock skew between processes, or such an older Note), appears on the next read from the start. There is no filter: it would have to read every Note again and defeat paging.

Notes are optional information. A Notes storage failure is returned to the calling Manager as a tool error, which also shows that nothing was read or kept, and does not stop the Run. Mandatory results are stored separately, and their failures still stop it. Without this a single unreadable Note file would stop every future Run of the project.

- `ask` reaches only the direct parent or a direct child; the refusal names the allowed addressees. Siblings align through their common parent.
- A message to an idle Manager carries its newly delivered events and Run's diagnostics; `await` delivers events that arrive while it works and refuses at once when nothing can arrive.
- The end of a native response is not a judgment. A response without one leaves the assignment active; Run continues it, naming the open task, only when nothing it waits for (a working child, an open question) is outstanding. Questions and answers never need a judgment, also before the first one.
- A continued response counts as idle only when it does nothing at all: it calls no Manager tool (any call counts, also `check`, `read_notes` and a refused one), its Session observes no native execution, and the working state stays unchanged. Run does not judge whether an action was useful, so read-only review is never standstill. After two idle continued responses in a row the Run ends technically incomplete with `ErrNoProgress` and a diagnostic naming the Manager; the message budget bounds every other loop. A Session that implements `ActingSession` reports native executions outside Run's tools: the Codex adapter reports every completed native item other than text – a command, file change, tool call, web search or subagent – during the Exchange, also on a native subagent thread.
- Run checks a judgment when the Manager records it and before relying on it. After a response ends, a changed assessed state invalidates the judgment with the reason "your working state changed after your judgment". Root completion checks Root's earlier judgment again on the quiet hierarchy.
- A correction is a new task: no earlier judgment applies. A late adverse judgment about a fixed handoff stays in force; the parent's acceptance no longer holds, ancestors that already handed off work again, and the nearest active ancestor loses its judgment. A model blocker cannot be corrected within the Run.

## Checks

Every Implement submission is fixed, checked and delivered to the parent with its `Check`, also when the check fails. The parent can neither approve nor integrate an invalid submission; it rejects with Findings, settles the interface or reports a model blocker. Root has no parent: Root's Implement submission or Assessment/Verify approval of a state that fails its check is refused with Root's own diagnostic. The `check` tool runs the same check on the caller's assessed state for optional self-correction. Assessment and Verify handoffs carry no check; reviewers use `check` for the fixed input. A Manager's fixed state is checked once: the `check` tool, a judgment and a handoff of the same state share one result, so the Run records each declared check once per checked state. Each Implement check also lists the build outputs of the Manager's copy, the untracked ELF files no registry shard names, which no fixed state holds; they never fail a check. The final handoffs list those each copy holds when the Run completes, so a build after a check is reported too. Verify's Root assignment and every Verify check carry those of the Implement Run that produced the fixed input.

The check is structural validation and accounting, then the declared checks placed in that Manager's copy (Assessment runs only the structural part). Declared checks additionally require obligation eligibility and directory ownership confined to the Manager subtree, including nested exact-file areas. Root runs the complete suite; checks without `requiredBy` remain Root-only. A child state that only lacks integration still outstanding elsewhere is therefore not invalid; `Check.Checks` lists the checks that ran, and a check that did not run is never reported as passed. Assessment and Verify retain their fixed input; review scratch cannot replace product bytes. Implement submission establishes no independent approval or publication.

A registry link to a Definition the model no longer has is stale realization (`project.StaleLinks`), for example after the owner deleted a Definition; so are the registrations and shard of a Package the model no longer has, which go to the Manager owning each artifact's area and to Root. `Check.Stale` lists the stale items in the Manager's responsibility: its own Package subtree, everything for Root. They make an Implement or Verify check invalid, so the shard owner's handoff, every ancestor up to Root and Root's completion are held to them, while siblings are not. Assessment only reports them as work for Implement. Publication refuses any stale link.

## Validity of closed results

`ValidateClosed` (`validate.go`) is the one check that a returned or stored result is complete: bound to its request and checked preparation, technically completed, with a candidate that keeps its fixed input for Assessment and Verify, a decision valid for the mandate, mandatory Findings for a rejection or model blocker, every Manager's session and copy, the workers and the Git service closed once and the complete hierarchy handed off. The closure names stay inside Run; workflow and publication call this function and name no Run resource.

## Limits and evidence

The shared allowance bounds all messages and questions; the request bounds Manager count, cleanup and terminal persistence separately. `MessageTimeout` bounds the provider work of one response: serving its tool calls pauses that clock, so a parent may await working children longer, while the Run deadline bounds everything. Partial startup, blocked adapters, cancellation, observation failures and storage/read-back failures cannot produce successful technical completion. Cleanup records actual outcomes and uncertainty; a timeout never claims a process was killed.

`gitrepo.LocalGit` supplies real isolated repositories and self-contained stored bundles, including ancestry, modes and explicit empty model directories. `runstore.Store` supplies immutable terminal records and concurrent project Notes read in bounded pages. Candidates and Notes reopen through fresh adapter instances after temporary copies close.

The real-Git vertical fixture has Root, two siblings, a grandchild and an empty Package. Controlled Sessions execute all three mandates with crossed parent/child questions and questions after fixed handoff. Implement additionally exercises rejected-child correction, an invalid child candidate reaching its parent, actual Git merge conflict recovery, late Reject repair and repair after accepted parent integration. Separate controlled tests cover each counterexample of concept §13.3, refused questions outside the hierarchy, read-only Assessment and Verify review across continued responses, and the idle stop. Failure tests inject partial startup, blocked Exchange/Close, cleanup/storage/read-back failure and insufficient preflight limits. These are source proofs, not native provider or container-isolation evidence.

The production Git workspace shape is `gitrepo.LinuxGit`: one held Git service per Run and private volume-backed Manager copies. Check input/home copies preserve explicit directory inventory as well as bytes and modes. Provided native Session observations bind the runtime profile identity, image and rendered harness digest; controlled observations remain transport evidence. Physical Linux/container and provider loading proofs retain their separate source-bound results. The [delivery plan](../../docs/implementation-plan.md) owns current scope.
