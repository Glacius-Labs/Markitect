# Authoring

The owner's changes to the project's `.markitect` inputs made through the [cockpit](../adapters/cockpit/README.md) are proposals ([DEC-065](../../docs/concepts/register.md#dec-065-work-through-the-cockpit-agent-proposed-model-changes-and-configuration), [concept](../../docs/design/cockpit.md#working-through-the-cockpit)). This package makes, checks and decides them; bootstrap composes it with the repository's capture and publisher.

## One proposal path

1. **Capture.** A proposal starts from the committed source, captured as Apply captures it: the working tree must equal its head, and the capture carries the guard a publication is checked against. A dirty working tree refuses with `ErrNotClean`. A proposal made from the head the owner read reuses that capture for 15 minutes; reuse is safe because acceptance checks the guard, and a started publication drops the capture. Settings read at another head than the current one are refused with `ErrMoved`.
2. **Change.** A producer builds the proposed tree. The configuration producer edits `.markitect/execution.yaml`; a proposal may change only the paths its producer permits.
3. **Check.** `apply.CheckProposal` prepares the proposed tree as `markitect check` prepares the repository: Model check, registry, File check, execution settings and context selection. Like the capture's second pass, instruction and ignore files the proposed tree newly references are read from it and the tree is prepared once more. A diagnostic that a later stage repeats is reported once. The proposal keeps the structural status and every finding with its stage, code and location.
4. **Review.** The proposal lists each changed file with its line difference (three lines of context, longer unchanged runs cut).
5. **Decide.** Discarding writes nothing. Accepting needs a passing check: bootstrap's fence takes the lock of every observed state directory, then Apply's publisher preflights the guard, writes exactly the changes and reads every path back. A source that changed since the capture refuses the publication; only an applied (or no-change) receipt accepts the proposal. A fence that cannot be taken leaves the proposal open; every other unapplied outcome fails it with its receipt. Nothing is committed and no Apply starts. `Wait` returns when every started publication has its receipt.

Proposals live in the cockpit process; what was accepted is in the working tree, ready to be committed.

## Execution settings

`Settings` reads the budget, role profiles, per-Package profile overrides and team of the committed `.markitect/execution.yaml`, with the model's local Packages. `ProposeSettings` changes only the fields whose value differs in the document's YAML node tree, so unchanged fields keep their text, comments and style and every other field (ownership, top-level and per-Package instructions, scope, checks) stays as it is: scalars change in place, a Package entry left empty is removed, a changed team is written anew, and a team of `nil` removes the authored team, which restores the product's default team. The product's strict decoding judges the result in the check.

## Model sessions

A model session lets an Agent propose changes to the canonical model on the owner's prompts. `StartSession` captures the committed source with its settings and the Runtime profile through the `SessionOpener` bootstrap composes, as an Apply captures it, and reads the session's basis with `apply.SessionBasisOf`: Root's Execute profile, the turn timeout and the Agent-turn limit of the execution budget, the language guide of the model's vocabulary that Extract's Agents receive, and the repository directory of the model's Definitions from its manifest. It materializes the session's workspace from the committed tree and runs the first turn. A failed or uncertain materialization closes the workspace; a session closed while it prepares is closed when the preparation ends.

Each turn is one `run.Agents` Execute turn of Root's Execute profile: the workspace is read-only except the model's directory (`.markitect/model` by default) and `.markitect/registry`, the Agent home and the provider conversation carry over between the owner's prompts, the turn timeout bounds it, and its transcript is written under `<state>/sessions/<session>/transcripts/`. The session offers three tools. `check` peeks at the workspace (an uncertain observation is tried again, as the run engine does) and answers with the changed files and `apply.CheckProposal`'s findings. `submit` peeks at the workspace and makes a `model` proposal through the one proposal path, with the Agent's summary; only paths under the model and the registry may change. `answer` keeps the Agent's text for the owner without a proposal. The Agent's final text is kept too. The first prompt states the task, the language guide, the registry's format and that the owner is the author of intent, so a contradictory or unclear point is reported, not decided.

A session runs one turn at a time; a prompt while it prepares or works, beyond its Agent-turn limit, while it closes or to a closed session is refused, and only one session is open. A turn whose container end was not observed, or a record that could not be written, halts the session: it takes no prompt, so no second container uses the workspace. `CloseSession` marks the session closing, stops a working turn or cancels the preparation, then closes the workspace and removes the Agent home without holding the service lock; as for Apply, a failed home removal is recorded, since a home no container used may not exist. Dependency models outside the repository are checked but are not in the Agent's workspace. The session's record (`events.jsonl`: start, prompts, turn starts with workspace, mounts, home and resumed conversation, tool uses, proposals with paths and summary, turn ends with usage, failure, close) stays under the state directory. A session's proposals start from its capture, so after accepting one, commit it and start a new session.
