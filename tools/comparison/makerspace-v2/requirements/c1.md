# Makerspace change C1: audit records permission refusals

Applies to the requirements of W0. Section numbers refer to [w0.md](w0.md), including its section 16 "Architecture".

## What changes

Until now the audit log records only accepted mutations. From this change on, it also records every refusal for missing permission, together with the actor's role.

1. **Refusals with code `forbidden` are recorded.** Every request refused with `forbidden` appends one audit entry. This holds for every operation, mutations and reads alike, and for both kinds of `forbidden`: a role without permission (check 4 of section 3.1) and an ownership violation (check 6).
2. **Every audit entry gains two fields:**
   - `actorRole`: the role of the acting user, `member`, `staff` or `admin`;
   - `outcome`: `accepted` for an entry of a mutation answered `ok`, `refused` for an entry of a `forbidden` refusal.
3. **Content of a refusal entry:** `seq` is the next number of the one shared sequence; `at` is the request time; `actor` is the acting user; `actorRole` is that user's role; `op` is the requested operation; `target` is `null`; `outcome` is `refused`.
4. **Content of an accepted entry:** as before, plus `actorRole` and `outcome` `accepted`.

The audit entry record (section 5) is now: `seq`, `at`, `actor`, `actorRole`, `op`, `target` (`null` in refusal entries), `outcome` (`accepted` or `refused`).

The refusal itself is unchanged: the response is still `status: "refused"` with code `forbidden` and a reason. Apart from the audit entry, a `forbidden` refusal still changes nothing: no other record, no identifier counter, and the request-time order is still set only by requests answered `ok` (section 4.4). A refusal entry can therefore carry a later `at` than the accepted entry that follows it; `listAuditEntries` still returns entries in `seq` order.

Section 2.8, "Audit targets are not identifiers", now begins: an audit `target` is a plain string, or `null` in a refusal entry.

Section 16, Architecture, now reads in its list of realized concerns:

- **Audit** is realized in `protocol`: The protocol module appends the audit entry after a mutation is answered `ok`, using the operation's audit target, and after a `forbidden` refusal; area modules do not write audit entries.

Section 3.1, last paragraph, now reads: when a check fails, nothing else happens, except that a `forbidden` refusal appends its audit entry (section 4.2).

Section 4.2 now reads, in its first paragraph: every request to a mutation answered `ok` appends exactly one entry with outcome `accepted`, and every request refused with `forbidden` appends exactly one entry with outcome `refused`. Reads answered `ok`, other refusals and invalid requests append nothing.

Example: member `ada` sends `listAuditEntries` at `2026-03-05T10:00Z`. The response is a `forbidden` refusal, and the log gains `{"seq": 7, "at": "2026-03-05T10:00Z", "actor": "ada", "actorRole": "member", "op": "listAuditEntries", "target": null, "outcome": "refused"}` (with `seq` the next number).

## What is not recorded

- Refusals with any other code, including `invalid_argument`, `unknown_actor`, `time_regression`, `not_found` and every operation rule code.
- Invalid requests.
- A request that fails an earlier check than the permission checks. The order of checks in section 3.1 does not change, so, for example, a request from a member with an earlier `at` than the last accepted request is refused with `time_regression` and is not recorded, even though the member also lacks permission.

## What stays as it is

Everything else: the permission matrix, the refusal codes and their order, the operations that are audited when accepted, the `target` values of accepted entries, the numbering of entries and the permission to read the log (admins only).
