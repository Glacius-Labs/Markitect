# Makerspace requirements: W0 (fresh build)

This document describes the complete product for the first delivery. The later changes C1 to C9 are separate documents that each amend the result of the previous step.

## 1 Overview

Makerspace runs the day-to-day operations of a fictional community workshop. It is one local program. Front-desk tools send it requests on behalf of the person who acts; the program decides, records and answers.

- **Members** join on a membership tier and pay a monthly fee that depends on the tier. Staff can suspend a member; a suspended member is not in good standing.
- **Training:** courses certify members for a tool family, such as laser cutters. A certification is valid for 365 days.
- **Equipment:** machines belong to a tool family and have a rate per minute. Staff schedule maintenance windows during which a machine cannot be reserved.
- **Bookings:** members reserve machines in 30-minute steps inside opening hours, check in when they start and check out when they finish. They are charged for every metered minute at the machine's rate, minus a tier discount.
- **Materials:** a small shop sells materials from stock.
- **Billing:** once a month staff generate invoices: one per member, with the monthly fee and all charges of that month. An invoice is due 14 days after it is issued. Members pay their invoices; an overpayment becomes credit, and credit reduces the next invoice.
- **Safety:** staff record safety incidents per machine.
- **Reporting:** staff and admins read utilization and revenue reports.

Four policies apply to every operation: authorization, audit, money and time (section 4).

Cross-area rules at a glance:

- A reservation needs a member in good standing, a certification for the machine's family that is valid on the reservation date, a machine without maintenance in the reserved slot, a free machine, and a slot inside opening hours that follows the booking granularity.
- Machine use produces a usage charge in billing, an audit entry and report data. Course enrollments and material purchases also produce charges.

Out of scope: persistence across runs, network access, user interfaces, concurrency, real payments or refunds, notifications, scheduled jobs, deletion of records and integration with other systems.

## 2 Program interface

### 2.1 Program, build and process

- The Go module lives at `realization/go.mod`. The program's main package lives at `realization/cmd/makerspace`. From `realization/`, `go build ./cmd/makerspace` builds the program and `go test ./...` runs its tests. Only the Go standard library is used. The internal package layout is fixed by section 16; the design within each package is the implementer's choice.
- The program reads requests from standard input, one JSON object per line, and writes exactly one response line per request to standard output, in request order. It writes and flushes each response before it reads the next request. Standard output carries responses only: no banner, prompt or log line. Diagnostics, if any, go to standard error. When standard input closes, the program exits with exit code zero.
- One process holds one makerspace, which starts in the initial state of section 2.6. Requests are processed one at a time, in order.
- The program never reads the machine clock, the network, environment-dependent data or files at run time, and writes no files. All time comes from the requests. Given the same request lines, it produces the same response lines.
- There is no reset, state import, clock override or other test-only operation.
- Request lines up to 64 KiB must be accepted.

### 2.2 Requests

A request is a UTF-8 JSON object with exactly three members:

```json
{"id":"q1","op":"registerMember","args":{"actor":"admin","at":"2026-03-02T09:00Z","memberId":"ada","name":"Ada Byron","tier":"plus"}}
```

- `id`: a nonempty string chosen by the caller. It is echoed in the response. It is only a correlation value, not a domain identifier and not an idempotency key; two requests with the same `id` are two separate requests.
- `op`: the name of one operation of this document. Names are case-sensitive.
- `args`: a JSON object with the operation's arguments. Every operation takes `actor` (the identifier of the acting user) and `at` (the request time) in addition to its own arguments. All arguments are required; no operation has optional arguments.

### 2.3 Responses

Every response is one JSON object on one line, with exactly the members shown for its status.

Success:

```json
{"id":"q1","status":"ok","result":{"member":{"memberId":"ada","name":"Ada Byron","tier":"plus","standing":"good","registeredAt":"2026-03-02T09:00Z"}}}
```

Refusal of a well-formed request (section 3):

```json
{"id":"q2","status":"refused","code":"already_exists","reason":"A user with identifier ada already exists."}
```

`code` is exactly one of the codes in section 3.2. `reason` is a nonempty, understandable explanation; its wording is free.

Invalid request (section 2.4):

```json
{"id":null,"status":"invalidRequest","reason":"The line is not valid JSON."}
```

### 2.4 Invalid requests

The response is `status: "invalidRequest"` with a nonempty `reason` when:

- the line is not valid JSON, is empty, or is not a JSON object;
- `id` is missing, is not a string or is empty;
- `op` is missing, is not a string or names no operation of this document;
- `args` is missing or is not a JSON object;
- the request object has a member other than `id`, `op` and `args`;
- `args` has a member that is not an argument of the named operation, including a member whose name differs from a stated argument only in letter case.

The response's `id` is the request's `id` when the line is a JSON object whose `id` member is a nonempty string; otherwise it is `null`. A last line that ends without a line feed is still a request and gets a response. Behavior for JSON objects with duplicate member names and for lines that are not valid UTF-8 is not specified and is not tested. An invalid request changes nothing: no state, no audit entry, no identifier counter and no request-time order (section 4.4).

A request whose `args` lack a stated argument, or carry an argument with a wrong value, is not invalid in this sense. It is refused with code `invalid_argument` (section 3).

### 2.5 Argument values

| Value type | Rule |
| --- | --- |
| identifier | A JSON string of 1 to 64 characters from `A`–`Z`, `a`–`z`, `0`–`9`, `.`, `_` and `-`, whose first character is a letter or digit. Identifiers are compared exactly and are case-sensitive: `Ada` and `ada` are different identifiers. |
| text | A JSON string that contains at least one character without the Unicode `White_Space` property. It is stored and returned exactly as supplied, without trimming. |
| integer | A JSON number written as an optional minus sign followed by digits, without a fraction part or exponent (`10.0` and `1e3` are not integers), within the range the operation states. Every range in this document starts at 0 or higher, so any value written with a minus sign, including `-0`, is out of range. |
| timestamp | A JSON string `YYYY-MM-DDTHH:MMZ` naming a valid UTC calendar date and time from `2000-01-01T00:00Z` to `2099-12-31T23:59Z`, for example `2026-03-02T09:00Z`. Hours are `00` to `23`, minutes `00` to `59`; there are no seconds. |
| date | A JSON string `YYYY-MM-DD` naming a valid calendar date from `2000-01-01` to `2099-12-31`. `2026-02-29` is not valid; `2028-02-29` is. |
| month | A JSON string `YYYY-MM` from `2000-01` to `2099-12`. |
| enumeration | A JSON string equal to one of the listed values, compared exactly. |

An argument that is missing, `null`, of the wrong JSON type or outside its format or range is refused with `invalid_argument`. Each argument is checked on its own. Relationships between arguments, such as an end that is not after a start, and relationships to stored state are checked later and have their own codes.

These formats and ranges apply to arguments, including `at`. An integer argument outside its range is out of range however many digits it has. Values the program computes can lie outside these ranges; section 2.8 states the rules for those values.

`actor` is an identifier argument and `at` is a timestamp argument of every operation. An `actor` that is missing, `null`, not a string or not a valid identifier, such as `"bad id!"` or a string of 65 characters, is refused with `invalid_argument` at check 1 of section 3.1, like any other argument. Only a valid identifier that names no user is refused with `unknown_actor`, at check 2.

### 2.6 Initial state and generated identifiers

A new process contains exactly one user: identifier `admin`, name `Administrator`, role `admin`. There are no members, families, machines, courses, materials, reservations, invoices, incidents or audit entries.

The program generates the identifiers of these records:

| Record | Format |
| --- | --- |
| Reservation | `res-1`, `res-2`, … |
| Maintenance window | `mnt-1`, `mnt-2`, … |
| Purchase | `pur-1`, `pur-2`, … |
| Invoice | `inv-1`, `inv-2`, … |
| Payment | `pay-1`, `pay-2`, … |
| Incident | `inc-1`, `inc-2`, … |

Each kind has its own counter. The first record of a kind gets number 1 and each further record of that kind gets the next number, in decimal without leading zeros. Numbers are never reused. Refused and invalid requests consume no number. "Creation order" in this document means the order in which records of a kind were created, which is the order of their numbers.

### 2.7 Records in responses

A `result` object has exactly the members its operation names, and every object inside it has exactly the members stated for it: records have the fields of section 5, and other objects, such as an opening-hours object, a utilization row or the members of a report, have the fields their operation lists. There are never fewer or additional members. Nullable fields are present with the value `null` when they have no value. Lists are JSON arrays; an empty list is `[]`, never `null`. Amounts, counts and minutes are JSON integers. The order of members inside a JSON object is free; the order of list elements is fixed by section 4.5.

### 2.8 Computed values and limits

Request times and time arguments lie between 2000 and 2099 (section 2.5), but some values the program computes from them lie later. Integers grow with the number of requests. These rules cover every computed value.

- **Times after 2099.** A computed timestamp or date can lie after 2099. It uses the same format as its type, with a four-digit year, and the Gregorian calendar continues as usual: 2100 is not a leap year, so `2099-03-01` plus 365 days is `2100-03-01`. The latest values a result can show are a `dueAt` of `2100-01-14T23:59Z` (14 days after `2099-12-31T23:59Z`) and an `expiresOn` of `2100-12-31` (365 days after `2099-12-31`). Points used only in comparisons can also lie after 2099: the first minute after the month `2099-12` and after the date `2099-12-31` are both `2100-01-01T00:00Z`. No computed time lies before `2000-01-01T00:00Z`.
- **The end of the calendar.** No request time is later than `2099-12-31T23:59Z`. The following consequences follow from the rules of this document and are stated so that they are read only one way:
  - `2099-11` is the last month that can be invoiced. `generateInvoices` for `2099-12` is never accepted: when it reaches the operation rules (section 3.1, check 7), it is refused with `month_not_ended`. The revenue report for `2099-12` always has `invoicesGenerated` `false`.
  - An invoice whose `dueAt` lies after 2099 is never overdue. A certification whose `expiresOn` lies after 2099 is never reported `expired`.
  - The last day a utilization report can include is `2099-12-30`, because `to` is at most `2099-12-31` and is excluded from the range.
  - A maintenance window ends at the latest at `2099-12-31T23:59Z`, so the last minute of 2099 cannot be covered. Reservations end by closing time and are not affected.
- **Integers are exact and never negative.** Within the integer limit stated under "Large sums and counters" below, no computed integer is negative. Stock cannot fall below 0 (`insufficient_stock`). Credit and payments are applied at most up to an invoice's balance. Metered minutes are at least 0, because a check-out cannot precede its check-in in the request-time order. Maintenance minutes are part of the open minutes they are subtracted from.
- **Single lines cannot overflow.** The argument ranges keep every line amount and the product inside its formula (section 4.3) below 2^53. The largest is a usage line: metered minutes are fewer than 52,596,000 (from `2000-01-01T00:00Z` to `2099-12-31T23:59Z`), and at 10000 cents per minute the product `minutes × 10000 × 100` stays below 5.26 × 10^13. A material line's product is at most `10000 × 1000000 × 100` = 10^12.
- **Large sums and counters.** Sums and counters grow with the number of requests: invoice totals, balances, credit balances, stock, report sums and minute totals, `seq` and the numbers in generated identifiers. The program keeps every integer exact up to 9007199254740991 (2^53 − 1); signed 64-bit integer arithmetic satisfies this. Once a stored or returned integer, or an intermediate value of a formula in this document, would exceed 2^53 − 1, the rest of the run is not specified and is not tested. Reaching that limit takes at least tens of thousands of requests.
- **Generated identifiers stay valid identifiers.** A generated identifier is its prefix followed by a number. Within the integer limit it has at most 20 characters (a four-character prefix and at most 16 digits), so it always meets the identifier format of section 2.5 and can be passed back as an argument.
- **Audit targets are not identifiers.** An audit `target` is a plain string. A target that joins two values with `/` can be up to 129 characters long and need not meet the identifier format.
- **Durations.** A reservation lasts at most 240 minutes. Maintenance windows and metered sessions have no maximum length apart from the timestamp range.
- **Request size and depth.** The 64 KiB of section 2.1 are 65,536 bytes, not counting the line feed. Longer lines, and lines with any JSON value nested more than 100 levels deep in arrays or objects, are not specified and are not tested.
- **Counting depth.** Levels count arrays and objects only. The outermost array or object of the line, normally the request object, is level 1, and an array or object directly inside a level-n array or object is level n + 1. So `args` is level 2, and an array or object given as an argument value is level 3. Strings, numbers, booleans and `null` add no level. A JSON value is nested more than 100 levels deep when it is an array or object at level 101 or deeper, or lies inside one. Up to level 100, all other rules apply in full. A line that is not valid JSON is answered by section 2.4 whatever its depth.

## 3 Processing a request

### 3.1 Order of checks

A well-formed request is checked in the following order. The first check that fails decides the refusal and its code.

1. **Arguments:** every argument is present and valid by section 2.5 → otherwise `invalid_argument`.
2. **Actor:** `actor` identifies an existing user of any role → otherwise `unknown_actor`.
3. **Request time:** `at` is not earlier than the request time of the most recent request that was answered `ok` (section 4.4) → otherwise `time_regression`.
4. **Role permission:** the actor's role may use the operation at all, as "all" or "own" in the operation index (section 14) → otherwise `forbidden`.
5. **Referenced records:** every argument that names an existing record names one that exists, checked in the order the operation lists its arguments → otherwise `not_found`. An argument that names a member must name a user whose role is `member`; the identifier of a staff or admin user does not name a member.
6. **Ownership:** when the actor's permission for the operation is "own", the record concerned belongs to the actor (section 4.1) → otherwise `forbidden`.
7. **Operation rules:** the refusals listed for the operation, in the order listed.

When a check fails, the response is `status: "refused"` with the code and a reason, and nothing else happens: no record is created or changed, no identifier number is consumed, no audit entry is written and the request-time order is not advanced. When every check passes, all of the operation's effects take place together and the response is `status: "ok"`.

### 3.2 Refusal codes

| Code | Meaning |
| --- | --- |
| `invalid_argument` | An argument is missing, `null`, of the wrong type, or outside its format or range. |
| `unknown_actor` | `actor` does not identify a user. |
| `time_regression` | `at` is earlier than the request time of the latest request answered `ok`. |
| `forbidden` | The actor's role may not use the operation, or may use it only for the actor's own records and the record concerned belongs to another member. |
| `not_found` | A referenced record does not exist. |
| `already_exists` | A record with the supplied identifier already exists. |
| `invalid_state` | The record is not in a state that allows the operation. |
| `invalid_interval` | An interval's end is not after its start, or a report range is longer than allowed. |
| `starts_in_past` | An interval starts before the request time. |
| `invalid_slot` | A reservation does not follow the booking granularity or its duration limits. |
| `outside_opening_hours` | A reservation is not inside the opening hours of its day. |
| `member_suspended` | The member is not in good standing. |
| `not_certified` | The member has no certification valid on the relevant date for the machine's family, or there is no certification to revoke. |
| `already_enrolled` | The member is already enrolled in the course. |
| `course_full` | The course has no free place. |
| `not_enrolled` | The member is not enrolled in the course. |
| `machine_in_maintenance` | A maintenance window of the machine overlaps the reservation. |
| `machine_booked` | Another active reservation of the machine overlaps the reservation. |
| `member_double_booked` | Another active reservation of the member overlaps the reservation. |
| `reservation_conflict` | An active reservation overlaps the maintenance window. |
| `check_in_too_early` | The reservation has not started yet. |
| `insufficient_stock` | The material's stock is lower than the requested quantity. |
| `month_not_ended` | The month to invoice has not ended at the request time. |
| `already_invoiced` | Invoices for the month have already been generated. |
| `invoice_paid` | The invoice is already paid. |

## 4 Cross-cutting policies

### 4.1 Authorization

Every user has exactly one role, fixed when the user is registered: `member`, `staff` or `admin`. Members are the workshop's customers. Staff run the front desk and the workshop floor. Admins also manage the catalog, credits and users.

For each operation and role, the operation index in section 14 states one permission:

- **all:** the role may use the operation for any record.
- **own:** the role may use the operation only for records that belong to the actor.
- **none:** the role may not use the operation.

A record concerned belongs to the actor when:

- the operation has a `memberId` argument and it equals the actor's identifier;
- the operation has a `reservationId` argument and the reservation's member is the actor;
- the operation has an `invoiceId` argument and the invoice's member is the actor.

A "none" permission is refused at check 4, an ownership violation at check 6 (section 3.1). Both use the code `forbidden`.

### 4.2 Audit

Operations are either mutations or reads, as the operation index states. Every request to a mutation that is answered `ok` appends exactly one audit entry, even when the operation changes no data, such as setting a member's standing to its current value. Reads, refusals and invalid requests never append an entry. Entries are never changed or removed.

An audit entry has these fields:

- `seq`: the entry's position in the log, starting at 1 and increasing by 1 for each entry;
- `at`: the request time;
- `actor`: the acting user's identifier;
- `op`: the operation name;
- `target`: a string that identifies the record the operation acted on, as stated per operation in the operation index.

Admins read the log with `listAuditEntries`:

#### `listAuditEntries`

Read. Arguments: none besides `actor` and `at`. Result: `entries`, all audit entries in `seq` order.

### 4.3 Money

- All amounts are integer numbers of cents, represented as JSON integers. There are no fractions of a cent, no floating-point amounts and no currency field. Stored and returned amounts are never negative.
- Every charge is a line with a `quantity`, a `unitPriceCents` and a `discountPercent`. Its amount is
  `amountCents = (quantity × unitPriceCents × (100 − discountPercent) + 50) div 100`,
  where `div` is integer division. This is the exact value rounded half up to a whole cent. Rounding happens once per line. Totals are sums of rounded line amounts and are never rounded again.
  Example: 37 minutes at 45 cents with a 10 % discount: `(37 × 45 × 90 + 50) div 100 = 149900 div 100 = 1499` cents.
- A charge's amount is fixed when the charge is created. Later changes to a rate, a tier or a price never change existing charges.
- Each member has a credit balance, initially 0. It increases by credits issued by an admin and by overpayments. It decreases only when credit is applied to a new invoice (section 11.1). It is never negative. Credit is never paid out.

### 4.4 Time

- All times are UTC with a precision of one minute. Timestamps, dates and months use the formats of section 2.5. The day of the week of a timestamp is that of its UTC date. The date of a timestamp is its UTC calendar date.
- **Request time:** `at` is the time at which the request happens. It is the program's only notion of "now". The request time of every request must not be earlier than the request time of the most recent request answered `ok`; an equal time is allowed. Refused and invalid requests do not move this point. Before the first `ok` response, any valid `at` is accepted.
- **Intervals are half-open.** An interval `[start, end)` contains its start minute and excludes its end minute. Two intervals `[a, b)` and `[c, d)` overlap exactly when `a < d` and `c < b`; intervals that only touch, such as 10:00–11:00 and 11:00–12:00, do not overlap. The length of an interval in minutes is `end − start`.
- **Day and date arithmetic:** a day is 1440 minutes; "N days after timestamp t" is `t + N × 1440` minutes. "N days after date d" is the calendar date N days later, so `2027-03-01` plus 365 days is `2028-02-29`.
- **Opening hours** are the same every week:

  | Day | Opens | Closes | Open minutes |
  | --- | --- | --- | --- |
  | Monday to Friday | 09:00 | 21:00 | 720 |
  | Saturday | 10:00 | 18:00 | 480 |
  | Sunday | closed | closed | 0 |

  The opening period of a day is the interval `[opens, closes)` on that date. A reservation is inside opening hours when its whole interval lies in the opening period of its start date: its start is at or after the opening time and its end is at or before the closing time of that same date. A reservation ending exactly at closing time is inside. Sunday has no opening period.
- **Booking granularity is 30 minutes.** A reservation's start and end must each fall on a minute that is a multiple of 30 within the hour (`:00` or `:30`). A reservation lasts at least one granularity step (30 minutes) and at most 240 minutes.
- **States that depend on time** are evaluated at the request time of the request that reads or uses them: a reservation that is `missed` (section 9.1), a certification that is `expired` (section 7.2) and an invoice that is `overdue` (section 11.1).

### 4.5 Order of listed results

Identifiers are ordered by ASCII byte value (so `-` < `.` < digits < uppercase letters < `_` < lowercase letters, and `M10` < `M9`).

| List | Order |
| --- | --- |
| `listCertifications` → `certifications` | `familyId` ascending |
| `listMachines` → `machines` | `machineId` ascending |
| `getMachineSchedule` → `reservations` | `start` ascending, then creation order |
| `getMachineSchedule` → `maintenance` | `start` ascending, then creation order |
| `listMemberReservations` → `reservations` | `start` ascending, then creation order |
| `listMaterials` → `materials` | `materialId` ascending |
| `generateInvoices` → `invoices` | `memberId` ascending |
| `listInvoices` → `invoices` | `month` ascending |
| invoice → `lines` | the membership line first, then the other lines by their `at` ascending, then in the order the charges were created |
| `listIncidents` → `incidents` | creation order |
| `utilizationReport` → `machines` | `machineId` ascending |
| `listAuditEntries` → `entries` | `seq` ascending |

## 6 Members

### 6.1 Registry

The registry holds every user: the initial admin, staff and admins registered by an admin, and members registered by staff or admins. Users, including members, share one identifier space. Users are never deleted and their identifier, name and role never change.

#### `registerUser`

Mutation. Registers a staff member or an admin.

- Arguments: `userId` (identifier), `name` (text), `role` (enumeration `staff` or `admin`).
- Refusals: `already_exists` when any user, including a member, has the identifier `userId`.
- Effect: creates the user.
- Result: `user`.

#### `registerMember`

Mutation. Registers a member with a membership.

- Arguments: `memberId` (identifier), `name` (text), `tier` (enumeration `basic`, `plus` or `pro`).
- Refusals: `already_exists` when any user has the identifier `memberId`.
- Effect: creates a user with role `member`, the given tier, standing `good`, `registeredAt` equal to the request time and a credit balance of 0.
- Result: `member`.

#### `getMember`

Read. Arguments: `memberId` (identifier, an existing member). Result: `member`.

### 6.2 Memberships

A membership has a tier and a standing. The tier sets the monthly fee and the discount on machine usage:

| Tier | Monthly fee | Usage discount |
| --- | --- | --- |
| `basic` | 2500 cents | 0 % |
| `plus` | 4900 cents | 10 % |
| `pro` | 9900 cents | 25 % |

The fee is charged once for every invoiced month (section 11.1), without proration. The usage discount applies only to usage charges, never to course or material charges.

A member is **in good standing** when the standing is `good`. A suspended member cannot make reservations, check in, buy materials or enroll in courses. Suspension does not cancel existing reservations or enrollments. A suspended member can still cancel reservations, check out, see their records and pay invoices, and still receives the monthly fee. Reinstating good standing removes these restrictions; all other rules still apply.

#### `changeTier`

Mutation. Changes a member's tier.

- Arguments: `memberId` (identifier, an existing member), `tier` (enumeration `basic`, `plus` or `pro`).
- Effect: sets the tier. Setting the current tier succeeds without a change. The new tier applies to membership fees of invoices generated afterwards and to usage charges created by later check-outs.
- Result: `member`.

#### `setMemberStanding`

Mutation. Suspends or reinstates a member.

- Arguments: `memberId` (identifier, an existing member), `standing` (enumeration `good` or `suspended`).
- Effect: sets the standing. Setting the current standing succeeds without a change.
- Result: `member`.

## 7 Training

### 7.1 Courses and enrollments

A course teaches the safe use of one tool family. It has a fee and a capacity. A member enrolls; staff record completion, which certifies the member for the course's family. There is one enrollment record per course and member. It is created by the first enrollment; a later enrollment after completion reuses and resets it.

The course's `enrolledCount` is the number of its enrollments with status `enrolled`. A place becomes free when an enrollment is completed.

#### `addCourse`

Mutation.

- Arguments: `courseId` (identifier), `familyId` (identifier, an existing family), `title` (text), `feeCents` (integer 0 to 1000000), `capacity` (integer 1 to 1000).
- Refusals: `already_exists` when a course with `courseId` exists.
- Effect: creates the course with `enrolledCount` 0.
- Result: `course`.

#### `enrollInCourse`

Mutation. Enrolls a member in a course.

- Arguments: `courseId` (identifier, an existing course), `memberId` (identifier, an existing member).
- Refusals, in this order: `member_suspended` when the member is not in good standing; `already_enrolled` when the member's enrollment in this course has status `enrolled`; `course_full` when `enrolledCount` equals `capacity`.
- Effect: the enrollment gets status `enrolled`, `enrolledAt` equal to the request time and `completedAt` `null`. A course charge is created for the member (section 11.1): `kind` `course`, `ref` the course identifier, `quantity` 1, `unitPriceCents` the course fee, `discountPercent` 0, `at` the request time. A course with fee 0 creates a charge of 0 cents.
- Result: `enrollment` and `course` (after the change).

#### `completeCourse`

Mutation. Records that a member completed a course and certifies the member.

- Arguments: `courseId` (identifier, an existing course), `memberId` (identifier, an existing member).
- Refusals: `not_enrolled` when the member has no enrollment in this course with status `enrolled`.
- Effect: the enrollment gets status `completed` and `completedAt` equal to the request time. The member's certification for the course's family is issued (section 7.2). Standing is not checked.
- Result: `enrollment` and `certification`.

### 7.2 Certifications

A member has at most one certification per tool family. Completing a course issues it: `issuedOn` is the date of the request time and `expiresOn` is 365 days after `issuedOn`. If the member already has a certification for that family, whether valid, expired or revoked, it is replaced by the newly issued one.

A certification is **valid on date D** when it is not revoked and `issuedOn ≤ D < expiresOn`. It is not valid on its `expiresOn` date. Its reported `status` at a request time is `revoked` when revoked, otherwise `expired` when the date of the request time is on or after `expiresOn`, otherwise `valid`.

#### `revokeCertification`

Mutation. Withdraws a member's certification, for example after a safety incident.

- Arguments: `memberId` (identifier, an existing member), `familyId` (identifier, an existing family).
- Refusals: `not_certified` when the member has no certification for the family or it is already revoked. An expired certification can be revoked.
- Effect: the certification becomes revoked; its dates do not change. Existing reservations stay, but check-in requires a valid certification (section 9.2).
- Result: `certification`.

#### `listCertifications`

Read. Arguments: `memberId` (identifier, an existing member). Result: `memberId` and `certifications`, all of the member's certifications, including expired and revoked ones.

### 8.2 Maintenance

A maintenance window takes a machine out of service for an interval `[start, end)`. While a scheduled window overlaps a slot, the machine cannot be reserved for it, and since every use starts with a reservation and its check-in, the machine cannot be used in the window. The one exception is a session that is already checked in and runs past its reservation's end: it is not interrupted, keeps metering until check-out and counts in `usedMinutes` (section 13). Windows may use any minute, are not limited to opening hours and may overlap each other.

#### `scheduleMaintenance`

Mutation.

- Arguments: `machineId` (identifier, an existing machine), `start` (timestamp), `end` (timestamp), `reason` (text).
- Refusals, in this order: `invalid_interval` when `end` is not after `start`; `starts_in_past` when `start` is before the request time; `reservation_conflict` when the window overlaps an active reservation of the machine (status `reserved` or `checkedIn`, section 9.1).
- Effect: creates the window with status `scheduled`.
- Result: `window`.

#### `cancelMaintenance`

Mutation.

- Arguments: `windowId` (identifier, an existing maintenance window).
- Refusals: `invalid_state` when the window is already cancelled or its start is at or before the request time.
- Effect: the window gets status `cancelled`. A cancelled window no longer blocks reservations and no longer counts in schedules or reports.
- Result: `window`.

## 9 Bookings

### 9.1 Reservations

A reservation books one machine for one member for an interval `[start, end)` on one day. Its stored status moves from `reserved` to `checkedIn` to `completed`, or from `reserved` to `cancelled`. Its reported status is the stored status, except that a stored `reserved` reservation whose `end` is at or before the request time is reported as `missed`. A missed reservation can no longer be checked in or cancelled and causes no charge.

A reservation is **active** when its reported status is `reserved` or `checkedIn`. Only active reservations block a machine or a member. Conflicts are judged on the reserved interval `[start, end)`, not on the actual check-in and check-out times.

**Reservation rules.** A new reservation is accepted only when all of the following hold. These rules connect members, training, equipment and time:

1. its slot follows the booking granularity and duration limits and starts at or after the request time (section 4.4);
2. the slot lies inside the opening hours of its start date;
3. the member is in good standing;
4. the member holds a certification for the machine's family that is valid on the reservation date, which is the date of `start`;
5. no scheduled maintenance window of the machine overlaps the slot;
6. no other active reservation of the machine overlaps the slot;
7. no other active reservation of the member, on any machine, overlaps the slot.

#### `createReservation`

Mutation.

- Arguments: `memberId` (identifier, an existing member), `machineId` (identifier, an existing machine), `start` (timestamp), `end` (timestamp).
- Refusals, in this order:
  - `invalid_interval` when `end` is not after `start`;
  - `invalid_slot` when `start` or `end` is not on a 30-minute boundary or the length is outside 30 to 240 minutes;
  - `starts_in_past` when `start` is before the request time;
  - `outside_opening_hours` when the slot is not inside the opening hours of its start date;
  - `member_suspended` when the member is not in good standing;
  - `not_certified` when the member has no certification for the machine's family valid on the date of `start`;
  - `machine_in_maintenance` when a scheduled maintenance window of the machine overlaps the slot;
  - `machine_booked` when another active reservation of the machine overlaps the slot;
  - `member_double_booked` when another active reservation of the member overlaps the slot.
- Effect: creates the reservation with status `reserved`.
- Result: `reservation`.

Example: on Saturday `2026-03-07`, the slot `17:30`–`18:00` is inside opening hours and `17:30`–`18:30` is not; on Tuesday `2026-03-03`, `10:15`–`11:00` is refused with `invalid_slot`.

#### `cancelReservation`

Mutation.

- Arguments: `reservationId` (identifier, an existing reservation).
- Refusals: `invalid_state` when the reported status is not `reserved`.
- Effect: the reservation gets status `cancelled`. There is no fee and no credit.
- Result: `reservation`.

#### `listMemberReservations`

Read. Arguments: `memberId` (identifier, an existing member). Result: `memberId` and `reservations`, all of the member's reservations in every status.

#### `getMachineSchedule`

Read. Shows one machine's day.

- Arguments: `machineId` (identifier, an existing machine), `date` (date).
- Result: `machineId`; `date`; `openingHours`, an object `{"open": "HH:MM", "close": "HH:MM"}` with that day's times, or `null` on Sunday; `reservations`, the machine's reservations whose `start` falls on that date, in every status except `cancelled`; `maintenance`, the machine's scheduled windows that overlap the interval from `00:00` of that date to `00:00` of the next date.

### 9.2 Check-in, check-out and metering

The member checks in when starting to use the machine and checks out when done. The program meters the minutes in between and charges them at the rate captured at check-in, with the member's tier discount.

#### `checkIn`

Mutation.

- Arguments: `reservationId` (identifier, an existing reservation).
- Refusals, in this order: `invalid_state` when the reported status is not `reserved` (so a missed, cancelled, checked-in or completed reservation is refused); `check_in_too_early` when the request time is before `start`; `member_suspended` when the member is not in good standing; `not_certified` when the member has no certification for the machine's family valid on the date of the request time.
- Effect: status `checkedIn`; `checkedInAt` is the request time; `rateCentsPerMinute` is the machine's current rate.
- Result: `reservation`.

#### `checkOut`

Mutation.

- Arguments: `reservationId` (identifier, an existing reservation).
- Refusals: `invalid_state` when the status is not `checkedIn`.
- Effect: status `completed`; `checkedOutAt` is the request time; `meteredMinutes` is `checkedOutAt − checkedInAt` in minutes, which may be 0 and may extend past the reservation's end or closing time. A usage charge is created for the member: `kind` `usage`, `ref` the reservation identifier, `quantity` the metered minutes, `unitPriceCents` the captured rate, `discountPercent` the discount of the member's tier at check-out, `at` the request time. A charge of 0 cents is still created. The reservation's `amountCents` is the charge's amount. Standing is not checked.
- Result: `reservation` and `charge`.

## 11 Billing

### 11.1 Charges and invoices

Usage, course and material charges collect on the member's account until they are invoiced. A charge belongs to the month of its `at`. A charge is **unbilled** until it appears on an invoice.

Invoices are generated per calendar month, for all members at once, when staff request it. Generation for a month is possible once the month has ended at the request time, and only once per month. Months can be generated in any order.

For a month M, every member whose `registeredAt` is before the first minute of the month after M receives one invoice, whatever the member's standing. The invoice is built as follows:

1. `invoiceId` is the next invoice identifier. Members are processed in ascending `memberId` order.
2. `issuedAt` is the request time; `dueAt` is 14 days after `issuedAt`.
3. `lines` starts with the membership line: `kind` `membership`, `ref` the member's current tier, `quantity` 1, `unitPriceCents` the tier's monthly fee, `discountPercent` 0, `at` the request time. All of the member's unbilled charges whose `at` lies in month M follow, ordered as section 4.5 states. These charges are no longer unbilled.
4. `totalCents` is the sum of the line amounts.
5. `creditAppliedCents` is the smaller of the member's credit balance and `totalCents`. The credit balance decreases by that amount.
6. `paidCents` is 0. `balanceCents` is `totalCents − creditAppliedCents − paidCents`.
7. `status` is `paid` when `balanceCents` is 0, otherwise `open`.

Because request times never go backwards and generation needs the month to have ended, no charge can be created for a month after that month was invoiced.

An invoice is **overdue** at a request time when its status is `open` and the request time is at or after `dueAt`. The `overdue` field reports this at the request time of the response. Being overdue has no other effect.

Worked example: member `ada` on tier `plus` uses a machine with rate 45 from `2026-03-03T10:00Z` to `10:37`. At check-out a usage charge of 1499 cents is created (section 4.3). Generating `2026-03` at `2026-04-01T08:00Z` gives `ada` an invoice with the membership line (4900) and the usage line (1499): `totalCents` 6399, due `2026-04-15T08:00Z`.

#### `generateInvoices`

Mutation.

- Arguments: `month` (month).
- Refusals, in this order: `month_not_ended` when the request time is before the first minute of the following month (for `2026-03`, before `2026-04-01T00:00Z`); `already_invoiced` when invoices for this month were generated before.
- Effect: creates the invoices as described above and marks the month as invoiced, even when there is no member to invoice.
- Result: `month` and `invoices`, the invoices created by this request.

#### `listInvoices`

Read. Arguments: `memberId` (identifier, an existing member). Result: `memberId` and `invoices`, all of the member's invoices.

### 11.2 Payments and credit

A payment pays one invoice. The part of a payment that exceeds the invoice's balance becomes credit on the member's account. Admins can also issue credit as a goodwill gesture. Credit is applied automatically to the next invoices generated (section 11.1); it is never applied to an invoice that already exists.

#### `recordPayment`

Mutation.

- Arguments: `invoiceId` (identifier, an existing invoice), `amountCents` (integer 1 to 100000000).
- Refusals: `invoice_paid` when the invoice's status is `paid`.
- Effect: `appliedCents` is the smaller of `amountCents` and the invoice's `balanceCents`; `creditedCents` is `amountCents − appliedCents`. The invoice's `paidCents` increases and its `balanceCents` decreases by `appliedCents`; when `balanceCents` reaches 0 its status becomes `paid`. The member's credit balance increases by `creditedCents`. A payment record is created with `memberId` the invoice's member (whoever acts) and `at` the request time. Paying after the due date is allowed.
- Result: `payment`, `invoice` (after the change) and `creditBalanceCents`, the member's credit balance after the change.

#### `issueCredit`

Mutation.

- Arguments: `memberId` (identifier, an existing member), `amountCents` (integer 1 to 100000000), `reason` (text).
- Effect: the member's credit balance increases by `amountCents`. The credit counts as issued at the request time (section 13).
- Result: `memberId`, `amountCents` and `creditBalanceCents`, the member's credit balance after the change.

#### `getAccount`

Read. Arguments: `memberId` (identifier, an existing member). Result: `account`, where:

- `creditBalanceCents` is the member's credit balance;
- `openBalanceCents` is the sum of `balanceCents` over the member's invoices with status `open`;
- `overdueBalanceCents` is the same sum over the member's overdue invoices;
- `unbilledCents` is the sum of the amounts of the member's unbilled charges.

## 13 Reporting

Reports are read-only and are calculated from the current state at the request time.

#### `utilizationReport`

Read. Shows how much each machine was used compared with the time it was available.

- Arguments: `from` (date), `to` (date). The report range is the interval from `00:00` of `from` to `00:00` of `to`; `to` itself is excluded.
- Refusals: `invalid_interval` when `to` is not after `from` or the range is longer than 366 days.
- Result: `from`, `to`, `machines` (one row per machine that exists at the request time) and `totals`. A row has the fields `machineId`, `openMinutes`, `maintenanceMinutes`, `availableMinutes`, `usedMinutes` and `utilizationPercent`; `totals` has the same fields without `machineId`.
  - `openMinutes`: minutes of the range that lie inside opening hours. Every machine gets the full count, regardless of when it was added.
  - `maintenanceMinutes`: minutes of the range that lie inside opening hours and inside at least one scheduled maintenance window of the machine. Overlapping windows count once.
  - `availableMinutes`: `openMinutes − maintenanceMinutes`.
  - `usedMinutes`: for every completed reservation of the machine, the minutes of `[checkedInAt, checkedOutAt)` that lie in the range, summed. Opening hours do not limit this count. Reservations that are checked in but not checked out are not counted.
  - `utilizationPercent`: `(usedMinutes × 100 × 2 + availableMinutes) div (availableMinutes × 2)`, which is `usedMinutes × 100 / availableMinutes` rounded half up to an integer, or 0 when `availableMinutes` is 0. It can exceed 100.
  - `totals`: the sums of `openMinutes`, `maintenanceMinutes`, `availableMinutes` and `usedMinutes` over all rows, and `utilizationPercent` computed from these sums with the same formula. With no machines, all totals are 0.

#### `revenueReport`

Read. Summarizes billing for one month.

- Arguments: `month` (month).
- Result fields:
  - `month`;
  - `invoicesGenerated`: whether invoices for the month have been generated;
  - `invoiceCount`: the number of invoices of the month;
  - `membershipCents`, `usageCents`, `materialCents`, `courseCents`: the sums of the line amounts of each kind on the invoices of the month;
  - `invoicedCents`: the sum of those four;
  - `creditAppliedCents`: the sum of `creditAppliedCents` over the invoices of the month;
  - `outstandingCents`: the sum of `balanceCents` over the invoices of the month at the request time;
  - `paymentsCents`: the sum of `amountCents` of all payments whose `at` lies in the month, for any invoice, including the parts that became credit;
  - `creditsIssuedCents`: the sum of credits issued with `issueCredit` whose request time lies in the month. Credit from overpayments is not included.
- For a month without generated invoices, the invoice figures are 0 and `invoicesGenerated` is `false`; payments and issued credits are still reported.

## 16 Architecture

The program is written in Go; the module root is `realization`. `go build ./cmd/makerspace` builds it and `go test ./...` runs its tests. No dependency beyond the language's standard library is permitted.

Each Package below is one Go package under the module root, named after it.

| Package | May depend on | Rule |
| --- | --- | --- |
| `billing` | members, policies | The billing Package depends only on members, policies. |
| `bookings` | members, training, equipment, billing, policies | The bookings Package depends only on members, training, equipment, billing, policies. |
| `equipment` | policies | The equipment Package depends only on policies. Where maintenance must know about reservations, equipment declares what it needs and the protocol Package supplies it from bookings, so equipment never depends on bookings. |
| `materials` | members, billing, policies | The materials Package depends only on members, billing, policies. |
| `members` | policies | The members Package depends only on policies. |
| `policies` | nothing | The policies Package depends on no other Package of the project; every other Package may depend on it. |
| `protocol` | policies, members, equipment, billing, training, bookings, materials, safety, reporting | The protocol Package is the outer layer: it reads requests, runs the checks every operation shares and calls the area Packages. It may depend on every other Package; no Package depends on it. |
| `reporting` | equipment, bookings, billing, policies | The reporting Package depends only on equipment, bookings, billing, policies. |
| `safety` | equipment, policies | The safety Package depends only on equipment, policies. |
| `training` | members, equipment, billing, policies | The training Package depends only on members, equipment, billing, policies. |

A dependency is any use of another Package's records, rules or operations, in the documentation and in the code. The standard library is not counted.

- **Audit** is realized in `protocol`: The protocol Package appends the audit entry after a mutation is answered `ok`, using the operation's audit target; area Packages do not write audit entries.
- **Authorization** is realized in `protocol`: Checks 2, 4 and 6 of the order of checks run once, in the protocol Package, before any operation's own rules; area Packages do not check roles or ownership themselves.
- **Time** is realized in `protocol`: The protocol Package keeps the request-time order (check 3) and passes the request time to the area Packages as their only notion of now.

- **Members interface:** What other Packages may use of members: its operations, the user and member records, tier and standing, and the refusal `member_suspended`. Other Packages also ask whether a member exists, whether the member is in good standing, and the member's tier with its monthly fee and usage discount. Operations: `registerUser`, `registerMember`, `getMember`, `changeTier`, `setMemberStanding`. Types: user, member, tier, standing.
- **Training interface:** What other Packages may use of training: its operations, the course, enrollment and certification records, and the refusal `not_certified`. Other Packages also ask whether a member holds a certification for a family that is valid on a date. Operations: `addCourse`, `enrollInCourse`, `completeCourse`, `revokeCertification`, `listCertifications`. Types: course, enrollment, certification.
- **Equipment interface:** What other Packages may use of equipment: its operations and the family, machine and maintenance window records. Other Packages also ask for a machine's family and current rate and for the scheduled windows of a machine that overlap an interval. Equipment in turn needs to know whether an active reservation of a machine overlaps an interval; it declares that need, and the protocol Package supplies the answer from bookings. Operations: `addFamily`, `addMachine`, `setMachineRate`, `listMachines`, `scheduleMaintenance`, `cancelMaintenance`. Types: family, machine, maintenance window.
- **Bookings interface:** What other Packages may use of bookings: its operations and the reservation record. Other Packages also ask whether an active reservation of a machine overlaps an interval, and for the completed sessions of a machine. Operations: `createReservation`, `cancelReservation`, `checkIn`, `checkOut`, `listMemberReservations`, `getMachineSchedule`. Types: reservation, opening hours of day.
- **Materials interface:** What other Packages may use of materials: its operations and the material and purchase records. Operations: `addMaterial`, `restockMaterial`, `purchaseMaterial`, `listMaterials`. Types: material, purchase.
- **Billing interface:** What other Packages may use of billing: its operations and the charge, invoice, payment and account records. Other Packages create a charge for a member through billing; billing computes its amount by money. Operations: `generateInvoices`, `listInvoices`, `recordPayment`, `issueCredit`, `getAccount`. Types: charge, invoice, payment, account.
- **Safety interface:** What other Packages may use of safety: its operations and the incident record. Operations: `reportIncident`, `resolveIncident`, `listIncidents`. Types: incident.
- **Reporting interface:** What other Packages may use of reporting: its operations and its report rows. Operations: `utilizationReport`, `revenueReport`. Types: utilization row, utilization totals.
