# Project operations

This reference describes current source before the [Apply rebuild](implementation-plan.md). New package work follows the [target contracts](design/canonical-model/README.md); proposed new operations are not advertised as supported here.

This page is the current operational reference for the model-first `markitect <verb>` source workflow. It is not in the published v0.14.1 CLI. Build/use a candidate from the matching Markitect source checkout; commands and MCP tools below do not change that release pin.

## MCP server and tool groups

Start the repository-local stdio server with `markitect mcp --repo ABSOLUTE_PROJECT_ROOT`. The server fixes Host authority to that root at startup. MCP schemas are typed; input schemas are closed, result schemas are open. Write operations enforce the exact authorization, preview digest, compare-and-swap, or durable-identity rules declared by their schemas. Consult `tools/list` for the exact current schema. Input schemas are written inline and closed. Result schemas (`outputSchema`) write each repeated type once under `$defs` and are not closed objects, which keeps `tools/list` small; they keep their required lists. `markitect mcp --read-only` serves only reads and previews; it writes nothing and starts no agents or checks.

CLI and MCP share the application composition root `projectapp.NewOperations`. It supplies the model Host, local workspace service and transport invoker without starting a provider or creating a workspace. Adapters parse and present requests; the facade owns product reads, briefing history, status aggregation and runtime calls.

The composed project server exposes these operation groups:

- **Inspect:** `schema`, `model`, `check`, `context`, `impact`, `status`.
- **Work Item and model:** `explore`, `ready`, `brief`, `edit`, `plan`, `deliver`.
- **Execution lifecycle:** `run`, `resume`, `repair`, `verify`, `apply`, `packet-export`, `packet-list`, `packet-submit`.
- **Brownfield:** `adopt`.
- **Setup and views:** `init`, `onboard`, `config`, `doctor`, `docs`.

Read-only inspection does not start a role. Setup and doctor inspect local prerequisites; project operations start inner roles only when explicitly invoked through an authorized run/delivery path. The outer client is not itself an inner Manager.

## Ordinary Work Item

Follow [Project workflow](project-workflow.md): inspect, record a typed exploration, edit canonical model only when needed, check and establish readiness, then deliver or use the staged lifecycle. A preview is not a write. For any preview/write pair, use the digest returned by that operation and do not reconstruct it. `deliver` requires the existing caller's explicit execution authorization and advances the same durable run through Verify, preflight, and guarded Apply. The staged tools preserve each plan/run/candidate/verification identity; use the returned bindings.

`check` returns structural findings and coverage. An error result remains an error; it is not converted into a successful empty result. `check` with `coverage` reports nonconforming coverage as a failed operation while returning its report. Resolve those diagnostics before planning or readiness.

## Why something is in the impact

`impact --explain` adds, for every element of the change impact, the reason it is included, a shortest witness path of model relations from a change, and a class: `change` (must be updated or rechecked) or `context` (only to read). The class is a priority signal. The impact and every plan built from it stay as they are. With `--manager`, the explanation shows only what that Manager may see; the impact itself stays project scope.

A Manager's `context` lists the Checks it owns under `checks`, and under `foreignChecks` the Checks other Managers own that its own Artifacts declare or that use its own Statements, with their owner, command and limitation. Neither list exposes another Manager's private Statements.

In guided mode, `context` and `brief list` read accepted briefing history without persisting it. Pass the `stateDigest` returned by `brief list` to `brief dismiss --expect … --write`; dismissal validates that accepted-history view and persists history plus dismissal in one guarded update. A stale token or intervening store change is rejected before replacement. The delivered-but-uncommitted status hint remains a display of the matching persisted-store state.

Manager briefing events project their before and after definitions and relations through that Manager's context at each corresponding historical revision. Ancestors cannot read private child Statement details through these events. Canonical history, digests and opaque event IDs remain intact; this scoped projection does not hide the existence of history or establish a general confidentiality boundary.

Full Verify passes each child's audit summary to its parent as free-form agent prose. It counts verdicts for private or unknown Statement IDs without naming them in the structured subject list, but does not redact summary text. A child summary may still reveal private facts or identifiers; this is a known visibility limitation, not a confidentiality boundary.

`context MANAGER --trace ID` also walks that Manager's knowledge graph, which is built from its context alone, and returns each node it reaches with one shortest witness path. `--direction` and `--depth` bound the walk. A node the Manager cannot see is reported as not found, exactly like a node that does not exist.

## CLI, setup and current roots

The runtime configuration contract lives in `projectconfig`: setup, runtime operations and MCP schema reflection use its types and strict validation. It loads one bounded `.markitect/runtime.yaml` document, validates finite role limits and portable instruction paths, and projects the explicit invocation configuration. The method coordinator owns accepted Manager references, scheduling and enforcement of cumulative budgets.

The CLI exposes matching operations for shell use. Read the candidate's `markitect help` for exact flags; the MCP operation schemas are the preferred contract for outer agents. `--repo` is the project authority root. For an MCP server, pass an absolute path so its selected root is explicit.

`init`, `onboard`, `edit`, `explore`, `ready`, `adopt`, `config`, `docs`, and `apply` have preview/write or guarded-write semantics as defined by their operation. Do not apply a stale plan. Onboarding writes only repository-local guidance and skills; it does not register MCP, configure global accounts, or authenticate a provider. Setup configures the native Codex App Server runtime by default; `--input` with a setup options record selects per-role profiles, including bring-your-own process executors (see [Provider adapters](provider-adapters.md#role-profiles)). Metered agents require explicit budget weights; unmetered agents record unknown cost. Configured cost is an estimate, not billing enforcement. On Windows, `config` defaults to process-local `--windows-sandbox-backend mxc`; the option may also be supplied explicitly. This setting leaves global Codex configuration and Windows Managed Policy unchanged. Setup applies one `:workspace` permission profile to every generated Manager, independent Review role, and Verifier. Each native role runs in its own owned workspace, and a process executor runs in a fresh empty directory and returns candidate files; Host artifact guards remain authoritative, and Review/Verify must return an empty candidate delta. Helpers inherit their parent profile. `--codex-profile` overrides the shared profile for all generated roles. `doctor` does not start roles.

`doctor` reports the installed Git version under `git-version`. Git 2.40 or later is required because Explore, Plan and Apply use `git check-attr --source`. An older, missing or unrecognized Git version produces a failed prerequisite report before model loading or provider inspection; the observed version remains in the diagnostic when available. Doctor does not write project files.

Native App Server roles inherit the caller's environment through `appServer.environmentMode: inherit`. Markitect binds the effective values into the role fingerprint and receipt digest without exposing them. `Agent.Environment` remains the selected-name policy for declared-check executable resolution, not a filter on the inherited App Server environment. Ordinary process adapters retain explicit allowlists.

Within Manager work and integration turns, `markitect_start_helper` delegates scoped file authoring and returns Host-validated file changes after delivery and cleanup. Its current contract has no report-only result for standalone read-only inspection or analysis. Use normal parent tools and the parent's typed report for that work, or the existing independent Review roles for candidate assessment. Authoring helpers may still inspect context and run checks for their edits. Safe read-only and analysis-helper returns are historical package RUN-04 in the retired plan in the [backlog](https://github.com/Glacius-Labs/Markitect/blob/bc4b49e76f9b9e4b3ec98033a0b8c73d5013b310/docs/work-items/backlog.yaml); this capability is not implemented.

## Candidate workspaces and recovery

An authorized plan can use external execution with `packet-export RUN --execute`. This advances the existing scheduler until a Manager or independent review packet is ready and returns `awaiting-external`. `packet-list RUN` checks current source and method-policy bindings before reading immutable pending requests; source or policy drift is reported as stale. Each packet binds its plan, selected source, scope, task attempt and exact candidate; repeated reads preserve its original invocation bytes. Store the complete protocol response under `.markitect/drafts/` or `.markitect/runs/`, then use `packet-submit RUN --packet ID --expect DIGEST --response RELATIVE_FILE --execute` and continue with `packet-export RUN --execute`. The same three operations are available through MCP; only `packet-list` is available on the read-only server. Submission returns `stored: true`; the scheduler validates its task or review content during continuation. Verify and guarded Apply remain separate operations, and the configured verifier runs through the normal local verification path. Run budgets, including elapsed duration, remain in force while awaiting a response. External reported usage feeds cost estimates and does not authenticate provider spending. An external verdict does not establish human acceptance. Internal runs keep their original execution mode and uncertainty handling.

Native work executes in an owned candidate workspace. The bridge binds each candidate to the fixed accepted source, repository identity, overlay, task, and candidate delta. The source working tree is preserved as the service baseline; the fixed accepted project snapshot supplies only the candidate overlay. Apply rechecks freshness and writes only the reviewed delta through guarded Host operations.

A run's observed root and known owned child starts must be terminal before the Host harvests/closes their workspace. Adapter lifecycle accounting remains **partial**: the report records durable Host starts and observed nested starts separately, and observed nested totals are a lower bound. It does not claim an exhaustive child census or proof that no unobserved process exists. Workspace lifecycle evidence is cooperative; it is not OS isolation.

On interruption, inspect `status` and the private durable run/journal. Resume or repair the same run only when the durable state identifies a known safe continuation. Unknown native outcomes are not replayed. Recovery inspects the exact saved provider configuration and already dispatched thread/session/turn; it never starts a new role or resubmits the turn. If ownership, bindings, or terminal state cannot be established, the candidate and journal remain preserved for inspection. A trusted dispatched original turn can be inspected even when an interrupted Host left the outer journal at `prepared`. Known nonterminal Host helper reservations and uncertain helper cleanup block Verify and Apply. Automatic helper-journal reconciliation is not implemented; preserve the private handle and resolve its concrete ownership before proceeding. Generic partial child telemetry alone is not such a blocker.

### Record layout and cutover

Durable domain records use `.markitect/records/`: Runtime owns `run/<id>/` and `run/full-<report-hex>/record.json`, Explore owns `exploration/<id>/record.json`, accepted History owns `briefing/accepted/record.json`, and Brownfield owns `brownfield/<id>/record.json`. JSON fields and domain digest meanings remain unchanged; returned paths and operational-selector bindings change deliberately. Existing requests using former bindings require a fresh preview.

Before upgrading a physical repository, stop and quiesce every old-layout writer and its in-flight recovery activity. Older binaries cannot honor the new lease paths. Affected-kind reads and writes refuse observed old domain data, leases or remnants and preserve original bytes; they never import, migrate, delete, replay or choose an old/new fallback. Inspect interrupted old work with its original source revision after stopping new writers, then observe the same cutover precondition before returning to the new version. Unsupported overlapping versions have no technical fencing guarantee.

Direct safe regular JSON inputs under old `.markitect/runs/` remain transport. An old `<hex32>` directory is transport-only only when it contains at least one exact regular `external-response-<hex32>.json` input and no other child. An empty or mixed directory refuses new Runtime admission. The authoritative submission lives under new `records/run/<id>/external/responses/`; input bytes are never rewritten. Private native journals and logs stay in the separate old private subtree below and cannot reconstruct domain history or refill budgets.

The legacy `manager-runs.json` basename/schema is observed read-only inside the new `records/brownfield/<id>/` container; its budget or attempt evidence blocks new Manager authority and is never imported or refilled. Old `drafts/brownfield` authority is separately refused by cutover detection. The prior-layout diagnostic does not ask you to delete or migrate retained evidence. The separate unsupported-format diagnostic for a new canonical History store retains its existing manual rebuild advice and warning that stored dismissals and resolutions would be lost; no automatic reset is performed.

New Init templates include anchored `/records/` in `.markitect/.gitignore`. Existing projects must add that rule through their normal reviewed project edit before supported new writes; Init refuses an existing ignore file and record operations leave its bytes unchanged. Ignore is a setup precondition, not a security boundary or a Git check performed by recordstore. Native source capture independently omits both exact old runs and new records subtrees, while candidate control writes remain observable and forbidden.

The [architecture contract](architecture.md#operational-record-storage) defines leases, POSIX cooperative namespace limits, exact measured Windows support and created/unknown/published outcomes. Unsupported capability refuses before domain admission. Preserve reported remnants and uncertainty for inspection; a passing flush or test is not power-loss proof or human acceptance.

Agent logs and run journals live in `.markitect/runs/private`, which Markitect creates owner-only: a protected owner-only access list on Windows, mode 0700 elsewhere. It refuses an existing directory that is not owner-only. Known limit for Windows users whose native runs in earlier releases created that directory: those releases gave it the parent folder's access list, so after upgrading every run stops with "existing private log directory … is not owner-only". Delete `.markitect/runs/private` once to continue. The native journals of runs interrupted before that cannot be recovered afterwards; resume such a run with the release that started it before you upgrade.

Those exercise limits are separate from configured runtime defaults and do not guarantee cost or acceptance. Source-level tests, the recorded native A01 result and post-merge gates retain their own source identities and evidence limits.
