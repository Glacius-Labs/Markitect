## Technical decisions from implementation

Decisions taken within concept 1.0 while implementing; they do not change product semantics.

- **Bounded no-progress stop (A1, refined by [PR #696](https://github.com/Glacius-Labs/Markitect/pull/696)):** an open assignment is continued with a message that names the task. After two continued responses in a row that do nothing at all – no Manager tool call, no native execution the Session observed and no change of the working state – the Run ends technically incomplete with a diagnostic that names the Manager. Any tool call counts, also `check`, `read_notes` and a refused call; the Codex adapter reports every completed native item other than text, such as commands, file changes and tool calls. Run never judges whether an action was useful, so read-only review is not standstill (concept §3.7). The message budget bounds every other loop, including repeated refused calls; that stop ends incomplete as an exhausted allowance and names no Manager. This keeps concept §13.2 – a single response end is never a failure and never demands a judgment – while honoring §20 finite limits and honest results.
- **Stale registry links ([PR #701](https://github.com/Glacius-Labs/Markitect/pull/701)):** a registry link to a Definition the checked model no longer has is stale realization, not invalid input (concept §5.4, §6.3). The registry stage keeps the record and accounting lists the link under `stale` instead of failing, so preparation, `markitect check` (exit 0, listed under `stages.structural.files.accounting.stale`) and the Apply preflight accept the model. The one candidate check (`ValidateCandidate`, scoped by `ValidateCandidateFor`, concept §12.1) holds each Manager to the stale links in its own Package subtree and Root to every shard: Implement and Verify checks fail on them, Assessment only reports them in `Check.Stale`, and publication refuses any. The shard owner's handoff therefore carries the diagnostic to its parent, and nothing stale is published. Markitect's own Main is maintained directly, not through Apply, so its CI fails on any stale link that `check` lists.
- **Orphaned registry shards ([PR #705](https://github.com/Glacius-Labs/Markitect/pull/705)):** the shard of a Package the checked model does not have, after the owner removed it or merged it into another, is stale realization too, not `registry.unknown_owner`. Accounting hands each file such a shard still explains (`registry.orphaned`) to the Manager that owns the file's declared area, or to Root where no area owns it. That Manager registers the file in its own shard, and the live entry supersedes the orphaned one, or it removes the file. `StaleLinks` gives Root the shard itself (`registry.orphaned_shard`), so only Root edits it. Responsibility follows the declared ownership because accounting assigns every path by area (concept §6.1, §6.2), and the model records neither a move nor a receiving Package; a merge that also moves the area, such as Phase C's C7, therefore names exactly the receiving Package. `check` lists such shards under `stages.structural.registry.orphaned`, and Main's CI fails on them as on stale links.
- **Build outputs ([PR #706](https://github.com/Glacius-Labs/Markitect/pull/706), corrected by [PR #724](https://github.com/Glacius-Labs/Markitect/pull/724)):** the registry decides what a candidate holds, not the file format. A snapshot leaves out only untracked ELF files that no registry shard names by exact path; a directory entry claims none of them, and a staged unregistered binary still fails `file.unexplained`. `Check.BuildOutputs` lists every left-out file at each Implement check and at Run completion, so the Manager, its parent, the stored record and Verify see it; it never fails a check (concept §6, nothing vanishes untraced).
- **Provider idle limit ([PR #725](https://github.com/Glacius-Labs/Markitect/pull/725), refined by [PR #734](https://github.com/Glacius-Labs/Markitect/pull/734)):** `providerIdleTimeoutSeconds` (run-config format 4; format 3 is refused by name, and `messageTimeoutSeconds` is no longer a key) bounds the longest stretch of provider work without a served tool call; every served call restarts it at the full limit. Phase C chain 3 showed that bounding a busy turn's total provider work cut off an actively coordinating Root seven times. Before #734, #725 had already stopped counting host-served time, and its rationale still holds: time the host spends serving a Manager's tool call (`await`, `review`, `delegate`, `check`, Notes) does not count, because `await` blocks inside the provider turn and would otherwise bound a parent's whole subtree; step 4's Makerspace W0 smoke on 4840fb20 stopped exactly there. A provider that stalls without a tool call still times out, and the Apply deadline and message budget bound everything else.
- **Provider retries ([PR #733](https://github.com/Glacius-Labs/Markitect/pull/733)):** a transient provider error (closed list: `serverOverloaded`) is retried at most twice per response, with 30 s and 120 s backoff inside the Run deadline and off the idle limit, only while no tool call of that response was served; after served actions, or when that is unclear, the Run ends with the cause. Retries are counted in the Apply report as `providerRetries`.
- **Message accounting ([PR #734](https://github.com/Glacius-Labs/Markitect/pull/734)):** `ask` costs no allowance unit of its own; a question costs only as the delivered, batched message. A Manager may have at most 8 open questions; a further `ask` is refused with the reason and a next step. Before a correction pair the Apply checks that at least 2 × Managers messages remain and otherwise ends as a budget stop. A question still unanswered when its addressee hands off is closed with a reason and a next step; only Managers with an open assignment count toward the no-progress stop (WP5).
- **`judge` is a Run tool (A1):** like every other Manager tool, its semantics live in Run (concept §14.2); the provider adapter only maps it.
- **Failure classes (A1):** port or provider failures that stop a Run are reported as failed; deadline, budget, observation and no-progress stops stay incomplete (concept §20.1).
- **Review mandates (A1):** Assessment and Verify child handoffs carry no check result; reviewers run `check` themselves when they need one.
- **Host messages (A1):** every refusal and diagnostic names the concrete reason and a next step that the tools accept (concept §3.7).

## Git remote collaboration (owner direction 27 October)

The owner [gave the direction](concepts/sources/git-remote-collaboration-20261027.md) that agents work through a Git remote, like engineers and their managers in a company, and that a verified result lands on the target branch without owner review ([DEC-078](concepts/register.md#dec-078-agents-collaborate-through-a-git-remote-without-owner-review)). Before a run, a run branch is created from the target branch, which the owner names per run. Each agent works on its own branch or on a shared one, and each Manager takes in, reviews and merges its children's work. Whether agents do this with Git themselves or only through host tools in their harness is designed and discussed with the owner first (question 1). Nothing from Git is mounted. This replaces the runner's checkout mount and its hand-back as a branch, and publication into the owner's working tree. The Manager hierarchy, closed Runs, Verify and model blockers stay as they are. The current mount, hand-back and working-tree publication stay until G1 lands.

Guarantees stay in host state, not in prompts:
- **The handoff:** when an agent stops, the host commits its working copy if needed and pushes it to the agent's branch (in the recommendation, one branch per agent), as it secures the stand today ([DEC-067](concepts/register.md#dec-067-agent-workspaces-and-reviewed-handoffs)). The handoff is that branch tip as the host reads it, not what the agent says, so unpushed work is never lost.
- **Integration:** the host checks that a parent merged exactly that commit.
- **Publication:** the host moves the target branch to the verified commit only if the target is still at the run's base.
- **Write access:** only the host may write the target branch.

Open questions, with the coordinator's recommendations:
1. **How agents reach Git.** The owner allows a push credential in every agent container, asks to also consider a remote-less option such as a local remote, and asks whether agents should use Git at all or only tools that the host provides and configures in each agent's own harness. G0 designs the options and brings them to the owner for discussion; nothing is built before that.
   - Interface (i): agents run Git themselves against the remote: clone, pull, commit, push.
   - Interface (ii): agents use no Git. Host-provided tools in each agent's harness move work, for example to hand off, fetch a child's work, merge it, and sync with the base. The host performs and checks each step ([concept 1.0 §14.1](concepts/v1-concept.md#141-a-fixed-small-tool-set)).
   - A hybrid: ordinary Git inside the agent's own clone, such as commit, diff and log, and every move between agents through host tools.
   - The remote: in the recommendation, a local remote that the host runs for the Run would always exist, so a run would need no hosted remote. Today the Run's Git service container only holds the Run's volume, and the host runs Git in it. Under (i) agents need a network remote there, which means building a Git server: a network protocol, per-agent credentials, a hook that enforces branch ownership, and a container network. Under (ii) and the hybrid the host performs every move between agents, so the service can stay host-operated and no agent needs a credential or a network path to it. Each agent's clone then lives in its own container, and the host moves Git objects between that clone and the service through the container engine, as it moves bytes today; no Git directory is mounted. A hosted remote such as GitHub is optional behind it. GitHub scopes a token to repositories and permissions, never to a branch, so agents with GitHub tokens could write every unprotected branch, and the target stays safe only under a ruleset whose bypass list holds the host alone.
   - Recommendation: the hybrid, against the local remote, with any hosted remote optional, written only by the host. The owner likes the hybrid, wants Git as the abstraction rather than a specific remote such as GitHub or GitLab, and wants every agent to have its own tailored harness. The owner leans towards little interference with an agent's local work. The choice follows the design.
2. **The target moves during a run.** Recommendation: fail closed. The Apply ends with "target moved", publishes nothing, and a new Apply starts from the new target. A later step can merge the new target in and verify again.
3. **The target branch.** Decided by the owner: the branch the owner wants to work on, which the owner can specify. Recommendation: the run configuration names it, and the remote's default branch applies when none is named.
4. **Cleanup.** Recommendation: the host deletes the run's branches at the end of the Apply. The evidence keeps the branch commits in a host-side mirror inside the state volume.
5. **V1 acceptance.** Decided by the owner, 27 October: V1's acceptance covers the current publication; the Git variant is judged after its prototype and is not part of V1's acceptance ([owner](concepts/sources/owner-evening-decisions-20261027.md#5-v1s-acceptance-scope-2015-utc)). Its changed handoff and publication contracts need their own qualification (G4); evidence on F2 does not cover them.
