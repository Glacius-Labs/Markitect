## Technical decisions from implementation

Decisions taken within concept 1.0 while implementing; they do not change product semantics.

- **Bounded no-progress stop (A1, refined by [PR #696](https://github.com/Glacius-Labs/Markitect/pull/696)):** an open assignment is continued with a message that names the task. After two continued responses in a row that do nothing at all – no Manager tool call, no native execution the Session observed and no change of the working state – the Run ends technically incomplete with a diagnostic that names the Manager. Any tool call counts, also `check`, `read_notes` and a refused call; the Codex adapter reports every completed native item other than text, such as commands, file changes and tool calls. Run never judges whether an action was useful, so read-only review is not standstill (concept §3.7). The message budget bounds every other loop, including repeated refused calls; that stop ends incomplete as an exhausted allowance and names no Manager. This keeps concept §13.2 – a single response end is never a failure and never demands a judgment – while honoring §20 finite limits and honest results.
- **Stale registry links ([PR #701](https://github.com/Glacius-Labs/Markitect/pull/701)):** a registry link to a Definition the checked model no longer has is stale realization, not invalid input (concept §5.4, §6.3). The registry stage keeps the record and accounting lists the link under `stale` instead of failing, so preparation, `markitect check` (exit 0, listed under `stages.structural.files.accounting.stale`) and the Apply preflight accept the model. The one candidate check (`ValidateCandidate`, scoped by `ValidateCandidateFor`, concept §12.1) holds each Manager to the stale links in its own Package subtree and Root to every shard: Implement and Verify checks fail on them, Assessment only reports them in `Check.Stale`, and publication refuses any. The shard owner's handoff therefore carries the diagnostic to its parent, and nothing stale is published. Markitect's own Main is maintained directly, not through Apply, so its CI fails on any stale link that `check` lists.
- **Orphaned registry shards ([PR #705](https://github.com/Glacius-Labs/Markitect/pull/705)):** the shard of a Package the checked model does not have, after the owner removed it or merged it into another, is stale realization too, not `registry.unknown_owner`. Accounting hands each file such a shard still explains (`registry.orphaned`) to the Manager that owns the file's declared area, or to Root where no area owns it. That Manager registers the file in its own shard, and the live entry supersedes the orphaned one, or it removes the file. `StaleLinks` gives Root the shard itself (`registry.orphaned_shard`), so only Root edits it. Responsibility follows the declared ownership because accounting assigns every path by area (concept §6.1, §6.2), and the model records neither a move nor a receiving Package; a merge that also moves the area, such as Phase C's C7, therefore names exactly the receiving Package. `check` lists such shards under `stages.structural.registry.orphaned`, and Main's CI fails on them as on stale links.
- **`judge` is a Run tool (A1):** like every other Manager tool, its semantics live in Run (concept §14.2); the provider adapter only maps it.
- **Failure classes (A1):** port or provider failures that stop a Run are reported as failed; deadline, budget, observation and no-progress stops stay incomplete (concept §20.1).
- **Review mandates (A1):** Assessment and Verify child handoffs carry no check result; reviewers run `check` themselves when they need one.
- **Host messages (A1):** every refusal and diagnostic names the concrete reason and a next step that the tools accept (concept §3.7).

## Repository structure

The owner wants a repository that is state of the art, tidy and well organized. Two slices in step 3 deliver it, before the native requalification, so that step 4 qualifies the final layout. R1 is done ([PR #680](https://github.com/Glacius-Labs/Markitect/pull/680), [repository structure](development/repository-structure.md)), and the owner accepted its six recommendations ([DEC-071](concepts/register.md#dec-071-repository-structure-and-archive)). The ruleset protecting `archive/**` refs is active. R2 is done: the restructured layout is described in the [repository layout](development/repository-layout.md), and everything it removed from Main stays at the archive point `archive/main-pre-r2-20261024` (bundle included) that the [archive index](archive.md) lists, together with the six pinned pre-reset commits.

- **R1 – inventory and target layout (read-only, Opus):** classify every top-level directory and every document and experiment as current, archive or delete. Today `docs/` holds about 540 files, about 270 of them design records, and `experiments/` about 500 files. R1 also proposes a target layout: where fixtures, examples, packaging, tooling commands and scripts live, how the documentation is grouped, and how archived material stays traceable, for example through a durable archive ref plus an index page instead of files on Main. It also writes a one-page repository guide and reconciles or replaces the existing [repository layout](development/repository-layout.md) page, so that there is one repository guide. The owner sees the target layout before R2 moves anything. R1 can start at any time because it changes nothing, and its result also tells the documentation translation which historical records still need translating.
- **R2 – execution (writer, Sonnet):** apply the work list of the repository structure document mechanically: archive point and refs, moves, archival, deletions, registry and self-model paths including the changed tag Rule, code map, source packaging, CI, links and anchors. Behavior stays unchanged. It runs directly after A1 has landed, alone in the affected paths, and before C1.

Two current layout choices are deliberate:

- **No `src/` folder.** Markitect is a Go module, and Go places `cmd/` and `internal/` at the module root; a `src/` folder is not idiomatic Go. R1 keeps the Go layout and tidies the rest of the top level around it.
- **`.markitect/` in Markitect's own repository.** It holds Markitect's canonical self-model, registry shards and ignore rules. Markitect develops itself model-first with its own product, and every file in the repository is accounted for there (concept §5.5, §6). R1 keeps it and explains it in the repository guide.

## Integration

Keep the existing development policy: focused PR, meaningful local checks, independent complete-diff review, freeze the reviewed head, merge the exact head without bypassing protection, then read Main back. Recompose and review substantive overlapping changes. Automatic CI is paused; full CI is manually available, and final or release evidence remains separate. No merge waits for hosted CI by default, and absent hosted execution is never reported green.

Use isolated worktrees from verified integrated bases, non-protected scoped branches, preserve unrelated work and revalidate ownership before changes. No parallel Go commands or source edits during a gate in the same checkout. [CONTRIBUTING](../CONTRIBUTING.md#verify-a-change) owns routine checks. New or deleted artifacts require exact registry updates. Self-model changes require the official docs preview, digest and write, not manual edits of generated views.
