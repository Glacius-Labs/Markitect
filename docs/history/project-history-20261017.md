# Markitect's project history: intent, turns and working method

Date: 17 October 2026. This retrospective brings the project timeline and the assistant's process assessment into one account, at the owner's request. It explains how the project reached its current direction; it does not set policy or dispatch work.

## One continuing problem

The owner wanted architecture and working rules to survive across code, documentation and Claude/Codex guidance. In the originating project, representations repeatedly contradicted each other, changes missed rules, and documentation developed what the owner called "Bleeding". Repeated AI consolidation found more drift, took a long time and left the owner unsure what applied or was missing. These are reported experiences, not measured failure rates for agentic development in general.

The proposed answer followed a clear chain. Keep one authoritative account of intent. Use types and explicit relationships to find expressible structural errors before execution. Divide realization among bounded responsibilities instead of asking one Agent to remember everything. Review both contributions and integration. Let the person concentrate on modeling and decisions.

Government follows as a possible later step: delegate some maintenance of the model itself within explicit authority. Managers realizing an accepted model and Government deciding model changes are separate axes. The core motivation remained recognizable as the implementation changed. [Owner account and causal sequence](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/concepts/origin-and-rationale.md)

## The main turns and reversals

### From documentation to the intended project world

The initial implementation was narrower than the later product definition: typed Texts, Rules, Contracts, Workflows, Skills and Agents, with generated views and bounded checks. Architecture contracts then extended the subject, and the later product framed code, tests, configuration and documentation as realizations of a canonical project world.

The assessment here reads this mainly as uncovering the originating motivation. The narrow executable starting point nevertheless shaped later interpretations. Markitect repeatedly had to be distinguished from a linter or a context tool for agent instructions. The recorded common misreadings also correct the idea that delegated realization is incidental scope expansion. [Product interpretation](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/vision.md#common-misreadings)

### From capability breadth to a complete working cycle

Packages, policies, adapters, adoption and projection mechanisms supplied real capabilities and exposed real defects. Their accumulation did not itself answer whether an ordinary job could finish through failure, review, repair and integration without continual expert coordination.

The 6 October assessment already identifies that priority. The 16 October decision takes a more radical route after further design work: rebuild against the completed v1 language and a selected Manager concept, retaining useful lessons rather than preserving every old mechanism. These are decisions at different source and design states; the later reset does not retroactively invalidate the earlier assessment.

The cutover shows the size of the reversal. PR316 changes 701 files, adding 10,714 lines and deleting 143,300, including tests and supporting material. Deletion counts do not establish quality or wasted effort. They do show a deliberate replacement of a substantial product generation. [Cutover change](https://github.com/Glacius-Labs/Markitect/commit/d8eccc274ee18ac8eb325b0ec1efa106be0bdb98)

### From overlapping product generations to a single active foundation

Published Project/Domain contracts, a canonical Projection alpha and a newer managed-project line overlapped for a time. Each carried different status and evidence. That created explanation and maintenance work even when the distinctions were carefully documented.

The new direction preserves release identity and historical evidence in Git, while removing compatibility obligations from current source. At the cutoff, that deliberately trades some previously executable behavior for a smaller coherent foundation. Public Apply returns unavailable before acquisition or effects. Historical Apply successes belong to their earlier engine. [Cutoff README](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/README.md), [explicit CLI refusal](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/internal/adapters/cli/command.go#L113)

### From repairing runtime symptoms to choosing a controlled environment

Windows paths, permissions, process lifetime and ambient configuration repeatedly complicated execution and experiments. The small real handshake on 17 October tested a consequential uncertain boundary before the next adapter implementation.

Both coding CLIs could receive a Host tool. Direct host runs inherited user configuration; clean configuration isolation was observed in the tested Linux-container paths. One container run failed to create a file but still submitted a success claim. Independent file observation therefore mattered even for this small task. The accepted response was a container per Agent session and check, with two adapters using MCP through a session helper. The experiments did not test a finished helper, pinned production image, recovery or reliability. [Results and limits](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/validation/runtime-handshake-20261017.md)

## How the project was developed

The owner repeatedly set direction, clarified authority and corrected narrow readings of the product. Design conversations worked through alternatives and small examples. Coordinating chats split work, managed dependencies and reserved shared files. Delivery chats implemented bounded packages in isolated worktrees. Independent reviewers examined candidates; local checks and hosted CI supplied separate evidence.

The first documented parallel wave launched Init, Copy Me, Risk, .NET, Docs, Codex, Claude, GitHub, Azure DevOps and Konfyra workstreams. All produced bounded results; eight completed source/test/report slices without shared semantic writes, while Init and Copy Me delivered proposals with durable implementation deferred. Review found concrete adapter and interoperability defects before integration. This supports scoped parallelizability, not a claim of reduced human coordination cost. [Wave record](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/validation/parallel-development-wave-1.md)

The initial process centralized shared publication and merges. Later coordination accumulated detailed queues, evidence and status management. On 17 October, integration responsibility moved to deliveries: complete independent review, freeze the exact head, await required CI, then self-merge with head matching. A newer Main revision alone no longer requires recomposition; substantive overlap or conflicts do. Repeated Main-CI and source-artifact observation after every merge was removed from the routine. [Accepted integration rules](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/implementation-plan.md#integration)

This history contains a central tension. Markitect aims to remove routine agent scheduling and synchronization from the owner's day, while its own development required considerable scheduling and synchronization. That is understandable during construction. It remains an important outcome to examine rather than treating the development arrangement as proof that the product method works.

## Assessment of the working method

The following judgments are the assistant's dated assessment. They are not new accepted decisions or measured comparative results.

| Area | Assessment and basis | Practical implication |
|---|---|---|
| Direction and decisions | Strong continuity of motivation and willingness to discard substantial work. The scope changed more than the underlying problem. | Give an accepted foundation enough actual use to reveal its limits before another broad redesign. |
| Evidence discipline | A particular strength: failed attempts, fixed revisions, negative controls and limits remain visible. Source integration, runtime execution, release and acceptance are distinguished. | Preserve the discipline, while choosing evidence that resolves the next consequential question. |
| Independent review | Concrete findings in the wave and later repair history demonstrate useful review, not merely an extra role label. | Judge review by the obligations and combined effects it examines, rather than the number of rounds. |
| Parallel development | Bounded disjoint work can succeed. Shared contracts, ownership and centralized integration still consume coordination. | The new direct-delivery integration rules are a sensible correction. Their effect on attention has not been measured. |
| Prioritization | Capability breadth and technical assurance repeatedly advanced ahead of a reliable complete user workflow. The 6 October assessment and later Apply reset expose the recurring gap. | Protect the two-Apply target from unrelated feature expansion. |
| Experiments | Findings are reported candidly, but environment and harness failures often limit interpretation. | Test the riskiest uncertain operational boundary early with a small real probe. The handshake is an example of this approach. |
| Knowledge maintenance | Good separation of sources, decisions and evidence; many historical layers and changing status passages still make navigation difficult. | Give each current subject one owner, date historical status and link to the current owner instead of repeating it. |

The main concern is the distance between accepted product intent and repeatably observable product effect. Components improved while the complete process still often needed an experienced Coordinator. Technical rigor was useful; further rigor alone could not close a missing process transition.

There is also a cost to repeated architectural resets. Earlier proofs remain valuable for their original subjects, but cannot simply transfer to the new engine. Some must be established again at the new boundaries. The useful inheritance is therefore a combination of concepts, failure lessons, independent expectations and reusable mechanisms whose assumptions still hold.

Knowledge upkeep illustrates the originating problem inside Markitect itself. At the cutoff, the normative v1 language document still says production Go implementation remains outstanding, while the root README describes integrated v1 compilation. Some concept-register current-source paragraphs also describe the retired runtime generation. These are documentation-status discrepancies, not findings that the selected language is incomplete or that the current compiler has been independently proved correct. They warrant bounded correction at their owners while preserving dated evidence. [Language status text](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/design/canonical-model/minimal-language/language-contract.md), [source description](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/README.md), [register](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/concepts/register.md)

The early matched comparison does not establish superiority over simpler agent guidance. It shows explainable policy-migration mechanisms and extra model upkeep; no independent truth owner or concrete human review step was removed. Later comparison attempts of the delegated method were dominated by runtime, environment and harness problems and do not establish either success or failure of that method. Bounded Commerce successes remain valid earlier-generation evidence. None establishes the benefits of the new Apply engine. [Comparison findings](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/validation/agents-md-vs-markitect.md), [distinction between evaluation subjects](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/concepts/register.md#dec-008-the-delegated-method-has-not-yet-been-tested)

## Route chosen at the cutoff

The selected route starts with canonical compilation, immutable snapshots, organization and artifact accounting. RUN and its Journal, repository and session adapters then support actual execution and recovery. A single Package must complete work, independent review and repair before recursion, integration, complete evidence and guarded publication are composed.

The immediate demonstration is precise: freeze one product/profile; realize library model M1 as actual artifacts A1; independently examine code, tests, documentation and history; change only the loan limit from five to three; then Apply M2 against actual A1 and assess A2. No manual artifact repair is allowed between the Applies. At the cutoff, preparation and initial run admission/reconstruction exist, while actual public Apply remains unavailable. [Selected sequence and scope](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/implementation-plan.md)

Four later working-day scenarios test whether the organization can continue while the owner stays responsible for intent and decisions: a reserved question and continuation, internal defect correction, interruption and recovery, and insufficient budget. These are follow-up evidence after the technical core, not additional gates silently added to the first Apply. [Scenario proposal and boundaries](https://github.com/Glacius-Labs/Markitect/blob/3b3cbdd8/docs/concepts/reflections/working-day-demonstration-20261016.md)

The assessment recommends keeping this sequence stable. Further architecture work should name an observed failure, a missing accepted obligation or a blocked necessary step. This delays some generalization in exchange for earlier feedback from a real complete workflow. Similarly, consolidate knowledge at existing owners rather than creating another status layer, and retain the exact-head review/CI discipline while letting deliveries own routine integration. These recommendations do not reopen accepted language or product decisions.

The outcome still to establish is the original practical hope: the owner changes the model, and the organization realizes that change cleanly, visibly and with substantially less routine intervention. The history supplies reasons to pursue that test and reasons to keep its result open.
