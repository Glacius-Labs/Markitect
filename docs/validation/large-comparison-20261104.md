# The first side-by-side page: the large Makerspace's builds, 4 November 2026

Each result has a neutral label until the key. There is no overall score: the figures point at what is worth looking at, and the conclusion is the owner's.

Step U3 of the [delivery plan](../implementation-plan.md#concept-30-build): what [concept 3.0 §13](../concepts/v3-concept.md#13-how-we-know-it-works) keeps and compares, on the six builds of the [large Makerspace](../../tools/makerspace-large/README.md) that exist. How the page was made, and its dispatch, come after the key.

All six passed all 327 hidden cases, and all six have the spec's 48 modules at their paths with no import the spec forbids. So neither the hidden cases nor the module table tells them apart. What follows is what does.

**Worth looking at:**

- **Size and repetition.** A is the smallest, with 9,117 program lines against 11,510 to 17,319, and repeats the least: 2.0 % of its lines in renamed copies, against 6.5 to 19.5 %.
- **Tests.** A has 101 test functions, and the others have 590 to 686. A's reader still gave its tests 4 of 5. Only F got 5.
- **One enormous function.** A and B each hold their operation table in a single function, of 619 and 1,010 lines. The others stay at 217 lines or fewer.
- **Tests that cross module lines.** In C, D and E the tests import between modules 124 to 143 times where the program itself may not. A, B and F have none.
- **The same weakness in most reads.** The readers of A, B, E and F name it without knowing of each other: the list of gates for a machine is written out separately for reserving, for checking in and for the compliance view, so a new gate means editing each by hand. Test 2's changes should reach it.
- **The readers barely differ.** Every architecture score is 4, and D and F alone get a plain yes on taking over. The reasons say more than the scores.

**Limits.** Each result has one read, and a reader opened 19 to 29 files of 76 to 207, in one and a half to three minutes, so a read is a sample and not an audit. Scores from one reader are not comparable to another's to the point. Blinding removes files, not words in the code, and F's code and tests name the model it was made from, so its read shows how it was made. The measured figures say nothing about whether the code is right, which the hidden cases say for these six.

### A

**Architecture (4 of 5).** Good: Each area is its own package. architecture_test.go parses every package's imports, checks them against the dependency table and fails on any extra edge, so the module boundaries are enforced, not just documented. protocol does the shared checks 1–6 once, in process.go Handle. Area modules only do check 7 and the effects, so a new operation is one registry entry plus one module method. Upward needs use small interfaces declared by the module that needs them (bookings.Premises, training.Attendance/Assessment, materials.Hazard/Stocktake), and app.go New wires them in one visible place. Modules consistently run every refusal check before they change anything (bookings.Create/CheckIn, materials.Purchase, escalations.Escalate, training.Enroll), which keeps the rule 'a refused request changes nothing' local to each method. Weak: The eligibility gates are listed three times: bookings.Create, bookings.CheckIn and compliance.Blockers each repeat suspended/consent/certified/waiver/lockout(/inspection). Adding a gate means editing several modules and keeping their order in sync by hand. Some business rules sit in protocol. The utilization range limit (to<=from or >366 days) is in ops_training.go, and generateInvoices calls CheckGenerate and then Generate from the handler instead of the module owning the whole operation. Opening hours live in bookings (HoursOf/OpeningHoursOf), and access reaches into bookings for them and for CodeOutsideHours. Bookings declares CodeNotOnPremises, commented as 'added by access', and training declares codes 'stated by classes and assessments'. Codes and shared rules end up where the dependency direction allows, not where they belong. The materials Hazard interface returns a bare code string, so the hazmat module's reason is lost and materials writes a generic one. billing.Generate hard-codes the household discount rule (>=3 members, 10%) inside invoice generation, not in households or policies.

**Naming (3 of 5).** Good: Domain types and methods read well: Reservation, Invoice, Charge, Ladder, Case, RefuseSuspended, RefuseNotCertified, HoldsValid, ActiveOverlap, OverdueInvoices. Status and code constants are named per module (bookings.CheckedIn, billing.CodeInvoicePaid, access.CodeSponsorNotInside), and wire names match the struct json tags. Weak: ops_training.go holds training plus about 25 unrelated areas (materials, bookings, safety, reporting, access, events, purchasing, quotes, jobs, compliance, finance), so the file name misleads. helpers.go is a grab-bag of three unrelated functions. The protocol DSL uses cryptic one- and two-letter names: id/plain/txt/ts/dt/mo/en/num, c.str/c.i/c.b/c.t/c.d/c.m, okr, fail, pNo/pOwn/pAll, kIdent. They are dense to read. Container types are named inconsistently: Registry, Catalog, Book (used for about 25 different modules), Billing, Training, Shop, Doors, Lists, Reader, Reports, Roster, Store. Book says nothing. The same kind of helper has different names and homes: passProduct(c) in ops_money.go, but assessmentOf(c)/classificationOf(c) in helpers.go. Doors has Enter but LeaveDoor. policies.Ceil60 is a vague name for a domain rule.

**Cleanliness (3 of 5).** Good: Modules are short and direct, with no needless abstraction layers. State is maps and slices, and copies (view functions) are returned so callers cannot change internal records. process.go Handle is a linear, commented walk through checks 1–7 that is easy to follow. No dead code or TODO stubs in the files opened. Constants replace string literals for statuses and codes. Weak: Every handler repeats `x, r := ...; if r != nil { return fail(r) }; return okr(result{...}, target)`, about 150 times across the ops_*.go files. Some handlers unpack report structs field by field into result maps (revenueReport, financeSummary, agedReceivables, complianceSummary, getProjectCost), so the wire names are spelled twice even though the structs could carry json tags. The guard sequences in bookings.Create and CheckIn are near copies, and each gate has two forms (RefuseX and a boolean X/Missing) to serve compliance. Some arguments are accepted but never used: issueCredit's reason is dropped (the ledger memo is the memberId), and forfeitDeposit's reason is never passed on. app.go spends 40 lines on ref* one-liners, and ownerOf in ops.go is a switch on argument names. Both are stringly-typed tables that must be kept in step with every new record kind by hand.

**Tests (4 of 5).** Good: Protocol tests drive the real request lines and check exact values: invoice totals, credit applied, journal entry ids, accounts and memos, trial-balance invariants (billing_test.go TestInvoiceWorkedExample). A wrong rounding or posting would fail them. The order of checks, invalid requests and argument formats get their own tables (protocol_test.go): -0, 1e3, numbers past 2^63, case-sensitive op and arg names, leap days, 2100 out of range. fuzz_test.go runs 12000 random requests per seed over 6 seeds. It checks determinism (two runs give identical output), that the ledger's receivable equals the sum of invoice balances and its credit liability the sum of credit balances, non-negative stock, and audit seq without gaps. harness_test.go is a compact DSL (ok/no/is with dotted paths). no() also insists on a non-empty reason, and an optional coverage dump records which (op, outcome) pairs were exercised. architecture_test.go makes the dependency rules executable. Weak: Almost all tests sit in protocol. Area modules have nearly no unit tests (guardians_test.go is the only one), so a module's rules are only reached through the full stack and failures point at the protocol, not the rule. Refusal atomicity ('a refused request changes nothing') is only checked by audit length after invalid requests. No test checks module state after a refusal deep in check 7. The coverage dump is opt-in through an environment variable and nothing asserts on it, so a missing refusal test goes unnoticed. Many assertions depend on generated id order (inv-1, jrn-4, entries.N-2), which makes tests brittle to harmless reordering of postings.

**Taking it over: yes, with doubts.** The skeleton is sound: one declarative operation registry, shared checks in one place, small focused modules, enforced dependency rules, and a strong behaviour plus invariant-fuzz test suite. That makes changes safe to make and verify. The doubts are the repeated eligibility gates, which must be kept in sync, some business rules leaking into protocol or into the wrong modules, a misnamed catch-all ops file, and the near absence of module-level tests. First: Split ops_training.go into one ops file per area (or per module group), and fold helpers.go into them. Put the reservation/check-in gate list in one place, shared by bookings.Create, bookings.CheckIn and compliance.Blockers, so a new gate is added once. Move the rules now in protocol into their modules (the utilization range check, invoice generation as one operation), and move opening hours and the household discount to where they belong. Make the hazard gate return a *p.Refusal instead of a bare code, and use or remove the dropped reason arguments of issueCredit and forfeitDeposit. Add unit tests per area module for their check-7 rules, including tests that a refusal leaves the module's state unchanged.


### B

**Architecture (4 of 5).** Good: Each area is its own package with a Service and New; the package comment lists exactly what it uses, what it answers and the refusal codes it adds (bookings/bookings.go, billing/billing.go, materials/materials.go). protocol/server.go keeps checks 1 to 6 (argument decoding, actor, time order, role, record existence, ownership) in one place, and area modules only do their own check-7 refusals. The registry design (Op, Arg, Perms, Handler in protocol/op.go) is a clean table-driven boundary. Cycles are broken only in protocol/world.go, using small adapter structs (equipmentReservations, attendanceGate…). Modules declare the interfaces they need (bookings.Premises, materials.HazardGate), so the one-way dependency rule holds. Weak: Two different cycle-breaking mechanisms: adapter structs in world.go, and Gate/Freeze objects with a late Bind in hazmat and stocktake. Bind is order-dependent and only fails with a runtime panic. Eligibility rules are spread out. The same gate sequence (standing, consent, certified, waiver, lockout, inspection) is written separately in bookings.CreateReservation, bookings.CheckIn and compliance.blockers, so changing a gate means editing three places and keeping their order in sync by hand. Adding a record kind touches several places: an Arg Ref string in an ops_group file, the string switch in World.exists, and possibly World.ownerOf (protocol/lookups.go). The kinds are untyped strings, so a typo only shows up as a not_found at runtime. Results are defined twice. Modules return json-tagged *Result structs, and every protocol handler unpacks them into map\[string]any by hand (ops_group1/3/4.go), so a change to a result's shape has to be made in two places.

**Naming (3 of 5).** Good: Domain names are precise and consistent with the wire protocol: ReservationStatus, reportedStatus versus stored status, CancelReserved, ReservationsStillToCome, ChargeOnPaidInvoice, OverdueInvoices. Refusal codes are named constants with Code prefixes (policies/refusal.go, bookings.CodeMachineBooked), and json tags match the field names. Weak: The g1/g2/g3/g4 prefixes on argument helpers (g1Ident, g3Ref, g4Ident) name a file grouping, not a meaning. The same name has different signatures: g1Ident(name) versus g2Ident/g4Ident(name, ref). Test helpers carry per-area prefixes (xaBookingsTs, xaClassesMust, xaHazmatAssertCode…) only to avoid collisions within one package. One thing goes by different names: billing's fields are registry and journal (for members and ledger) while other modules use members and ledger. Its constructor parameter is householdRegistry. Args.Ident's comment says it reads 'an identifier or text argument', and Ident, Text and Enum are all the same str call. The Server doc comment says it holds the audit log and last time, but those live in World.

**Cleanliness (3 of 5).** Good: Functions are short and linear, with refusals checked in the listed order and early returns (bookings/operations.go, training/operations.go). Returned records are copied deliberately (bookings.view with copyPtr, billing.copyInvoice). Comments state invariants such as 'the list is never nil'. No dead code or TODO stubs in the files opened. The registry panics on duplicate names. Weak: The argument helpers are copied four times across ops_group1..4.go (Ident, Text, Ts, Date, Month, Enum, Int), each copy slightly different. Refusal-code strings are declared more than once: hazard_not_certified in materials and hazmat, stocktake_open in materials, purchasing and stocktake. Modules repeat not_found checks that protocol check 5 already guarantees, labelled 'defensively' (compliance.CheckEligibility, compliance.ComplianceSummary, training.AddCourse). Every handler closure repeats the same boilerplate (call method, if err return, build map, Target), across about 188 operations. bookings.memberActiveOverlaps and ActiveReservationOverlaps are the same loop with a different field.

**Tests (4 of 5).** Good: protocol/spec_test.go parses TASK.md and checks every operation's name, mutation flag, argument order and per-role permissions against the registry, which would catch drift in the operation table. Behavioural tests check exact values: billing_test.go walks the worked example down to invoice totals, credit applied, each journal entry and trial-balance figures. The lockers and bookings tests compare whole records and boundary times (cancellation at 10:59 versus 11:00, rate captured at check-in). e2e_helpers_test.go checks the response wire shape strictly: exactly one object per line, with exactly the members its status allows. Weak: The xarea_*_fixture_test.go files each rebuild their own copies of ts, Must and AssertCode helpers and their own service graph, rather than using a shared fixture or NewWorld. ops_group1_test.go only checks that names are registered and have no duplicate arguments, which is a smoke test. spec_test.go reads ../../TASK.md from outside the module, and hard-codes 188 operations. Several large modules (bookings, compliance, training, materials) have no tests in their own package and are covered only through protocol, so module-level regressions surface far from the code.

**Taking it over: yes, with doubts.** The module boundaries, documented package contracts, centralised check order and spec-driven registry test make it easy to find where a rule lives and to trust the tests. Doubts: the protocol layer is large and repetitive, record kinds and refusal codes are untyped strings copied across packages, and the eligibility gate sequence exists in three copies. Routine changes are likely to miss one of the places they need to touch. First: Merge the g1..g4 argument helpers into one set in op.go, and generate the result map from the module's *Result struct (or return it directly), removing the per-handler boilerplate. Extract the reservation eligibility gates into one shared function that bookings (create and check-in) and compliance both use. Give record kinds a typed constant (or register them per module) so that Arg.Ref, World.exists and ownerOf cannot drift, and keep each refusal code in its owning module only. Replace the hazmat.Gate and stocktake.Freeze Bind objects with the same adapter pattern world.go already uses, and share one test fixture across the xarea tests.


### C

**Architecture (4 of 5).** Good: Every module is described the same way: a list of policies.Op entries giving arguments, ref kinds, permissions, the owned argument and a Run func (policies/op.go). The protocol runs checks 1–6 once for all operations in a single numbered function (protocol/request.go check). The modules hold only their own refusals and effects. Where a module would otherwise depend on one it may not import, it declares a small interface: equipment.ReservationOverlap, training.AttendanceGate/AssessmentGate, bookings.Premises. wiring.go supplies these through explicit forwarder links, so the construction order and the cycle-breaking are all in one readable place. Each package is one area with its own state and ID counters (billing.Module, bookings.Module, escalations.Module). Reads such as finance and reporting only call the exported accessors of billing, ledger and refunds. Weak: Charge kinds are plain strings shared across packages. bookings/ops.go passes "usage", materials and consumables pass "material", training passes "course". billing.revenueAccount panics on any kind it does not know, finance.chargeKinds repeats the list and silently skips unknown kinds, and reporting.revenueReport switches on four of them. Adding a kind means editing at least four packages, and nothing fails at compile time. Some modules compare another module's status strings directly: escalations checks inc.Status == "resolved", refunds checks inv.Status != "paid", and workorders checks inc.Status == "open". Meanwhile safety and billing keep those same constants unexported. Record existence (s.refs) and ownership (s.owners) are both keyed by strings in protocol/wiring.go. A new Ref or Owned value that is missing from those maps only shows up as a panic at request time, and no test checks the maps are complete. Constructors take many concrete module pointers: bookings.New takes 13 parameters and training.New takes 8. finance.New accepts members.Module and never uses it.

**Naming (4 of 5).** Good: Domain names are precise and match the spec: ReportedStatus vs Stored, ActiveReservationOverlaps, ChargeOnPaidInvoice, CreditsIssuedSum, invoiceDueDays, certificationDays. Comments in policies/op.go explain each type and constant (PermOwn, Owned, Call), and the check numbers in request.go match the spec's order of checks. Weak: Handler names follow two conventions: runX in members, equipment, escalations and finance, but bare names in billing, bookings and training (generateInvoices, checkIn, addCourse). One idea gets several names: the record-to-JSON helpers are record() in bookings, certificationBody() in training and invoiceRecords() in billing. The time helpers in tests are tm/dt/mo in bookings_test but at/day/month in finance_test. The argument-builder helpers Stamp, Day and Mon are terse abbreviations next to Time, Date and Month. Ref kinds are literals almost everywhere, but equipment.go declares local constants refFamily/refMachine and then still writes "window" as a literal. Refusal reason style varies: equipment says "A family with identifier %s already exists." while training says "a course with this identifier exists", and bookings uses lowercase fragments.

**Cleanliness (3 of 5).** Good: Handlers are short and linear. Refusals are checked in spec order in one function (bookings.createRefusal, checkInRefusal), and the effects follow after. Money and time logic sits in policies (policies.Amount, Month.Contains, AddDays) and is reused, not reimplemented. Weak: bookings.Reservation has every field tagged json:"-" and is copied field by field into a near-identical reservationRecord. Accessors in training copy structs (Course, Enrollment) while billing hands out live *Invoice pointers, so the code has no consistent mutability policy. There is small dead code and needless indirection: CancelReserved takes a now it never uses, finance.New has an unused mem parameter, training.Operations only forwards to operations(), and checkInRefusal is a free function taking m while createRefusal is a method. protocol/wiring.go has eleven near-identical owner-lookup closures. A generic helper like the existing has\[T] would remove them. Only some packages split their operations into ops.go (bookings, training, materials, purchasing…) while others keep everything in one file, so where to look for a handler varies by package.

**Tests (4 of 5).** Good: The tests check behaviour. bookings_test covers boundary slots (exact opening, closing, 240 minutes, Saturday hours), the refusal order ("Opening hours come before standing"), and that refusals consume no identifier numbers. The tests build the real module graph rather than mocks, and they decode responses through JSON so they read what the program actually answers (decodeInto in bookings_test, decode in finance_test). finance_test sets up a multi-month money scenario (household, charges, payments, refunds) and checks exact cents per kind, which would catch arithmetic or rounding regressions. Weak: Module tests call op.Run directly, so checks 1–6 (argument parsing, permissions, existence, ownership) are only tested by four short tests in protocol_test.go. The PermOwn path is tested for only one operation. Fixtures are copied in every package: tm/guard/decodeInto, run/ok helpers, and the hand-wired module graph appear in about 20 test files. A constructor change in one module means editing many test files, and bookings_test re-implements the forwarders from wiring.go. TestOperationsContract repeats each Operations() declaration as a table, so it fails on any edit to the declaration rather than catching a wrong behaviour. The README admits some paths are untested, for example a waiting-list guardian refusal and an escalation that should leave a checked-in reservation untouched.

**Taking it over: yes, with doubts.** The op-table and protocol design is sound and the same in every package, so adding an operation usually stays inside one package, and the tests are dense with real numeric assertions. My doubts are cross-cutting changes. Charge kinds, statuses and ref names are strings scattered across packages, and the protocol's ref and owner maps fail only at runtime. Shared test scaffolding is copied about 20 times, so refactoring a constructor or a shared concept would cost a lot of edits. First: Make charge kinds a typed enum owned by billing (with its revenue account and report order), and use it in bookings, materials, consumables, training, finance and reporting. Export status constants from their owners (safety, billing), or add predicate methods, and stop comparing "resolved"/"paid" literals in other modules. Add a protocol test that walks every Op and asserts each Ref is in s.refs and each Owned is in s.owners. Add protocol-level tests for PermOwn on more operations. Collapse the owner closures in wiring.go into a generic helper, remove unused constructor parameters, and move the repeated test helpers into a shared internal test package.


### D

**Architecture (4 of 5).** Good: A single shared contract in policies (Operation, Arg, Call, Refusal, Records) lets every area module declare its operations as data. protocol/server.go runs checks 1-6 once, in a clearly commented order, and modules only implement check 7. Every dependency is a small consumer-side interface (bookings.go declares Members, Training, Equipment, Billing, PPE, Lockouts, Premises and so on), so a module never imports more than it needs. Compile-time assertions in bookings/fixture_test.go prove that the real modules satisfy them. protocol/wire.go is a readable composition root. Back-edges that the architecture forbids as imports (equipment/staffing to bookings, bookings to access) are supplied after construction with SetReservations and SetPremises, and each one is commented. Record existence and ownership are registered per module through policies.Records.Define, so the protocol can judge ownership without knowing any module. Each module splits its domain types and queries (bookings.go, billing.go) from its wire operations (operations.go). Weak: Record kinds are untyped strings. Some modules export constants (bookings.Kind, quotes.KindQuote, access.BadgeKind), but references to other kinds are literals like Ref: "member", "machine" and "family" in about 27 files. A typo there becomes a not_found at runtime, not a compile error. Setter injection (eq.SetReservations, staff.SetReservations, bk.SetPremises, train.SetGates, instr.SetClasses) leaves modules half-built until wire.go finishes. Bookings silently skips the premises gate when premises is nil. Values are pulled out of Call by name with unchecked type assertions (c.Str("memberId")). Renaming an argument in Args without renaming it in Run compiles fine and panics at runtime. Responses are built from map\[string]any (Record methods everywhere), so the wire shape has no type the compiler can check.

**Naming (4 of 5).** Good: Domain names are precise and used consistently: Reservation, Invoice, Charge, Escalation, Badge, DoorEvent, Posting, TrialBalance, Row and Side. Interface names say the role the dependency plays (Premises, Incidents, WorkOrders, Passes), and capability methods read as intent (CheckGoodStanding, CheckGate, CancelReserved, HasBadgeNotInside, DrawMinutes). Refusal codes are typed constants grouped per module (CodeMachineBooked, CodeCheckInTooEarly), each with a one-line meaning. Stored vs reported status is spelled out: Reservation.Stored vs Status(at), with StatusMissed documented as reported-only. Weak: Call accessors are inconsistent: Str/Int/Flag/Time/Day vs YearMonth and Clock, and the comment on Flag says "ArgFlag returns". The ID field is named inconsistently: Reservation.ID, Badge.ID and Entry.ID vs Escalation.EscalationID and Job.JobID. Counters have different names in each module: count, counter, numbers, invoiceNumbers, badgeNumbers. ledger has two near-identical names, EntriesIn (returns entries) and EntriesOfMonth (returns a count). "Kind" means three things: the record kind for Records (bookings.Kind), the charge kind (billing.Kind) and the notice kind.

**Cleanliness (4 of 5).** Good: Functions are short and direct. createReservation and checkIn express their ordered refusals as a slice of gate closures that run in sequence, which makes the refusal order visible and easy to change. Money and posting rules have one home each (policies.LineAmount, ledger.Post with a zero-amount no-op and panics on programming errors). Doc comments state invariants and edge cases precisely. No dead branches or TODOs in the files read. Invariants are enforced where they belong: NewServer rejects duplicate ops, a missing handler, or own permission without Owned. Copies are returned from queries (copyOf, copy), so callers cannot alias internal state. Weak: Permission maps (memberOwn, everyone, staffAdmin) are redefined in each module's Operations instead of living in policies. Modules repeat defensive not_found re-checks for records that check 5 has already guaranteed: bookings.lookup, billing.checkMember, jobs.lookupJob, the quote lookup in escalations/jobs. ledger.PostAll is used only by tests. ledger.New takes recs only to discard it (_ = recs). Balanced is documented as "It always does" yet finance exposes it. Billing looks up payments by parsing the index out of the pay-N string (paymentByID), but invoices through a map; two mechanisms for the same job. maxPaymentCents is defined separately in billing and jobs.

**Tests (4 of 5).** Good: Module tests assert exact behaviour:
  - Whole result records compared with reflect.DeepEqual.
  - Worked money examples (37 × 40 × 75 + 50 div 100 = 1110).
  - Refusal precedence, e.g. invalid_state before check_in_too_early, consent before certification, waiver → PPE → lockout → premises.
  - Boundary minutes (10:59 vs 11:00 for missed). The bookings fixture's refused() helper snapshots reservations, the id counter and the charges, and fails if a refusal changed any of them. ok() checks that mutations set an audit target and reads do not. Fixtures wire the real dependent modules, with small recording or stub doubles only where needed (chargeLog, premises map). Protocol tests go through Server.Handle with exact response-shape checks (member sets, integer-only numbers, non-empty reasons). Ledger balance is re-checked in billing, deposits, refunds, jobs, events, purchasing and stocktake tests. Weak: protocol/spec_test.go reads ../../TASK.md and calls t.Skipf when it can't. In this layout that file doesn't exist, so the spec-conformance test silently does nothing. The ts/wantOK/fixture helpers are copied into about 45 test packages instead of a shared testutil. Tests reach into internals (f.bk.ordered, f.bk.count.Peek(), h.s.audit), which ties them to the storage layout. Module tests go through policies.Invoke, which bypasses checks 1-6, so per-op permission and ownership correctness depends on protocol tests alone.

**Taking it over: yes.** Modules have clear jobs and use small consumer interfaces. The checks every operation shares live once in the protocol, and the tests pin exact behaviour, refusal order and no-change-on-refusal. Most changes to one area stay in one package. The weak spots are stringly-typed glue (record kinds, argument names), boilerplate copied across modules, and a spec test that can silently skip — all fixable without restructuring. First: Make protocol/spec_test.go fail, not skip, when the spec file is missing, and point it at the real requirements path. Introduce typed record-kind constants in their owning modules and use them in every Arg.Ref instead of "member"/"machine"/"family" literals. Move the common permission maps (memberOwn, staffAdmin, everyone, adminOnly) into policies. Add a shared internal test helper package (ts, wantOK, wantRefused, fixture plumbing). Remove the redundant not_found re-lookups and dead ledger.PostAll / the unused recs parameter, and unify the ID field naming (ID vs EscalationID/JobID).


### E

**Architecture (4 of 5).** Good: Every area is its own package with the same shape: a domain file (`Service`, record types, `Kinds`/`Find`) and an `ops.go` that declares its operations as data (`policies.Op` with Args, Perms, Own and Handle). Adding an operation stays inside one package. `protocol/server.go` runs the shared checks once, from the declared descriptors: argument values, actor exists, time regression, role, referenced records exist (through `Finder`) and ownership. Handlers only do their own rules. `NewServer.register` refuses bad wiring at startup (duplicate op, unknown Ref kind, an own permission with no Own argument). Dependencies run one way. Where that would make a cycle, the module declares a small port that `protocol/wire.go` connects (for example `bookings.PremisesPort`, `training.AttendancePort`/`AssessmentPort`, and the `staffingReservations` adapter). `policies` is a real shared kernel: refusal codes, roles, access, Ref kinds, `Counter`, `LineAmount` and `Call` with typed accessors. Weak: The machine-gate sequence (standing, guardian consent, certification, waiver, lockout, inspection) is written out by hand in `bookings.createReservation`, again in `bookings.checkIn`, and again in `compliance.blockers`, which says it follows the createReservation order. Changing a gate or its order means editing three places in two packages. Constructors take concrete services in long lists: `bookings.New` has 12 `*Service` parameters and `compliance.New` has 8. Each module is tied to the whole graph and can't be built in isolation. Opening hours live in `bookings` and are exported only as formatted "HH:MM" strings. `reporting/utilization.go` then parses them back with `clockMinutes`, ignoring errors, so a policy value round-trips through text across a module boundary. `wire.go` keeps two hand-written lists of the same ~46 services, one for finders and one for Ops, in slightly different orders. Leaving a module out of one list fails silently or only at startup. `training.Service` holds an `equipment` dependency it never calls.

**Naming (4 of 5).** Good: Names match the domain: `CertificationRefusal`, `MachineWaiverRefusal`, `ReservationsStillToCome`, `CancelReservationForEscalation`, `OldestUnusedRedemption`, `makerNeedsCertification`, `maintenanceUnion`. Conventions hold across packages: `CodeX` for refusal codes, `StatusX` for statuses, `RefX` for record kinds, `KindX` for charge kinds, and exported view types next to unexported stored state (`Invoice` / `invoice`). The `XxxRefusal` gate methods return a code or "" everywhere, so the gate pattern is easy to recognise. Weak: Some names are too generic or used inconsistently. `training` has a package-level `view(c, at)`, while `bookings` and `billing` use a `view` method. The ID counter field is called `ids`, `counter`, `jobIDs` or `invoiceIDs` depending on the package. Value typing is uneven: `members.Tier` is a type but standing is a plain string, and reservation and invoice statuses are untyped string constants. In `ledger_test.go`, two time helpers, `at` and `at2`, do the same job under unhelpful names. `policies.RefRow = "consumptionRow"`: the constant name says less than its value.

**Cleanliness (3 of 5).** Good: Handlers read top to bottom: refusals in spec order, then effects, then the result (`bookings/ops.go`, `escalations/ops.go`, `training/enroll.go`). Nothing changes state before the last refusal. Stored records are copied defensively on the way out (`clonePtr`, `cloneEnrollment`, `Escalation.clone`, `invoice.view`), and lists are built with `make(..., 0)` so they encode as `\[]`. Comments are short, accurate and tied to the rule they implement. I saw no commented-out code, TODO stubs or placeholder handlers. Weak: Permission-map helpers (`memberOwnStaffAdmin`, `adminOnly`, `allRoles`, `staffAndAdmin`) are re-declared in about 20 packages instead of once in `policies`. The gate checks and their refusal messages are copied almost line for line between `createReservation` and `checkIn`. Small duplications: `bookings.ReservationsStillToCome` sorts inline although `sortByStart` exists in the same package, and `ledger_test.go` has two time helpers. The README says lines up to 64 KiB are accepted, but `cmd/makerspace/main.go` uses unbounded `ReadBytes` and enforces no limit. The README's q4 example also shows two different reason texts for the same refusal. In `main.serve`, an I/O error with an empty line still sends an empty line to `Process` before returning the error. It is minor, but odd.

**Tests (4 of 5).** Good: Tests check behaviour, not just that code runs. `bookings/reserve_test.go` is a table of every createReservation refusal with its expected code, including the boundary cases (ends exactly at closing time, touching reservations) and ordering cases taken from the spec (lockout before inspection, invalid_slot before opening hours). `protocol/e2e_test.go` drives real request lines and checks that every response has exactly the members its status allows, plus exact JSON, ledger worked examples and audit targets. `protocol_test.go` covers invalid requests, time regression, refusals not moving the time, forbidden by role and by ownership, not_found and wiring errors. Ledger tests assert exact entry IDs, amounts, sides and the balance, including that zero amounts consume no number. Weak: Every package's fixture rebuilds part of the service graph by hand (`bookings/fixture_test.go` and `escalations/escalations_test.go` each repeat about 18 constructor calls, plus copies of `staffAdapter` and `mustTime` in 11 files). A constructor change ripples through many test files, and the copies can drift from `wire.go`. Package tests call handlers directly and skip the protocol checks, so the Perms/Own/Ref declarations in each `ops.go` are only exercised where e2e tests happen to reach them. The ledger worked-example tests post entries by hand rather than through billing, so they would not catch billing posting the wrong accounts. Only the e2e path covers that.

**Taking it over: yes, with doubts.** The core design is sound and the same in every module: declarative operation descriptors, one protocol layer for the shared checks, one-way dependencies with ports, and behaviour-level tests. A new operation or rule usually stays in one package. My doubts are about the rules that cut across modules: the machine gates are copied into three places, about 20 packages re-declare the permission helpers, the wide concrete-service constructors make the graph rigid, and hand-built test fixtures repeat the wiring in many packages. First: Pull the machine eligibility gates into one ordered function (or a small gate list) that bookings create and check-in and compliance all use. Move the permission-map helpers into `policies`, for example `policies.MemberOwnStaffAdmin()`, and delete the per-package copies. Make one shared test builder (or use `protocol.NewMakerspace` with a request helper) so package fixtures stop copying the wiring. Export opening hours as minutes or a typed value instead of "HH:MM" strings that reporting re-parses, and remove unused dependencies such as `training.equipment`. Bring the README in line with the code (the 64 KiB limit and the q4 reason text), or actually enforce the line limit.


### F

**Architecture (4 of 5).** Good: There is one Go package per area module, and each exposes the same small surface: New(deps...), Ops() \[]policies.Op and Refs() map\[string]policies.Ref. Each module owns its state and declares its operations as data (args, perms, audit target, Run), as in bookings/bookings.go and billing/billing.go. The shared request pipeline is in one place. protocol/server.go process() runs the checks in order (arguments, actor, time regression, permission, referenced records, ownership, then the operation) and appends the audit entry. Modules never handle JSON or auditing. Modules are wired with named steps that declare their dependencies (protocol/world.go register/NewWorld, one wire_*.go per module). Reverse needs are injected as function hooks in small 'needs' files (wire_bookings_needs.go, wire_equipment_needs.go). This keeps the import graph acyclic, and protocol/architecture_test.go checks it against the table in architecture_table_test.go. policies/ is a true leaf package holding the shared value types, codes, Ref kinds and the Op/Call contract (policies/op.go, refs.go, codes.go). Weak: Modules depend on each other's concrete *Module types, not on narrow interfaces. bookings.New takes 12 concrete modules (bookings/bookings.go:101), and compliance and escalations do the same. That couples every module to the full API of its dependencies and makes unit tests outside protocol impractical. The order of the reservation gate checks is written twice: in bookings.createRefusal (bookings/bookings.go:312) and in compliance.Blockers (compliance/compliance.go:39). Changing the rule order or adding a gate means editing both, and only tests keep them in step. Ownership is inferred from argument names. server.go has hard-coded name sets (selfArgs, recordArgs) and special cases for guardianId and projectId (protocol/server.go:200-232). An op with a newly named argument silently gets different authorization unless someone remembers OwnArgs. Modules are looked up by string keys and type assertions (Mod\[*bookings.Module](w, "bookings") in world.go and every wire_*.go), so a wrong name only fails at runtime as a panic.

**Naming (4 of 5).** Good: Domain names are precise and used the same way everywhere: Reservation.StatusAt vs the stored Status, ActiveAt, InGoodStanding, HoldsCertificationOn, ConsentMissingOn / ConsentGateRefusal, AddCharge / AddCredit (bookings.go, training.go, guardians.go, billing.go). Each module uses the same vocabulary: XRecord functions build wire records, Refs/Ops/New are the entry points, and refusal helpers are named createRefusal / checkInRefusal / refusal. Constants for codes and ref kinds are spelled out in full (policies.CodeMachineLockedOut, policies.RefReservation). Weak: Field naming is inconsistent between modules. bookings and compliance use full names (members, equipment, training), but escalations uses eq, sf, lk, bk, wo, nt, and it names its map field `policies`, the same as the imported package (escalations/escalations.go:30-36). Local variables shadow builtins: `min` in escalations.refusal and setEscalationPolicy, and `close` in bookings.OpeningMinutes and reporting. The Args accessors are single letters (S, I, T, D, M, B in policies/op.go:50-55), which makes call sites terse but hard to read. Tier is a named type but Standing, statuses and severities are plain strings (members/members.go:11-23, escalations severityRank), so 'one thing, one type' is only partly applied. Test helpers carry a per-file prefix and are copied: about 40 xxxLastAudit helpers and several xxxMin helpers, and bookingsMin simply calls billingMin (protocol/bookings_test.go:12).

**Cleanliness (4 of 5).** Good: Functions are short and direct, and there is no speculative abstraction. Refusals are computed before any mutation, with comments saying so (bookings.createRefusal, billing generateInvoices, escalations.refusal). Doc comments are dense and say how a function behaves (copies vs pointers, ordering, the meaning of nil hooks). See training.SetAttendanceOwed and bookings.SetPremises. Shared behaviour is not repeated in modules: JSON parsing, argument validation, the time-regression check, auditing and nil-slice normalization all live once in protocol/server.go. Weak: compliance.Blockers takes an `at` parameter it never uses (compliance/compliance.go:39). escalateIncident keeps a defensive `continue` with a 'cannot happen' comment (escalations/escalations.go:122-124). billing.generate creates `inv` with ID "" and then assigns it on the next line (billing/billing.go:334-337). This is minor noise. reporting re-implements interval overlap (overlapMinutes) even though policies.Overlap exists, and MaintenanceMinutes merges intervals by hand inline. normalize uses reflection over the whole result to turn nil slices into \[] (protocol/server.go:338-384). Modules already use \[]T{} almost everywhere, so this pass is a safety net that hides the remaining inconsistency. TierFeeCents falls back to the pro fee for any unknown tier (members/members.go:26-35).

**Tests (5 of 5).** Good: The tests are black-box behaviour tests through the wire protocol, using a small harness (protocol/harness_test.go ok/refuse/do). They assert exact result records with reflect.DeepEqual, audit targets and audit counts. Refusal order is tested as chains. Every cause is made true at once and removed one at a time, so a swapped check would fail (TestBookingsCreateReservationRefusalOrderChain, TestBookingsCheckInRefusalOrderChain). Boundaries are tested explicitly: opening and closing minutes, 30/240-minute limits, missed at the end minute, check-in at exactly the start, certificate expiry day (protocol/bookings_test.go). A seeded random-request fuzzer checks atomicity. It dumps all module state by reflection and asserts that a refusal or a read changes nothing, that each accepted mutation adds exactly one audit entry, and that the ledger stays balanced and matches invoices and credits (protocol/atomicity_test.go). There are structural tests too: the import-graph test (architecture_test.go), and a coverage test that compares the observed op|role|status|code tuples with the model's Definitions (zz_coverage_test.go, observe_test.go). Weak: All tests live in package protocol and go end to end, so a failure deep in billing or training only shows up through long fixtures. No module has unit tests of its own except policies. The coverage and model-agreement tests depend on file-name ordering ('zz_'), a global observed map, a count threshold of 800 and a model folder outside the realization. They skip silently when that folder is missing. Each test file copies its own helpers (xxxLastAudit, xxxMin, fixtures) instead of sharing them in harness_test.go. Some tests poke internal hooks directly (bookingsMod(h).SetPremises(...)) instead of setting up the state that would produce the behaviour.

**Taking it over: yes.** The structure is consistent and predictable: one package per area, operations declared as data, one shared check pipeline, and wiring checked by tests. The code is well commented and the behaviour tests are strong enough (order chains, boundaries, an atomicity fuzzer) that I could change a rule and trust the suite to catch regressions. The weak spots are local: concrete-type coupling between modules, gate order written twice, and ownership inferred from argument names. First: Make ownership explicit on every Op (always set OwnArgs or an Owner rule) and remove the name-based selfArgs/recordArgs/guardianId/projectId heuristics in protocol/server.go. Put the reservation gate order in one place, an ordered list of gates that both bookings.createRefusal and compliance.Blockers use. Have modules depend on small consumer-side interfaces instead of concrete *Module types, starting with bookings.New's 12 dependencies, so modules can be unit-tested. Move the copied xxxLastAudit/xxxMin test helpers into harness_test.go, and make the coverage test independent of file-name ordering and the 800-observation threshold. Make the small cleanups: give escalations' fields full names and stop shadowing the min/close builtins, and drop the unused `at` from compliance.Blockers.

## How it was made

**Kept.** Each launch is in the [lasting store](../../tools/evaluation/kept.py) in `%LOCALAPPDATA%/markitect-kept/`, with its final repository, transcripts, records and cost, and the store's check passes. The weekly figures are the runner's reading from the launches' records; the Haiku lead's launch has none recorded here.

**Measured.** [`measure.py`](../../tools/evaluation/measure.py) ran on each kept repository with Go 1.27.1, `staticcheck` v0.8.2 and `deadcode` from x/tools v0.52.0.

**Read.** Six sessions of [`blind_read.py`](../../tools/evaluation/blind_read.py), one attempt each, all with valid answers and only `claude-opus-5-5` answering. They took 77 to 179 seconds each and left the runner's weekly reading at 22, against an expected 3 to 6 points. No credential shape is in the evidence, and nothing labelled with the evaluation remained.

**Failed starts.** Before the first session, the wrapper started twice and failed: the tool read a missing default for the suite's series, and then the frozen source lacked `tools/library-oracle`, which the suite's reader imports. No session ran in either. Both are fixed: the default in the tool, the second by freezing the whole `tools/` folder.

**The review's fixes after the reads.** The independent review of these tools found defects that did not change these figures. The figures were measured again after the fixes, and the reads, which did not depend on them, were not repeated.
