# Cockpit project list and guided setup — 21 October 2026

**Scope:** the owner adopted the cockpit as desktop app ([DEC-066](../concepts/register.md#dec-066-the-cockpit-is-markitects-desktop-app-and-starts-and-stops-apply), [design](../design/cockpit.md#the-cockpit-as-desktop-app)). This change implements its next step: `markitect cockpit` without project flags opens a per-user project list, a project is opened and switched without flags, and a form sets a project up through the function behind `markitect setup`. It is described in the [cockpit adapter](https://github.com/Glacius-Labs/Markitect/blob/447ac3b152de79b52de80513e14dc94349a060bd/internal/adapters/cockpit/README.md#projects-and-guided-setup). It changes neither Apply, the run engine, the run configuration, the Runtime profile nor setup's behaviour and formats, and it adds no owner request to the form.

## What was built

- **Project list.** `<user configuration directory>/markitect/cockpit/projects.json` (format version 1) names each project's repository, model selection and runtime directory, and the project used last. It is replaced atomically, created with its directories, refused and never overwritten when it has another version, malformed content, repeated names or relative paths.
- **Host.** One listener serves the page and the `/api/projects` routes and delegates every other API route to the current project's single-project `Server`; without a project those routes answer 409. Bootstrap builds a project's `Server` as the flags would (repository, model, dependencies, run configuration and Runtime profile of its runtime directory, run controller, sessions, proposals). A project without a runtime is observed and proposes, and starts no run and no session.
- **Switching** is refused while a run the cockpit started is active, a model session prepares, works or closes, an accepted proposal is written, or the project is being set up. The new project is built before the old one is closed, so one that cannot be built leaves the open one as it is. Writes are admitted and counted under the host's lock; a switch drains them (new writes answer 409), reads the busy state again and only then swaps and closes. A setup of the open project makes it busy, so no run or session starts under it. A stopping cockpit waits for a switch and a setup under way.
- **Command line.** Without `--state`, `--run-config`, `--runtime-profile`, `--repo`, `--model` and `--dependency` the cockpit opens in project mode (the last project, else the list). With any of them it opens that project directly as before, saves nothing, and the page offers *Keep in the project list*.
- **Guided setup.** The form calls bootstrap's setup function with the project's repository, model and dependencies and the form's inputs, after a review that says which files are written where. Setup's status, error text, bound identities and files are shown as they are. On success the runtime is stored and the project reopens with runs enabled.
- **Page.** `#/projects` with a card per project, a card to add one, the keep offer and the setup form; the top bar names the open project and links to it; with no project open every place leads to the list; the Runs area and the session page point a project without a runtime to *Set up runs for this project*.

## Checks

- Store tests: a missing file is an empty list; an update creates the directories, writes mode 0600 and leaves no temporary file; nine kinds of unusable file are refused by load and update and stay byte-identical; a refused update changes nothing; the validation of a project's entry (name, absolute repository and runtime, model and dependency files, `run.json` and `runtime.yaml`).
- Host tests with fake projects (real `Server`s over recorded state directories): the page and the new module are served; 409 without a project; writes need their purpose header and an own origin; adding validates and rejects duplicates; opening delegates to the project, closes the old one and remembers the last; switching and removing are refused for a working, preparing or closing session, a publishing proposal and an active cockpit-started run (the last through a real run controller), and allowed for a waiting or halted session and a proposal still to decide; a project that cannot be built leaves the open one; removal touches no file; keeping a flag-opened project, also under another name; setup receives the right inputs with setup's defaults for engine and effort, empty check rows are dropped, refusals reach the page unchanged and store nothing, a busy open project refuses a setup, the form's own validation; the last project opens at start and its failure is reported; an unusable list is shown and not overwritten; a host without a list still serves; `Serve` closes the current project when it ends; a `Server` may now have a repository and no state directory.
- Bootstrap tests on a repository with a fake container engine: the list sits under the injected user configuration directory; a project without a runtime is observed, offers settings and sessions as unavailable and reports why runs are; **the form writes the same bytes as `markitect setup`** (the second call with the same inputs reports both files `unchanged` and the runtime tree is identical), the project then reopens with run control and model sessions available, and the list holds the runtime but no credential content; a missing check profile is refused in setup's own words and leaves no directory; a state directory held by an Apply refuses setup in setup's own words; the call carries no owner request; the entry of a flag-opened project, with the runtime only when the run configuration and Runtime profile are the pair setup writes.
- Admission tests: a write admitted before a switch is waited for and a new write is refused with "switching projects" while reads go on; an admitted write that started work refuses the switch and the project takes writes again; `Serve` waits for a switch under way and closes the project that is current when it settled, and nothing switches after it; during a setup of the open project a run and a session start are refused, switching and removing are refused, reads go on, and everything works after it.
- Command tests: project mode for no flags and with `--listen` and `--no-open`; every project flag, also with its default value, opens a project directly; a project flag without `--state` or `--run-config` is refused; the repository selection equals check's.
- `gofmt`, `go vet`, `go test` of the cockpit, CLI, bootstrap and architecture packages, `markitect-check-architecture`, `node --check` of every changed page module, `markitect check` on this repository and the documentation link check.

## Page demonstration

A cockpit built from this branch ran with a temporary user configuration directory (`APPDATA` of the process) in headless Chrome driven over the debugging protocol, at 1280 and 390 px. Observed:

- Started without flags and with an empty list, the page led from `#/` to `#/projects`, showed the empty-list note and no project in the top bar; the other API routes answered 409.
- Adding the repository of this branch (name from its directory) and a scratch repository through the form produced two cards ("Not set up: no runs and no model sessions"); the same name again was refused with the cockpit's message in the form's status.
- *Open* on a card led to the hub with the project's name in the top bar; the Runs card said the project is not set up and offered *Set up runs for this project*, which opened the setup form with the runtime directory suggested under the user configuration directory.
- The review step read "Writes runtime.yaml and run.json in DIR". With the default engine on Windows the cockpit refused the form because `/usr/bin/docker` is not a native absolute path (the same check `markitect setup` makes); with an absolute but absent engine path and a missing credential file, setup's own refusal "the credential file cannot be observed" was shown in the form and nothing was written.
- Reloading opened the last project directly; the top bar link led back to the list, where *Open* switched to the second project; *Remove…* asked for confirmation and *Keep it* returned the focus to *Remove…*.
- At 390 px the hub, the list and the model area fit without horizontal scrolling; the project name is shortened in the top bar and hidden inside an area.
- A second cockpit started with `--state DIR --repo REPO` opened that project directly, offered *Keep in the project list* in the list page and, after it, showed the project as saved and open.

## Not established

- A real setup through the form with a container engine, a real workspace image and a credential: the setup function was real in the page demonstration but stopped at the credential check, and the bootstrap tests use a fake engine. That the files written for a real image are right is as `markitect setup` already shows, not observed through the cockpit.
- A real run or model session in a project that was set up through the form, and a switch between two projects that both have runs.
- The setup form's default container engine is setup's Linux default; on Windows the owner has to enter a native path, as for `markitect setup`.
- Two cockpits writing the same project list at once: each change reads the file again and replaces it atomically, but there is no lock between processes.
- Owner use of the project list, and macOS and Linux paths of the user configuration directory (only Windows was observed).
