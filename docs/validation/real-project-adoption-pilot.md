# Real-code adoption pilot

Recorded 2026-10-03. This pilot tests one assigned engineering change against an isolated subset of the public MIT-licensed [MyMeetings modular monolith](https://github.com/kgrzybek/modular-monolith-with-ddd), upstream commit `91c8ef24b4cb6ef558c95d8267fa07d68c7059f8`. It is a substantial architecture reference application, not an active customer adoption or production acceptance. The task was chosen for this experiment, not drawn from a demonstrated product backlog.

The pilot uses the public v0.12.0 Windows executable, SHA-256 `b03424560caa460322e3580785d6abc9dfbf2137df878e03ddedcf76b3a8fa47`. [PR 54](https://github.com/Glacius-Labs/Markitect/pull/54) was reviewed and integrated before this work. Its merge is `d12e42516bf17e97e6d8a0dd32c51b39adfb4416`; the separate immutable v0.12.0 release binds `83b715c415e39af79715cd8a40b3c79237a4c850`. See the [release assessment](../production-assessment.md) for commit-bound Windows/Linux gates and publication evidence. Release verification establishes no product benefit.

## Method and boundaries

The [source selection](../../experiments/real-project-adoption/source-selection.md), [provenance](../../experiments/real-project-adoption/provenance.md) and [manifest](../../experiments/real-project-adoption/evidence/source-manifest.json) identify 646 original files, 711,461 bytes, copied byte-for-byte from the Windows upstream working tree. Git normalizes line endings when freezing the subset; a [raw-blob audit](../../experiments/real-project-adoption/evidence/fixed-source-audit.json) verifies that both arms match each other at all 646 original paths. Forty-seven upstream Git blobs differ only by newline representation; there are no content differences after CRLF normalization. The subset retains five Modules, BuildingBlocks, Application/Domain/IntegrationEvents projects, actual Commands/Queries/Handlers/Aggregates, ADRs, selected architecture tests and SQL read-model definitions. API, module Infrastructure, database configuration, runtime services and most tests are excluded. No credentials, private repository material or customer records are included. The original README and ADRs remain human-owned and unchanged.

The task in both arms is [GetMeetingAttendeeCount](../../experiments/real-project-adoption/task-request.md): accept MeetingId and count the attendee records returned by the existing Query, without attendee details, guest expansion or a new endpoint. Separate cold agents receive the same request and frozen source-tree bytes, content-equivalent to upstream after CRLF normalization. The assisted arm additionally receives the frozen compiled context. They may inspect necessary implementation files; those reads are logged. The agents do not see the other arm's code or report. This is one uncontrolled comparison, with shared host/tool caches, differing preparation overhead and no randomized repetitions. Timing cannot establish productivity. Actual model calls and tokens were not separately instrumented; byte counts are not token estimates.

Canonical structured intent, human narrative, technology-specific evidence and unmodelled semantics are separated in the [model classification](../../experiments/real-project-adoption/model/modeling-classification.md). The Domain and exact-pinned package are adopter policy, not Markitect defaults. Both package versions are complete explicit definitions. No Core primitive or source-code semantics were added during the pilot.

## Baseline

The original-source baseline is `ec01cb6805f93c8a4dbe37efe2a129a58a7ed28d`. Its [read ledger](../../experiments/real-project-adoption/evidence/baseline/reads.jsonl), [search ledger](../../experiments/real-project-adoption/evidence/baseline/searches.jsonl), [activity](../../experiments/real-project-adoption/evidence/baseline/activity.jsonl), [patch](../../experiments/real-project-adoption/evidence/baseline/implementation.patch) and [report](../../experiments/real-project-adoption/evidence/baseline/report.md) record the actual run.

There were 17 successful content-read records totalling 17,372 UTF-8 bytes: 14 original-source reads, one pilot scope note and two reads of the new implementation. Four searches and filename inventory are recorded separately. Three guessed paths were corrected; one Countries handler read added little after the scalar-count convention was found. The agent found ADR 0009, the module Query contract and existing Dapper count pattern. It produced a typed `QueryBase<int>` and internal `IQueryHandler`, using `COUNT(*)` over the same attendee view and MeetingId predicate. Build passed with zero warnings/errors against an explicitly selected public NuGet source. No database execution, runtime behavior or acceptance was verified. The observed 7m19s wall clock is not a comparative performance measure.

## Implementation evidence

The [project-owned check](../../experiments/real-project-adoption/checks/README.md) evaluates MSBuild ProjectReference items, including imported build targets, for 18 mapped projects. The [positive observation](../../experiments/real-project-adoption/evidence/implementation-positive.json) has 35 edges and zero findings. The [negative control](../../experiments/real-project-adoption/evidence/implementation-negative-control.json) adds Payments.Application to UserAccess.Application through a temporary MSBuild import; exactly that prohibited edge is caught. Control success means detection succeeded, not that the mutated architecture passed.

This check owns its explicit technology-specific map and boundary rule. It checks the manifest’s declared origin and mapped-path inventory, without verifying every manifest byte/hash entry. Its report hashes explicitly listed inputs, not the complete SDK/import chain; the recorded environment used SDK 8.0.418. Markitect binds the declared check command to a fixed project snapshot; it does not infer C# behavior or automatically reconcile every observed edge with each normalized Interface identity. Runtime DI, reflection, network coupling, message semantics and the contents of contract assemblies are unproved. Read-only inspection of the full upstream found Registrations.Infrastructure references to UserAccess.Application/Infrastructure, outside the extraction. Consequently the positive result cannot establish whole-upstream conformance. This is a concrete known coverage boundary, not a waived violation.

## Authoring and falsification

Preflight caught malformed Domain YAML, an undeclared relation name, a Core/Module modeling mistake and an area/namespace mismatch. These were corrected before freezing the assisted input. They are observable adoption friction, not a new Core-language defect. Preparation effort was not timed reliably. Versioned full Domain definitions, resource records, package pins, source ownership mappings and the project-owned check introduce maintenance alongside existing ADRs and architecture tests. No existing authoritative document or test was removed.

The [independent falsification note](../../experiments/real-project-adoption/falsification-notes.md) asks whether an adopter-owned AGENTS.md pointing to the existing ADR and architecture tests could provide the needed Query guidance more simply. That alternative is plausible and was not measured as a third arm. Successful compilation in the baseline is evidence against a claim that Markitect was necessary for this change. The experiment must report missing context, global impact and extra maintenance without repairing them into a favorable result.

Instrumentation had limitations. The baseline logger mixed BOM-decoded content hashes with raw-file hashes; the audit reconciles every record to the actual source bytes, while preserving the original ledger. The setup operator temporarily renamed the compiled-context file and restored its exact bytes, causing a failed repeat read and a duplicate read. ## Architecture-contract evolution and impact

The independent evolution branch starts at the same frozen v1 adopter, without the new Query. Exact-pinned package v1 leaves Validators optional; v2 requires one for the explicitly labeled AddMeetingAttendee and CancelMeeting Commands. [Package pins](../../experiments/real-project-adoption/evidence/setup/package-pins.json) and the executed [setup replay](../../experiments/real-project-adoption/evidence/setup/replay-check.json) retain the content identities:

| 2.0.0 | `0ed97c9f0b21e10b5e2a0ff232bdb910bd468ac04f84441ae24d5b7cefb2b504` |

The explicit pin update is `a0f89e7c0ce43a1be556c17c41cd19f8e7f32d7f`. Repeated check/model outputs are deterministic. Exactly the two intended `selected-commands-require-validator` results fail; their Command-intent guards pass. This proves the modeled cohort rule, not that every state-changing Command has been selected correctly.

The failed-policy candidate exposes an important limitation: both Context and Impact exit 1 with a failed validation report instead of their usual output. PolicyResults identify the two violations, but there is no Impact affected set at this state. False negatives and precision are consequently unmeasurable there. A migration reviewer can inspect the failures/model, but the planned context/impact workflow is obstructed. The pilot records this application workflow gap without changing Core or suppressing the failure.

One Validator was implemented first; the remaining Command received one explicit, narrow digest-bound temporary exception. Context then succeeded and retained the waived result, rationale and expiry. The second Validator was implemented and the exception removed. Actual FluentValidation source files and canonical Validator links were added deliberately; there was no automatic application-code migration. Passing revision `c507172b24da9005904422c03cc3d66a2b5efcec` passed repeated fixed checks/models and selected contexts. The Application project compiled with zero warnings/errors using public NuGet. This does not establish runtime validator registration or that the chosen field checks are sufficient business validation.

The [evolution report](../../experiments/real-project-adoption/evidence/evolution/README.md), [implementation patch](../../experiments/real-project-adoption/evidence/evolution/implementation.patch) and offline [snapshot bundle](../../experiments/real-project-adoption/evidence/adopter-snapshots.bundle) preserve exact intermediate and final states. Final fixed `verify` also passes the declared MSBuild check.

At the passing candidate, package/configuration and inventory changes broaden impact to 73 GraphKeys in the complete graph. All 12 UseCases are named; only two require the selected Validator change, leaving ten outside that implementation cohort. Unrelated Modules therefore remain in the review set. These ten are overinclusive for the defined implementation task; the global fallback is conservative, not evidence of precise affected-set discovery. No intended cohort subject is absent from the later set, but the failed-state absence of an Impact result prevents a stronger claim about the point where help was needed.

A separate comment-only change to one declared Handler source file has exactly two affected resources: that Handler and its UseCase. It does not include unrelated Modules. This shows bounded known-input propagation, not business-semantic impact reasoning. The ordinary new Query/model inventory change instead reports 72 affected keys and all 13 UseCases. The pilot therefore demonstrates both a useful local dependency case and noisy normal adoption/evolution cases; it must not advertise universally bounded engineering impact.

## Reconciliation and Copy Me

The [reconciliation record](../../experiments/real-project-adoption/evidence/reconciliation/report.md) brackets operations with source-tree hashes. Observe returns expected drift (exit 1); Plan is read-only and two outputs are byte-identical. Apply without `--write` is rejected. Changing the Skill input invalidates the saved plan; the original bytes are restored exactly before replanning. Explicit Apply and Verify succeed for 72 outputs, followed by `operations: []`. This establishes convergence for the configured safe local projections, not for arbitrary external adapters.

The [Copy Me candidate](../../experiments/real-project-adoption/discovery/candidate.md) proposes one narrow typed/immutable Query and internal module QueryHandler convention. Its [ledger](../../experiments/real-project-adoption/discovery/evidence.yaml) binds ten deliberately selected sources, supporting examples, counterevidence, uncertainty, the committed run manifest and tool/snapshot/selection/context identities. The direct-table UserAccess Query counters a universal database-view rule; the candidate deliberately avoids that claim. The task's row-count instruction is not discovery evidence. The existing helper validates those evidence bindings and then rejects the placeholder human-decision record, as expected. It neither authenticates reviewers nor automatically adopts a candidate.

Human adoption is pending the explicitly requested decision on candidate `sha256:1d6014e3cf02bb85448f36022b550ae5d72e5f7ac58c9a2b70edbfa0b893e474` and evidence `sha256:cd8dcb5a4ef7df3408c89198c16e3518352c2f8f9ee08f0c7f05033f9b7895d7`. No candidate rule has been silently made canonical. The old ADR dates, scope beyond the sampled Modules, desired visibility/naming and adoption rationale require human judgment. Ten files were inspected for discovery; elapsed authoring effort was not instrumented. This is a reviewable bootstrap dossier, not yet a completed adoption or proof that discovery is cheaper.

## Separate conclusions

| Category | What this pilot supports |
|---|---|
| A. Technical proof | Typed ownership/Feature equality, selected versioned Validator policy, reproducible pins/results, narrow exception lifecycle, fixed check execution and local projection convergence |
| B. Apparent agent benefit | Ownership/slice guidance was understood; fewer manual existing-source reads and no competing architecture in this single run |
| C. Human judgment | Task/business semantics, label completeness, ADR currentness, runtime scope, quality of validation, and Copy Me adoption |
| D. Outside the model | SQL/runtime correctness, authorization, complete code inventory, runtime coupling and excluded Infrastructure |
| E. Authoring discomfort | YAML/static-reference/namespace preflight errors, explicit resource bookkeeping, complete versioned Domain copies and discovery ledger setup |
| F. Noise and omissions | Missing governing ADR; project-file/Domain context overhead; global inventory/package impact; blocked failed-policy Context/Impact |
| G. Eliminated consistency work | Machine generation updated the selected projections; finite policy checks replaced manual verification of those modeled invariants. No existing duplicated authoritative source was removed |
| H. Added maintenance | 65 initial resource files, two Domain definitions (390 lines / 13,216 bytes), package pins, check/map, source declarations and evidence/decision records beside existing docs/tests |
| I. Unproven claims | Productivity, token savings, fewer defects, safer autonomy, lower total upkeep, customer demand and broad business benefit |

The project-reference map repeats ownership coordinates also present in model inputs; the check does not derive all its mappings from the normalized graph. That is an explicit adapter maintenance surface, not demonstrated removal of duplicated truth. A short AGENTS.md plus the existing ADR and architecture tests is a plausible simpler solution for this Query task. The pilot did not measure that third arm, so it cannot assert equivalence or superiority.

## Decisions and the twelve utility questions

1. **Actual duplicated truth removed?** No existing authoritative document/test was removed. Projection synchronization is automated, while the model/check map add maintained information.
2. **Less architectural rediscovery?** The assisted agent reports it and read fewer source files manually. The missing read ADR and the obvious existing Query example limit the inference.
3. **Materially focused context?** The graph closure excludes other Modules, but the compiled artifact is larger than the baseline's logged reads and omits a governing rule. Overall focus improvement is not established.
4. **Real affected set without misses?** Failed-pin Impact is unavailable. Later conservative impact includes both intended Commands; the known local Handler probe includes both dependents. Complete semantic recall is unproved.
5. **False-positive impact?** Ten of twelve evolution UseCases lie outside the two-Command implementation cohort. New Query inventory affects all thirteen UseCases; local Handler input affects exactly two resources.
6. **Reconciliation converged?** Yes for the safe configured projections: verified output state followed by an empty plan.
7. **Constitution cheaper to maintain?** Unproved. It introduces model/package/map upkeep; no controlled long-term maintenance measurement exists.
8. **Human judgment still required?** Business semantics, evidence coverage, complete selections, desired conventions, runtime behavior and explicit adoption.
9. **Repeated language gaps?** Explicit cohort selection and source ownership bookkeeping are uncomfortable. Existing relational/fan-out gaps remain deferred; no repeated new generic semantic failure was established.
10. **Another Core primitive justified?** No. The strongest negative findings concern source selection, impact precision and failed-policy workflow access.
11. **Could a simpler solution work?** Plausibly AGENTS.md plus existing tests for the Query; not measured. It would not by itself provide these exact package/exception/plan contracts.
12. **What next?** Investigate read-only explanation/context/impact for policy-failing candidates without permitting structural-invalid waivers. Then test repeated owner-led work against the simpler baseline, improve source-selection/authoring feedback and measure maintenance before expanding product claims.

The [pressure observations](../../experiments/real-project-adoption/language-pressure.md) classify findings without Core expansion. Public positioning remains justified for deterministic versioned engineering contracts, explicit context and governed projections, with the documented workflow limits. This pilot does not establish that the machinery materially improves real engineering overall. Product messaging should describe feasibility and these specific observations, not promote general productivity or AI-safety benefits.
