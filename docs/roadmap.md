# Roadmap

Where Main is, what comes next and what may come later. The [concept](concept.md) is the target; the [decisions](decisions.md) are what holds.

## Where Main is

The latest release, 0.32.0, carries the whole concept on Claude Code: the spec with `check`, `tidy`, `vet`, `list` and `doc`; the record with `status` and `mark`; the eight skills and four agents whose rights a hook holds; the strategies with the shipped parallel workflow and `harness.yaml`; and releases with the Claude Code plugin and `markitect update`. The first spec of an existing project is verified against the project before the owner gets it ([DEC-105](decisions.md#dec-105-a-first-spec-of-an-existing-project-states-what-is-as-what-should-be)), and what the architect has to ask the owner waits in `.markitect/questions.md` ([DEC-100](decisions.md#dec-100-skills-are-named-after-the-activity-agents-after-the-role)). A project set up with an earlier release runs `markitect update` once ([keep it current](guides/project-workflow.md#8-keep-it-current)): it replaces the hooks, names the standard Library `std` at 2.1.0 in the manifest and the lock, and moves the architect and the auditor to `opus` at effort `medium` unless the project's `harness.yaml` sets them. A folder `.agents/skills/markitect-architect/` is deleted by hand, and a routine scheduled earlier is set up again with `/markitect-schedule`. In the spec language of this release a folder is a namespace, and a Package is a folder that holds its anchor, a Definition of kind `Package` ([DEC-108](decisions.md#dec-108-a-folder-is-a-namespace-a-package-is-declared-by-its-anchor)); a thing with parts is a folder that holds the Definition of its own name, and a link to the folder means that Definition ([DEC-109](decisions.md#dec-109-a-thing-with-parts-is-read-as-a-whole)). A project of an earlier release gives each Package folder its anchor, `members/members.md` for `members`, and lists it in the registry. Until it does, its folders are namespaces of Root: `check` refuses each link to one and each registry page of one, and `markitect list` shows which Packages are left. Since 0.31.0 a Kind declares the fields and parts of its Definitions, which the compiler checks, and the standard Library `std` 2.0.0 holds the Kinds of a whole project's description in place of the five of 1.1.0 ([DEC-110](decisions.md#dec-110-a-kind-declares-fields-and-parts-and-std-describes-a-whole-project)); a thing with its parts is built and verified as one item ([DEC-111](decisions.md#dec-111-a-thing-with-parts-is-built-and-verified-as-one)). A spec written in the Kinds of 1.1.0 is rewritten in those of 2.0.0, where `std/Feature` is `std/Operation`, or its project commits the five earlier Kinds as a Library of its own and names that in its `kind` lines. `rest` and `cli` are gone from the binary, and a project that used one commits its Kind the same way or writes its endpoints and commands as Routes. The record of an earlier release lists each thing with parts once more, and every Definition of a standard Kind is to verify again once. Since 0.32.0 a list of more than 40 items is built in slices, what others rely on first ([DEC-112](decisions.md#dec-112-a-long-list-is-built-in-slices)), `markitect doc --read` prints the spec as one text to read, and `markitect list --kinds` what it has of each Kind. `std` is 2.1.0 with the declaration `last`. All of it but the verification of a first spec, the review of what a builder left and the session's walk through the slices, which are the skills' text, is covered by tests, and small real runs have passed ([concept, §13](concept.md#13-what-is-shown-and-what-is-not)).

## Later

Agreed directions that are not scheduled.

- **A routine that audits the spec.** Cleanup, bug hunt and a full review run as routines, and the audit of the spec runs only when the owner or Claude starts it. A scheduled audit reads the spec regularly and tells the owner what is contradictory, missing, unclear or duplicated.
- **More skills and checks.** `security` and `improve` skills, and a CI check with `markitect status` that ships with Markitect.
- **Observed code dependencies widen what `status` lists.** The spec's links do not contain the code's own calls, imports and shared types. Optional, language-specific tools could observe them and widen the list, never narrow it ([OQ-001](decisions.md#open-questions)). Until then, `/markitect-review --all` is the safety net.
- **More spec-quality signals.** `vet`'s zone measures once real records exist; files that realize unusually many Definitions; and the size of a spec change against the code change it causes. Like `vet`, findings and recommendations, never gates.
- **Tests bound to Definitions.** Review whether a test really verifies its Definition, and report Definitions whose only evidence is an unreviewed test. The reviewer's case counts on `mark` are a first step.
- **Models and perspectives per role.** Mixing models, such as one building and another reviewing, as an experimental factor ([OQ-004](decisions.md#open-questions)), and teams per perspective, such as security or architecture, whose roles differ in question, context, tools and model.
- **Another provider,** once Claude's version is reliable ([DEC-094](decisions.md#dec-094-the-users-own-session-runs-the-agents-natively)).

## Ideas

Recorded, not planned: detailed planning waits until a usable, stable version exists ([DEC-084](decisions.md#dec-084-continuous-work-runs-outside-the-tool-and-autonomy-grows-in-steps)).

- **A cockpit with a personal AI,** and a project organization in which people architect, set rules and develop ideas while agents keep the project realized and tidy; a conversational agent that searches the project, proposes spec changes and shows what matters.
- **Government:** agents maintain the spec within explicit mandates, with people briefed and asked only about what matters; departments such as security or architecture raise objections on spec changes. It must keep the spec's quality high.
- **The project seen from every side:** a project is something different for each of its stakeholders, and no single role holds every view, so a description of a whole project may be the sum of its views rather than one objective definition. As a tomograph turns around a body, agents would go around the project one perspective at a time, such as architecture, security, operation, schedule and benefit, and the views together give the picture. It may answer what a spec must contain to describe a project, and give people their overview. In one trial, a pass per view with a merge described little more than a single pass at several times its cost, and most Definitions drew on more than one view, so views look like questions to ask of a project, not passes over it or folders of its spec ([trial](https://github.com/Glacius-Labs/Markitect/pull/1040)). Candidate Kinds for the shipped Libraries, for deployment, operating procedures and roles, were tried by hand on one spec and did not make it better: sorting a Definition into a Kind's parts changed what three of them said, and a role became a hub that every Definition naming it links. What helped is that a Kind's parts show what a Definition leaves unstated ([trial](https://github.com/Glacius-Labs/Markitect/pull/1051)).
- **Views of the spec:** reports, visualizations or dashboards that show a spec's structure and what a change did to it, so that a person keeps the overview without reading every Definition.
- **The spec as institutional memory:** agents keep neither memory nor responsibility over time, and the spec and its record supply both.
- **Priorities and strictness:** Rules with a strictness and work with a degree of freedom; a project's ranking of its non-functional properties; local priorities at every level of the spec, with the inherited ones visible.
- **Precedents and instances:** reasoned decisions kept as precedents that later cases cite; disagreements with a severity and higher instances to settle them; an agent that brings a case it cannot settle to a higher instance while it works.
- **Briefings and visibility:** regular short briefings of what happened and what waits; the same evidence-bound events feeding briefings, history, observability and a view of the project's responsibilities, activity, decisions and health; gamification that makes verified progress visible without false incentives.
- **Operation:** monitoring, logs and data collection for more autonomous operation, with Kubernetes or etcd once a concrete need is stated; logs of a running system checked against the spec, as a kind of `doctor`; an optional offline classifier of claims and evidence, never a replacement for `check` or the reviewer.
