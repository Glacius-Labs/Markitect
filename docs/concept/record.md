# The record

`.markitect/review.sum` is the record of what was verified, committed with the project like `go.sum` ([the record](../../internal/run/README.md#the-record-file)). It holds one line per item, a Definition with its parts ([DEC-111](../decisions.md#dec-111-a-thing-with-parts-is-built-and-verified-as-one)), sorted, each a JSON object: the verdict, the hash of each input ([§3](tools.md#how-status-works)), the evidence the reviewer gave, why, and with an `ok` or a `skip` the reviewer's counts of cases. After the lines come the directories they name: for a Package that something binds, each binding Definition with its hash, so that `status` can say later which of them changed ([DEC-113](../decisions.md#dec-113-what-binds-is-an-input-of-what-it-binds)).

| Verdict | Means |
|---|---|
| `ok` | The Definition is implemented, and the reviewer found that the Rules of its Package and those above it held for it, as the evidence shows. For a Rule about changes a reviewer has caught a planted violation once, where the changed Definition stated the case, and an earlier run recorded such a violation `ok` ([§13](what-is-shown.md)) |
| `fail` | It is not; the line says why |
| `skip` | Verified as far as the project can show, with the reason. A note, which never changes `status`'s exit code |
| `spec-problem` | The spec contradicts itself or leaves open behaviour at the project's boundary, and only the owner can settle it |

**A verdict is bound to what the reviewer read.** `status` prints each item as `DEFINITION@FINGERPRINT`, the fingerprint being the start of the hash of every input but the evidence, and `mark` refuses when the inputs changed since: a builder editing a file beside the reviewer, or the reviewer's own test run changing one. The evidence, `path` or `path:line`, must be files of the folder, and their hashes become inputs, so a weakened test that served as evidence puts its Definition back on the list. Go does the same: it does not cache a result whose inputs changed while the test ran.

**The history** beside it, `.markitect/history.jsonl`, keeps how the work went ([DEC-114](../decisions.md#dec-114-process-data-lives-in-the-history)). The record says what is verified now; the history is appended, one JSON event per line with its time and type, and never rewritten. `mark` appends a `verdict` event for each verdict right after it writes the record, under the same lock: the Definition, the verdict, the hash of its own text, the reviewer's counts, and the other Definitions whose own text was pending then, or their number beyond 30. The skills and workflows add `run-start`, `run-slice` and `run-end` events through `markitect run`, and the hook a `refusal` event for each call it refuses. A verdict belongs to the run whose start and end enclose its time, and a run without an end is open. `vet` derives from these facts what it knows of change, without Git history. **Revisions** count how often a Definition's own text changed between verdicts, as the basis for `vet.hotspot`: a first verdict counts none, and a change of a link, a file or the evidence counts none. **Co-changes** count, per pair, how often two Definitions' own texts changed in one round, as the basis for `vet.change_coupling`: a revision counts one with each other Definition pending beside it, each change once with each partner, and a round of more than 30 changed Definitions, such as a reorganisation, counts none: no verdict while more than 30 are pending, nor the first verdict after, and what is left of the round counts with nothing until its own verdict.

**The inbox**, `.markitect/inbox.jsonl`, holds what waits ([DEC-118](../decisions.md#dec-118-one-inbox-for-everything-that-waits)): a question for the owner, an audit's finding, later a signal from outside. One line opens an item, with its source, kind, place, text, question and whether only the owner may settle it or an agent may; a later line closes it, settled, answered or dropped. `markitect inbox` lists the open items, the tool checks each item's shape, a subagent closes only an item for an agent, and `status` counts the open items, those for the owner apart.

**How it is written.** `mark` writes under a short lock in the user's cache folder, the record as one whole file and the history with one more line, so parallel reviewers, for example one per Package, do not lose lines. A verdict rewrites only its own Definition's line. A gone Definition stays on the list with the files that realized it until a reviewer finds them removed or with a new basis and records `ok`, which removes its line.

**How it merges.** `init` writes `.markitect/.gitattributes` with `merge=union` for the record and the history, so Git keeps both sides; the history is read in time order. Of two lines for one Definition, `status` takes the one whose inputs match the folder; if both match with different verdicts, it lists the Definition as a conflict to verify. The directories of both sides are kept. The next `mark` writes the file clean and drops the directories no line names.

**What it is:** a record, not a proof. A line written by hand shows in the diff, and the hook keeps agents from writing one. It holds hashes, not text: what a changed Definition said before comes from Git. A CI job runs `markitect status`, and any item fails the build.
