# Drivers

A driver is whatever starts the agents, decides how often and how long, and makes the Git steps ([DEC-096](../decisions.md#dec-096-the-tool-computes-and-checks-a-driver-acts)). **A driver is harness files and nothing else**; there is no code interface to implement. **It may change** the prompts, agents, skills, settings, limits and every Git step. **It may not change** the tool, the record's inputs or what the hook refuses. A person can drive the work too, with the same commands.

**Claude decides the parallelism per run** ([DEC-103](../decisions.md#dec-103-claude-chooses-the-parallelism-per-run-through-a-shipped-workflow)). Each skill that starts agents runs by a **strategy**, set per skill in the harness configuration ([§9](harness.md)):

- **`auto`,** the default: Claude estimates the work and chooses. Parallel when `status` lists more than about 30 items in at least two Packages; cleanup, bughunt and audit count the spec's Definitions instead, and build, cleanup and bughunt need a Git repository for it. Below that size a parallel run's fixed cost buys little: one builder has settled change steps of 21 to 64 items in one context ([trials](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/lean-trials-20261107.md)). Until the parallel strategy has proven itself on a long list, `auto` chooses sequential; so far it has passed two real runs on a project of 6 Definitions ([record](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/parallel-strategy-20261108.md)).
- **`sequential`:** one builder or reviewer at a time, as [§5](what-build-does.md) describes; a build of a long list goes slice by slice. An audit starts its auditors at once under every strategy, since they only read, as [§8](other-skills.md) describes.
- **`parallel`:** the shipped workflow `.claude/workflows/markitect-parallel.js`. It plans strands per Package, in waves along the dependencies `list --deps` names, what is depended on first. Builders run in parallel, at most 8 at once, each in a worktree of its own, where it commits its work; a strand asks `status --package` for its items, changes only its Package's files, and shared files, which Root owns, go to Root's strand, last and alone. Claude Code gives a workflow's agents no tool to start an agent, and lets an agent in a worktree run Git only on its own, so the rest of a strand is steps of the script: after each batch a plain agent merges the strands' branches by name into the run's branch, a reviewer per strand verifies its Package there, and a plain agent commits the verdicts and runs `status` again, since a workflow script has no shell. It stops when `status` lists nothing a builder can settle, or three rounds in a row leave the list no shorter than it has been, and reports what remains. Review runs one reviewer per Package; bughunt has one reviewer per Package hunt before the build rounds; cleanup runs one round over every Package; audit starts the same auditors as the skill does. Before a parallel build, cleanup or bughunt the session enters a worktree of its own, since Claude Code branches each builder's worktree from the session's `HEAD`: a later wave then starts from what the earlier ones merged, and the owner's branch is untouched until the session merges back by §5's rules. The owner architects in another session meanwhile.
- **A custom workflow:** a saved Claude Code workflow, named in `workflows.NAME`, that keeps the same contract. It takes the mode, the branch the work comes back to, the focus and, for a review, whether to verify every Definition, reads `markitect status --json`, keeps to the four roles, with a plain agent at most for status and Git, and stops by the same rule.

Claude Code asks before each workflow run unless the owner answered "don't ask again" for it.
