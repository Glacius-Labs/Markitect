# Canonical verification reuse provenance

`ProposeCanonicalController` may pass a Host-translated `VerificationBinding` to a Module only when an exact passing result can be reproduced from the current controller inputs. A changed request digest by itself is expected after applying generated bytes because current target preimages participate in the request; Host adapts it only after proving all verifier inputs equivalent.

New `VerificationResult` events carry optional, atomic source evidence fields `evidenceRevision` and `evidenceSnapshotDigest`. Controller results also carry atomic `controllerConfigDigest` and `controllerVerifierInputDigest`. These fields are omitted for legacy results, preserving their serialized bytes and content IDs. Historical results remain valid records but cannot be reused without this provenance. Standalone verification may carry the evidence pair without controller fields; it is not a substitute for a controller verifier result.

The evidence snapshot digest binds the exact selected source Snapshot for one scope: its own active target artifacts, descendant active target artifacts, and all declared controller and scope check inputs. The immutable evidence revision identifies where those bytes and modes came from. The controller-config digest binds external scope/check/runtime policy. The controller-verifier-input digest is the stable digest of the exact pure `agentexec.Request` before run ID/nonce allocation; it covers the full prompt context and artifact facts, including direct-child outcomes, result IDs, checks, and bytes.

Reuse remains read-only and follows the declared assurance DAG child-first. It is attempted only when the owner explicitly sets `auditAll`; ordinary impact planning does not widen observation to find cached passes. For each scope, Host reacquires its exact evidence path union, compares the fixed source and declared check inputs, verifies current working bytes and modes against both the active record and immutable evidence snapshot, reloads the current verifier runtime fingerprint, recomputes the fixed check identities and agent-check identity, and builds the same pure verifier request used during verification. A child is reusable only after its own exact result passes freshness validation; parent input is then recomputed using that exact child result. `records.ValidateVerificationFreshness` receives the complete recomputed current identity set. Only a passed, exact current result becomes a Module binding for the current request digest and active artifacts.

Missing provenance, stale source/model/runtime/check/evidence facts, changed target bytes or modes, failed/incomplete/unknown child outcomes, missing scopes, and changed verifier inputs remain conservative. Reuse executes no check or verifier, writes no records, authorizes no materialization, and claims no semantic acceptance. Public standalone proposals remain unchanged.

An Agent Rules proposal may contain rendered bytes even when its decision is `no-op`; that decision only means no materialization is needed. Host still reports evidence refresh for an active record without current independent verification, including when canonical model, revision and target bytes are unchanged. Only the same validated cached-PASS path described above can clear that requirement. No-op and verified are distinct states.
