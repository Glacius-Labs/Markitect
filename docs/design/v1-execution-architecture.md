# V1 execution architecture

Concrete packages and contracts for [V1 concept 1.0](../concepts/v1-concept.md) ([DEC-068](../concepts/register.md#dec-068-v1-concept-10)). The corrected v0.17 architecture was accepted for source implementation on 23 October 2026 in the [owner approval](../concepts/sources/v1-source-implementation-approval-20261023.md); this page now states the target after decisions D10–D18. Where the current source still differs, the [delivery plan](../implementation-plan.md#known-deviations-from-concept-10) lists the deviation and its step. The [counter-review](../development/v1-architecture-audit-20261023.md) and the [conformance audit](../development/concept-conformance-audit-20261024.md) bind earlier observations to source. Evidence moved to the [V1 qualification record](../validation/v1-qualification-20261024.md).

## Scope

Build Model -> Artifacts. Preserve canonical language, identities, imports, compiler diagnostics, registry, ownership, accounting and suitable deterministic foundations. Existing runtime APIs, implementations and package boundaries have no preservation right. Extract, Cockpit/UI, interactive authoring and their migration impose no requirements on the new foundation. Their active consumers are retired in the bounded cut, not ported.

Assessment, Implement and Verify each use the same complete model-derived organization: Root and every local Manager, including empty and intermediate Packages. Root-only is valid only for an actually Root-only model. One executor handles all mandates. Review mandates aggregate judgments; their scratch changes are not candidate product changes. Run organizes Managers; workflow chooses Runs; the command publishes.

## Package direction

These are concrete proposed locations, not preservation obligations for existing code.

| Package | Responsibility and reason | Inward dependencies |
| --- | --- | --- |
| `internal/model`, `internal/snapshot` | Preserved canonical checking and immutable source values | Existing pure dependencies |
| `internal/organization`, `internal/realization` | Complete topology/context and registry/ownership/accounting | Model, snapshot; no executor |
| `internal/project` (new) | Checked capture/preparation shared by check/context/docs, standalone Run and Apply | Foundations and its own source port; no Apply/Run |
| `internal/runtimeconfig` (new) | Closed profile decoding and optional static metadata preparation for CLI/Bootstrap and native/check adapters | Captured Project source values; no Run, provider sessions or credential reads |
| `internal/harness` (new) | Pure versioned rules, project/Manager context and mandate instructions consumed by the native renderer in the Codex adapter for V1 | Project/context values; no Run, provider or I/O |
| `internal/run` (replacement) | Sole public Execute lifecycle, hierarchy, explicit per-Manager assignment state, messages, handoffs, feedback, durable result, cleanup and the single validation of closed results | Project, harness, foundations, ports consumed here |
| `internal/apply` (replacement) | Command preflight, shared allowance/deadline, the direct workflow sequence and final publication; the import gate keeps adapters out of it | Project, Run result values and validation, its own Executor and publication ports |
| `internal/adapters/gitrepo` | Source capture, Run copies/integration, durable Git bundles, guarded publication in separate collaborators | Consumer ports in project/run/apply, snapshot, technical transport |
| `internal/adapters/runstore` (new) | One file-backed adapter for terminal results and separate project Notes | Run values; no orchestration |
| Codex adapter | Native harness rendering/installation/use, normal account login and technical sessions. A Claude adapter follows on the stabilized contract (D18) | Run session contract, harness, container/agentd |
| Container, agentd, check adapter | Process/resource transport and isolated project checks | Technical or Run check contracts; no workflow |
| Bootstrap and CLI | Composition, parsing and result display | Actual application services; no second lifecycle |
| Modeldocs/documents adapter | Existing readable canonical view and guarded write | Rebind preparation to project, model, snapshot; no executor |

CLI -> Apply -> Workflow -> Run -> Project/foundations. Diagnostic commands call Project directly. Adapters are injected by Bootstrap. Run cannot import Apply/Workflow/adapters; foundation cannot import execution. Enforce directions for tests too. New package roots require actual consumers and a distinct responsibility. No shared-contracts mega-package, repository framework, DSL, event bus or duplicate model ontology.

Runtimeconfig is the outer preparation consumer for native/check profile metadata. Project and Run do not import it. Its observations retain only the identities, instructions and diagnostics used by those consumers; old strategy, role, helper-team and Turn settings are removed rather than moved into this package.

## Minimal model connection

Project capture invokes existing `model.Check`, registry parsing/accounting, `organization.BuildTopology` and `SelectContexts` on fixed bytes. Reuse their values/diagnostics directly. Preserve source closure, dependency/missing-input diagnostics, empty Packages, explicit ignore classifications and exact captures. Check must not need credentials, images or container metadata.

`project.Prepared` holds the checked input capture and manifest, canonical result, topology/context, registry/layout and declared checks. It is an immutable in-process value, not another serialized compiler AST. Persistence retains sufficient fixed source/input identities to recapture and verify it. Model content digest alone does not cover the complete organizational Package inventory. Git commit, tree and model identity remain distinct.

Do not inherit Extract flags, artifact-advisory policies, PassSpec, strategy/review-team settings or legacy preparation DTOs. Runtime profile decoding belongs outside the compiler. Apply fixes canonical/control/ignore inputs; valid registry updates remain realization work. Candidate validation reuses foundation logic against fixed intent and candidate registry/tree, not a second model validator.

## Necessary contracts with actual consumers

Land each contract with a caller and concrete implementation, never an interface-only wave.

| Contract owner | Producer -> consumer | Contents |
| --- | --- | --- |
| Project: Prepared/CandidateRef | Capture/Git store -> Run, diagnostics, Apply | Checked input binding; durable project-scoped storage key, Git object format, commit/tree; no live object/volume |
| Run: Request/Result | Workflow or standalone caller -> Execute -> workflow/CLI | ID, mandate, prepared binding, input candidate, the command's bound input with the optional host fact that it was already verified, required Findings and shared allowance; technical completion, judgment, output reference, observations, actual cleanup |
| Run: closed-result validation | Run -> workflow and publication | One check that a stored or returned result is bound, technically completed, fully closed and carries a valid mandate decision with required Findings; callers do not know resource names |
| Workflow: Executor | Run -> direct Apply composition | One fully closed Run per call; workflow chooses subsequent call |
| Run: Sessions/session | Native adapter -> executor | Open with harness/workspace, ordinary messages/tools, cancellation/closure and observations; no domain Turn/Pass |
| Run: workspace/candidate port | Git adapter -> executor | Open one Run, task bases, fixed handoffs, reviewed integration, retain/reopen candidate and close; handles stay inside execution |
| Run: records/Notes port | Runstore -> executor/Manager tools | Save/read closed record; append separate project Notes with origin/context and read them in bounded pages ordered by creation time (the ID starts with it), each within the tool transport limit, with a cursor and without silent truncation. Append refuses oversized Notes with a reason. Notes storage failures are tool errors, not Run failures |
| Run: checks port | Check adapter -> executor | Named check on exact candidate, actual exit/timeout/cleanup observations |
| Apply: publication port | Git adapter -> command | Durable accepted candidate, source/target guards, transfer/readback; no living Run |

The Run integration owner alone defines and changes the consumer-local Sessions/session port. The Harness/Provider owner implements it and supplies capability evidence; a joint reviewed handoff precedes contract freeze. Provider-dependent signature decisions stay provisional until the early native gate below. Use consumer-local interfaces. One concrete adapter can implement several small ports; no combined Git/source/publication interface. No session handle appears in persistent results. Technical completed/failed/incomplete is separate from semantic approve/reject/model blocker. Implement submits a checked candidate, not publication approval. Lost transport is not Reject.

The Manager tool set is fixed: `delegate`, `await`, `review`, `ask`, `reply`, `judge`, `check`, `read_notes` and `append_note`, one tool per purpose, each with one implementation in Run. The host binds known identities: the acting Manager, Run, mandate and own commits are never requested from the model, and Findings carry no sender field. `review` names the reviewed child commit so that no stale approval can apply. A refused call returns its concrete reason and the possible next step; host process states are not explained in harness text or messages.

A judgment belongs to the assignment, not to a message. Run keeps one explicit assignment state per Manager instead of separate flags. A judgment is bound to the current assignment (task and mandatory Findings) and the assessed state: for Implement the Manager's working-copy commit when it judged, for Assessment and Verify the fixed input candidate. Parent rejection or correction with Findings, new mandatory Findings, a late adverse child finding about an accepted handoff and a change of the assessed state invalidate it; a message that only handles questions or answers does not. The end of a native response is not a completion attempt: a response without a judgment leaves the assignment active, also when it only handled questions before any judgment, and Run continues it without demanding a judgment merely because the response ended. Completion validity is checked when the Manager judges and before Run relies on an earlier judgment (Root completion); an invalid completion receives its concrete reason. The explicit state succeeds only if it makes domain events clearer and leaves the agent fewer technical special cases. A judgment from an earlier message is never reused after an invalidating event. An open assignment whose continued responses twice in a row do nothing at all – no Manager tool call of any kind, no native execution observed by the Session and no working-state change – ends the Run as incomplete with a diagnostic naming the Manager. A Manager without an open assignment, for example after its handoff, is never stopped this way. Run does not classify actions as productive; the message budget bounds every other loop.

Questions use a small Run-local inbox: Ask accepts only the asking Manager's direct parent or a direct child and returns a correlation ID without waiting for an answer; Await can deliver an incoming question while an earlier answer is pending; Reply carries the addressed Manager's actual answer. Sibling coordination goes through the common parent and cross-level coordination step by step through the Managers in between. A submitted task does not close that Manager's conversation. The host transports questions and answers and validates their association; it does not answer for a Manager. A question takes no allowance of its own: it costs only as part of the message that delivers it, batched with the receiver's other waiting events. Each Manager has at most 8 open questions, a question being open until its answer reaches the asker; one more is refused with the next step, to wait for answers with `await`. A question needs `reply` while its addressee has an open assignment. One the addressee received and leaves unanswered when its response ends without an open assignment, after its handoff or before it has a task, is closed, and the asker receives the host's reason and next step in place of an answer. A question the handed-off Manager has not received yet still reaches it once, so it can answer or report a late finding; left unanswered, it is closed the same way. In Phase C (M-c3-C8) a child answered its parent's questions with `ask` instead of `reply` and handed off; the host delivered them again until the no-progress rule stopped a Run in which 18 of 19 children had handed off.

The native adapters wait for a pending tool's response and cannot supply synchronous Answer-during-Exchange. Reception therefore happens at supported tool/message boundaries, without assuming nested inference or immediate preemption. Direct delegation remains the Manager's responsibility. The [V1 qualification record](../validation/v1-qualification-20261024.md) retains the native observations of crossed questions, later answers and complete Library Apply on the earlier contract. Each additional provider requires its own evidence.

## Complete Run lifecycle

`run.Executor.Execute` is the single closure owner, including standalone use:

1. Validate checked binding, full topology, mandate and finite allowance. Open one Git Workspace Service for this Run and fresh Manager environments only for its topology. No future-Run reservations. Each Manager retains its copy/conversation within this Run.
2. Install harness and coordinate the full hierarchy. Deliver questions even while other Managers wait; serialize mutations to one parent's copy, not all children. Cancellation releases waiters. Parent reviews/integrates fixed child results in completion order.
3. End active writes before capturing a handoff/Root commit, using ordinary session synchronization and internal Git commits. Bind decisions/checks to that immutable object; a later change requires renewed affected checks/review. No per-write/freeze protocol.
4. Persist required candidate objects and verify independent readability before deleting temporary copies. Retain diagnostic partial candidates where possible; failed retention never yields acceptance.
5. Close every Manager process/container/home, Run Git service and temporary volumes, including partial-start failures. Use bounded cleanup even after work cancellation; no further agent work is granted. Record actual close errors.
6. Save and read back the terminal result including cleanup outcome, then return. Storage failure returns technical error plus available diagnostic identities; never claim a saved result exists. A crash before terminal storage is incomplete, not inferred success or automatic resume.

Cleanup uncertainty, missing decisions and persistence failures block successful return/publication. Standalone caller provides finite limits. Apply supplies one shared concurrency-safe allowance and original deadline to every Run, including corrections. The provider idle timeout bounds the longest stretch of provider work in one response without a served tool call. Time the host spends serving a tool call, such as a parent's `await` on working children, does not count, and every served call, refused ones included, restarts the stretch; the host does not judge whether a call was useful. The Run and Apply deadline bound the total time. Resource counts have explicit technical meaning, not domain Turn semantics; no reset after Reject. Before a correction pair, Apply checks that the remaining allowance can start Implement and Verify, each with every Manager once; otherwise it ends incomplete with the cause "budget does not cover a correction pair". This refuses only a start that is already impossible; a started pair can still run out. A Run whose start the allowance cannot cover ends incomplete with a budget cause, not as an invalid request.

Phase C showed why the timeout became an idle limit: in chain 3, Root's single Implement response hit the earlier whole-response limit six times at 594–599 s of provider time while it kept delegating, awaiting and reviewing. Run configuration format 4 therefore names the limit `providerIdleTimeoutSeconds` and refuses format 3, whose `messageTimeoutSeconds` bounded all provider work of a response, rather than reading it with the new meaning.

A bounded probe on 23 October 2026 observed that host-directory binds through Windows/Docker Desktop do not preserve executable modes ([record](../validation/v1-qualification-20261024.md#bounded-component-probes)). Native candidate workspaces therefore use private Linux volumes.

Use the intended Run-owned Git service with private Linux-volume working copies for native execution. Git operations and each Manager operate on the same copy, with only that Manager's copy mounted into its container. Local Git remains useful for controlled tests; do not synchronize a second writable host mirror. Native/check attachment identifies the actual owned copy without interpreting a host directory as a volume. Export self-contained candidate bundles before closure and verify their commit, tree and file modes through Git objects in an independent empty repository; a Windows checkout is not a filesystem-mode oracle.

## Candidates, state and publication

Propose self-contained Git bundles with a named candidate ref and bound metadata in project-scoped operator state outside the repository. Include candidate objects and required ancestry without an old-volume or incremental-bundle dependency. Verify in an empty Git repository with exact commit/tree readback. A bundle is storage, not approval ([official Git documentation](https://git-scm.com/docs/git-bundle)). No new Git server or recovery framework.

Git objects and Runstore use the same project state root with separate records. Secure candidate data before writing its terminal reference. Terminal records use temporary-file/atomic publication, appropriate flush/readback and tested platform failure handling; do not claim a multi-file transaction. Notes use unique append records with atomic visibility and bounded reads so concurrent processes cannot overwrite them. No database/event-sourcing or automatic retained-evidence garbage collection is required for initial V1.

Apply waits for every preceding Run to return, then reopens persisted acceptance and candidate data. Approval binds exact candidate and project inputs. Publication uses host Git in an isolated temporary repository, never the closed Run service; no Agent container remains. Recheck candidate and target/source guards before transfer. Any relevant drift from the captured clean target ends in conflict for narrow V1; no semantic merge or approval reuse for changed content. No automatic owner commit/push.

Check guards immediately before mutation and read back afterward. Cooperating command locks plus guarded per-path transfer limit races; they cannot make an unrelated editor transactionally exclusive. Preserve intervening user changes and report partial transfer/readback failure honestly, rather than promise global atomicity.

## Checks and Manager responsibility

The same deterministic core serves four checkpoints: command preflight before resources, every fixed child handoff, fixed Root completion, and publication. In Implement a submitted child candidate is always fixed and delivered to the parent together with its check result, also when the check fails; the host does not route an invalid submission back to the child. The parent cannot approve or integrate an invalid candidate; it rejects with Findings, settles the interface or escalates. Invalidity refers to the checks that apply to the fixed child state, such as structural validity, accounting and project checks placed in that copy; integration still outstanding elsewhere is not invalidity, and checks that did not run are never reported as passed. A child can run the same check on its current copy through the `check` tool before submitting. Root has no parent and receives its own completion diagnostic. In Assessment and Verify a child handoff is a judgment about the fixed input candidate; scratch files are not adopted, and a check result about the input informs the judgment without blocking acceptance of the child's review. Unresolved invalidity blocks Implement success/approval. Review may successfully reject an invalid candidate; it must not repair that candidate just to obtain a green gate. Required project tests remain meaningfully scoped and commit-bound; not every child runs the entire suite.

Accounting proves registered ownership, not who changed a file. Review additionally receives Manager/task, task-base/result diff, and exact integrated child commits/integration bases. Check unexplained out-of-area changes, while recognizing legitimate child integration. Never subtract accepted child paths/hunks from the parent diff: later parent edits could disappear. Parent conflict-resolution changes still require review; unresolved child-owned work returns to the child. Keep small Git review context, not a global provenance ledger or ACL system.

## Harness, provider and authentication

One Harness/Provider owner covers the complete chain: versioned Markitect rules -> canonical project -> Manager ownership/context -> mandate/Findings -> native instructions/tools/start -> actual provider loading. Pure text/digest tests are insufficient. Per D14 the V1 harness uses the provider's native base and developer instructions with the complete statically selected mandatory context; modular files, skills or loadable context are added only for a demonstrated size or usability need. A generic AGENTS.md representation for unknown providers stays planned as best effort, not an adapter; its V1 status is recorded with the provider matrix (concept §15.5 and §28.1). Harness text holds role, rules, context, task and answer format, not host process states (D13). Generated instructions/tools live outside product candidate content. Mandatory-context overflow is explicit, never silent truncation.

Inventory repository instruction files and native load precedence. Use supported native overrides/controlled instruction mounts to make canonical generated instructions authoritative without editing tracked files. If a pinned provider cannot prevent contradictory instruction loading, fail that capability gate. Test actual loaded paths, tool availability and priority per provider. Native subagents do not replace modeled Managers.

The implemented Codex path starts the Manager container with agentd awaiting initialization, provisions its private home through one bounded private setup message, then starts the provider. It uses allowlisted paths, rejects symlink traversal, restricts permissions, redacts secrets and keeps credentials outside argv/env/logs/harness/Notes/bundles. Partial setup retains its cleanup responsibility. The tested path installs access-only material from a normal account login; it does not share a mutable host home or copy refresh authority. Expiry, refresh and another provider need their own evidence. No renamed auth-helper container.

Native evidence is an early dependency gate, not a late observation: provider-dependent contract decisions stay provisional until bounded native evidence exists. The [early native hierarchy evidence](../validation/v1-qualification-20261024.md#early-native-evidence) satisfied this gate for Codex on the earlier contract. The changed collaboration contract passes this gate again through the bounded step 2 Codex contract proof before it is fixed. Per D18, V1 acceptance covers Codex; the Claude adapter is built later on the stabilized session and tool contract and needs its own gate.

No Codex API-key route, profile branch or example exists; secret validation and redaction tests for account login remain. Native `turn/start` identifiers remain adapter facts. Each provider's qualification is independent; one does not certify another.

Notes are persistent project-scoped noncanonical hints with provenance; they do not grant authority or schedule work. Mandatory Findings stay in results and explicit next-Run inputs; only Findings that name a Definition of the current checked model become Initial Findings of Implement, and Assessment and Verify keep the others as Notes ([DEC-073](../concepts/register.md#dec-073-change-minimality-on-an-unchanged-model)). Verify sees fixed model/candidate, the complete diff against the command's bound input across correction loops and necessary technical observations, not Implement conversations/self-approval. Notes remain attributed hints. Hidden outside-oracle expectations never enter Implement context.

## Acceptance and decisions

First prove a complete small hierarchy using real local Git, controlled sessions, durable result/Notes, cleanup, reopening and publication; then all-mandate freshness and failure branches. Prepare a separately authorized early native probe before broad dependent work. Final qualification covers complete source gates, preservation/no-change, seeded defects and an outside oracle, plus each claimed provider separately.

No unresolved product choice blocks planning: concept 1.0 settles hierarchy, communication paths, judgment validity, tool set, harness form, Notes, exclusions, normal login and the Codex-only V1 acceptance. The standing owner instruction delegates useful finite real proofs to the coordinator; claimed provider support still follows actual evidence. Routine API, package or storage choices do not create extra permission rounds.
