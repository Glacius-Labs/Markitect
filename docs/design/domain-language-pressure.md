# Domain-language pressure test: modular DDD and vertical slices

**Status:** Design assessment for the shipped v0.11.0 language and a bounded software-architecture experiment. This document does not add a language feature or make archived proposals canonical.

## Decision under test

Can a project express a useful modular DDD / vertical-slice constitution with the existing versioned Domain language, and can one structured policy drive readable documentation, bounded agent context, and deterministic checks? The intended proof is a realistic resource graph and a sequence of architecture changes, not a catalogue of hypothetical features.

The current answer is **yes for selected structural rules; no for implementation semantics or arbitrary relationships between values**. A composed Domain can define Modules, Features, UseCases, Handlers, Interfaces, and extension kinds; type their fields and references; set per-relation effects and cardinalities; and evaluate finite assertions over resources and selections. The v0.11.0 constitution example already proves a narrower vertical-slice contract and a versioned policy change. It does not prove that source code follows the model.

The experiment in [software architecture pressure test](software-architecture-experiment.md) makes that answer falsifiable. It records each policy's desired meaning, present expression, observable result, acceptable boundary, and best owner for anything outside the language.

## What the language can establish

The constitution fixture defines a combined Software Domain in an exact-pinned package. Its v1 contract expresses `Module`, `Core`, `UseCase`, `Handler`, and named extension kinds. `UseCase.intent` is a closed `Command|Query` value; typed relations require exactly one Module and exactly one Handler; `hasExtension` limits optional references to declared kinds; and an `allowed-targets` assertion allows Module dependencies only to `Core`. Package v2 adds a per-UseCase Validator count. Tests exercise the exact package update, changed check result, `impact`, a bound waiver, visible context and generated views, and waiver removal after the resource is brought into compliance.

These are checks over the canonical resource graph. Structural relation errors such as an absent required Handler are graph diagnostics and cannot be waived. A finite constraint produces a `PolicyResult` only for its selected resources or collection. A recorded result means the selected assertion evaluated against fixed inputs; it does not establish implementation truth, architectural wisdom, human approval, or code migration.

The language also keeps several different meanings explicit: a Domain package is selected at an exact pin; a resource kind and its policy belong to one active Domain API version; custom references resolve within that API version; relation context and invalidation behavior are declared separately; and `conformsTo` does not import another Domain's constraints. Interacting rules for one resource shape therefore live in one composed Domain rather than independently stacked traits. This is enough to test the current package-conformance idea without a Core `Pattern`, trait stack, or separate pattern DSL.

## Concrete pressure points

The matrix avoids turning missing semantics into a feature list. A gap is only a gap relative to an explicitly desired invariant; an acceptable boundary means that no claim of enforcement is made.

The experiment distinguishes four outcomes:

1. **Expressible and demonstrated:** the model compiles, the intended positive case passes, the negative mutation fails with a traceable diagnostic or result, and the same policy value is visible to its configured consumers.
2. **Expressible with an explicit modeling choice:** for example, selecting a labeled `Command` subset and asserting `intent == Command`. The label is an opt-in boundary; an unlabelled Command is intentionally outside that constraint and is not auto-discovered.
3. **Outside the current Domain language:** do not claim the policy is enforced. Keep it as human guidance or move the check to explicitly selected project inputs and a project-owned check or adapter. Record the gap and its consequence.
4. **Candidate for a future generic primitive:** only after a recurring, essential policy fails the experiment, and only after a small finite rule cannot be expressed clearly without hiding duplicate facts or weakening diagnostics. A failing example is not by itself authority to expand the kernel.

The experiment's ten exit questions and case-by-case evidence are recorded separately in the [software-architecture experiment](software-architecture-experiment.md). They include whether the generic language is sufficient without Core exceptions; which rules are elegant, awkward, or unmodelable; whether filesystem/.NET semantics leaked into canonical data; whether policy applicability and impact are understandable; whether package evolution is explicit; and whether any evidence justifies Pattern/Composition primitives.

## Smallest candidate if the join pressure repeats

The two tested ownership joins justify discussing a narrowly bounded **resolved-target equality assertion**, not adopting one now. Its smallest useful form would compare the resolved GraphKey reached by two fixed, named relation paths from one selected subject, with a small maximum path depth (for example, two edges). A first version could cover the singleton Feature path only. It must define what missing or multiple targets do, bind both path definitions into the constraint digest (so waivers go stale when the meaning changes), return deterministic subject-level results, and include traversed edges in dependency/impact reasoning. It must not accept arbitrary query expressions, override conflicting constraints, or hide uncertainty.

The Aggregate case adds fan-out and empty-set semantics; it is not covered merely by proving singleton equality. A project-owned check/adapter and model normalization remain alternatives. Inverse ownership, mixed-relation cycle groups, and allowlists over pairs of resource properties are different operations and would not be solved by this equality assertion. These fixture cases justify a focused design decision, not a Core implementation or a Pattern/Composition primitive.

## Product conclusion

The present language is sufficient for a declarative slice skeleton and scoped policy evolution, but not for fully enforcing modular DDD ownership and exclusivity. The demonstrated gaps are target joins, exclusive incoming ownership, and cycles across relation types. The Interface already names its authoritative provider Module; the experiment does not claim a defect in that ownership model. None of the tested gaps proves that a Pattern or Domain-composition primitive is the right remedy: the missing semantics are relational predicates and inverse cardinality, not pattern composition. Keep accepted limits explicit, route source facts through project checks/adapters, and defer Core expansion until recurring concrete policy evidence supports it. Reduced effort, lower drift, safer autonomy, and market demand remain unproven until measured on repeated real tasks.
