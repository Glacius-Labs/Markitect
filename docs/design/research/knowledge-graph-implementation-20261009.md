## Decision and scope

The requested product direction is to make Markitect's YAML-authored project model a more complete, navigable knowledge graph. YAML remains the canonical authoring source for this work. RDF/SPARQL is a separate technical-fit evaluation: interesting benefits are hypotheses to test, not a format decision. A canonical RDF switch is considered only after a fair comparison and an explicit decision.

Here, “full” means that important questions within the project's explicitly declared coverage can be followed forward and backward across intent, ownership, relationships, decisions, expected artifacts, candidate changes, checks, verification, and application. It does not mean automatic discovery of every fact in arbitrary source code. A graph edge is descriptive; it does not by itself schedule work, grant authority, invalidate evidence, prove implementation, or establish human acceptance.

The existing source already has typed definitions and relationships, model provenance and digests, project-level analysis, context selection, conservative impact traversal, and durable operational records. The gap is a coherent, bounded explanation and trace view across these parts. Preserve the distinctions between:

- canonical accepted YAML intent, imported or proposed claims, observed facts, and candidate changes;
- expected realization, present bytes, inspected bytes, check results, verifier outcomes, applied changes, and explicit human acceptance;
- semantic graph relationships, context/routing dependencies, impact/evidence invalidation, and execution DAG edges;
- known facts, partial coverage, and unknowns.

No RDF/SPARQL work is a prerequisite for the YAML KG work, and neither plan adds a Main-readiness gate, changes the P01–P10 queue, authorizes a release, or constitutes a case study.

## Current source reference

At the pinned source, the model path is approximately: YAML parse and normalization → identity/reference resolution → closed shape, type, and cardinality checks → semantic digest → project report and analysis. Core definitions have identity based on API version, kind, namespace, and name; resolved edges carry their property path and source location/digest. The project vocabulary includes Managers, Statements, Artifacts, Checks, and Decisions with typed relationships such as `parent`, `uses`, `requires`, `realizes`, `checks`, `subject`, and `actor`.

`projectmodel.Analyze` checks manager structure, delegation, ownership overlap, private-boundary references, paths, and required coverage. Context selects the manager's scope and direct public contracts. Impact considers both revisions, including removed edges, reverse consumers, ancestors, and artifact/check coverage; `uses` and `requires` have distinct effects, and uncertainty broadens conservatively. The `Decision` core kind is not currently projected as its own project-report entity. Host records already link much of exploration/scope, plans, tasks, candidates, checks, verification, apply, accepted model history, and resolution evidence, but no single query provides the complete explanation paths. Namespaces and names are identity-bearing, so a rename currently appears as removal plus addition rather than an explicit continuity relation.

These structures support useful declared-impact answers; they do not prove source-code or prose completeness, arbitrary semantic truth, or user acceptance. Brownfield claim/evidence/contradiction records capture explicitly supplied conflicts and provenance; they do not infer or decide arbitrary contradictions.

Useful source anchors at the inspected model baseline include `internal/core/types.go`, `internal/core/compile.go`, `internal/modules/projectmodel/projectmodel.go`, `analyze.go`, and `impact.go`, `internal/host/projectwork/project.go`, `internal/host/projectexplore/types.go`, `internal/host/projectrun/types.go`, `internal/host/projectbriefing`, and `internal/host/projectadoption`. The P02 handoff is the current source for shared app/workspace/invocation ownership and adapter limitations.

## Terms used in the RDF plan

An RDF graph represents facts as subject–predicate–object relationships. SPARQL is a standard language for querying those relationships, including paths across several edges. SHACL describes graph shapes and reports whether a dataset conforms to them. These standards can improve interchange, reusable constraints, and flexible queries; they do not guarantee correct facts, provenance, privacy, product usefulness, or acceptance. An RDF dataset can be derived from YAML without making RDF canonical. A graph database is not proposed unless measured scale or concurrent-query needs justify one.

### KG01 first assignment and ownership

KG01 is disjoint from P03–P10 implementation: it reads the pinned source and writes only a reference/acceptance artifact. Its first concrete output is the question-to-facts/path/source/limit matrix plus a current-versus-missing inventory. It does not edit Core, schemas, Host, MCP, CLI, queues, or generated mirrors. It can start in its own feature worktree as soon as Root assigns that worktree and confirms the common base. This produces a reviewable decision input for KG02, rather than another general research pass.

The bounded question set for that first assignment is:

| Question | Expected facts/path and source | Boundary to record |
|---|---|---|
| Who owns a declared file and the definition that claims it? | `Manager.owns` / namespace-derived ownership → Statement or Artifact → normalized path; projectmodel analysis and project report. | Ownership is model-derived and may be incomplete; it does not prove every source file is declared. |
| Which consumers depend on a changed contract, and why? | `requires` / `uses` reverse traversal across base and candidate models → Managers, Artifacts, Checks; projectmodel Impact. | Declared graph coverage only; no inferred source call graph. |
| What changes when the relation itself is removed? | Removed edge in base/candidate Impact → affected consumers and coverage. | Must preserve conservative expansion; no stale candidate result becomes current evidence. |
| Which decision supports this rule? | Decision subject/actor/source and rule relationship in Core model. | Decision exists in Core but is not currently a first-class project-report node; reason text is not proof of truth. |
| Which accepted work led to an applied change? | Explore/Scope → accepted model event/ResolutionEvidence → Plan/ManagerTask → Candidate/file → Check/Review/Verify → ApplyReceipt. | Records are split across Host packages; a missing link stays unknown, and Apply is not human acceptance. |
| Which required artifact or check is missing? | `realizes` / `checks` coverage → declared path/check and current candidate or verification record. | Expected coverage is not observed bytes or a passed check. |
| Was a concept renamed or replaced? | Old/new identity and references under `[apiVersion, kind, namespace, name]`; current model diff and history. | Today this is remove-plus-add; do not infer continuity from similar names. |
| Why is a relationship visible to one scope but hidden from another? | Manager Context and public/private boundary rules → selected scope and allowed cross-scope contract. | Graph navigation must not widen existing Context access. |
| Which supplied claims explicitly conflict? | Brownfield Claim/EvidenceRef/Contradiction/Question and their provenance. | Only recorded conflicts are visible; arbitrary semantic disagreement is not detected or resolved. |
| Is evidence current, stale, historical, partial, or unknown? | Model/snapshot/receipt digests and timestamps across candidate, checks, Verify, Apply, and accepted history. | Historical PASS is not current PASS; unavailable telemetry is unknown, not zero. |
| Why did Context include a contract? | Selected Manager scope → own statements and direct public `uses` contracts. | Context/routing is separate from Impact and does not include an unrestricted graph dump. |
| Does the model declare full coverage for this obligation? | `requires`/`realizes`/`checks`, manager coverage analysis, and actual evidence chain. | A structurally complete declaration does not establish code/prose completeness or user acceptance. |

KG01 closes when all twelve rows have a concrete source-bound answer or an explicit missing/unknown result, and an independent reader can reproduce the stated boundary from the pinned source. Root then hands the matrix to KG02; further discovery becomes a separately scoped item only if one of these questions exposes a specific gap.

KG02 can be split. After KG01 acceptance, a separate owner can implement **only new pure module files** for model/report projection and indexing behind module-local, Core-neutral graph DTOs. A provisional package is `internal/modules/projectknowledge`; the Integration owner must confirm the long-term module location before implementation because P08 owns source moves. This narrow slice can proceed parallel to P03–P10 if the new directory is reserved and imports only Core and permitted generic libraries. ProjectModel report facts reach it through explicit neutral input DTOs; mapping happens outside the pure module under the shared owner's contract, not through sibling-module or Host imports. It must not change `internal/core`, shared schema/generated files, Host/app services, MCP/CLI composition, `go.mod`, or source layout.

Runtime-evidence DTO shape and adapters, new shared Core/schema vocabulary, Host/MCP/service integration, dependency changes, composition roots, and `src/` moves remain Integration-owned. KG02 cannot claim end-to-end operational graph coverage until those neutral DTO contracts are accepted. KG03/04/05/06 should not edit the shared surfaces in parallel; Integration assigns one owner or sequenced handoff for each. A single owner remains responsible for each canonical fact.

## Plan B: RDF/SPARQL technical fit, evaluate then decide

Compare three variants over the same questions, project facts, and Markitect meaning:

- **A:** current YAML/Core compiler and a native typed graph projection;
- **B:** YAML stays canonical; a deterministic RDF dataset is derived and queried with SPARQL;
- **C:** bounded-scope canonical Turtle/RDF, SPARQL, and SHACL.

The evaluation separates graph capability gains from format/engine changes. Variant A is a valid winner. Variant B adds an export/query path and must prove its maintenance value. Variant C requires an explicit decision; no migration is pre-authorized.

| Item | Work and ownership | Depends on | Acceptance |
|---|---|---|---|
| **RF01 — Comparison contract and mapping** | Map KG01 questions and representative models across A/B/C. Define stable IRIs, versioned vocabulary, namespace/kind/schema identity, source/revision/digest, relationship provenance, graph scopes, and separate accepted intent, imports, candidates, observations, and evidence. Document the current compiler pipeline and semantics: ordered literal check commands, absent/empty/null, duplicate references, int64/finite numbers, bounds, namespace/path effects. YAML already uses a standard-library parser; “RDF removes the compiler” remains a hypothesis. | KG01. | Bidirectional meaning mapping accounts for all input facts and calls out any intentionally changed semantics; no silent information loss. |
| **RF02 — Engine and packaging spike** | Evaluate at most two concrete engines, initially Apache Jena and Oxigraph. Verify actual SPARQL/SHACL support, versions, licenses, W3C cases, Windows/Linux delivery, package/startup cost, and bounded resource use. Jena is a Java stack; Oxigraph's SPARQL support does not establish SHACL support. No custom general SPARQL engine. Prefer a finite local/embedded process; disable network, `SERVICE`, and remote document resolution; pin local imports; bound query time, results, and memory. | RF01. | Required capabilities exist in the pinned versions and can be packaged on supported platforms, or the RDF engine path is rejected/reduced to export/import. No install or engine choice is implied by this design document. |
| **RF03 — Variant B projection and SPARQL** | Keep YAML authoritative. Build deterministic RDF projection with stable IRIs and source/graph/version binding. Query owner, contracts, consumers, artifacts, check coverage, decisions, and trace. Host selects manager-scoped datasets; query authors cannot broaden access. Return ordered results and witness explanations. Rebuild projections; do not make a second manually edited database. | RF01 and RF02. | Queries answer the same-source cases correctly, with witness explanations beyond path endpoints, no network, and no scope broadening. |
| **RF04 — Variant C bounded canonical RDF/SHACL** | Only if needed for a fair comparison, author the same bounded model canonically in Turtle. Cover types, counts, closed shapes, reference targets, and schema version with SHACL plus necessary Host checks. Keep semantic graph digest distinct from source-byte/snapshot digest. Use blank-node canonicalization only if needed and bounded. Count new glue, packaging, and schema work; identify exact old compiler rules that could be removed. | RF02; compare against RF03 where available. | Positive/negative parity cases include ordered/repeated command arguments, missing targets, unknown predicates, empty/absent/null, int64/finite numbers, identity/namespace/rename, conservative unknown impact, stale evidence, private scope, and removed edges. |
| **RF05 — Fit decision** | Compare A/B/C on correctness/diagnostics, implementation and ongoing maintenance, authoring and repair effort, query maintenance, deterministic IDs/diffs, setup/startup/size/resources, provenance, and versioning. Give KG improvements to every variant. Test AI familiarity separately on equivalent bounded author/change/query/repair tasks; do not infer productivity from standard familiarity. | RF03 and RF04, or explicit documented reason that a branch is unnecessary. | Record A, B, C, or reject, with evidence and trade-offs. A may win. B must justify its extra path. C requires a new explicit product decision. Developer source evaluation is not a product-role study. |
| **RF06 — Migration and product connection** | Only after an explicit choice of C: digest-bound conversion preview/apply, one authoring source per model version, updates to views/schemas/CLI/MCP/skills/examples/Brownfield/history/loaders/packages/manifests, and versioned upgrade/rollback. Keep historical YAML snapshots readable or explicitly migrate them. Remove obsolete compiler/parser/schema logic instead of carrying an unexplained permanent dual stack. | RF05 and explicit approval to select C. | Normal repository/platform gates and independent review pass. Old evidence remains historical and is never promoted to current PASS by a new graph digest. No release or automatic publication. |

### Later evaluation boundary

An engine comparison is a technical experiment, not a product-utility result. If later work asks whether KG features improve real work, first freeze requirements and source, then compare bounded actors with equal resources and independent evaluation. Separate technical A/B/C fit from product KG usefulness and from any conventional-agent comparison. Count failed starts and setup/maintenance effort; preserve unknown usage and the evaluator boundary. Reuse no closed grant or old study as authorization. Existing sandbox material is a source for planning only; it is not proof that a current trial is ready or authorized.
