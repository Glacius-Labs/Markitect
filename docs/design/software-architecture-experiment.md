# Software architecture language experiment

This is a bounded consumer-side proof for the claims in the [Domain-language pressure test](domain-language-pressure.md). The fixture is current source-tree evidence, not a release or evidence of market benefit. It uses one exact-pinned, composed Software Domain with Orders, Inventory, and Billing modules; Features, UseCases, Handlers, Aggregates, Interfaces, and named extension resources; and immutable package versions with an explicit v1.0.0→v1.1.0→v2.1.0 policy evolution. The historical v1.0.0 archive remains pinned to SHA-256 `22cb698924990fffe85d74489b971f239a2ff25863a1f69d65743b94facb3457`; v1.1.0 opts in a labeled Feature ownership cohort. No Core-specific architecture kind is added.

Keep the evidence baselines separate. The published v0.11.0 Windows binary (SHA-256 `4e563a19a2e572b0bfc940a24ffee38cf08509639e46a68aa60f2dfadd82f6d8`) passed `check`, `model`, `context` and `format` against the isolated consumer at fixed revision `9d4a7dafe3a04e767f2dae6b572b14d68c9c3e27`, after guarded canonical formatting and rendering. Its check reported `provisional: false`. That same binary built package v2 (SHA-256 `57add40cf389c0759a8c1e7b07c885d76184a0d31e3abacc433b27683018cc9d`) and reported exactly the two selected Command Validator failures after the explicit pin update. This establishes that the existing released language handles the modeled contract and its policy evolution; it does not contain the current source's richer context provenance or refined impact causes/scope.

For the pre-equality current-source baseline, local Windows gates passed: `go test ./...`, `go vet ./...`, `go build ./...`, `go mod verify`, generated schema checks, the authoring benchmark gate, and check/format across the then-current fixtures. The equality source candidate independently passed the full local Windows gates and fixed Software/Delivery replay; the [source verification record](resolved-target-equality.md#source-verification) records the executable hash, exact consumer revisions and separate Windows/Linux CI boundary. These results do not roll the earlier gate outcome forward; source checks are not publication or adopting-project acceptance.

## Reproduce and inspect

The runnable instructions and expected outcomes live with the [software-architecture fixture](../../examples/software-architecture/README.md). Run its focused suite with `go test ./examples -run SoftwareArchitecture -count=1`. The consumer-policy lifecycle tests include `TestSoftwareArchitectureV1PackageDrivesConsumerContextAndPolicy`, `TestSoftwareArchitecturePackageSourcesAndArchiveAreReproducible`, `TestSoftwareArchitectureV2PackagePolicyLifecycleUsesFixedSnapshots`, `TestSoftwareArchitectureStructuralAndPolicyFailuresRemainDistinct`, `TestSoftwareArchitectureConflictingDomainPoliciesRemainVisible`, `TestSoftwareArchitectureCommandPolicyIsExplicitLabelScope`, `TestSoftwareArchitecturePolicyExceptionExpiryAndStalenessAreActionable`, and `TestSoftwareArchitectureBoundedHandlerImpactAndReadOnlyReconcile`. The same-target package version tests exercise the selected Feature ownership cohort and explicit pin evolution. Negative language-pressure probes include `TestSoftwareArchitecturePressureUseCaseFeatureOwnerMismatchPasses`, `TestSoftwareArchitecturePressureUseCaseForeignAggregateOwnerPasses`, `TestSoftwareArchitecturePressureTwoUseCasesShareHandlerPasses`, `TestSoftwareArchitecturePressureInterfaceProviderIdentityMismatchPasses`, `TestSoftwareArchitecturePressureMixedRelationCyclePasses`, `TestSoftwareArchitecturePressureUniqueReferenceConstraintRejected`, `TestSoftwareArchitecturePressureArbitrarySpecFieldSelectorRejected`, and `TestSoftwareArchitecturePressureEmptyOptInCohortHasNoSubjectResultsV1AndV2`. A passing pressure probe proves only that the tested language accepted the mutation; it is not an endorsement of the mutated architecture.

Review a policy result against its exact subject, selected Domain/package identity, constraint source, and recorded exception decision. An unlabeled Command is outside the opt-in validation cohort by design. A passing model only proves the declared graph and finite assertion; source behavior and file-role conventions require explicit project-owned checks or adapters over declared inputs.

The v1→v2 scenario changes the selected package pin and policy together, then inspects check results, impact, and any exception lifecycle. A package update is an explicit review event: it does not rewrite application code or silently accept changed policy meaning. Results for this fixture are limited to the exact model, selected package bytes, and tests in the source tree being inspected. Bounded impact describes canonical subjects and declared dependents requiring review; it does not mean unrelated context commands remain available while project-wide diagnostics exist. Context still refuses a project with any unresolved diagnostic.

## Answers to the ten exit questions

| Question | Answer and evidence boundary |
|---|---|
| 1. Can the existing Domain language represent the architecture without Core special cases? | Yes for a typed slice skeleton and finite structural rules in one composed, versioned Domain. Current source adds one generic bounded `same-target` operator for two independent singleton path-equality cases. It remains insufficient for full enforcement of ownership, incoming exclusivity, and mixed-relation cycles. No Core-specific architecture kinds or Pattern/Composition primitives are needed for this evidence. |
| 2. Which recurring engineering statements are elegant? | Closed typed properties, explicit Module/Feature/UseCase/Handler/Aggregate/Interface kinds, typed relation endpoints and forward cardinality, named context/invalidation edges, finite `allowed-targets` and count constraints, exact package pins, and equality of two explicitly named resolved singleton paths. These are source-backed claims, not claims about code behavior. |
| 3. Which are awkward? | The singleton path comparison now has a fixed syntax, but still requires authors to define an explicit label cohort and named paths. Aggregate fan-out equality, incoming/exclusive ownership, selection by arbitrary spec-field predicates, cycles over multiple relation names, and minimal impact for broad collection policies remain awkward or unsupported. |
| 4. Which could not be modeled deterministically? | Current source models selected UseCase↔Feature Module equality and Deployment Service/Environment→Product equality through `same-target`. UseCase↔each Aggregate Module equality is still unsupported because the relation can fan out and the rule lacks explicit empty-set semantics. Inverse Handler ownership and mixed-relation cycle prohibition also lack current semantics. They can be checked deterministically in a separately configured project check/adapter with explicit inputs; the Domain alone does not prove them. |
| 5. Did the requirement tempt filesystem/.NET semantics into the canonical Domain? | No. Exact declared files can be included as opaque, regular UTF-8 byte inputs. Their presence and bytes do not establish file role, code behavior, or .NET project semantics. Those require explicit checks/adapters; no folder/name inference is claimed. |
| 6. Can a user understand why every important PolicyResult applies? | For this proof, review the selector (kind and exact labels), selected Domain/constraint provenance, exact subject, original violation, and any exception rationale/owner/decision/date in context or result output. Structural graph diagnostics remain distinct from waiverable policy results. This records the stated decision; it does not authenticate the human decision. |
| 7. Does a local architecture change have bounded impact? | Published v0.11.0 remains the conservative baseline. Current source records attempted path-source and successfully resolved-target dependencies, including valid prefixes, independent of relation context/invalidation. Impact unions base/candidate dependencies; changed path inputs select policy subjects, after which relevant context consumers and reverse invalidation dependents enter the review set. Collection-wide constraints, local Domain-definition changes, inventory changes and uncertain dependencies remain broad. Adapter observation binds source/model/config/tool and desired/observed evidence, but external state can change without canonical source changes; `impact` is not a generic adapter dependency graph. This describes source behavior, not the published binary; full gate and publication status is maintained in the immutable evidence record. |
| 8. Can package evolution be reviewed without silently changing old meaning? | Yes: select the exact package version/member, inspect resulting check and impact evidence, and review exceptions against the new constraint/subject digests. The v1→v2 fixture exercises that explicit transition; no automatic code migration or acceptance occurs. |
| 9. Do we need a Pattern/Composition primitive yet? | No. The evidence concerns resolved-path equality, fan-out, inverse cardinality, and multi-relation cycle semantics. Those do not show that reusable pattern composition is missing. One composed Domain remains sufficient for this experiment. |
| 10. If yes, what concrete evidence justifies it? | No Pattern/Composition primitive is justified. Two independent cases (selected UseCase/Feature and Deployment Service/Environment Product ownership) justify the accepted finite `same-target` operator. This is a small relational assertion, not a composition primitive or arbitrary query language. Aggregate fan-out and the other pressure points remain explicit limits. |

## Limits

This fixture does not establish that the represented architecture is desirable for every project, that developers follow it, or that Markitect reduces effort, drift, or risk. It is not a market validation. Continue only from repeated real change cases and measure review effort, missed updates, unexplained impact, and policy coverage before treating those benefits as demonstrated.
