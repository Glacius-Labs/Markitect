# Software architecture language experiment

This is a bounded consumer-side proof for the claims in the [Domain-language pressure test](domain-language-pressure.md). It is a source-tree experiment, not a release or evidence of market benefit. The fixture uses one exact-pinned, composed Software Domain with Orders, Inventory, and Billing modules; Features, UseCases, Handlers, Aggregates, Interfaces, and named extension resources; and a v1→v2 package-policy change. No Core-specific architecture kind is added. The checked-in v1 archive is pinned to SHA-256 `22cb698924990fffe85d74489b971f239a2ff25863a1f69d65743b94facb3457`.

Keep the evidence baselines separate. The published v0.11.0 Windows binary (SHA-256 `4e563a19a2e572b0bfc940a24ffee38cf08509639e46a68aa60f2dfadd82f6d8`) passed `check`, `model`, `context` and `format` against the isolated consumer at fixed revision `9d4a7dafe3a04e767f2dae6b572b14d68c9c3e27`, after guarded canonical formatting and rendering. Its check reported `provisional: false`. That same binary built package v2 (SHA-256 `57add40cf389c0759a8c1e7b07c885d76184a0d31e3abacc433b27683018cc9d`) and reported exactly the two selected Command Validator failures after the explicit pin update. This establishes that the existing released language handles the modeled contract and its policy evolution; it does not contain the current source's richer context provenance or refined impact causes/scope.

For the current source, local Windows gates passed: `go test ./...`, `go vet ./...`, `go build ./...`, `go mod verify`, generated schema checks, the authoring benchmark gate, and check/format across the new consumer and the existing minimal, repository-layout, canonical-engineering, constitution, discovery, package-consumer and v2 benchmark fixtures. The new consumer's model and context commands also passed. Core, strict Domain parsing and generated schemas are unchanged from the starting main commit `f65b9ab789ee4b1a1a0fb91c741c95e8d6706d0a`. CI additionally exercises the fixture on Windows/Linux and through the source-package bootstrap; those run-specific results belong to the candidate's CI evidence. These checks are source validation, not publication or adopting-project acceptance.

## Reproduce and inspect

The runnable instructions and expected outcomes live with the [software-architecture fixture](../../examples/software-architecture/README.md). Run its focused suite with `go test ./examples -run SoftwareArchitecture -count=1`. The consumer-policy lifecycle tests are `TestSoftwareArchitectureV1PackageDrivesConsumerContextAndPolicy`, `TestSoftwareArchitecturePackageSourcesAndArchiveAreReproducible`, `TestSoftwareArchitectureV2PackagePolicyLifecycleUsesFixedSnapshots`, `TestSoftwareArchitectureStructuralAndPolicyFailuresRemainDistinct`, `TestSoftwareArchitectureConflictingDomainPoliciesRemainVisible`, `TestSoftwareArchitectureCommandPolicyIsExplicitLabelScope`, `TestSoftwareArchitecturePolicyExceptionExpiryAndStalenessAreActionable`, and `TestSoftwareArchitectureBoundedHandlerImpactAndReadOnlyReconcile`. Negative language-pressure probes are `TestSoftwareArchitecturePressureUseCaseFeatureOwnerMismatchPasses`, `TestSoftwareArchitecturePressureUseCaseForeignAggregateOwnerPasses`, `TestSoftwareArchitecturePressureTwoUseCasesShareHandlerPasses`, `TestSoftwareArchitecturePressureInterfaceProviderIdentityMismatchPasses`, `TestSoftwareArchitecturePressureMixedRelationCyclePasses`, `TestSoftwareArchitecturePressureUniqueReferenceConstraintRejected`, `TestSoftwareArchitecturePressureArbitrarySpecFieldSelectorRejected`, and `TestSoftwareArchitecturePressureEmptyOptInCohortHasNoSubjectResultsV1AndV2`. A passing pressure probe proves only that the current language accepted the mutation; it is not an endorsement of the mutated architecture.

Review a policy result against its exact subject, selected Domain/package identity, constraint source, and recorded exception decision. An unlabeled Command is outside the opt-in validation cohort by design. A passing model only proves the declared graph and finite assertion; source behavior and file-role conventions require explicit project-owned checks or adapters over declared inputs.

The v1→v2 scenario changes the selected package pin and policy together, then inspects check results, impact, and any exception lifecycle. A package update is an explicit review event: it does not rewrite application code or silently accept changed policy meaning. Results for this fixture are limited to the exact model, selected package bytes, and tests in the source tree being inspected. Bounded impact describes canonical subjects and declared dependents requiring review; it does not mean unrelated context commands remain available while project-wide diagnostics exist. Context still refuses a project with any unresolved diagnostic.

## Answers to the ten exit questions

| Question | Answer and evidence boundary |
|---|---|
| 1. Can the existing Domain language represent the architecture without Core special cases? | Yes for a typed slice skeleton and finite structural rules, using one composed, versioned Domain. No for full enforcement of the modeled architecture's relational ownership semantics. The fixture exercises that boundary directly. |
| 2. Which recurring engineering statements are elegant? | Closed typed properties, explicit Module/Feature/UseCase/Handler/Aggregate/Interface kinds, typed relation endpoints and forward cardinality, named context/invalidation edges, finite `allowed-targets` and count constraints, and exact package pins. These are source-backed claims, not claims about code behavior. |
| 3. Which are awkward? | Comparing two resolved ownership paths, expressing incoming/exclusive ownership, selecting resources by a spec-field predicate, checking a cycle over multiple relation names, and getting minimal impact for broad collection policies. |
| 4. Which could not be modeled deterministically? | In this fixture, UseCase↔Feature Module equality and UseCase↔each Aggregate Module equality are not expressible as current finite assertions. Inverse Handler ownership and mixed-relation cycle prohibition also lack current semantics. They can be checked deterministically by a separately configured project check/adapter if it has explicit inputs; the Domain alone does not prove them. |
| 5. Did the requirement tempt filesystem/.NET semantics into the canonical Domain? | No. Exact declared files can be included as opaque, regular UTF-8 byte inputs. Their presence and bytes do not establish file role, code behavior, or .NET project semantics. Those require explicit checks/adapters; no folder/name inference is claimed. |
| 6. Can a user understand why every important PolicyResult applies? | For this proof, review the selector (kind and exact labels), selected Domain/constraint provenance, exact subject, original violation, and any exception rationale/owner/decision/date in context or result output. Structural graph diagnostics remain distinct from waiverable policy results. This records the stated decision; it does not authenticate the human decision. |
| 7. Does a local architecture change have bounded impact? | The published v0.11.0 baseline is conservative. Current source narrows safe resource-scoped cases and explains impact causes; collection-wide constraints, local Domain-definition changes, inventory changes, and uncertain dependencies remain broad. Adapter observation binds source/model/config/tool and desired/observed evidence, but external state may change without canonical source changes; no generic adapter dependency graph is claimed by `impact`. Focused tests cover these boundaries; the final repository gate is still a separate source-candidate condition, not a release claim. |
| 8. Can package evolution be reviewed without silently changing old meaning? | Yes: select the exact package version/member, inspect resulting check and impact evidence, and review exceptions against the new constraint/subject digests. The v1→v2 fixture exercises that explicit transition; no automatic code migration or acceptance occurs. |
| 9. Do we need a Pattern/Composition primitive yet? | No. The tested gaps are joins, inverse cardinality, and multi-relation cycle semantics. They are not evidence that reusable pattern composition is missing. A composed Domain is sufficient for this experiment. |
| 10. If yes, what concrete evidence justifies it? | No Pattern/Composition primitive is justified by this experiment. The two ownership-join cases justify considering a small bounded resolved-target equality assertion only if repeated essential policies demonstrate value over normalization or project checks. That candidate is not implemented or accepted. |

## Limits

This fixture does not establish that the represented architecture is desirable for every project, that developers follow it, or that Markitect reduces effort, drift, or risk. It is not a market validation. Continue only from repeated real change cases and measure review effort, missed updates, unexplained impact, and policy coverage before treating those benefits as demonstrated.
