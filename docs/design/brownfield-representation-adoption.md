# Zero-churn representation adoption (source alpha)

Existing representations do not become canonical intent. Owner-reviewed canonical Definitions and desired representations must exist first. A separate exact artifact selection matches existing bytes to one desired representation; it is not source inference, generation, normalization or permission to overwrite UNKNOWN files.

`adopt-plan` is read-only. Without `--runtime`, it retains the source-alpha diagnostic behavior: it binds a full canonical revision, full target Git revision and snapshot, selected paths/bytes/modes, resolved runtime capability, selected policies, declared command definitions, an explicit supplied active-record set and an owner-supplied review reference. It returns a prospective unverified ProjectionRecord and an adoption plan digest. The reference and approval are supplied claims, not reviewer authentication or proof that source semantics were reviewed.

`adopt` without `--runtime` remains a read-only compatibility path: it requires the exact reviewed plan digest, freshly derives the same plan and runs the existing immutable fixed-check verifier. Only a passing bounded result returns the adopted record together with that check result. It does not persist a record or select ownership.

Durable adoption is opt-in through `--runtime` and explicit `adopt --write`. The closed runtime configuration supplies the existing external record store and exact `checkInputs`; its Executor and Verifier configuration is validated as part of the shared runtime shape but neither runner is invoked. `adopt-plan --runtime` binds the configuration digest and ledger state, including whether the store is absent or its StoreID, head and active record IDs. The selection input must still contain `activeRecords: []`; active records are loaded from the validated ledger. Apply takes the controller's adjacent exclusive lease, re-derives the plan, reruns only selected fixed command checks over immutable selected evidence, and then initializes an absent store if needed, appends an `origin: adopted` record, and compare-and-swaps the exact prior active set plus that record. A plan made for an absent store becomes stale if another process creates or changes the store. No target/canonical artifact, Git index or HEAD is written. If append succeeds but active selection returns an error, the command reports partial failure and rereads the authoritative ledger. A readable result reports `observed-selected` or `observed-not-selected`, with the actual head and active IDs. Failed readback reports `unknown` and omits unobserved head/IDs. The error may follow a committed selection; it does not establish that the retained attempt is inactive. The original error and attempted record remain visible. There is no rollback or automatic retry.

Durable mode loads only the fixed canonical source blobs, selected artifact blobs and runtime `checkInputs`. Its unmatched path list is limited to those loaded evidence paths; the output says this is not a complete target-prefix inventory. Existing files outside the explicit selection are not thereby classified as owned or absent. A record proves only its exact selected artifact set, not whole-prefix completeness.

The operational record stores `origin: adopted`, the fixed adoption evidence revision, review reference and retained artifact facts. Those facts participate in content identity. Existing source-alpha records without adoption metadata retain their digest interpretation. Adopted records may contain only retained artifacts, never created/modified/deleted claims. Canonical revision and evidence revision remain distinct. Changed semantic inputs, source config/checks/capability, target revision/bytes/modes, artifact selection or review reference stale the approval. Later target drift still fails normal verification and contributes reconciliation work.

Durable adoption proves that the selected bytes and declared fixed commands were recorded in an external ledger and explicitly selected as active ownership. It leaves the record `materialized-unverified`; a separate fresh Verify is required before a PASS result exists. Fixed command success is only bounded technical evidence and does not establish semantic adequacy. Neither mode establishes whole-repository completeness, business correctness, independent agent assurance, authenticated owner approval, or acceptance by a human. Existing valid representations can be retained despite differing from a deterministic renderer's preferred form; adoption does not regenerate or normalize them.
