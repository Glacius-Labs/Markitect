# Implemented runtime contract of Apply

This is the technical owner of the Apply strategy implemented for [DEC-056](../../concepts/register.md#dec-056-recursive-reconciliation-with-a-shared-workspace) with the entry order of [DEC-058](../../concepts/register.md#dec-058-apply-always-executes-before-independent-verify). The [concept](manager-apply-concept.md#current-agreed-concept--19-october-2026) owns accepted intent and the [library walkthrough](manager-apply-library-flow.md#current-library-walkthrough) shows that target in sequence. The older [core](../../history/apply-design-before-dec-056/manager-apply-core.md), [execution](../../history/apply-design-before-dec-056/manager-apply-execution.md), [configuration](../../history/apply-design-before-dec-056/manager-apply-configuration.md), [port](../../history/apply-design-before-dec-056/manager-apply-port-contracts.md), [journal](../../history/apply-design-before-dec-056/manager-apply-journal.md), [architecture](../../history/apply-design-before-dec-056/manager-apply-go-architecture.md) and [rebuild](../../history/apply-design-before-dec-056/manager-apply-rebuild-plan.md) documents describe the earlier design. For implemented behavior, this document and the source win over those historical descriptions.

Status: on Main since PR #463 and #472; owner acceptance is pending. Source tests use scripted fakes; real runs are separate evidence in the validation records. The packages own their details: [run](../../../internal/run/README.md), [apply](../../../internal/apply/README.md), [realization](../../../internal/realization/doc.go), the [Claude](../../../internal/adapters/claudecode/README.md) and [Codex](../../../internal/adapters/codexappserver/README.md) adapters.

## Team and Brief

The team is permanent and derived, not planned: Root (`.`) and one Manager per local Package, with parents from the model hierarchy. Every Manager takes part in every Verify round. `run.Config` lists Root first and every parent before its children.

Apply renders each Manager's Brief from the captured model: the applicable obligations with provenance, its owned artifact areas, its registry shard and the required checks. Own Definitions are the Manager's obligations; included Definitions describe other areas' contracts, which it uses through their owners instead of realizing them again. A Manager with no Definitions of its own (Root, or an empty intermediate Package) additionally receives the Definitions the required checks name in `requiredBy`, with the reason "required by check <name>", so it sees what the whole-project checks and the shared files it owns are for; for Root the reason reads "required by check <name>; realized by <owner>, integrated and verified by you". An included Definition shows its owning Package ("owned by library"). Responsibilities are stated, not implied (DEC-057): every Manager with children gets a "Your children" section naming each child's path, areas and own Definitions, the Managers below each child with their parent, areas and own Definitions (so no descendant's area looks unowned), and the role statement that the children realize their own Definitions in their areas while the Manager supplies the foundations they need within its own area, coordinates them and integrates their results, does not implement their areas and cannot release them from their obligations. Every Manager but Root is told after its own obligations that they are its to realize in its area and that its parent coordinates but cannot take them over or waive them. When the write plan is enforced the areas section also says that only the listed areas and the registry shard are writable in `/work` and everything else is read-only. The engine adds the mandate, contacts, owner request and decisions, findings, messages and check results. A Manager runs with its Execute and Verify profile from the project's settings; Execute and Verify use separate provider homes and Verify never resumes. The homes are runtime volumes mounted by name; Apply removes them through the Host's container engine when the run ends.

## Ownership and registry shards

Ownership is the persistent `layout` of `.markitect/execution.yaml`: artifact roots mirror the model hierarchy (`realization/lending/reminders/...` belongs to `lending/reminders`), explicit exceptions with a reason name other owners (`realization/cmd/library` belongs to `library`), and the deepest mapping wins. Root owns the files directly in an artifact root (`realization/go.mod`, `realization/README.md`) and every file outside the roots. A file in a subdirectory of a root that is neither inside a mirrored Package directory nor inside an exception has no owner: it is a blocking finding `layout.no_owner` addressed to Root; `OwnerOf` returns Root for it. Root cannot fix it by registering the file, and exceptions live in the protected `execution.yaml`, so the finding says that the file has no owner under the persistent layout and Root must have it removed or ask the owner for a layout exception (Root cannot take over the children's domain logic in a Root-owned directory). On a start stand that already holds such files, preparation says that the layout needs an exception or the files must move. An exception declares its `kind`, `directory` (the default) or `file`; a file exception is never an area and can only be owned by Root, because a Package's base is read-only and a file cannot be mounted: preparation refuses a file exception owned by a Package and asks for a directory exception. An invalid layout fails preparation. Without a layout the registry shards alone decide, nothing is enforced and ownership is trusted.

Each Manager creates files in its area and registers them itself in its own shard: `.markitect/registry/registry.yaml` for Root, `.markitect/registry/<package>/registry.yaml` otherwise, with `form`, `realizes` and a `why`. There are no per-file reservations. Registering a path in another Manager's shard is a blocking structural finding.

**Write plans.** With a layout, `apply.Candidates.WritePlan(manager)` gives each Manager the `run.WritePlan` its Execute turns run with; the engine and the adapters enforce it as mount overlays on `/work`. Root has the whole tree writable except read-only `.markitect` (protected inputs), writable `.markitect/registry` (its own shard lives there) and read-only mounts for every other Manager's area and shard directory. A Package has nothing writable except its mirrored directory under each root, the exception directories it owns and `.markitect/registry/<package>`, minus read-only mounts for every deeper owner (descendant Package directories, other owners' exception directories, descendants' shard directories). Mounts are directories, parents before descendants, and list only where writability changes. Only directory exceptions are mounted: a file exception (declared `kind: file`), like a mirrored Package directory that is a file of the start stand and like the files directly in an artifact root, stays with trust and accounting. Without a layout the plan is zero and nothing is enforced. Enforcement needs volume subpath mounts, so Apply asks the container engine before any effect and refuses the run unless the Docker server is version 26 or newer.

## Candidate accounting and protected inputs

`apply.Candidates.Account` runs on every candidate before Verify. Its blocking findings each name the Manager that must act: an unexplained or duplicate file, a file without an owner (`layout.no_owner`, to Root), an invalid or unknown shard, a registration outside the registering Manager's area, and any canonical or control input that changed, vanished or appeared. A changed or deleted protected input quotes its original content when that is at most 8 KiB of UTF-8 text (otherwise its SHA-256 and size), so the owner can restore the exact bytes. Without a declared layout an unexplained new file is addressed to Root, which coordinates but does not own it: the Manager that created the file registers it in its own shard, and Root finds out who that is through its children. Shards are the one writable control input. Preparation runs the same accounting on the start stand before any Agent starts ([DEC-062](../../concepts/register.md#dec-062-start-stand-drift-is-the-owners-first-work)). Under a declared layout, repairable drift of committed files does not refuse the run: `file.unexplained`, `registry.missing_file`, `registry.dangling_basis` and `registry.outside_area`. A Git-ignored untracked file (`RawInputs.Untracked`) is no such drift. Apply passes the start stand's findings as `run.Config.StartFindings`. Each becomes a blocking `markitect` finding of round 0 that reaches its owner behind the initial item, and it closes when round 1 starts, where `Account` observes the candidate afresh. More than 20 findings of one owner and code become one finding that counts them and lists the first 20. A file without an owner under the layout, an invalid or unreadable shard or layout, and every other accounting fault still fail preparation. `markitect check` keeps strict accounting. Structural findings hold for exactly the candidate they were observed on.

## Reconcile cycle

`run.Reconcile` runs one bound reconciliation. It does no I/O itself. Every Apply runs the same order (DEC-058): Execute and integration first, then one captured candidate is verified. There is no initial Verify, no check before the first Execute turn (only the start stand's accounting from preparation, see above), and no special route for absent or unchanged artifacts. The same cycle serves Extract: `Config.Mandate` and `Config.VerifyGuidance`, when set, replace the Apply mandate and the Apply sentences that define what blocks in the Verify prompt (empty keeps the Apply texts), and the initial Execute items stay the same.

1. **Start.** The shared working tree `<runID>-work` is materialized from the start stand, plus the mount directories of the enforced write plans (the union of their mount paths, created empty). There is no candidate-0 volume. All Execute turns mount the shared volume at `/work`. A Manager with an enforced write plan mounts it read-only unless the plan's base is writable and overlays the plan's mounts in order; without an enforced plan the whole tree is writable. Verify turns never get mounts. The engine refuses invalid mounts before any effect: clean relative paths, no `.`, no duplicates, none naming a file of the start stand, parents before descendants.
2. **Execute, starting at Root.** Root gets the initial mandate item at once. Every other Manager gets its initial item only when its parent's first Execute turn has ended without error (finished or waiting) or the parent is disabled; a failed first turn that is retried does not release the children yet. A parent first establishes the foundation its children need within its own area, or assesses an existing one against the model and the children's known needs, preserves it when it fits and corrects or supplements it within its own area (or coordinates its owner), and tells them what concrete basis is available; the messages it sends them during that turn are queued behind the initial item for their first turn. A Manager that is not released runs no turn. Siblings then run in parallel. Every Manager takes part: its first turn compares its area with the model and may conclude that no change is needed. The release of each Manager is recorded once as `manager.release`. The initial item tells a parent to establish or assess the foundation within its own area because its children start when its turn ends, and a child that its parent's foundation is in place. Otherwise an owner starts as soon as it has undelivered items (except a parent with only child reports, see step 3), an item that restates a finding lapses when the finding is closed before it is scheduled, counted for quiescence or taken (messages and notes stay), and messages travel only between a Manager and its direct parent or child; only Root may ask the human.
3. **Integration upward.** When a child's Execute turn finishes with status `done`, its summary goes to its direct parent as the item "Your child X reports done: ..." (`child.report`), so the parent integrates its children's results. A turn that ends without `finish` counts as done and reports with a note that no summary was given; `waiting` reports nothing. Items that arrive while the parent runs are batched into its next turn. A parent whose undelivered items are only such reports does not start while a Manager below it runs or has undelivered items it can still receive; it integrates the reports of its quiet subtree in one turn instead of one turn per report. Any other item (a message, a finding, an owner answer) starts the parent at once, so a child that needs its parent sends a message.
4. **Quiescence and capture.** The phase is quiescent when no Execute turn runs, no released Manager the budget did not refuse has undelivered items and no owner question waits. The runtime then harvests the shared volume, which itself refuses while any container mounts it. The tree becomes candidate N (`<runID>-cN`) of round N, is materialized read-only and verified in a whole round. When Execute changed nothing it equals the start stand. Only an uncertain harvest ends the run Incomplete. An unsupported entry (a symlink, a device, a name that is no valid path) is kept out of the tree and raises, per owner of the paths (Root for an invalid name), one blocking `markitect` finding in that round that counts all entries and names at most 20, so such a candidate is never green, the prompt size stays bounded and the owner removes the entries in the next Execute phase.
5. **Round N.** A round runs `Account` and all required checks on the candidate in parallel, and one fresh Verify turn per Manager, read-only, children before parents. A parent starts when its children's turns ended. Independent branches run in parallel. Execute is paused for the whole round. The Execute phase before round N and its turns carry the number N.
6. **Green or repair.** A round is green when every Manager assessed it, no blocking finding is open and every check passed. Round 1 verifying an unchanged stand and being green yields Verified with the candidate equal to the start stand. Otherwise open blocking findings go to their owners, the Execute phase of the next round resumes the owners (and, through child reports, their parents), a new candidate is captured and a whole new round runs.
7. **End.** The run ends when a round is green (Verified), the round or agent-turn budget or the deadline ends (Incomplete), or a port or the configuration fails definitely (Failed). Candidate volumes close after their round. Once the shared volume `<runID>-work` holds the start stand, the engine never closes it (a failed materialization it closes itself): after `Reconcile` returns, in every outcome, the caller owns it; Apply closes it after a successful publication and keeps it as retained work otherwise.

**Findings.** A finding has one owner (a reporting Manager or a descendant) and one raiser. A Verify finding stays open until a later fresh Verify of its raiser closes it with a reason; a fresh reviewer that does not mention it does not close it. Failed checks and `Account` findings are raised by `markitect`. Only blocking findings go to Execute; advisory ones stay visible. Blocking means a concrete model violation, absent evidence the model requires or a failed required check. Under [DEC-060](../../concepts/register.md#dec-060-owners-realize-others-use-parents-settle-cross-area-matters), a Definition rebuilt outside its owner's artifacts and a change outside a Manager's own area are such violations; Briefs tell every Manager to use the owners' realizations and parents to settle cross-area matters between their children.

**Owner questions.** Root's `send` to `owner` publishes a question through the Owner port and work that does not depend on the answer continues. The answer reaches Root's next turn. An unanswered question at the end leaves the run Incomplete; without an Owner port the question is refused. [DEC-063](../../concepts/register.md#dec-063-the-model-is-authoritative-defects-escalate) is not implemented yet: the runtime has no model-defect outcome. Such a matter is decided by a Manager or asked as an ordinary owner question, and the run continues with a run-only answer.

**Budget and deadline.** The budget bounds Execute plus Verify turns (`agentTurns`), Verify rounds (`rounds`, each preceded by an Execute phase), each turn (`turnTimeout`) and the whole run (`Budget.Deadline`, an absolute time Apply sets from `executionTime` and the run configuration's optional `deadline`). The agent-turn budget must cover at least one Execute and one Verify turn of every Manager (2N), otherwise the run ends Incomplete before any effect. An Execute turn is only admitted while the budget also leaves room for one whole Verify round and for the first Execute turn of every other Manager that has not run yet and is not disabled, so a Manager's first turn stays possible. When a turn is refused, the engine records `execute.budget_limit` once for the phase and refuses every Execute turn that does not fit; running turns end, the pending items of refused Managers do not keep the phase open, the stand is captured and the reserved turns run the Verify round. The run ends Incomplete only when that round is not green and the next phase admits no Execute turn. The deadline cancels all running turns and checks and waits for them. A turn that fails after its container stopped is retried once with a note and the items it consumed again, even when the provider kept a conversation; a second consecutive failure stops scheduling that Manager, and the run ends Incomplete if that Manager still owns an open blocking finding. A Verify turn without a valid `assess` is retried once; if that fails too, the turn's error stays in the Incomplete reason. A turn that failed before any container started is reported `Stopped` with its error, so it never makes quiescence uncertain.

## Host tools

Served to the provider over MCP by `markitect-agentd` inside the turn's container.

| Tool | Turn | Behavior |
| --- | --- | --- |
| `send {to, text}` | Execute | `to` is `parent`, a direct child path or, for Root only, `owner`. Anything else is refused with the allowed contacts. The answer returns the caller's new undelivered items. |
| `finish {status, summary}` | Execute | `status` is `done` or `waiting`. It records how the turn ends; the turn itself ends when the provider stops, and the tools stay usable until then. A later call replaces an earlier one. A turn that ends without it counts as done. The summary of a child's `done` (or a note that none was given) is delivered to its parent. |
| `check {scope?}` | Execute, with `Config.CheckTool` (Apply and Extract set it) | Peeks the shared work volume through `Workspaces.Peek` (writers keep running), runs `Account` on the peeked tree and answers with the findings as compact text: the calling Manager's first, then the number of others (`scope: "all"` lists them too). It is advice; the candidate still comes only from Harvest. An uncertain or incomplete peek (an error, an uncertain observation or unsupported entries) is refused with the reason, which is not a failure of the run. The Execute prompt mentions the tool only when it is offered. Each use is recorded as `check.requested` with the Manager and the counts. |
| `assess {summary, satisfied, findings[], closed[]}` | Verify | Findings carry `owner`, `obligation`, `observed`, `blocking`. A report that contradicts the raiser's open blocking findings, or closes a finding it did not raise, is refused with the reason and may be repeated. A valid report is kept until the turn ends and applied then (closures, new findings, the assessment); a later valid call replaces it. With `Config.ArtifactFindingsAdvisory` (Extract's model phase, which supplies `Config.ResolveDefinition`) each finding also states `subject` (`artifact` or `model`) and, for an artifact, `definition`; a missing or invalid subject, or an artifact finding whose Definition the candidate model does not hold, is refused, and an artifact finding is stored non-blocking whatever the reviewer says. Apply does not set the option and sees neither field. |

A Manager's Execute turns get mandate, Brief, contacts, owner decisions, the shared-tree note and their items until one of them finished without error; later turns resume the provider conversation with new items only. With an enforced write plan the shared-tree note says that outside the writable areas `/work` is read-only and a write there fails, and that scratch output goes under `/tmp`; for a writable base (Root) it lists the read-only mounts and the writable overlays nested inside them. The Claude Code adapter keeps the `Write` and `Edit` tools for an enforced Execute turn with writable mounts and drops them only for Verify turns and turns that can write nowhere; the Codex adapter restricts no tools. The first Execute prompt carries the initial mandate item.

## Configuration

`.markitect/execution.yaml` (`apiVersion: markitect.execution/v1`, `strategy: shared-workspace-v1`) is closed. Its fields are `budget {executionTime, turnTimeout, agentTurns, rounds}`, `profiles {execute, verify}`, `instructions`, per-Package `packages` overrides, optional `layout {roots, exceptions}`, optional `scope` (modeled scope selectors `{kind, property}` that add Definitions to a Manager's context) and `checks` (id, profile, directory, args, `requiredBy`, timeout). The [apply guide](../../../internal/apply/README.md#execution-settings) shows the shape and the embedded product defaults.

The run configuration is a separate closed JSON file (`formatVersion` 2) with the explicit invocation facts: `repositoryIdentity`, `productBuild`, `ownerRequest`, optional `ownerDecisions`, `stateDirectory`, `engineExecutable`, `workspaceHelper`, `harvest {maxEntries, maxBytes}`, optional `deadline` (RFC 3339, UTC) and `credentials`. It adds no project settings or profile defaults.

## Evidence and state

The state directory of the run configuration is held by one Apply at a time (`apply.lock`). It must lie outside the repository; a state directory inside, equal to or containing the repository is refused before anything is created.

```text
<state>/apply.lock
<state>/current-run                          run identity of the Apply holding the lock
<state>/runs/<runID>/events.jsonl            append-only, synced per event
<state>/runs/<runID>/transcripts/<turn>.jsonl  provider stream, secrets redacted
<state>/runs/<runID>/report.json             written once at the end
<state>/questions/<id>.json                  open owner question
<state>/answers/<id>.txt                     the owner's answer
```

Event kinds: `run.start`, `round.start`, `check`, `assessment`, `finding.raised`, `finding.closed`, `round.end`, `check.requested`, `turn.start`, `turn.finish`, `turn.end`, `message`, `question`, `answer`, `owner.error`, `candidate`, `write.observed`, `execute.budget_limit`, `manager.release`, `child.report`, `manager.disabled`, `workspace.materialize`, `workspace.close`, `home.remove`, `outcome`. A run identity with an existing directory is refused; evidence is never overwritten. A failed record or report write ends the run Incomplete. The owner answers with `markitect answer ID --text ANSWER --run-config PATH`; the answer is accepted only for a question of the running Apply (`current-run`). When a new Apply opens the channel right after taking the lock, it removes only the channel's own question `.json` and answer `.txt` files of earlier Applies.

## Publication and read-back

Only a Verified outcome is published, as the exact verified candidate against the committed source captured at the start. The publisher refuses a source that changed since capture and a change set the target cannot represent, writes the changes and reads every path back. Multi-file publication is not atomic; a partial write stays visible and is reported. Apply closes the shared work volume only after an applied or unchanged receipt; after any other receipt or a publication error it keeps the verified work and reports it as retained. The command reports `Passed` only for an applied or unchanged read-back. Apply never commits, merges or pushes. Human acceptance and a later commit follow project policy.

## Extract: first bounded implementation

Extract (Artifacts -> Model, [DEC-057](../../concepts/register.md#dec-057-three-fundamental-starting-situations)) reuses the engine, Briefs, write plans, accounting, owner channel, evidence and guarded Publisher of Apply. This slice implements the [accepted workflow](commands.md#extract-the-existing-stand) for one stable Manager tree and states what it leaves out. Status: implemented, with tests on scripted fakes; the first real runs on the library are [recorded](../../validation/library-extract-20261019.md); owner acceptance is pending.

**Input.** A committed repository with existing artifacts under the artifact roots of `layout.roots`, the imported vocabulary (for example `.markitect/dependencies/core` and `.markitect/dependencies/software`), a Host-prepared manifest and lock with no local Definitions (the model root holds a placeholder file such as `.markitect/model/.gitkeep`, because Git does not track empty directories), and `.markitect/execution.yaml` with budget, profiles, layout roots and checks. Checks carry no `requiredBy`, because no Definition exists yet. `PreparationService.CaptureExtract` prepares this start like Apply, except that unregistered artifacts (`file.unexplained`) and artifacts that no Package covers yet (`layout.no_owner`) do not fail file checking; everything else is checked as for Apply. `Extract` refuses a start whose local model already has Definitions, and one without artifact roots. The required checks are prepared but not run: they verify the artifacts, which Extract leaves unchanged, and a failing check would otherwise block a sound model. The Briefs list them as evidence.

**Phase one, structure.** `run.Reconcile` with a team of Root only. Root inspects the artifacts and proposes responsibility boundaries as model Packages (folder names are clues, not authority). Under [DEC-061](../../concepts/register.md#dec-061-what-an-extracted-model-contains), one Package owns the project as a whole: purpose, scope and non-goals, delivery obligations and technical boundary. Root writes one overview Definition per Package (including intermediate ones, in the vocabulary's Concept Kind) so the candidate compiles, names the artifacts behind each boundary in its summary rather than in the Definitions, and adds the persistent layout exceptions the proposal needs. Where the artifacts document how the project is built and tested, Root also proposes those commands as entries of `checks` in `.markitect/execution.yaml` ([DEC-061](../../concepts/register.md#dec-061-what-an-extracted-model-contains)): each names a check profile the Host offers, which the Brief lists, carries no `requiredBy` because no Definition exists yet, and applies only once the owner adopts the model. Write plan: `.markitect` is writable; `.markitect/dependencies/<each in-repository dependency>` and every artifact root are read-only mounts over a read-only base. Single files (manifest, lock, ignore, the execution document apart from `layout.exceptions` and `checks`) cannot be mounted and stay with accounting. Verify (fresh) assesses the proposal's source support. For the library with the root `realization` and the dependencies `core` and `software`, Root's plan is: base read-only; `.markitect` rw; `.markitect/dependencies/core` ro; `.markitect/dependencies/software` ro; `realization` ro.

**Phase two, model.** The verified candidate of phase one is compiled and prepared again as a new capture (same dependencies, manifest, lock and Host facts; the candidate's model, layout and registry), the settings are resolved for its Package tree, and `run.Reconcile` runs the team of that topology, Root first and parents before children, with the phase-one candidate as start. Each Manager derives the model of its area from the artifacts as evidence. Binding is what is observable at the project's boundary or documented as intended (DEC-061); internal structure, names, wiring and the order of internal steps stay realization choices, observable behavior that intent leaves open is stated as free, each fact and value lives once at its owner, and evidence goes into registrations and summaries rather than Definitions. The Manager of the project Package also states the project-wide obligations. Observed behavior that contradicts clear intent becomes an artifact deviation, not a rule; unresolved intent goes through Root to the owner. A Manager registers every existing artifact of its area in its own shard with the Definitions it realizes. Parents integrate shared terms, boundaries and cross-area rules. The Manager tree is stable within the round: a Manager that sees a wrong boundary reports it as a proposal; a new or vanished Package is a blocking structural finding. Write plan: every Manager has a read-only base and writes only its Package's model directory `.markitect/model/<package>` (minus its descendants') and its shard directory `.markitect/registry/<package>`; Root writes only `.markitect/registry` (its own shard `registry.yaml`, minus the shard directories of the other Managers). For the library: Root has `.markitect/registry` rw with the shard directories of `catalog`, `lending`, `library` and `members` ro; `lending` has `.markitect/model/lending` rw, `.markitect/model/lending/reminders` ro, `.markitect/registry/lending` rw and `.markitect/registry/lending/reminders` ro; `lending/reminders`, `catalog`, `library` and `members` have their own model directory and shard directory rw. Artifacts, dependencies, manifest, lock and `execution.yaml` are read-only, so the proposed checks stay as Root proposed them and appear in every Brief with the declared checks. Every Manager's Brief names its artifact areas and files (from the candidate layout), the registry shape, a language v1 authoring guide with the vocabulary's Kinds, and the Package's overview Definitions. Both phases offer the Execute tool `check` (`Config.CheckTool`) and carry the phase's own mandate and Verify guidance (`Config.Mandate`, `Config.VerifyGuidance`). Verify reads the area's Definitions statement by statement and blocks on model defects (findings with subject `model`): an unsupported or invented statement, important observable behavior missing ("could important behavior change while the model still permits it?"), a realization choice made binding, a fact stated in several places, a statement contradicting clear documented intent, a source conflict decided without an owner answer, missing project-wide obligations in the project Package, or a registration whose Definitions do not describe its artifact. Compilation, link resolution and complete registration are not model-phase reviewer duties: `Account` blocks on them exactly and addresses the owner who can act (RXF-7 of the [Extract comparison](../../validation/library-extract-comparison-20261019.md) failed when a reviewer demanded a registration only Root could make). In the structure phase, a proposal without a project Package blocks. An artifact that deviates from a justified model statement is a finding with subject `artifact` that names the Definition (`Config.ArtifactFindingsAdvisory`, `Config.ResolveDefinition` compiling the candidate's model and confirming the identity): it is stored non-blocking whatever the reviewer's flag, so it never blocks the model.

**Accounting.** `Account` of each phase compiles the candidate from the tree (the same pipeline that prepares the next phase), so a candidate that does not compile, resolve imports or validate its layout is a blocking finding of the owner of the offending path. Phase one additionally requires at least one Package, a Definition in each Package, and an owner under the layout for every existing artifact (`layout.no_owner`, one finding per directory). Phase two requires the phase-one Package inventory and accounts every file with the Apply accounting: artifacts registered in the owner's shard under the candidate layout, registrations linked to Definitions that exist in the candidate model, valid shards. In both phases everything outside the phase's writable area must be byte-identical to the phase's start and nothing may be added there: artifacts, dependencies, manifest, lock and ignore always; `execution.yaml` in phase two and, in phase one, everything but `layout.exceptions` and `checks`. A proposed check that does not decode, or that names a profile the Host does not offer, is a finding of Root that states the defect and the profiles offered, so the candidate never reaches phase two with checks that make its preparation fail. A violation is a finding of the path's owner that quotes the original when it is small; this guard runs on every candidate, even one whose model or execution document does not prepare. `Account` is a pure function of the tree and is called concurrently by the check tool.

**Completion and publication.** Model completion is a Verified second phase (no open blocking finding; an unanswered owner question leaves the run Incomplete). Only then are the changes against the captured repository published through `Publisher.Preflight` and `Publish` with read-back. The change set must lie in `.markitect/model`, `.markitect/registry` and `.markitect/execution.yaml`; an artifact change refuses publication. An unverified phase publishes nothing and keeps its work volume as retained work. Extract never commits.

**Budget.** The deadline (`executionTime`, or the operator's earlier deadline) is shared by both phases. `agentTurns` is one total of at least 4: phase one may use at most half of it, phase two gets the rest phase one left and needs at least two turns per Manager of its tree. `rounds` and `turnTimeout` apply per phase. The phases run under the run identities `<run>-structure` and `<run>-model`, so volumes, homes and turns never collide. They share one owner channel: phase two gets phase one's answered questions (`Config.Questions`), shows them to its Managers and continues their numbering. Phase one's work volume is kept until phase two holds its own start, and kept as retained work when phase two cannot be prepared or started.

**Report.** `markitect extract` prints one JSON report: `modelComplete`, both phases (`structure`, `model`: rounds, findings, questions, turns, usage), `verify` (the last round of phase two with each Manager's assessment), `deviations` (the open artifact findings grouped by Definition: its identity and the owners, raisers and observed texts of its findings), `proposedChecks` (the checks that the verified candidate's execution document has and the start did not: id, profile, directory, args, timeout; whether they reached the repository, `publication` tells: they are published only when the publication applied), `openQuestions`, `publication`, `retainedWork` and `evidenceDirectory`. Status is `passed` only for a verified, published model. The evidence adds the event `extract.phase` per phase. After the JSON report on standard output, the command writes a short plain-text account of the same result as the last thing on standard error: status and reason, the Packages of the verified model with their overview titles, the owner questions with their answers, the deviations, the proposed checks, the last Verify round, the publication and, for a published model, the next step of adopting it by review and commit.

**Handoff to Apply.** Adoption follows the [accepted transition](commands.md#adopt-the-model-and-hand-findings-to-apply): the owner adopts the published model and registry together and commits them; the first regular Apply then starts from that commit. The open artifact deviations are in the report and the evidence only; storing them and passing them to that Apply is not implemented.

**Not in this slice.** Restructuring the Manager tree between phase-two rounds (a proposal stays a finding for Root and for a later Extract), resolving model questions by later Extract rounds, restore of an interrupted run, running the project's required checks, a readable adoption subject beyond the JSON report, the handoff of findings to Apply, and any artifact change. The initial Execute item is direction-neutral ("carry out your responsibility as the mandate describes"), so the Extract mandates direct the work without reinterpretation.

## Trusted and enforced

| Enforced by the code | Trusted |
| --- | --- |
| Complete accounting of start stand and every candidate; protected inputs unchanged. | Without a declared layout: Managers write only their own area. |
| Registration only in the owner's shard; under a layout, a file in an unmapped root subdirectory has no owner and blocks. | Files directly in an artifact root and file exceptions, which mounts cannot cover: only their owner writes them. |
| Under a layout, each Execute turn's container can write only its own areas and registry shard; protected inputs and other areas are read-only mounts. | A parent supplies foundations and coordinates rather than realizing its children's Definitions in its own area. |
| Quiescence observed by the container runtime before capture; verify only on an immutable read-only candidate; required checks on the same candidate. | Verify assessments and the Managers' judgment of obligations. |
| Parent/child-only `send`, Root-only `owner`. | The model and the human own intent; Managers do not change it. |
| Nothing publishes unless Verified, with evidence recorded. | |

The engine records `write.observed` for files of a Manager that changed although it ran no Execute turn since the previous candidate and shows them to that Manager's next Verify. This is an observation, not complete write attribution: it cannot see trespass by a Manager that ran in the same phase. Under a declared layout the write plans enforce ownership instead.

## Known limits

- Technical write enforcement exists only for Managers whose Execute turns carry an enforced write plan (read-only base with writable mounts); without one a Manager can write another Manager's files in the shared tree and the engine can only observe and account for the result.
- A Root-owned file exception inside another Manager's area cannot be written by Root under enforced ownership, because that area is mounted read-only and a single file cannot be mounted writable; keep such files outside other areas.
- No restore of an interrupted run. The deadline, SIGTERM or a crash ends the run Incomplete with its evidence; a new Apply starts again from the committed repository, not from the incomplete shared tree.
- Every round verifies the whole team again; unchanged areas are not skipped.
- Shared-tree scalability, native provider message behavior under load and real-provider cost are unproven.
- Source tests use scripted fakes; the two-Apply library demonstration with the independent oracle is separate evidence.
