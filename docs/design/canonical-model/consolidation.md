## Common basis

Markitect describes the intended project world and has its repository realization executed in a coordinated way. People decide meaning and degrees of freedom; structure checks, traceable impact, bounded responsibilities, independent reviews and concrete checks support the realization. This is the basis of the [vision](../../vision.md) and the [concept register](../../concepts/register.md).

Both design lines can be brought together in it: The terms explain **which kind of statement** is described. A Definition body contains the individual statements. Explicit relationships connect Definitions. From this, context, realization assignments and check assignments are to arise. How exactly this derivation works is to be determined per relationship. A word, a link, a composition and a realization obligation are different things.

## Working goal and shaky candidates

Clarification by the user of 15 October 2026: The starting point of the younger branch is an extensive, typed project documentation. The canonical model is to be able to express everything relevant about the intended project: what is to be and which stipulations apply. The vocabulary is developed from this description need. The existing implementation and its previous coordination procedure do not determine in advance which terms this new model must contain.

The goal remains to describe the intended project world and have it realized through Apply. A distinction is to be made between:

| Level | Content |
| --- | --- |
| Canonical project description | Purpose, scope, domain, behavior, rules, desired architecture as well as relevant technical and operational stipulations. |
| Apply procedure | Interpretation of the description, division of agent work, implementation, checking and integration. The exact new way of working is still to be designed. |
| Realization and evidence | Artifacts produced by the implementation, their determined assignment to the model as well as executed checks and observed results. |

Concrete files that have come into being are realization. An intended obligation such as “a user manual must be present” can nevertheless be relevant for the project description. Whether such obligations require an Artifact type of their own remains a separate design question. Accordingly, requirements on the software architecture are distinguished from the file or package structure actually produced.

The user explicitly names the following terms as **shaky candidates**. This means: need, place in the model and delimitation are to be checked; none of these terms has already been struck by this classification. The rationales below record the state of the conversation, not new final type decisions.

| Shaky candidate | Rationale and open question |
| --- | --- |
| **System** | Project already describes the overall context, Component can be a general building block. To be clarified is which additional expression System enables: for instance a standalone solution with an outer boundary, several solutions in one project or relevant external systems. These possible tasks are test examples, not yet a confirmed justification for a type of its own. |
| **Component versus Module** | After the extension of Component to logical and nestable building blocks, the previous meanings overlap. Desired architecture can belong to the target of the project; open is whether two types are needed for it and which different statement or relation they enable. The choice of the general Component meaning does not yet decide on the final need for both types. |
| **Artifact** | The model describes what is to be; only the implementation leads to concrete artifacts. A model type for files that have come into being would mix these levels. To be examined remains how necessary realization contributions or output requirements are described and whether a type of its own is required for this. |
| **Mandate** | The previous meaning describes assignment, responsibility and boundaries of the executing agents and thus initially belongs to the way of working for Apply. A place in the canonical project vocabulary is thereby not justified. Domain or operational responsibilities relevant to the project itself would have to be distinguished from it. |
| **Decision** | The applicable stipulation and, where appropriate, its rationale can belong to the project description. The course of the decision and its historical origin serve a different information purpose. Open is which necessary expression a Decision definition of its own enables in addition to the description at the subject of the stipulation. |

In addition, **the need for process descriptions, and thus the role of Workflow and Procedure, is open**. Domain procedures or prescribed operating procedures can belong to the intended project. Classic development procedures with pull requests, reviews and similar stations are not a presupposed part of the new canonical model. The new Apply variant is to be able to bypass or unblock such previous procedures more or less; its concrete replacement and its check and integration mechanisms are not yet determined here. The development processes in the Tasks term example remain illustrative material, not a requirement for this new model.

**Current priority of the user:** Clarify System, Component and Module together. The starting point is concrete statements of a sufficient project description. We examine which distinct expression and which relationships each term enables, where overlaps lie and what a merger would lose. The clarification of Artifact, Mandate and Decision follows afterwards. No selection of the types to keep has yet been made.

## Contradictions and decisions

### 1. Component: general system part or runtime building block?

**Previous library version:** A `Component` was limited to runtime/deployment building blocks. A `System` contained Components; a Component contained logical Modules. The first example contract did not allow direct Component-to-Component composition. See [architecture terms in the proposal](../product-model-refinement/canonical-model-proposal.md#4-beziehungen-gliederung-und-verantwortung).

**New vocabulary:** [Component](component.md) generally means a system part. The [relationships](relationships.md#structure-and-files) allow nested Components. Task Logic, Application, Command Line and Local Storage are there logical areas of responsibility, not promised separate runtime units.

**User decision of 15 October 2026:** „Allgemeiner Systembaustein, auch logisch und verschachtelbar.“ (English translation: “A general system building block, also logical and nestable.”) The [Component definition](component.md) thus also applies to Task Logic and to logical parts nested within one another. A process of its own or a deployment of its own is not a precondition. The earlier narrow meaning is superseded.

**Consequences:** The library building blocks Frontend, Backend and Database remain valid examples of Components. They no longer limit the term to runtime architecture. Component-to-Component composition becomes admissible; the already agreed derivation of the `realizes` scope also follows these `contains` descendants. The standalone benefit of System and Module and their delimitation, as well as complete parent and target set rules, remain to be decided. The two Kinds are not removed by this Component decision alone.

### 2. Interface: Actor access or technical contract?

**Library:** Interfaces also connect internal Modules, for instance via service and repository contracts; `provides` and `consumes` distinguish provider and consumer. **New vocabulary:** An [Interface](interface.md) is the access of an Actor to UseCases.

**Decision:** Does Interface apply exclusively to external interaction, or also to technical cooperation within the software? An internal caller must not become a new Actor merely so that an existing contract fits into the definition.

**Recommendation:** Take Interface as an agreed interaction contract; Actor access is a concrete use. Provider, consumer, offered operations and errors must remain traceable in the respective example. This is a proposed extension of the short working definition.

### 3. Fourteen terms are not yet a complete Kind list

The new vocabulary adds Actor, Scenario, Workflow, Procedure and Condition. It does not define Mandate, System and Module. Their absence does not revoke the older decisions. Conversely, an understandable term definition does not yet justify a machine-readable Kind of its own.

The set to be examined jointly thus comprises seventeen named terms. The new [classification of the shaky candidates](#working-goal-and-shaky-candidates) explicitly puts the need for and delimitation of System, Component/Module, Artifact, Mandate and Decision up for discussion. Their earlier inclusion in a draft does not anticipate the result of this examination.

**Decision:** For each term we examine separately whether it needs its own identity and referenceability, which individual statements it carries and what its presence effects for realization or checking. A fixed number of Kinds is not a goal.

**Special naming conflict:** `Decision.actor` references a Mandate in the library draft, while Actor in the new vocabulary describes a participating role. Role, assignment, executing agent and documented decision origin are to be clarified individually. None of these fields authenticates an approval.

### 4. General connection or computable relation?

The vocabulary explains connections such as “processes”, “documents” and “checks” in everyday language. The library draft distinguishes structured relationships and chooses for `realizes` an automatic scope via the `contains` substructure.

**Decision:** The everyday-language relationships are mapped to a language contract only after their individual examination. A body link declares an explicit usage, but not automatically containment, rule applicability, realization or write responsibility. There is no blanket implementation of all connections as `uses`.

**Preserved design direction:** Where `realizes` is used, it comprises according to the documented decision the target and transitive `contains` descendants corresponding to the contribution role. Other relationships do not automatically enlarge this target set. If we change the permitted `contains` children, we must therefore also examine this consequence.

### 5. Check: check assignment or exclusively executable command?

The new [Check definition](check.md) describes method and success criterion and can also carry a documentation comparison or a review. Main and the concrete library field candidate, by contrast, require a non-empty command as a literal argument list.

**Decision:** Is Check to be the general check assignment whose method can be a command or a reasoned review? Or do manual or agentic assessments remain a separate mechanism?

**Recommendation:** First describe expectation, method and success criterion in domain terms. Then decide how the execution is bound. Declaration, execution and recorded result remain different. A review assignment must not appear as an already executed Command check.

### 6. Removing Coverage: configuration or product obligation?

The library draft removes Coverage and its mode configuration from this concept step and specifies no additional complete repository coverage. Main and [DEC-006](../../concepts/register.md#dec-006-every-file-is-covered-or-explicitly-ignored) continue to require that every file is assigned or explicitly excluded.

**Decision:** Removing a term or switch does not answer whether unknown files continue to block the realization. If this obligation is to be retained, the new language too needs a traceable file recording and responsibility check. If it is to lapse, that would be an explicit change of the existing product decision.

**Recommendation:** Retain complete file accountability; decide model simplification and configuration location separately. Here neither is an old switch reintroduced nor DEC-006 changed.

### 7. Rule, Condition, Procedure and Workflow

Here there is initially a clarification rather than a proven contradiction: Rule obliges; Condition describes a truth value; Check examines an expectation. Procedure explains an activity; Workflow coordinates activities and participants. Scenario describes a concrete case. The [relationships page](relationships.md) provides the working delimitation.

**Open:** Whether conditions need Definitions of their own, how they are evaluated and which Workflow transitions take place by machine. The descriptions do not yet justify an expression evaluator or an executable workflow engine. Even a Procedure text phrased imperatively does not itself grant an agent the authority to execute the steps.

After the most recent [goal clarification](#working-goal-and-shaky-candidates), the need for separate process descriptions is already open. We first examine the subject of the procedure and its contribution to the target description before we treat Workflow and Procedure as required types.

### 8. Two Tasks representations with different precision

The [term example](task-management-example.md) uses Title/Identifier and exemplary `src/...` paths. The [standalone project documentation](../task-management/README.md) uses Text/Reference, Python 3.13, `python -m tasks` and a more precise storage contract. A missing confirmation signal after the commit explicitly does not prove a failed save operation there.

**Concrete deviation:** The term example says in general that a failed save preserves the previous data. The [more precise storage contract](../task-management/docs/storage.md#save-procedure-and-commit-point) separates errors before the replacement from errors in the subsequent confirmation. A later joint modeling must retain this boundary.

**Proposed use:** The standalone documents are the substantive counter-probe for the Tasks project; the term example remains a simplified draft for terms. We reconcile selected statements explicitly and do not present the different paths and names as the same finished model state. The historical seven-Kind attempt remains historical.

## Next design step

The current task is the [minimal language basis](minimal-language/README.md) with a Connector vertical slice for own Kinds and relations. On it we check expressiveness, meaning and checkability before a new language contract is fixed. System, Container, Component and the further shaky candidates are examined as possible vocabulary types. The concrete Apply way of working is considered separately; the handling of file accountability is to be clarified before an executable new variant.

For each decision we record the chosen statement, a small Tasks example, a counter-probe on the library, effects on existing decisions and remaining questions. Only after agreement do we change the affected term definitions and examples. Syntax and implementation follow the clarified meanings.

This consolidation contains no new language implementation and no proof of application or effectiveness. Current product contracts remain with the [vision](../../vision.md), the [architecture](../../architecture.md), the [concept register](../../concepts/register.md) and the existing operation guides; implementation status remains with the [roadmap](../../implementation-plan.md) and backlog.
