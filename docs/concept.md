# Concept

**You architect the project in Markdown. Markitect's tool checks the spec and says what is left to verify, an ordinary agent started by your own session builds the project to the spec, and a fresh reviewer verifies each Definition and records it.**

This page is the one description of the product, and the target that Main builds ([DEC-098](decisions.md#dec-098-one-concept-describes-the-product)). The [decisions](decisions.md) list what it rests on, the [roadmap](roadmap.md) the next steps, and the [vision](vision.md) why.

## 1. The aim

Make one clean and simple version work reliably on Sonnet ([DEC-009](decisions.md#dec-009-how-markitect-is-judged)): the spec as it stands gets applied reliably, with no human babysitting, review or other slowing down, so that people concentrate on architecture, which agents can't do by themselves. Every choice below is judged by that.

**The problem.** When agents build a project, trust and overview no longer come with the work, and nothing in the project states what it should be; the [vision](vision.md#why-markitect-exists) gives the reasoning. Markitect supplies that statement: one spec with authority, and every file accounted for in the registry ([§2](#the-spec)). The spec is how a change is made, so it cannot be ignored while work goes through it. On it, Markitect answers four questions:

| Question | Markitect's answer |
|---|---|
| Was something forgotten? | `status` lists what a change reaches, from the spec and the record, not from memory ([§3](#how-status-works)). Every Definition keeps a verdict at the inputs it was verified at, and a full review is `/markitect-review --all` |
| Was it understood correctly? | A fresh reviewer verifies every Definition a change reaches ([§5](#5-what-build-does)) and records its verdict ([§6](#6-the-record)) |
| Does the spec say what was meant? | Only the owner answers spec against intent; `vet` ([§4](#4-is-the-spec-good)) and the audit ([§8](#8-other-skills)) support that |
| How does the project stand, and how is it organized? | Follow the spec, not the code: `list`, `doc` and `vet` show its structure, and it moves only when the owner accepts a change ([§3](#3-the-tools)) |

**The way of working:**

1. A person architects the project in an ordinary Claude Code session, with the architect skill: the session asks, proposes and writes the spec, and hands a large draft to the architect agent. The person goes through it with the session, or reads the Markdown diff of a change, and the session commits it with the person's word.
2. The person runs the build skill. Agents started by the person's own session apply the spec as it stands, in a worktree of their own, so the person can go on architecting. They ask nothing about the spec, and nobody has to watch.
3. The spec stays as it was while they work: the hook keeps the agents that build out of it.
4. When `markitect status` lists nothing, or only `spec-problem`s for the person, the session commits the work with the record of what was verified and brings it to the person's branch. The person reads the verdicts when they want to, and answers only when the spec has a problem.
5. A bug hunt, a cleanup and a full review also run on a schedule, each on a branch of its own.

## 2. What Markitect is

| Part | What it is | Changes with the provider? |
|---|---|---|
| **Spec** | Typed documentation in Markdown, with the registry ([below](#the-spec)) | No |
| **Tool** | One program, `markitect`. It holds every fact and every rule that can be checked without judgment: it checks the spec, says what is to verify and records what was verified. It starts no agent, steers no work and uses no Git ([DEC-096](decisions.md#dec-096-the-tool-computes-and-checks-a-driver-acts), [DEC-097](decisions.md#dec-097-markitect-uses-no-git)) | No |
| **Harness** | The drivers: four agents in a 2×2 of rights, short skills named after their activity that have the owner's session start them, in sequence or through the shipped parallel workflow, routine prompts, a hook, the instruction files that `markitect init` writes, and the harness configuration ([§9](#9-the-harness), [§10](#10-drivers)) | Yes |

**A record of what was verified.** For each item, a Definition with its parts ([DEC-111](decisions.md#dec-111-a-thing-with-parts-is-built-and-verified-as-one)), the tool keeps the state at which a reviewer last verified it, as Go's test cache does for tests, and `markitect status` lists every item whose state changed since ([§3](#how-status-works), [§6](#6-the-record)). The builder is told: make the project match the spec for what `status` lists, and have the reviewer verify and record each item. When nothing is left to verify, the spec is implemented. So:

- nothing is held between commands outside the project, so compaction or a closed session loses nothing;
- the tool imposes no order, reviewers can work in parallel, and any driver, a person included, can verify at any time and in any amount;
- the prompt stays a task and an answer format ([DEC-051](decisions.md#dec-051-agents-get-tasks-not-process)), and the agents hold it in their own files;
- the hook guards only the record, the spec and what steers the agents.

What is left to the agents is what needs judgment: how to build it, and whether the code meets the spec. What is left to the driver is who starts which agent, when, how often, and every Git step. There is no token and no background session: the owner's session starts the agents, and they call `markitect` like any other tool ([DEC-094](decisions.md#dec-094-the-users-own-session-runs-the-agents-natively)).

### Words

| Word | Meaning |
|---|---|
| **Spec** | The one documentation of the project that has authority over its artifacts |
| **Definition, Kind, Package** | One Markdown file of the spec, its type, and a module of the spec: a folder that holds its anchor, a Definition of kind `Package` |
| **Registry** | One page per Package: the paths it owns and which Definitions each file realizes |
| **Record** | `.markitect/review.sum`: for each item, a Definition with its parts, the verdict and the inputs at which it was verified |
| **Owner** | The person who owns the project and its spec: decides intent, accepts every spec change and settles every `spec-problem` |
| **Builder, reviewer, architect, auditor** | The four agents: the builder writes code, the reviewer judges it and records, the architect writes large parts of the spec for the owner's session, the auditor judges the spec |
| **Driver** | Whatever starts the agents and makes the Git steps: by default the harness and the owner's session |

### The spec

**What belongs in it.** What good documentation of the project would state: what a book is, how many a member may borrow, which interfaces exist, which technologies are used, which modules exist. What nobody cares about stays out, and agents decide it ([DEC-079](decisions.md#dec-079-the-spec-is-as-explicit-as-good-documentation)). [What makes a good spec](guides/good-spec.md) says how to cut it.

**How it is written.** The spec lives in `.markitect/spec/`. A Definition is one Markdown file whose front matter names its Kind; a Kind is itself a Definition; a folder is a namespace, and a Package is a folder that holds its anchor, a Definition of kind `Package` that says what the Package is, whose Definitions reach its whole subtree ([DEC-108](decisions.md#dec-108-a-folder-is-a-namespace-a-package-is-declared-by-its-anchor)); a link `[[path]]` is a declared dependency, like an import; a cycle between Packages is a compile error; Libraries supply common Kinds, and `std` ships in the binary ([DEC-080](decisions.md#dec-080-the-spec-is-typed-documentation-in-markdown)). A Definition states one thing; a thing with parts is a folder that holds the Definition of its own name and its parts, a link to the folder means that Definition, and `doc` shows it whole ([DEC-109](decisions.md#dec-109-a-thing-with-parts-is-read-as-a-whole)). A Kind may declare the labelled fields of its Definitions and the folders of their parts, and the compiler checks them; `std` holds the Kinds of a whole project's description, from its purpose to how it is kept running ([DEC-110](decisions.md#dec-110-a-kind-declares-fields-and-parts-and-std-describes-a-whole-project)). A link is never decorative: it states a relation that matters for change, and navigation belongs in documentation rendered from the spec. A record that others name gets an identity Definition of its own, and a Package publishes what is not `internal: true`, as code writes both ([DEC-104](decisions.md#dec-104-a-link-is-never-decorative-identity-and-surface-are-written-as-code-writes-them)). The [spec language guide](guides/spec-language.md) is the canonical description.

**Authority.** Where an artifact differs from the spec, the artifact is wrong: code, tests, docs, pipelines and configuration alike. The agents that build never change the spec, and the owner accepts every spec change. A bad spec is never made to work during the build: its Definitions get `spec-problem`, and the owner changes the spec ([DEC-063](decisions.md#dec-063-the-spec-is-the-authority-and-its-defects-go-to-the-owner)). That loop runs per change, not as one long phase up front, because some flaws show only once something is built.

**The registry.** Every file has one owning Package, the most specific path pattern wins, and each file is listed with the Definitions it realizes, or is ignored. Shared files sit with the lowest common parent. The builder keeps every registry page current. When a Definition disappears, every file whose only basis it was goes, or gets a new basis ([DEC-006](decisions.md#dec-006-every-file-is-accounted-for)).

**Three starting situations.** A new project starts with the spec: `/markitect-architect` writes it with the owner, and `/markitect-build` builds it all, since nothing is verified yet, slice by slice where the list is long ([DEC-112](decisions.md#dec-112-a-long-list-is-built-in-slices)). An ongoing project changes the spec and builds what `status` lists. An existing project without a spec gets a first spec that states what is as what should be, drawn with the owner from every artifact: code, tests, documentation, scripts, pipelines and configuration ([DEC-105](decisions.md#dec-105-a-first-spec-of-an-existing-project-states-what-is-as-what-should-be)). It is finished when a build would change nothing: `/markitect-review --all` verifies every Definition against the project, the architect corrects the spec where it misread the project, and the two repeat until `status` lists only what waits for the owner. Those are the places where the project contradicts itself, which stay `fail` until the owner says which side holds, and behaviour the reviewer found that the spec leaves out, a `spec-problem` until the owner says whether it stays free; nothing is built before that. What looks like an accident the spec leaves unstated, and the architect asks the owner. The spec does not transcribe the project: the binding part is the contract callers rely on. Once the owner has accepted the spec, a confirmed defect stays a defect against it, and `/markitect-build` repairs it: rewriting intent to get an empty `status` would defeat adoption.

## 3. The tools

### Commands on the spec

None of these starts an agent or uses Git. `--repo DIR` names a folder of the project, whose root is the nearest folder with `.markitect/manifest.yaml` (default: the current folder), and `--json` prints JSON for scripts.

| Command | Does |
|---|---|
| `install` | Writes the personal skill, once per machine ([§9](#9-the-harness)). Optional: `init` says the same and gives a project its own skills |
| `init` | Sets up a project: `.markitect/`, the first page of the spec, the harness, `.markitect/.gitattributes`, a line in `.gitignore` for Claude Code's worktrees, and `AGENTS.md` and `CLAUDE.md` if they are missing. An empty folder is enough. It makes no repository and commits nothing, and sets `worktree.baseRef` in the project's settings when they name no base. Run again, it refreshes the harness and never touches spec pages |
| `tidy` | Brings the lock in line with the manifest, as `go mod tidy` does, and first names in the manifest the version of a standard Library this binary ships, where it names another. The lock holds a fingerprint of each Library, as `go.sum` does for modules; `check` only reads it, refuses a Library that no longer matches and says to run `tidy` |
| `check` | Compiles the project and fails on any error ([below](#what-check-refuses)). `--spec` looks only at the spec itself |
| `list [--deps]` | The Packages with their Definitions. With `--deps`, what each Package depends on and the links behind it, with its coupling, abstractness and distance |
| `doc TARGET` | A Definition with its text, what it links to and what links to it, the files that realize it and its record; with its parts and the parts of other things it links; or a Package with the text of its anchor and its public Definitions apart from its internal ones. `doc Root` shows Root |
| `vet [--strict]` | Measures the spec's design ([§4](#4-is-the-spec-good)). It warns, and exits 1 only with `--strict` |
| `update` | Installs the newest release over the binary, then lets the new binary bring what an earlier build wrote in line: the personal skill if there is one, and in a project the harness and the lock ([keep it current](guides/project-workflow.md#8-keep-it-current)). It commits nothing and says to read the lock before committing it. `--check` changes nothing and exits 1 if anything is out of date; `--files` leaves the binary alone; `--force` replaces a development build |
| `version` | The build, and whether the personal skill and the project match it |
| `config KEY`, `config [--user] KEY VALUE` | Reads the value in force, or sets one of the harness configuration ([§9](#9-the-harness)): the agents' model and effort per role, the strategy per skill and custom workflows, in the project's `.markitect/harness.yaml` or with `--user` in the user's; it rewrites the agents' files. `--list` shows each value and where it comes from, `--unset KEY` removes one |
| `licenses` | The third-party notices |

**Output and exit codes** follow Go's tools. A diagnostic is one line, `file:line: code: message`; `check` prints only diagnostics and one summary line, and `vet` only diagnostics and one line of notes. With `--json`, `check`, `vet`, `list`, `doc`, `status`, `mark` and `config --list` print one document that starts with `format_version` and `kind`. Exit 0 means all is well, 1 that the command found something, and 2 that it could not run; a note never changes the exit code. [The spec language guide](guides/spec-language.md#diagnostics-json-and-exit-codes) owns the details.

**`update`** does what `claude update` does ([DEC-095](decisions.md#dec-095-releases-a-plugin-and-a-binary-that-updates-itself)). It reads the newest tag from the redirect of GitHub's releases page, downloads the binary for the system, checks it against the checksums file of that release and replaces the running executable: by renaming over it on Linux and macOS, and on Windows by moving the old file aside first. The new binary then finishes the update, since only it knows the files it ships. This is the only place where Markitect uses the network, and only when the owner runs it; without a network it says so and still refreshes the files. A development build older than the newest release is not replaced unless `--force` says so. A binary the plugin manages is left to the plugin. Commands that read a project print one note when its skills, agents and hooks are older than the binary.

### What `check` refuses

`check` passes or fails, with no warnings: a project either compiles or it doesn't. Its errors come in two groups, and it prints them apart. One case passes: when the registry lists no file and the only errors are Definitions nothing realizes, it says that the spec compiles and nothing is built yet. `status` makes no such exception.

| Group | Errors | Who settles them |
|---|---|---|
| **The spec** | A Kind or link that does not resolve, a Package cycle, a link into a child's Definitions or to an internal Definition from outside, a Library that does not match the lock | The owner, in the spec |
| **The realization** | A file neither listed nor ignored, a registry entry for a Definition or file that no longer exists, and a Definition that nothing links to and no file realizes | The builder, in the work |

So `check` goes red the moment the owner deletes a Definition or adds one nothing uses yet, and stays red until the work has realized the change: spec and code don't match yet. `--spec` answers the narrower question "is the spec itself valid?", which is what a session on the spec asks. `status` gives no list while the spec has errors; errors in the realization are on its list.

### How `status` works

Like `go test`, which does not run a test again when nothing it depends on changed, Markitect keeps for each item, a Definition with its parts, the state at which a reviewer last verified it ([DEC-099](decisions.md#dec-099-a-record-of-what-was-verified), [the inputs](../internal/run/README.md#the-inputs)). That state is the set of everything the verification depended on, its **inputs**, each by its hash: the Definition's own text and that of each of its parts; their Kinds and the Definitions they link to, a Library Definition by its Library's digest in the lock, so that a newer binary changes nothing; the files its registry rows name; what binds it without a link, Package by Package; and the files the reviewer gave as evidence. **What is to verify** is every Definition with a changed input or no record, computed from the folder and the record alone.

| Distance | Reached | On the list |
|---|---|---|
| 0 | Definitions that changed, Definitions whose files or evidence changed, and Definitions a registry row gained or lost | Yes |
| 1 | Definitions that link to a changed one, are of a changed Kind, or are bound by a changed one | Yes |
| 2 and more | Everything further along the links | No |

**What binds is an input of what it binds** ([DEC-113](decisions.md#dec-113-what-binds-is-an-input-of-what-it-binds)). A changed Rule, Decision or Constraint reaches every Definition of its Package and of the Packages below it that a file realizes, and `status` names it on each of them: `changed: bound:architecture/rules/persistence`. The record keeps what bound each item when it was verified, so the name stays after the Rule itself is verified again, until each item it binds is verified against it. A Rule of Root binds everything that is built, so its change lists everything; a Rule that holds for one area lives in that area's Package. What no file realizes, such as a goal, and a Kind are bound by nothing. A Library counts as one, so a change of one Kind of a committed Library lists the Definitions of all its Kinds: more, never less. Three more kinds of item stay on the list until they are verified again: a Definition recorded `fail` or `spec-problem`, a Definition gone from the spec, with the files that realized it, and an error in the realization.

`status` doesn't follow the code's own imports ([roadmap](roadmap.md#later)). A full review now and then, `/markitect-review --all`, is the safety net. On the change steps of Makerspace, a study project, one step of links reached 33 of the 36 existing files that truly changed, and deeper reach 35 ([measurement](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/impact-reach-20261103.md)).

### Commands of the record

These are for whoever drives the agents, and for CI. They start no agent, keep nothing running, steer nothing and use no Git. [The record](../internal/run/README.md) owns how they behave.

| Command | Called by | Does |
|---|---|---|
| `markitect status` | The builder, the reviewer, the skills, the owner and CI | What is to verify, with which inputs changed, where to look and each item's fingerprint. `--all` lists every Definition, and `--package P` only the items of one Package, for a strand of a parallel run. `--slices` prints the slices a build of the list goes in, and `--slice` lists one. Exit 1 when it lists something; notes, such as a `skip` or an outdated harness, never change the exit code |
| `markitect mark` | The reviewer | Records `ok`, `fail`, `skip` or `spec-problem` on one Definition at the fingerprint `status` printed, as in `markitect mark members/limit@3f9a1c ok -e src/loans.go:42 --cases 4 --covered 4`, with its evidence and the reviewer's counts, or why ([§6](#6-the-record)). An `ok` and a `skip` carry the reviewer's counts, `--cases N --covered M` |
| `markitect hook` | Hooks only | The check of [§9](#9-the-harness) |

**The folder.** Every command reads the project folder by walking it, without what the project's `.gitignore` files exclude, read as plain text ([the folder](../internal/run/README.md#the-folder)). So ignored build output does not count, and a folder needs no repository. Files that Markitect's own ignore file lists are walked like any other; they need no registry row and are no input.

**The ignore file** is `.markitect/ignore`, written like a `.gitignore`: one pattern per line, `#` for a comment, and no `!`. The tool accounts for what `init` installs by itself, so a new project has no ignore file.

**There are no required checks** ([DEC-099](decisions.md#dec-099-a-record-of-what-was-verified)). A project that wants tests states them in the spec, with the command that runs them, and the reviewer runs them as evidence. So no proof in the work comes from outside an agent, apart from `check` and the record's inputs. If a Definition is verified that a test would have caught, the checks come back. The agents' `model` and `effort` are in their agent files, written from the harness configuration.

## 4. Is the spec good?

A spec is judged like code, so it gets the same kind of analysis code gets. `check` is the compiler: is it valid? `vet`, named after Go's, is the static analyzer: is it well designed? It warns or notes, never refuses, since granularity stays the author's choice, and its thresholds are provisional ([DEC-102](decisions.md#dec-102-what-vet-measures)).

| Measure | Code analogy | `vet` |
|---|---|---|
| Efferent and afferent coupling, instability, per Package | Clean Architecture | Warns: `vet.coupling`, `vet.unstable_dependency` |
| Size of a Definition and a Package | Long functions, large modules | Warns: `vet.definition_size`, `vet.package_size`; notes long lists of statements, `vet.statements` |
| Packages with no paths, or no Definitions and one child | Empty namespaces | Warns: `vet.no_paths`, `vet.thin_package` |
| Fan-in of a Definition, Root included | God class, `utils` file | Warns: `vet.hub` |
| A Definition named in prose without a link | An undeclared dependency | Notes `vet.unlinked_mention`; the auditor tells missing links from ordinary words |
| A Definition all of whose users lie in one Package below it | Misplaced code | Notes `vet.placement` |
| Change hotspots: revisions between verdicts times fan-in | Churn | Notes `vet.hotspot`; the record counts revisions, since the tool reads no Git history |
| Abstractness and distance from the main sequence | Martin's metrics | Shown by `list --deps`, no warning |
| Size against what the evidence demonstrates | CRAP | Notes `vet.risk`, from the reviewer's counts on `mark` |
| The spec's dependencies against the code's imports | Architecture tests | Not yet |

**Package cycles are a compile error**, as in Go. [The spec language guide](guides/spec-language.md#vet-warnings-and-notes) gives every code and threshold, and [what makes a good spec](guides/good-spec.md) says what each measure is for.

**Why no central page of values.** On the Makerspace specs, one page, `values`, with thirteen unrelated value formats, was linked by 60 Definitions, and by 268 on a project five times as large: a `utils` file. Split into one Definition per format, a change to one format lists between 2 and 52 Definitions instead of 61 ([measurement](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/spec-design-measures-20261107.md)). So a value rule of the project's own is a small Definition of its own, where it is used.

**What analysis can't say:** whether the spec is right. No threshold has been checked against outcomes yet, so a clean report doesn't show that a spec leads to better work.

## 5. What build does

The owner architects the project until the spec looks right, then uses `/markitect-build` in their own Claude Code session. The tool computes, checks and records; the skill, the agents and the session do the rest, and nothing steers them. [The project workflow](guides/project-workflow.md#7-build-and-review) says how to use it, and [the record](../internal/run/README.md) owns the rules.

1. **Start the builder.** The skill is a plain prompt: the owner's session starts the `markitect-builder` agent in a worktree of its own, through Claude Code's worktree isolation ([DEC-100](decisions.md#dec-100-skills-are-named-after-the-activity-agents-after-the-role)). The builder starts with fresh context, on the last commit of the owner's branch, and holds its task in its agent file. A worktree holds no uncommitted change, so the skill asks the owner to commit first.
2. **See what is to verify.** The builder runs `markitect status`. An error in the spec gives no list, and the builder says so.
3. **Implement.** The builder makes the project match the spec for what the list holds and keeps the registry current. It does not change the spec, and the hook refuses its edits under `.markitect/` except the registry pages. A gap with no effect at the project's boundary is its own to decide. Where the spec contradicts itself or leaves open behaviour at the boundary, it builds nothing for that Definition and tells the reviewer what it found. Where the machine lacks a program or a service the work needs, it stops and says so ([OQ-013](decisions.md#open-questions)).
4. **Review.** The builder starts the `markitect-reviewer` agent as its own subagent, the only agent the hook lets it start, and waits, so it keeps its context. The reviewer works in the builder's worktree, starts with fresh context, has no tool to edit files and starts no further agents. It runs `status`, reads each Definition, the Definitions it links to and the code, runs the project's tests where they bear on an item, and records a verdict with `markitect mark`. An `ok` covers the Rules of the Definition's Package and those above it too, so a change that breaks an unchanged Rule fails. It treats what the builder tells it as claims to check, and judges a reported spec problem on its own reading.
5. **Repeat.** The builder runs `status` again and works on what it lists, until it lists nothing or only `spec-problem`s for the owner. Each verdict is bound to the inputs the reviewer read, so a repair puts back on the list only what it touched. There is no limit on rounds, but the builder stops when three rounds in a row leave the list no shorter than it has been, so a list that swings down and up again ends too. What the builder notices beside its task it tells the reviewer, which records it as `fail` or `spec-problem`: the record is the one store of findings.
6. **Bring it back.** When the builder has ended, the owner's session runs `status` in the worktree and commits the work there together with `.markitect/review.sum`. If a Definition is listed there as changed or without a record after a sequential build, the builder ended with something no reviewer has seen, such as an edit after its last review, and the session enters that worktree and has the reviewer verify what is listed once more. When `status` is empty there, or says that only `spec-problem`s are left, it merges that branch into the owner's branch and removes the worktree: a `spec-problem` waits for the owner, no builder settles it, and it stays on the list of the owner's branch. Otherwise it asks the owner whether to merge the work as it stands. It pushes nothing. In a folder that is not a Git repository the builder works in the folder itself, and the session commits nothing.

**On a long list,** the skill's strategy may run the same steps in parallel, one builder and its reviewer per Package ([§10](#10-drivers)).

**Done** is an empty `status`: the project compiles and every Definition is verified at its current inputs, whatever happened in between. A file edited by hand, a commit made around the agents or a change on a merged branch changes the inputs it touches, and those Definitions are on the list again.

**Git is the driver's** ([DEC-097](decisions.md#dec-097-markitect-uses-no-git)). A branch that moved, a merge conflict or a pull request is ordinary Git, by the session or the owner, and the next `status` judges the folder that results. What the owner changes meanwhile meets the work at the merge: a changed spec puts its Definitions back on the list, and a conflict stops the merge.

**When the builder ends early,** nothing is lost: the list is computed from the folder and the record, so `/markitect-build` started again, or `/markitect-review`, takes up what `status` lists.

**A long list is built in slices** ([DEC-112](decisions.md#dec-112-a-long-list-is-built-in-slices)). One builder with its reviewer has been shown on lists of up to about 64 items, and the first build of a described project lists more. So the session asks `markitect status --slices`, which cuts a list of more than 40 items by Package in the order of the dependencies, what others rely on first. The session takes the slices one after the other, each as the steps above: a fresh builder with its reviewer in a worktree of its own, then the commit and, when the slice is settled, the merge into the owner's branch, from which the next builder starts. The command of a slice also lists the Packages before its own, so an item that a slice puts back on the list there is its work. The last slice holds what is verified on the whole project: what no file realizes, such as a goal or what the project leaves out, and what a Kind declares `last`, such as a quality. An item of a slice is judged on the project as it stands: a Rule holds for what exists so far, and what a later slice builds answers for the Rules above it. A slice that leaves an item is merged all the same when it shortened its list, and the next slice takes the item up; a slice that settled nothing stops the build, and the session asks the owner. A build that stops midway has lost nothing: what is settled is on the owner's branch, and `/markitect-build` cuts what is left again.

**Why the owner's own session.** Markitect is a way of agentic coding, not a platform with machinery of its own, so the agents are ordinary Claude Code agents started by the owner's session. The cost: the owner's session is busy until the work ends, the agents stop if that session closes, and they work under that session's permission mode, settings, plugins and memory, so they may ask for permission and differ from one person to the next. What it keeps: fresh context for the builder and the reviewer, which tests whether the spec alone is enough.

## 6. The record

`.markitect/review.sum` is the record of what was verified, committed with the project like `go.sum` ([the record](../internal/run/README.md#the-record-file)). It holds one line per item, a Definition with its parts ([DEC-111](decisions.md#dec-111-a-thing-with-parts-is-built-and-verified-as-one)), sorted, each a JSON object: the verdict, the hash of each input ([§3](#how-status-works)), the evidence the reviewer gave, why, with an `ok` or a `skip` the reviewer's counts of cases, and the number of revisions. After the lines come the directories they name: for a Package that something binds, each binding Definition with its hash, so that `status` can say later which of them changed ([DEC-113](decisions.md#dec-113-what-binds-is-an-input-of-what-it-binds)).

| Verdict | Means |
|---|---|
| `ok` | The Definition is implemented, and the Rules of its Package and those above it held for it when it was verified, as the evidence shows |
| `fail` | It is not; the line says why |
| `skip` | Verified as far as the project can show, with the reason. A note, which never changes `status`'s exit code |
| `spec-problem` | The spec contradicts itself or leaves open behaviour at the project's boundary, and only the owner can settle it |

**A verdict is bound to what the reviewer read.** `status` prints each item as `DEFINITION@FINGERPRINT`, the fingerprint being the start of the hash of every input but the evidence, and `mark` refuses when the inputs changed since: a builder editing a file beside the reviewer, or the reviewer's own test run changing one. The evidence, `path` or `path:line`, must be files of the folder, and their hashes become inputs, so a weakened test that served as evidence puts its Definition back on the list. Go does the same: it does not cache a result whose inputs changed while the test ran.

**Revisions** count how often a Definition's own text changed between verdicts, as the basis for `vet.hotspot` without Git history. A first verdict counts none, and a change of a link, a file or the evidence counts none.

**How it is written.** `mark` writes under a short lock in the user's cache folder, as one whole file, so parallel reviewers, for example one per Package, do not lose lines. A gone Definition stays on the list with the files that realized it until a reviewer finds them removed or with a new basis and records `ok`, which removes its line.

**How it merges.** `init` writes `.markitect/.gitattributes` with `merge=union` for the record, so Git keeps both sides. Of two lines for one Definition, `status` takes the one whose inputs match the folder; if both match with different verdicts, it lists the Definition as a conflict to verify. The directories of both sides are kept. The next `mark` writes the file clean and drops the directories no line names.

**What it is:** a record, not a proof. A line written by hand shows in the diff, and the hook keeps agents from writing one. It holds hashes, not text: what a changed Definition said before comes from Git. A CI job runs `markitect status`, and any item fails the build.

## 7. How sure we are

The tool can't stop a determined agent that runs as the user on the user's machine. This concept guards against forgetting and shortcuts, which is what has been seen, and against deliberate bypass only by making it visible.

| What the owner wants | What secures it | How firm |
|---|---|---|
| The spec compiles before it is verified | `status` gives no list and `mark` records nothing while the spec has errors | Firm |
| Every Definition is verified at the state it is in | The record's inputs, and `mark` binding a verdict to the fingerprint the reviewer read | Firm for one step of links, the registry and what binds a Definition: a changed Rule lists what it binds, by name; deeper reach and the code's imports are not followed |
| What is committed is what was verified | The session commits the work with the record; the tool commits nothing | Seen, not prevented: `status` on any checkout lists what differs from the record, and a CI check can refuse it |
| The work doesn't stop to wait for someone | Nothing: the agents work under the owner's session's permission mode. In early trials in `auto` mode, five of six runs had no denial ([trials](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/lean-trials-20261107.md#what-the-flow-showed)) | Weak by choice: the owner is there to answer. How often manual mode asks is not known |
| The work doesn't mix with the owner's own | The builder works in a worktree of its own, and its work comes back by a merge | Good: a conflict stops the merge. What the owner did not commit is not built. In a folder without Git the work shares the owner's folder |
| The spec doesn't change during the work | The hook refuses a write under `.markitect/` by any subagent but the architect, except the registry pages; only the owner's session starts the architect | Good for subagents, not proof: it reads the tool call, and a shell command can still write. Not prevented for the owner's session or for people: a changed Definition goes back on the list |
| The agent doesn't review itself | The hook lets only the reviewer run `markitect mark`, and lets the builder start only the reviewer | Good, not proof: the hook reads the command's text and the agent's name |
| The reviewer judges for itself | Its agent file says to take the list from `status` and treat the builder's message as claims to check. What that message passes on as the user's limits it keeps to, and an item they keep it from verifying it leaves unrecorded, so the item stays on the list | Weak: the builder writes that message. Reviews given a maker's claims did no worse on planted bugs ([17 of 18 blind, 18 of 18 with claims](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/k-checker-test-20261103.md)) |
| Nothing goes to a remote | The tool has no Git, and the skills push nothing. A routine the owner set up lands by a push when its source branch tracks a remote, and a cloud routine that cannot land pushes its own branch so that its work is not lost | Catches ordinary use only |
| The reviewer really read the code | Evidence checked for existence in the folder, and hashed | Not provable |
| The code is right | The reviewer and the project's tests | Not guaranteed |
| The work has a limit | No limit on rounds; the builder stops when three rounds in a row leave the list no shorter than it has been, and the owner can stop it | Prompt text: unbounded in time and calls. There is no spending limit |

**Anyone who wants more** can run `markitect status`, `markitect check` and the project's tests where the agent can't reach them: on a server of their own, in CI or in a hook on a remote. Markitect depends on none of these.

**What Markitect does not do:** prevent a deliberate bypass; commit by itself, so what is committed matches what was verified only if the driver does it right; isolate the work from the user's machine, so the work must not read untrusted input; review a clean copy, since the reviewer reads the folder as it stands, ignored leftovers included; refuse a changed file the ignore file lists; or keep the old text of a changed Definition.

## 8. Other skills

A skill names which agent the owner's session starts and on what task; the agents hold their tasks in their own files ([DEC-100](decisions.md#dec-100-skills-are-named-after-the-activity-agents-after-the-role)). The tool's commands run anywhere, from a chat, a terminal or a schedule; the agents need a driver, which today is the skills in a Claude Code session.

| Skill | Started by | Does |
|---|---|---|
| `markitect-architect` | The owner or Claude | Architects the project with the owner, in their own session. It sees whether the folder is an empty project, a project without a spec or an existing spec, and starts the spec by asking what only the owner can know and proposing the rest, with one audit before it hands the spec over, draws it from the project and has a reviewer verify it against the project, or changes it. The session writes the spec, since it holds the conversation; a large draft, such as a first spec drawn from a large project, it hands to the `markitect-architect` agent, which hands its questions back. It links the real unlinked mentions that `vet` notes. What the owner cannot answer at once, the session keeps in `.markitect/questions.md`, and `status` says while that file is there |
| `/markitect-build` | The owner | [§5](#5-what-build-does) |
| `/markitect-review` | The owner or Claude | The `markitect-reviewer` agent verifies what `status` lists, or with `--all` every Definition, records each verdict and reports what failed and what is a `spec-problem`. With the `parallel` strategy it starts one reviewer per Package ([§10](#10-drivers)). The session commits the record |
| `/markitect-cleanup` | The owner | The builder, in a worktree of its own, refactors without changing behaviour, and the reviewer verifies again what that put back on the list. The work comes back when it leaves nothing worse |
| `/markitect-bughunt` | The owner | The reviewer hunts beyond the list and records each bug as `fail`, or as `spec-problem` where the spec does not cover it; the builder repairs, and the reviewer verifies again. The work comes back when it leaves nothing worse |
| `/markitect-audit` | The owner or Claude | The `markitect-auditor` agent reads the spec fresh for contradictions, among them a case that an Operation or a Reaction and what binds it decide differently, gaps, unclear and duplicated statements, triages the unlinked mentions `vet` notes, and reports to the owner. Nothing is recorded or committed |
| `/markitect-schedule` | The owner | Sets up cleanup, bughunt and `review --all` as routines ([§12](#12-schedules-and-continuous-work)) |
| `/markitect-config` | The owner or Claude | Takes a request on the agents' model and effort, a skill's strategy or a custom workflow in plain words, asks whether it is for this project or all of the user's, and runs `markitect config` |

Only the owner starts the skills that change code or set up routines: their files set `disable-model-invocation`.

## 9. The harness

For Claude Code, `markitect init` writes these project files, so they are versioned with the project, and the tool accounts for them itself.

| File | Holds |
|---|---|
| `.claude/skills/markitect-architect/` | The architect skill, with `reference.md` and `examples.md` |
| `.claude/skills/markitect-build/SKILL.md`, `markitect-cleanup`, `markitect-bughunt` | Plain prompts: by the skill's strategy, start the `markitect-builder` agent in a worktree of its own on its task, or the parallel workflow from a worktree of the session's own, and when it has ended commit the work there and merge it back. They inject no command, allow `markitect status` and reading the strategy without a prompt, and set `disable-model-invocation: true` |
| `.claude/skills/markitect-review/SKILL.md`, `markitect-audit` | Start the `markitect-reviewer` or the `markitect-auditor` agent, or by the parallel strategy one per Package |
| `.claude/skills/markitect-config/SKILL.md` | The configuration skill ([§8](#8-other-skills)) |
| `.claude/workflows/markitect-parallel.js` | The parallel strategy, a saved Claude Code workflow ([§10](#10-drivers)) |
| `.claude/skills/markitect-schedule/` | The routine setup, and `routine.md`, which every scheduled run reads when it starts |
| `.claude/agents/markitect-builder.md` | The builder's three tasks, build, clean up and hunt bugs, and how it works. Tools Read, Edit, Write, Glob, Grep, Bash and `Agent(markitect-reviewer)`; model `sonnet`, effort `high`, as the reviewer; the architect and the auditor have `opus` and `medium` |
| `.claude/agents/markitect-reviewer.md` | The reviewer's two tasks, verify and hunt bugs, and the verdict words. No edit or agent tools |
| `.claude/agents/markitect-architect.md` | Write a large part of the spec as the architect skill says, only under `.markitect/`, and hand back every question and what it wrote that the owner's answers and the project do not state. No agent tool |
| `.claude/agents/markitect-auditor.md` | Read the spec fresh and report what is wrong with it. No edit or agent tools |
| `.claude/settings.json` | The hooks, below, and `worktree.baseRef: "head"` unless the settings name a base, added to whatever settings the project already has |
| `.markitect/.gitattributes` | `review.sum merge=union` |
| `.markitect/harness.yaml` | The project's harness configuration, below. `markitect config` makes it when the owner sets a value |
| `AGENTS.md`, `CLAUDE.md` | What kind of project this is, for any session: the spec is the authority, changes start there, and `markitect` is on the path. `CLAUDE.md` holds only `@AGENTS.md`. They hold no process, since the agents read them too. Written only if missing |

**The agents' settings** come from their files, whose model and effort come from the harness configuration ([DEC-103](decisions.md#dec-103-claude-chooses-the-parallelism-per-run-through-a-shipped-workflow)): one file format, `harness.yaml`, at two levels, the user's `~/.markitect/harness.yaml`, not committed, and the project's `.markitect/harness.yaml`, committed. Key by key the project beats the user, and the user beats the built-in values: `sonnet` at effort `high` for the builder and the reviewer, and `opus` at effort `medium` for the architect and the auditor. The spec is little text that everything else is built from, so the roles that work on it think on the larger model, and the roles that work on the code build and verify from it on the smaller one. These values are a reasoned starting point, not a measured one. It holds the model and effort per role, the strategy of each skill and the custom workflows. `init` and `update` write the agents' front matter from it, and `markitect config` rewrites them. A user's value reaches the committed agent files when that user runs these, since Claude Code has no agent scope that is not committed and beats the project's; a team that wants the same agents for everyone sets them in the project's file. Everything else is the owner's session: its permission mode, settings, plugins and memory.

**The worktree.** Claude Code branches a subagent's worktree from the repository's default branch unless `worktree.baseRef` is `"head"`, so `init` and `update` set it when the project's settings name no base; a base the owner chose stays. Claude Code keeps its worktrees under `.claude/worktrees/`, and the tool accounts for that folder itself. A reviewer the builder starts works in the builder's worktree.

**The hook** guards the record, the spec and what steers the agents, not the process. `markitect hook pretool`, in the project's settings, runs before a command of the Bash or the PowerShell tool that calls `markitect mark`, before every tool that writes a file, and before every tool that starts an agent or a workflow. Hooks in project settings run inside subagents too, and their input names the agent. The hook calls `markitect` only where its shell finds one, which is a binary on the `PATH`, since a hook does not see the plugin's `bin/`; with the plugin alone it does nothing, and the plugin's hooks guard. Where a session has both a binary and the plugin, the guard runs twice and says the same. Where a hook finds no `markitect`, or the plugin's launcher cannot fetch its binary, the call goes through: the guard never stops work because it could not run. It holds the four roles' rights for subagents only:

| Subagent | Writes | Records | Starts |
|---|---|---|---|
| `markitect-builder` | Code and the registry pages | No | Only `markitect-reviewer` |
| `markitect-reviewer` | Nothing | Yes, the only one | Nothing |
| `markitect-architect` | The spec, with the manifest, the lock and the Libraries, the registry pages and the ignore file; not the questions for the owner, which the owner's session keeps | No | Nothing |
| `markitect-auditor` | Nothing | No | Nothing |
| Any other | As the builder | No | Any agent but the builder and the architect; no workflow |

- **No subagent writes `.markitect/review.sum`,** which only `mark` writes, and none but the architect writes the rest of `.markitect/` except the registry pages. The owner's own session, where the owner architects, is not a subagent and stays free, but does not record either.
- **No subagent writes what steers the agents:** the project's Claude Code settings with the hook scripts and rules beside them (`.claude/hooks/`, `.claude/rules/`), Markitect's skills, agents and workflows, the harness configuration, and `AGENTS.md`, `CLAUDE.md` and `CLAUDE.local.md`. Nor does any write `.markitect/.gitattributes`, which `init` writes. The builder's work comes back without anyone reading its diff, so a builder must not be able to drop the hook on its way.
- **Only the owner's session starts the builder and the architect, or a workflow.** Claude Code ignores the agent types listed in a subagent's own tools, so the hook holds this. A workflow the owner's session starts may start the four roles, and the hook holds their rights inside it as anywhere; so it does in the user's own skills in `.claude/skills/`, which Markitect leaves alone.

The hook reads tool calls, so a command hidden in a script, or one that names `markitect` by another spelling, still gets through; the project's hook starts only for what Claude Code's rule matches, which leaves out a `markitect` named by its path. It guards against mistakes, not against intent.

**The personal skill.** A session that runs `init` started before the project's files existed, and Claude Code doesn't watch a skills folder that wasn't there when the session started. So help and `init` say what Markitect is, and `markitect install` writes a personal skill, `~/.claude/skills/markitect/SKILL.md`, which reaches a session in any folder. `init` never writes to the home folder. The skills and agents call `markitect` by name, so `version`, `init`, `install` and `update` warn when the `PATH` finds no `markitect` or another one.

**The plugin.** `plugin/` is the Claude Code plugin `markitect`, installed as `markitect@glacius-labs` from the marketplace repository [Claude-Plugins](https://github.com/Glacius-Labs/Claude-Plugins), whose entry pins it to the tag of a release. It carries the personal skill as `markitect:getting-started`, a launcher, `bin/markitect`, with `bin/markitect.cmd` beside it, and five hooks. Claude Code puts `bin/` on the `PATH` of its shell, but on Windows only its PowerShell tool gets it. So a session-start hook, which Claude Code waits for, appends a line that puts `bin/` on the `PATH` to the file `CLAUDE_ENV_FILE` names, which Claude Code runs before every command of the Bash tool, the agents' included; where `bin/` is on the `PATH` already, the line does nothing. `markitect.cmd` runs the launcher from PowerShell or cmd with the bash of Git for Windows. The launcher downloads the binary of the release with the plugin's version into the plugin's data folder, checks it against the release's checksums and runs it; `update` then leaves the binary to the plugin. Another session-start hook fetches the binary in the background, outside the shell's sandbox, but only in a project with a `.markitect/` folder. The other three hooks run `markitect hook pretool` through the launcher, because the project's hooks run in a shell that does not see the plugin's `bin/` and so leave the guard to them; the two that guard writes and agent starts act only in a project with a `.markitect/` folder, and a launcher that cannot run reports an error and lets the call through. The plugin does not replace `init`: the project's skills, agents and hooks still come from `markitect init`, since Claude Code ignores hooks and permission modes in plugin agents.

## 10. Drivers

A driver is whatever starts the agents, decides how often and how long, and makes the Git steps ([DEC-096](decisions.md#dec-096-the-tool-computes-and-checks-a-driver-acts)). **A driver is harness files and nothing else**; there is no code interface to implement. **It may change** the prompts, agents, skills, settings, limits and every Git step. **It may not change** the tool, the record's inputs or what the hook refuses. A person can drive the work too, with the same commands.

**Claude decides the parallelism per run** ([DEC-103](decisions.md#dec-103-claude-chooses-the-parallelism-per-run-through-a-shipped-workflow)). Each skill that starts agents runs by a **strategy**, set per skill in the harness configuration ([§9](#9-the-harness)):

- **`auto`,** the default: Claude estimates the work and chooses. Parallel when `status` lists more than about 30 items in at least two Packages; cleanup, bughunt and audit count the spec's Definitions instead, and build, cleanup and bughunt need a Git repository for it. Below that size a parallel run's fixed cost buys little: one builder has settled change steps of 21 to 64 items in one context ([trials](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/lean-trials-20261107.md)). Until the parallel strategy has proven itself on a long list, `auto` chooses sequential; so far it has passed two real runs on a project of 6 Definitions ([record](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/parallel-strategy-20261108.md)).
- **`sequential`:** one builder, reviewer or auditor at a time, as [§5](#5-what-build-does) describes; a build of a long list goes slice by slice.
- **`parallel`:** the shipped workflow `.claude/workflows/markitect-parallel.js`. It plans strands per Package, in waves along the dependencies `list --deps` names, what is depended on first. Builders run in parallel, at most 8 at once, each in a worktree of its own, where it commits its work; a strand asks `status --package` for its items, changes only its Package's files, and shared files, which Root owns, go to Root's strand, last and alone. Claude Code gives a workflow's agents no tool to start an agent, and lets an agent in a worktree run Git only on its own, so the rest of a strand is steps of the script: after each batch a plain agent merges the strands' branches by name into the run's branch, a reviewer per strand verifies its Package there, and a plain agent commits the verdicts and runs `status` again, since a workflow script has no shell. It stops when `status` lists nothing a builder can settle, or three rounds in a row leave the list no shorter than it has been, and reports what remains. Review runs one reviewer per Package; bughunt has one reviewer per Package hunt before the build rounds; cleanup runs one round over every Package; audit runs one auditor per Package and one that looks for contradictions across Packages. Before a parallel build, cleanup or bughunt the session enters a worktree of its own, since Claude Code branches each builder's worktree from the session's `HEAD`: a later wave then starts from what the earlier ones merged, and the owner's branch is untouched until the session merges back by §5's rules. The owner architects in another session meanwhile.
- **A custom workflow:** a saved Claude Code workflow, named in `workflows.NAME`, that keeps the same contract. It takes the mode, the branch the work comes back to, the focus and, for a review, whether to verify every Definition, reads `markitect status --json`, keeps to the four roles, with a plain agent at most for status and Git, and stops by the same rule.

Claude Code asks before each workflow run unless the owner answered "don't ask again" for it.

## 11. Providers

Markitect supports Claude Code only. A provider needs subagents with their own agent files, and a hook before a tool call that names the agent; another provider comes once Claude's version is reliable, and the tool does not change for it.

No token is needed: sessions run on the user's own stored login in the unmodified program, and each uses the user's subscription quota. Markitect pins no version of Claude Code, so a change of its defaults can arrive unannounced. Markitect starts no session and touches no credentials, so each user simply runs Claude Code on their own login, with Markitect as a tool it calls.

There is no app. If one comes, it works over the same commands.

## 12. Schedules and continuous work

The loop runs outside Markitect, as a scheduled job or routine that calls `markitect`, and there is no daemon in the product ([DEC-084](decisions.md#dec-084-continuous-work-runs-outside-the-tool-and-autonomy-grows-in-steps)). The tool sets no budget and counts no rounds; a budget per task or per day belongs to the job and the driver.

The cheapest scheduled check needs no agent: `markitect status` in CI or a job fails on any item, so a change made around the agents, a merge or a hand edit is seen.

**Routines** act on it. The harness ships one routine file for three: cleanup, bughunt and `review --all`. A scheduled prompt is one line that names the routine and points at that file, which the run reads when it starts, so `update` reaches a routine that is already scheduled. `/markitect-schedule` sets them up with the owner through Claude Code's own scheduling, a scheduled task of the desktop app on the owner's machine or a cloud routine on a fresh clone; Markitect schedules nothing itself.

- **A branch of its own.** A run works in a worktree or clone of its own, from the newest commit of the source branch, the remote's when the branch tracks one, so that nothing unpushed goes out.
- **It lands only when three things hold.** It leaves nothing worse: `status` lists no Definition that it does not also list on the source branch as it now stands. The project's tests pass. And the change is the agents' work alone: it touches nothing under `.markitect/` but the record and the registry pages, and no file that steers the agents, since the run's own session is no subagent and the hook does not hold it. If the source branch moved, the run merges it first and has the reviewer verify again what the merge put on the list or the builder left unverified. It lands as a fast-forward, by a push when the source branch tracks a remote, otherwise by moving the local branch, which Git refuses while it is checked out in a folder.
- **Otherwise it leaves its branch** and says why; a cloud routine, whose clone ends with the run, pushes that branch so that the work is not lost.
- **Each run ends with a short note:** what landed, what is open, and which spec-problems wait for the owner.

So a review that records a new `fail` does not land: its branch holds the record, and its note names the item. Routines take no strategy: nobody is there to answer the prompt with which Claude Code asks before a workflow starts. Two limits stay: the machine must be on and signed in, so a server without a stored login is not covered yet, and external signals need isolation, since issue text can hold instructions aimed at the agent and a native agent has the user's rights. Work that reads outside input needs an isolated machine with limited rights.

## 13. What is shown and what is not

**Shown in real runs, on small projects.** Agents started by the owner's own session made three small Makerspace changes: the skill's prompt makes the session start the builder, the builder starts the reviewer as its own subagent and waits for it, the hook fires inside subagents, and a planted bug and a planted contradiction were caught ([trials](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/lean-trials-20261107.md)). Those trials ran an earlier form of the flow, before the record. The parallel strategy built a project of 6 Definitions twice, the second time on a release with the plugin alone, with the merges, the reviews and the record working and a planted defect caught ([record](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/parallel-strategy-20261108.md)). With the plugin alone, the guard holds ([probe](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/project-hooks-20261108.md)). A build in slices ran once with release 0.32.0, on a project of 36 Definitions and 24 items, in four slices of at most six items, each built by a fresh builder, verified, committed and merged before the next, in 15 minutes on Sonnet. Items of earlier slices came back twice, through changed files, and the slice that changed them settled them. The test of its Scenario built the program and started it. A full review then recorded the same 24 verdicts. After a change of one Rule of Root, 17 items named the Rule as what changed, the builder moved the code, and three spec-problems were left, which were gaps of the spec ([run](https://github.com/Glacius-Labs/Markitect/pull/1071)). The project is small enough for a reviewer to read at once, so the reviewers recorded their verdicts in one batch and did not read what binds each item, and the first slice recorded a Rule `ok` that nothing yet carried out. With release 0.32.1 the first slice of a spec of real size was built once from nothing: of a spec of 396 Definitions and 158 items, one builder with its reviewer settled the 36 items of Root in 19 minutes on Sonnet, with 35 `ok` and one spec-problem, a conflict inside the spec; the session stopped after the slice as it was told, and the program starts and answers ([runs](https://github.com/Glacius-Labs/Markitect/pull/1074)). The second slice followed once, in a session of the desktop app: one builder with three rounds of its reviewer settled the 37 items of the three areas of the domain in 30 minutes, with 35 `ok` and two spec-problems. The reviewer found two defects, which the builder repaired. Eight items of Root came back through changed files and evidence and were settled in the slice, and the foundation of 4,000 lines gained 60 lines and lost 8. One change went through that a Rule of Root rules out: the builder changed a step of the migration of stored data in place, where the Rule asks for a new step with every change, and the items that file realizes were recorded `ok` without a reason. The two last slices did not run ([run](https://github.com/Glacius-Labs/Markitect/pull/1075)).

**Not yet shown:** the record, the skills and the roles on a real project over a series of changes; a bug hunt, a cleanup, an audit and the routines; the `vet` notes on a real build's record, and a reviewer that meets `mark`'s demand for its counts; a long list in parallel; a crash or a conflicting merge; the two last slices of a spec of real size, among them a last slice of more than nine items, and so a list longer than about 64 items built to its end; a reviewer on a project too large to read at once; how often the owner's manual permission mode stops a builder. These are covered by tests only. The [roadmap](roadmap.md#current-steps) tries them next.

**What the evidence does and doesn't cover:**

- **A plain Sonnet session has done the work from a typed spec, once.** In an earlier version, one launch built the 5× project, a study project five times the size of Makerspace, with one repair round and passed all 327 hidden cases ([record](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/default-arm-20261104.md)). That is one launch and not a rate, and its change steps have not run. So the implementation doesn't look like the main risk; the process around it does.
- **How often a native agent skips steps is unmeasured.** With the record, a skipped step should show as an item still on the list, not as a wrong verdict.
- **A separate reviewer catches planted bugs:** 17 of 18 blind, with no false alarm, in an earlier harness ([record](https://github.com/Glacius-Labs/Markitect/blob/d0c23a31efc928e95f3acc0633deb01a5f887884/docs/validation/k-checker-test-20261103.md)).
- **Drawing a first spec was first tried as a dry run without the record.** On one existing project of 131 files, a reviewer per Package found 78 of the 95 Definitions of a first draft true of the project. One round of corrections settled 12 of the other 17, and most of what stayed were places where the project contradicts itself. A second check that asked what the files hold that the spec does not say turned the spec into a transcription; asking what should also be in the spec did not. The project's tests could not run there, so the reviewers judged by reading ([trial](https://github.com/Glacius-Labs/Markitect/pull/1040)).
- **The skill has drawn the first spec of that project with the record.** On the same project, one unattended session drew 119 Definitions in six Packages in 53 minutes; the first review found 102 of them true of the project, and after three rounds of corrections the record held 113 as `ok`, with the project's own contradictions left for the owner. A blind scoring put the spec level with the best one of the earlier trial. The list did not empty, since each review found something new in what it verified again, and the session's limits did not reach the reviewer ([run](https://github.com/Glacius-Labs/Markitect/pull/1047)). It is one project and one run, and the skill is text that no test covers.
- **On a second, small project, a drawn first spec stayed below a hand-written one, once.** For a project of 31 files, a blind scoring against 170 obligations gave a hand-written spec of the same state 169.5, and the spec the skill drew 149. The skill then told the architect to leave free which refusal is reported when several apply, though that project's tests check it. With a first wording of the rules the skill has now, to bind what the project fixes and to give Definitions of one shape a Kind of their own, a second draw scored 156, with 150 of the 154 core obligations, 6 incidental statements where the first had 3, and 2 wrong statements in 84 checked where the first had 1 in 80 ([runs](https://github.com/Glacius-Labs/Markitect/pull/1051)). It is one project and one draw each.
- **A review found planted defects behind weakened tests, once.** In that small project, with its 80 Definitions all verified, one commit planted two bugs whose tests had been changed to hide them, one bug the tests catch, and a contradiction in the spec. A review without any hint recorded all three bugs as `fail`, named both weakened tests, and put the contradiction to the owner as a `spec-problem`, with no false alarm. A sequential and a parallel build then repaired the bugs, put cases back into both weakened tests that catch the bugs again, though not all the removed ones, and left the spec alone, and the hook refused a subagent's edit of the spec and of the questions file ([runs](https://github.com/Glacius-Labs/Markitect/pull/1050)). It is one small project, and the builders never tried to change the spec, so the hook was shown by a probe.
- **A review found planted defects again, on the project built in slices.** With release 0.32.1 one commit planted six defects behind passing tests: two violations of a Rule that binds without a link, a receipt that is not written, two refusals checked in the other order with the test changed to match, a test emptied of its assertions, and a page an Exclusion rules out. A review of everything recorded five as `fail` with the place, two of them after starting the program, and named the emptied test in its reason, leaving that item `ok` since another test shows the same ([runs](https://github.com/Glacius-Labs/Markitect/pull/1074)). The project is 1,800 lines, which the reviewer read at once: it says nothing for a project too large for that.
- **At the 5× size, a reviewer caught every planted bug.** In five launches of an earlier form of the review, on the 5× project with 20 planted bugs that its own tests do not catch, Sonnet found all 20 each time, with one reviewer for the whole project or one per Package, in 9 to 22 minutes. Four launches on the project without the bugs raised one finding, which looks like a real defect ([reading](https://github.com/Glacius-Labs/Markitect/pull/1050)). It was one launch per variant, the findings were matched to the bugs by reading them, and each bug broke one rule that the spec states plainly, so subtler bugs are not shown.
