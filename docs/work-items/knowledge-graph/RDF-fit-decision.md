# RDF/SPARQL fit decision

Date: 2026-10-09
Status: bounded technical fit recommendation; no implementation, dependency choice, migration, benchmark, product study, or release is authorized by this document.

## Decision

Keep the project model in YAML and keep Core compilation, ownership, visibility, impact, freshness, and execution decisions in their current owners. The graph already has a pure projection and bounded traversal API. RDF is a plausible **optional export format**, and SPARQL is a plausible **derived read-only query adapter** when a real need for user-composed relationship queries or external graph interchange is established. This is Variant B from the research plan: YAML remains authoritative, RDF is rebuilt from selected facts, and SPARQL results remain bound to the same source, snapshot, and visibility scope.

Do not move canonical authoring to Turtle (Variant C). No evidence here shows that it would remove meaningful compiler or Host behavior. Do not install or select an engine now: there is no measured workload, package comparison, or demonstrated query gap that justifies a runtime dependency. The current six bounded knowledge actions can remain the normal product interface. A later RF01–RF05 evaluation may close without an RDF implementation if native graph operations meet the accepted questions with lower total maintenance.

This is a technical fit conclusion, not evidence of improved developer productivity, agent performance, semantic correctness, full source coverage, or human acceptance. No benchmark or product-role trial was run.

At the pinned model/compiler reference, the flow is YAML parse and normalization, typed identity/reference resolution, closed shape/type/cardinality validation, semantic digest, then project analysis. Core identity is the full tuple `[apiVersion, kind, namespace, name]`; relationship edges retain property path and source location/digest. ProjectModel derives Manager ownership, path ownership, coverage, Context, and base/candidate Impact. `uses` and `requires` have different effects; incomplete inputs broaden Impact conservatively. The derived project graph has bounded traversal, selected fields and edges, bindings, explicit unknown/partial state, and witness paths. The existing graph API is not SPARQL and is intentionally read-only.

RDF is a data model of subject–predicate–object triples. Turtle is a text syntax for writing that graph; it is not itself a compiler or query engine. A dataset can hold a default graph and named graphs, and SPARQL can query graph patterns and arbitrary-length property paths. SHACL can validate graph shapes, including closed shapes. These features make serialization, flexible relationship queries, and reusable shape descriptions possible; they do not supply Markitect's authority, source acquisition, ownership, access control, evidence freshness, or product semantics. ([RDF 1.1 Concepts](https://www.w3.org/TR/rdf11-concepts/), [Turtle](https://www.w3.org/TR/turtle/), [SPARQL 1.1 Query](https://www.w3.org/TR/sparql11-query/), [SHACL](https://www.w3.org/TR/shacl/))

## Four hypotheses

| Hypothesis | Assessment | What would establish it |
|---|---|---|
| **RDF simplifies the compiler and CLI.** | Not established; unlikely as a blanket claim. Turtle changes the serialization. The compiler still has to assign exact Markitect identity, resolve references, reject unknown fields, preserve literal values, apply project rules, bind provenance and snapshots, and produce conservative impact. SHACL can cover some graph constraints, but does not replace path-to-Manager ownership, filesystem inventory, source-snapshot handling, Manager visibility, base/candidate invalidation, or the guarded execution workflow. A new graph exporter and engine could add a second parsing/validation/query surface. | For each candidate rule, identify the exact current code removed, the replacement check and its diagnostics, and all negative parity fixtures passed. Compare author/repair steps and ongoing code/config surface; count glue and packaging as well as deleted code. |
| **Agents are more familiar with RDF standards.** | Plausible, unmeasured. A public standard and familiar vocabulary do not show that Markitect's users or agents can author, repair, or query this project model more accurately or quickly. | A separate, balanced task exercise with the same model, tasks, instructions, tools, and allowed resources. Measure completion/correctness, repair effort, setup, and explanation quality. Do not treat preference or recognition as productivity evidence. |
| **External knowledge imports add useful graph content.** | Interoperability is a credible technical benefit: RDF datasets can keep source graphs separate and vocabularies can use shared IRIs. There is no current inventory showing which external project facts Markitect cannot already represent. “Import” must distinguish a locally pinned vocabulary/shape from imported assertions about an adopting project. Neither an IRI nor a named graph authenticates its publisher or makes its claims accepted Markitect intent. | Name one required external vocabulary or source and a concrete KG01 question it enables. Pin the bytes, version, license, retrieval provenance, and digest; keep imported claims in a separately identified, non-authoritative graph; show explicit mapping and conflicts; disallow network fetch during product queries. If no question improves, do not ship imports. |
| **SPARQL makes relationship queries more reliable.** | SPARQL is a strong fit for flexible joins and property paths when users need queries beyond `graph`, `relations`, `explain`, `trace`, `history`, and `coverage`. Reliability is conditional: a query sees only the dataset supplied to it, does not know which Markitect relationships affect ownership or coverage, and cannot prove that absent data is complete. SPARQL solution order is unspecified unless `ORDER BY` is used; even then, a stable total tie-break is required for deterministic reports. A property path can answer reachability without returning every explanatory witness. | Run the same fixed KG01 questions against A and B on the same selected data. Require exact answers, provenance-bearing witness explanations, deterministic result ordering, explicit incomplete/unknown status, result and execution bounds, and privacy-negative cases. Compare maintenance with the fixed native API. |

The RDF specifications support these technical distinctions: RDF graphs are sets of triples; Turtle only serializes such a graph. SPARQL property paths can express arbitrary-length connectivity, while SPARQL starts with unordered solution collections and needs `ORDER BY` to define output order. SHACL Core includes `sh:closed`, but SHACL Core does not require SPARQL support, so SHACL support and SHACL-SPARQL support must be checked separately for any engine. ([RDF graph and dataset model](https://www.w3.org/TR/rdf11-concepts/#section-rdf-graph), [Turtle introduction](https://www.w3.org/TR/turtle/#sec-intro), [SPARQL property paths](https://www.w3.org/TR/sparql11-query/#propertypaths), [SPARQL result ordering](https://www.w3.org/TR/sparql11-query/#modOrderBy), [SHACL closed shapes and SPARQL relationship](https://www.w3.org/TR/shacl/#ClosedShapeConstraintComponent))

## Markitect semantics an RDF layer must preserve

| Concern | Existing owner and rule | RDF mapping or query constraint |
|---|---|---|
| **Identity and ownership** | Core identity is the four-part tuple. ProjectModel resolves nearest namespace Manager and selected repository path ownership, checks overlaps/delegation, and rejects private foreign references. | Mint deterministic IRIs from an escaped, versioned mapping of the full identity; keep the original tuple and model schema/version. Projected `ownedBy` facts retain whether they came from a declaration or a derived path selector. The Host supplies only permitted nodes, fields, and edges before a query runs. |
| **Closed validation** | Core rejects undeclared properties, invalid types/cardinality, null values, duplicate reference targets, unresolved or wrong-kind references, and invalid numeric values. ProjectModel adds path, ownership, privacy, and required-coverage checks. | SHACL may restate closed properties, counts, datatypes, and reference-shape checks over the projected graph. Parser acceptance is not model acceptance. SHACL validation remains additive until negative and diagnostic parity is shown; path, inventory, and cross-snapshot policy remain Host/ProjectModel responsibilities. |
| **Unknown and completeness** | Missing inventory or record joins are unknown/partial; they do not prove absence, no activity, failure, or success. | Emit coverage/basis state explicitly for each selected source. An absent triple means only that it was not present in this graph. Never turn missing imported data or a zero-row SELECT into a complete negative claim without a completeness assertion. |
| **Provenance** | Source path, line, property path, revision/snapshot/model digests, candidate, runtime and receipt bindings are distinct. Actor and caller-supplied provenance are claims, not authenticated identity. | A triple has no built-in source-path, author, trust, or acceptance field. Use a deterministic relation/assertion resource or another explicit vocabulary mapping to attach edge provenance and snapshot binding. Keep semantic graph digest separate from source-byte and snapshot digests. |
| **Order and repetition** | Check command arguments are ordered literal strings and may repeat. Repeated reference targets are invalid. | RDF graph triples are a set, so repeated identical triples collapse and a set of literal objects has no list order. Represent ordered argv with indexed/list entries (including repeated values); preserve the validator's rejection of duplicate references. Do not depend on serializer order. |
| **Named graphs and privacy** | Manager visibility follows existing Context rules; records are opt-in. Whole-project scope requires caller authorization. | Named graphs organize facts and snapshots; their names are not access-control rules. Select/filter the authorized dataset in Host first, then give the query engine only that dataset. Never let a query change Manager scope, inspect hidden counts/IDs, or fetch remote graphs. |
| **Paths and file facts** | Host obtains repository inventory and normalizes exact repository-relative paths; ProjectModel validates selectors and derives ownership/coverage. | A path triple is a selected fact, not permission to read the file. Carry path normalization, inventory binding, and known/present/missing/unknown status from Host. |
| **Impact and execution** | ProjectModel computes conservative impact across base and candidate graphs, including removed edges. `uses` routes context/owners; `requires` also affects realization/check coverage. Host owns execution, receipt freshness and guarded Apply. | A single RDF snapshot/property path cannot replace two-revision Impact. A query cannot schedule work, execute Check commands, authorize writes, establish result freshness, or make Apply safe. Keep these operations and their evidence bindings in Host. |

SPARQL federation explicitly defines remote `SERVICE` query patterns. Any future local Markitect query adapter should disable federation and remote document resolution, accept only a Host-selected local dataset, and enforce time/memory/result limits outside the SPARQL standard. ([SPARQL 1.1 Federated Query](https://www.w3.org/TR/sparql11-federated-query/))

## Plain German example

Angenommen, die YAML-Datei sagt: `cancel-order` benötigt den Vertrag `release-reservation`. Ein Artefakt setzt `cancel-order` um und nennt die Pfade `src/shop/orders/` und `docs/cancellation.md`; ein Check prüft diese Umsetzung. Markitect kann schon heute die Beziehung zum Vertrag und die betroffenen Dateien und Checks im ausgewählten Scope erklären.

Eine abgeleitete RDF-Sicht könnte dieselben Angaben so abfragen:

```sparql
PREFIX mk: <https://markitect.example/vocab/project#>

SELECT ?manager ?path ?check
WHERE {
  <urn:markitect:statement:cancel-order> mk:requires ?contract .
  ?contract mk:ownedBy ?manager .
  ?artifact mk:realizes <urn:markitect:statement:cancel-order> ;
            mk:path ?path ;
            mk:checkedBy ?check .
}
ORDER BY ?manager ?path ?check
```

Das Ergebnis bedeutet nur: **Im ausgewählten Modell** ist der Vertrag diesem Manager zugeordnet und das Modell deklariert diese Pfade und diesen Check. Es bedeutet nicht, dass alle Implementierungsdateien gefunden, der Check ausgeführt, das Ergebnis aktuell oder ein Mensch einverstanden ist. `ORDER BY` plus vollständige Bindung/Scope sind nötig, damit ein wiederholtes Abfragen dieselben geordneten Modellfakten reporten kann.

## Bounded implementation plan

These are optional future evaluation items, not queued code changes. Keep the original RF numbering so the decision can be reconciled with the design plan. Each item uses the KG01 twelve-question matrix and the same pinned inputs for A and B. Variant C is only explored when its specific compiler-removal or canonical-authoring hypothesis cannot be answered by A/B.

| Item | Deliverable | Acceptance gate |
|---|---|---|
| **RF01 — Freeze mapping and comparison** | A concise schema-to-RDF mapping for the full Core identity, types, relations, literals, ordered argv, source/property-path provenance, scope, snapshot bindings, graph/query versions, imports, and known/partial/unknown. Map every applicable KG01 row to both the native graph and a candidate RDF form. Identify which current owner supplies each fact. | Round-trip semantic comparison for representative Shop cases, with no unlisted loss or silent meaning change. Explicitly mark facts that are Host-derived. No package or source edit. |
| **RF02 — Verify engine and delivery options** | At most two concrete candidates, chosen only after RF01 identifies the needed features. Record exact version, RDF/Turtle/SPARQL property-path support, SHACL Core versus SHACL-SPARQL coverage, relevant W3C conformance tests, license, Windows/Linux delivery, startup and size, memory/time/result bounds, and local-only configuration. Consider export-only separately from query-engine packaging. | Candidate can be delivered on supported platforms with external access disabled and all required bounds enforced, or engine-backed SPARQL is rejected in favor of export/native traversal. Dependency choice stays deferred until measured package/dependency evidence exists. |
| **RF03 — Variant B export and query prototype** | A deterministic rebuildable RDF dataset exported from the selected Host-projected facts. A tiny set of representative SPARQL queries for owner, contract consumers, artifacts/checks, decisions, and a trace. Return source/revision/snapshot/scope/query bindings and explanatory edge witnesses; keep YAML authoritative and imported claims separate. | Same fixed inputs give the expected KG01 answers, equal or stricter privacy, useful witness explanations, explicit unknown/partial coverage, deterministic output using a complete tie-break, and hard resource limits. Include no-network and malicious scope-expansion negatives. |
| **RF04 — Conditional Variant C comparison** | Only when a specific question remains: author a matched bounded fixture in Turtle and express closed/type/count/reference constraints in SHACL Core, plus only necessary host checks. List the exact compiler checks that could be deleted and the checks that remain. | Positive/negative parity covers unknown predicate, missing/wrong target, null/absent/empty, int64/finite values, duplicates, ordered/repeated argv, namespace/path ownership, removed relations, stale/unknown records, and private scope. If no concrete rule can be removed or no authoring need is established, record “not needed” and stop C. |
| **RF05 — Fit decision and measured conclusion** | Compare A (YAML + current native projection), B (YAML + export/SPARQL), and C only if RF04 ran. Account for correctness/diagnostics, explanation quality, model author/repair effort, query author/repair effort, maintenance surface, dependency/platform costs, deterministic IDs/diffs, provenance/versioning, and operations. Run any agent-familiarity task separately with equal instructions/resources and independent scoring. | State A, B, C, or reject with the actual tested SHA, config and logs; do not claim benchmarks for unrun checks. B passes only if its unique query/interchange value outweighs its ongoing second representation/engine cost. C requires a separate explicit canonical-format decision. |
| **RF06 — Only after an explicit C decision** | If C is selected later, specify one canonical authoring source per model version, digest-bound preview/apply migration, read/rollback rules for historical YAML, regenerated schemas/docs/examples/CLI/MCP/skills/loaders/manifests, and removal of superseded compiler code. | New explicit product decision, migration and rollback parity, normal platform gates, and independent review. A graph digest never upgrades historical evidence to current PASS. No release or automatic publication. |

**Stop condition:** If RF03 cannot identify a question that the existing six read-only operations cannot answer acceptably, close RDF fit at RF05 as Variant A. Do not create permanent dual authoring. If a query gap is shown but engine cost fails RF02, publish export-only and keep native bounded queries. If B passes, the follow-up is a separate read-only, derived interface with no change to YAML authority.
