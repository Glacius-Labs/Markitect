## Targeted checks: model context completeness

The owner adopted [automatic full required context plus bound lookup](../design/canonical-model/manager-apply-workflow.md#model-context-delivery-and-completeness) and requested targeted completeness checks. A owns production selection/Brief/prompt/adapter-boundary tests and any necessary bounded correction; B owns independent small controls and semantic equivalence of its `plan.md` packets. C consumes those checked model inputs; D reports delivery evidence separately from task success. Coordinate shared files through their existing owners. This is not an extra provider series or a start signal; existing limits remain in force. Record any missing provider-retention proof rather than expanding the assignment to a generic context-management system.

| Targeted control | Discriminating assertion |
| --- | --- |
| Own and linked/scoped content | An independently enumerated model requires known own, incoming/outgoing, scope and type/property entries; compare actual selection, owner labels and inclusion reasons. Include unrelated content to prove the test does not simply require the whole model everywhere. |
| Full values and conditions | A tiny Definition has a decisive final sentence, nested/list values, numeric/boolean boundaries and a reference. Dropping a field, trailing condition or reference target must fail a test of the resulting packet, not pass because its ID remains present. |
| Root inventory and foreign context | All local Definitions occur in Root's overview with their owners; reference-only entries are not counted as full text. Required full entries remain full. Included foreign obligations do not become the reader's ownership. |
| Actual transport and binding | Capture the real adapter request/prompt and lookup response using a provider-free transport seam. Compare independently expected content with transmitted payload, not only the renderer. Wrong-model/source content, wrong recipient or a lost suffix must be detected even when IDs/manifest hashes look correct. |
| Conversation and fresh review | A new work context and each fresh Verify context receive the required packet; resumed work is explicitly recorded as relying on history. Simulate context reset/observable compaction and check rehydration behavior; unsupported/unobservable retention stays a stated gap, not a passing assertion. Verify cannot inherit the author's conversation. |
| Capacity and lookup | At a declared size boundary, required content is never silently cut: explicit complete partitioning precedes dependent work, or the operation is incomplete. Lookup returns the complete requested Definition from the bound model with correct ownership, including content whose working-tree copy changed. |
| Ordinary-Agent equivalence | Independently compare `plan.md` plus its explicit lookup material with the same intended requirements, freedom and unresolved choices. Do not derive the expected answer by running the formatter under test twice. |

Use distinct expected data and deliberate faulty variants so the checks can detect omissions and substitutions. The coverage record belongs in existing Run evidence and distinguishes selected, full/reference-only rendered, submitted and looked-up content. A provider acknowledgement and Agent compliance remain different observations. Reuse already authorized run transcripts where they actually expose these boundaries; source/transport tests alone do not prove provider retention or faithful realization. Freeze any resulting source/input changes explicitly so the B0/B1 lifecycle comparison does not attribute a context correction to container reuse.

## Session A: lifecycle contract and portability

Use the common recursive Pass unchanged: parent work and checked accepted basis, released children, tree-only questions in both directions, parent acceptance/integration and sealed aggregate result. Direct includes local planning and preparation in Implement, then a fresh Verify; findings return to an ordinary Implement and another complete fresh Verify. Staged retains explicit Plan/Prepare/Implement. Neither a Turn exit nor an idle container means Done.

Target one reusable working container per logical Manager within a Run. Distinguish Manager identity, runtime instance generation, provider process/conversation, Turn, Pass and candidate. Preserve project-wide reads, most-specific write ownership, protected authority inputs, local registry checks and read-only communication during blocked productive work. Helpers temporarily exclude the parent from delegated writes. Rights-driven container replacement is an explicit, measured exception when enforceable transitions cannot safely happen in place; a prompt cannot revoke a writable mount. Verify reviewers start in a fresh environment/conversation for each Verify Pass; checks and helpers remain separately isolated. Author context never becomes independent review context.

Before accepting stable bytes, capturing a candidate or replacing a writer, prove cessation of every relevant writer and descendant. A reusable idle container may remain alive, but cannot conceal a background writer. Correlate operations/results with Run, Manager, instance generation and Turn; reject stale/duplicate completions. Bound start, stop, cancellation and cleanup; uncertain stop blocks acceptance/publication and replacement access to that writable workspace. Preserve evidence and retained work. A Run restart follows existing semantics, not an invented automatic recovery of an interrupted Apply.

Keep domain scheduling independent of Docker commands and host paths. Define the smallest Runtime capability contract needed for start/observe/execute/stop/dispose, workspace access and capability changes. Evaluate how it maps to a later Kubernetes Pod, separate reviewer/check workloads, persistent evidence and storage. Document shared-workspace visibility, ownership enforcement across nodes and snapshot requirements; do not assume a Docker volume path becomes distributed storage. Separate orchestration credentials from Agent access, declare images/resources/network explicitly, and avoid privileged containers, Docker-socket access or mount tricks as the portability solution.

A future backend must preserve uncertain-stop semantics during node/network loss: an API deletion is not proof a writer stopped. Kubernetes explicitly warns that [forced Pod deletion need not confirm process termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination). Its [read-only mount setting applies to the container, not immutable storage](https://kubernetes.io/docs/concepts/storage/volumes/#read-only-mounts). Therefore treat storage fencing or verified cessation and an actually immutable candidate as contracts, not names for API calls. The present deliverable is Docker implementation plus a concrete portability design; no Kubernetes adapter, cluster, manifests or distributed lease framework is required now.

Prove with focused source and real-container tests: multiple Turns reuse an instance; blocked communication cannot write; helper exclusion is enforced; late/background writers cannot mutate accepted bytes; cancellation/crash/uncertain stop cannot publish or create competing writers; fresh Verify has no author memory; candidate bytes remain unchanged under hostile probe attempts; teardown retains evidence and leaves no unowned resources. Exercise both providers' shared interfaces where affected without launching an unrequested model series.

Probe optimization is a second change: read-only access to immutable candidate data with separate writable scratch may avoid copies. Some probes legitimately mutate a control copy; retain a disposable-copy path for them and bind those receipts to that copy. A read-only mount of the live working tree is never a Verify candidate. Keep the old probe-copy behavior for B0/B1 comparison; record B2 separately or defer it if safe separation is expensive.

## Session B: scenarios that answer one question

Extend the existing playground, not a new general benchmark platform. Prefer a tiny scenario with one primary hypothesis and an independently checked conforming/faulty pair. Record secondary observations without claiming causal isolation for a large mixed case. Complexity has distinct axes: obligation difficulty, number of Managers, tree depth, dependency fanout and size of required work; increase one at a time before combining them.

| Case | Primary question and independent success criterion |
| --- | --- |
| Detection (V1/V2) | Does fresh immutable Verify reject the known hyphen-name defect and accept the conforming control? Verify-only harness separates detection from an Implement repair. |
| Repair (A1) | Does a complete Apply repair the defect, preserve unrelated correct behavior, independently close findings and publish the checked candidate? |
| Preservation (A2) | Does a complete Apply preserve an independently conforming stand without optional refactoring/test expansion? Required evidence adequacy is specified before the run; surviving arbitrary mutants alone are not a new model obligation. |
| Public gap (A4/S-QV) | Does an unspecified externally visible name limit reach the owner before a choice is implemented? Use a deterministic answer script and also a no-answer control; no answer means honest Waiting/Incomplete without publication. |
| Permitted freedom | Does the Agent accept explicit freedom to choose an internal detail without unnecessary owner escalation? Pair with the public-gap case to measure false alarms. |
| Model change (A5) | Does a supplied owner policy change to 40 affect exactly the required behavior, tests and docs? Bind the same starting artifacts for every comparison arm. |
| Contradiction (A7) | Does Root identify an actual contradictory obligation and stop without publication or an override question? |
| Dependency (DEP) | Does a tiny branching tree release a consumer on the accepted prerequisite it needs, route an A-to-parent-to-B question and answer, and avoid idle Turns? Trace actual dependency binding, consumed version and invalidation; include cycle/stale-input negative controls at source level. |
| Complexity | Separate fixtures for harder local semantics and greater dependency fanout/depth, with explicit bounded dimensions and known obligations. Do not relabel Depot as a scaling proof. |
| Realistic integrated run | One finite complete project with multiple areas, genuine dependencies, substantial implementation, tests/docs, independent assessment and publication. Combines mechanisms intentionally; diagnoses failures through smaller cases rather than claiming one-factor causality. |

Every case manifest states its hypothesis, exact input/model/artifact hashes, expected public behavior and process evidence, allowed implementation freedom, false-positive control, answer script, external oracle, resource bounds and stop rules. Hidden answers, fault locations and oracle code stay outside Agent-visible packets and mounts. Independently validate the conforming control and show the oracle rejects a deliberately wrong variant while permitting alternate correct implementations. Fixture changes create a new version, never repair an already scored attempt retroactively. Missing evidence is not a pass.

For each full-Apply scenario provide a matched ordinary-Agent packet: deterministically assemble a readable `plan.md` from the same checked model/requirements, preserving Definition provenance, all obligations and unresolved choices. This is a generated input artifact, not a new product command named Compile and not an Agent-written solution plan. Give it to one coding Agent with ordinary code/test tools and the same project starting bytes, model/effort, environment, whole-run ceilings and owner-help policy. The Agent organizes its own planning and execution; do not prescribe Markitect's Manager/reviewer tree. Source model/context must remain inspectable or be equivalently represented, including exclusions and freedom. Independently check semantic coverage of the packet before running.

All arms get fresh workspaces/conversations and the same external outcome oracle. Direct/staged additionally expose their process guarantees; the single Agent's completion report is not called Markitect Verified. Do not score nonexistent child-event behavior against the single-Agent arm; compare its correct dependency-dependent result and owner attention, and report Markitect-specific event obligations separately. Count plan generation/model preparation, review, owner answers and corrective prompts; do not donate hidden expert work to an arm. Record ordinary first completion before any human-guided correction. Counterbalance order within available resources; a single triplet is a diagnostic sample, not a reliability estimate. Follow the existing [measurement contract](../measurement.md#quality-first-comparative-evaluation).

## Session C: model assessment before realization

Call this **Model assessment**, distinct from deterministic **Model check**. The experiment runs Model check and File check first, then a read-only team on the fixed model/context, before any realization. Reuse the common recursive Pass/result mechanics where practical through an isolated harness; do not implement a second production scheduler. Managers assess their own model obligations and parents review interfaces and cross-area consistency. An independent challenge perspective checks proposed findings and the evidence for accepting the model. Team size follows the actual model; no mandatory large roster for a tiny case.

The assessment asks: are public choices resolved or explicitly delegated, do linked obligations contradict, are required contracts and responsibility boundaries sufficiently defined, and does the model leave legitimate implementation freedom? Every finding names source Definitions, the competing interpretations/consequence and the missing decision. No finding quota, invented preferred architecture, inferred policy from existing code, or requirement that an application already exists.

Record a purpose-specific assessment conclusion: `accepted` (no unresolved material issue found), `needs_clarification` (a concrete owner decision is missing), or `model_error` (a sourced contradiction/error). These are semantic payload classifications, not new Manager lifecycle or Pass verdict values: use the existing common envelope, Waiting for pending questions, structured Problem escalation and Root's model-error decision. Execution failure, timeout or missing evidence is separately `Incomplete`, never acceptance or rejection of model quality. Record coverage and dissent as evidence, not a completeness theorem. In the experiment only an accepted assessment releases its downstream realization treatment. Compatible clarification can be recorded by the owner; a changed model requires new checks and a new assessment binding. No Agent edits authority inputs or treats an answer as permission to override them. Apply still escalates newly discovered gaps and runs independent Verify even after acceptance.

Compare public gap, permitted freedom, contradiction and a complete model. Run the gap trial alongside the unmodified Apply A4 treatment, not as a silent fix to its input. If comparing downstream Apply with/without assessment, bind resulting decisions explicitly and charge assessment/owner effort; that is a separate treatment from container reuse. Deliver evidence and an integration recommendation. Making this a mandatory product gate or adding cockpit/CLI authoring behavior waits for the owner's assessment of the trial.

## Frozen builds and finite evaluation

Before any paid run write a finite attempt manifest. These are proposed ceilings activated when the owner sends the matching startup prompt, not permission granted by this document's presence. Lower ceilings are fine; never increase them or rerun until green without a new owner grant. Count failed starts, retries, timeouts and abandoned attempts. Whole-series elapsed allocation includes provider work, waiting and cleanup; report actual elapsed time separately from provider-reported cost/usage. Keep finite per-Run, Turn, Pass, probe and cleanup limits; reserve time to stop and preserve evidence.

**A — targeted retest:** maximum 20 Sonnet attempts and 12 summed execution hours, at most 90 minutes per attempt. B0 is integrated direct plus current shared fixes, old lifecycle/copies, no model-assessment treatment. B1 changes only the Manager lifecycle. Run each of V1, V2, A1, A2, A4, A5, A7 and DEP once on B0 and once on B1 (16 attempts), interleaving matched pairs where practical. If B2 is implemented, spend two slots on A1/A2 for its isolated probe change; otherwise those slots remain unused. At most two remaining slots validate a named correction, with a new build identity and the previous failed pair retained. A defect already present in B0 is a product finding; a newly failed B1 case is a potential regression. A fix that changes both arms requires fresh comparable evidence or an explicitly unproved comparison within this same ceiling.

The A4 owner script tests escalation, not willingness to accept a preloaded answer. A clean end state with no question still fails A4. A2 must show no optional changes, no ancestor-finding stall and no unexplained repeated Verify. Exercise #553's probe-error disposition with a true candidate failure and an unrelated passing probe: semantic mismatch must not close evidence just because both receipts name one obligation. Ensure a genuine correction and fresh closure are actually observed; A1 repaired before Verify alone does not demonstrate this. Use one reserved correction slot for a bounded seeded handoff to the existing Verify/correction harness if no natural cycle occurs, and label that as process evidence rather than a blind discovery.

After final Sonnet candidate passes the relevant safety/source/container tests and V1/V2/A1/A2/A4/DEP, permit at most four Haiku attempts and four summed hours, 60 minutes per attempt: V1, V2, A1 and DEP on that frozen candidate. Failed or unrun gates stop this stage; budget exhaustion closes the report honestly. No Luna series or default-model change. Report all eight Sonnet case outcomes even when a case is not a Haiku release gate.

**B — kit:** no provider evaluation authorized by the fixture-building prompt. Deterministic oracle self-tests and local harness controls only. Prepare the large case without running it.

**C — model-only trial:** at most 12 Sonnet assessment attempts and 90 summed minutes, 10 minutes per attempt: three fresh repetitions of each of the four model controls. No full Apply. Measure missed gaps, false alarms, source-supported findings, disagreement and owner effort. Do not tune mandates against hidden answers and then present the same inputs as independent validation.

**D — comparative pilot:** at most 12 Sonnet full-run attempts and 12 summed hours: one direct/staged/plan-Agent triplet each for preservation, public gap, dependency and the realistic integrated case. Small attempts cap at 60 minutes; the integrated case caps at 180 minutes per arm. Larger per-attempt caps do not enlarge the total ceiling. Use identical lifecycle/probe behavior for direct/staged on the final frozen A build. Keep Model assessment off for this primary comparison so that the strategy effect is interpretable. Select and freeze order before starting, preserve incomplete triplets and do not add retries beyond the cap. No reliability-rate claim from one run per condition; a subsequent repetition study needs its own scope.

Use external verdicts to detect false success, missed/false findings, optional changes, owner-question behavior, actual correction/closure and publication/read-back. Measure total time, time waiting for owner/prerequisites, provider Turns, Passes, container starts and peak concurrency by role, startup/materialization/cleanup and known/unknown cost. Distinguish controller report from actual resource cessation. All final reports include source/input/image/profile hashes, every attempt and unavailable criterion, local checks versus real-provider evidence, and proposed next changes. Successful source tests, fewer containers and a green Agent verdict never substitute for those outcomes.
