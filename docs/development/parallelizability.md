# Parallel development boundaries

## Current source ownership after consolidation

The [Module guide](modules.md) and [consolidation report](../validation/clean-architecture-consolidation.md) supersede the package/readiness map below. Nine capability owners now have independent Module subtrees; Markdown and Agent Rules no longer share a renderer dependency. Host supplies config/IR/artifacts and composes outputs, with explicit collision checks. Content-package/source authoring remain Host-owned, acquisition is Infrastructure, and Core is the generic finite kernel/IR. The mandatory AST gate forbids sibling/Host imports by Modules, including tests/platform files.

Module-local work can proceed independently behind that frozen Core contract, while Host wiring, output-target ownership, source/schema semantics and release changes remain coordinated. Init and Copy Me retain separate responsibilities behind their implemented immutable handoff within the Adoption capability. Owner review/adoption and remote write authority remain genuine external dependencies. Published v0.13.0 remains separate from this source consolidation.

## Workstream classes and readiness

The **class** describes the kind of workstream goal, independently of whether its current code path is easy to change:

- **A — independent consumer goal:** a provider, adapter, or output consumer has its own desired behavior and evidence claim. Separate A goals can be designed and tested independently when they use existing contracts and disjoint files/targets.
- **B — conceptually coupled adoption:** work is about adopting, authoring, preparing, or validating a project workflow. It depends on the adopter's choices and human review, even when its files can be studied separately.
- **C — shared semantics:** work changes common meaning, evidence identity, schemas, shared dispatch, or a shared mutation/ownership boundary. It needs one contract owner and coordinated integration.

**Readiness** is a separate implementation judgment. A class-A provider goal can still touch a shared renderer hotspot. Readiness below identifies what is independently actionable now and which exact seam must be coordinated.

## Adapter parallelizability audit

The proposal `04-adapter-modularity-contract.md` describes goals. Its example `consumes` / `capabilities` registration syntax is illustrative, not current Project syntax. Existing entries use `name`, `type`, `version`, and `config`; only `type: command` is accepted. The YAML command protocol is a usable source-level seam for parallel consumers, but its identifiers are `v1alpha1`, not a permanent compatibility guarantee. There is no self-registration API or per-adapter capability manifest.

| Acceptance question | Current source answer |
|---|---|
| Can .NET and GitHub be implemented from one baseline? | **Yes** as separate external command consumers using the same request/model/result/plan contract, with adapter-owned files, tests and disjoint targets. |
| Can Azure DevOps and Claude be implemented from one baseline? | **Yes as independent goals.** Azure can use an external command. Claude's built-in projection has a shared renderer seam; a Claude-only output helper/test can be owned separately while changes to shared files are coordinated. |
| Must one adapter edit another adapter? | **No** for separate external command implementations. Native provider goals can remain separate, but their current common renderer files need coordinator review when touched. |
| Are provider details kept out of Core? | External adapters can put mappings/interpretation in their own `parameters` and executable. Existing Codex/Claude configuration is part of the intentional native projection contract; it is not a requirement that new command providers add Core fields. |
| Is there a central switch for every new adapter? | **No** for a new `command` consumer. Adding another configured adapter type or built-in provider family crosses format validation, app/CLI dispatch, schema and/or renderer switches. The adapter CLI entry point is `cmd/markitect/cli_reconcile.go`; `cmd/markitect/cli_dispatch.go` is not the adapter-specific route. |
| Can adapters self-register without semantic coupling? | There is **no self-registration**. Project YAML selects a named configured command/argv. This is enough for external execution, but not a plugin registry or capability discovery system. |
| Can each adapter test independently? | **Yes** for external commands, as the .NET package tests and canonical-engineering integration demonstrate. Native provider-specific helpers can have their own tests; shared renderer and ownership changes need common suite coverage. |
| Can evidence limitations be stated independently? | **Yes.** Each command result can name findings/status, scope and evidence kind. Markitect validates envelope identity and status shape, not provider-specific truth. |
| Can each adapter own targets independently? | **Only by coordination.** Target identity is bound within one adapter's result/plan, but cross-adapter equal strings, aliases, and overlapping sub-resources are not detected. |
| Can an adapter be absent without changing Core behavior? | **Yes** for command consumers, which run only when configured and invoked. Native outputs are opt-in by Project target, although their implementations remain compiled into Markitect. |

## Evidence and fan-out limits

v0.10.0 is the **historical release baseline** for the generic semantic model and configured command adapter. At the integrated source baseline above, DTO and protocol identifiers remain `v1alpha1`; do not infer that every published v0.12.0 binary implements later source behavior or that the alpha contract is permanently compatible. Record and check the actual CLI/adapter build used by a consumer.

Command adapter plans bind source/model/config/observation and CLI identity, the declared adapter version, and a digest computed from resolved executable file bytes. The byte digest detects executable changes between stages; by itself it does not prove publisher identity, source provenance, signed release status, or that the declared version string is truthful. Observations are time-bound evidence, not semantic correctness or proof of continuing remote state. The command runner executes with caller authority and does not guarantee that an `observe`, `plan`, or `verify` program is side-effect free.

Safe initial fan-out means independently owned external commands with verified read-only behavior, or demonstrated disjoint targets with coordinated effects. Shared-target writes, protocol/Domain/Project semantics, snapshot/evidence changes, common CLI/schema/reconciliation changes, and shared renderer file/path ownership need serialized contract ownership. Built-in Docs/Codex/Claude remain three independent consumer goals; where they touch shared `render.go`, Agent/navigation helpers, `provider_adapters.go`, `rules.go`, or output-path/inventory code, those changes are coordinated. No current consumer demonstrates a need to repair Core or add a general plugin framework merely to build separate GitHub or Azure command adapters.
