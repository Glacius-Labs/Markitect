# Markitect V1 – Complete product and architecture concept

**Model-based realization through a derived Manager organization**

**Document version:** 0.18 – consolidated concept version  
**As of:** 24 October 2026  
**Document type:** Target concept and basis for concept conformance, implementation and acceptance  
**Scope of validity:** Narrow V1 for Model → Artifacts  
**Status:** Consolidation of the decisions D1–D9 that were taken, of later scope clarifications and of the most recently formulated clarification requests. Open technical decisions and unconfirmed audit assumptions are marked separately.

> **The canonical model describes the intended project world. The Manager organization is derived from it. The Managers realize, review and integrate this world; the host provides a few clear technical guarantees for it.**

This document describes how Markitect should work. It does not claim that the current implementation already meets all requirements. It grants neither a new implementation approval nor a formal product acceptance, release or deployment approval.

## 1. Authority, sources and reading rules

### 1.1 Purpose of the consolidation

The previous conception arose in several conversation and document versions. This document brings the applicable content together into one coherent target picture. It should enable a new Coordinator or implementer to understand the product idea without having to reread all historical conversations.

Two errors are avoided in doing so: earlier requirements that have since been explicitly rejected are not reintroduced. Conversely, current code is not declared the target retroactively merely because it has already been implemented or successfully tested.

### 1.2 Sources and their different roles

The basis is formed by the joint decisions D1–D9 and the clarifications accepted in the conversation [Q1], the consolidated plan v0.17 [Q2], the concept conformance audit of 24 October [Q3] and the most recently provided correction request to the Coordinator [Q4]. The source register in section 29 explains the status of each.

**Owner decisions determine the product semantics.** An architecture proposal is not decided merely by being written out. An audit is not a new product requirement. A successful test is not a tacit decision to change anything. Technical detail decisions remain delegable within the approved limits.

### 1.3 Three kinds of statements

| Category | Meaning in this document |
|---|---|
| **Fixed** | Decided product semantics or a responsibility boundary that follows directly from it. |
| **To be designed technically** | The goal is fixed; API, storage form, provider mapping or the concrete package cut need a reasoned implementation. |
| **Later / outside V1** | Deliberately not part of the current scope of delivery. Must not shape the new core through premature compatibility obligations. |

Wording such as “must” refers to applicable domain or technical invariants, not to a prescribed implementation file. “For example” and “intended” mark suitable forms, not automatically mandatory frameworks or technologies.

### 1.4 No new audit and no retroactive approval

Producing this concept version involves no new repository, test or provider check. The commit `6c7d758cbe55e079a7d0b6bcfdedb46e9ba58998` named in [Q3] is a historically fixed audited state, not a claim about a later Main state.

The most recently named implementation questions on communication paths, child handoffs, completion semantics, Publication and Notes are tracked visibly in section 28. Their exact correction is not anticipated by this document.

## 2. Product idea and initial problem

### 2.1 The problem is not a lack of text production

With AI agents, code, tests, documentation and working instructions can be produced quickly. The hard part is keeping their meaning consistent over a longer time. An architecture decision can affect code, interfaces, tests, configuration, documentation and agent rules at the same time. A local change can look successful and still violate obligations elsewhere.

The starting point of Markitect was, in particular, growing collections of rules, skills, workflows and other agent instructions. References, responsibilities and rules became increasingly contradictory. Pure text maintenance and repeated complete AI reviews proved to be an insufficient basis for reliable consistency.

### 2.2 One canonical model instead of several competing truths

Markitect represents the intended project world in a canonical model. The model describes domain requirements, architecture, relationships, rules, responsibilities and quality obligations. Code, tests, documentation and configuration are realizations of this intent.

The direction is therefore:

```text
Intent and architecture in the canonical model
    → deterministically checked structure
    → Manager organization derived from it
    → realization and integration
    → independent verification
    → artifacts published under control
```

The name combines Markdown and architecture. The mature concept, however, is not limited to linting Markdown or prompt files. The canonical language uses typed YAML Definitions with meaning-bearing Markdown prose; the exact language syntax remains the subject of the existing language reference.

### 2.3 Compiler and agents complement each other

The compiler checks expressible structural properties. The Managers judge semantic questions and implement the model. Neither should a language model guess trivial reference errors, nor should the host force all domain work into a deterministic process.

The analogy to typed programming languages extends as far as the early detection of expressible structural errors. It is **no proof** that arbitrary natural-language requirements are realized completely or correctly.

### 2.4 Product thesis and limit of evidence

The central thesis is: an authoritative model, bounded responsibility, hierarchical reviews, independent verification Runs and controlled integration can make consistent changes possible more reliably than a single agent that has to keep all obligations in view alone.

This is a product thesis to be tested, not a guarantee that follows from the mere use of several agents. Universal reliability, less human review effort and advantages over simpler agent approaches must be demonstrated through suitable comparisons and real projects.

## 3. V1 scope and later extensions

### 3.1 Binding deliverable

V1 concentrates on **Model → Artifacts**. It comprises deterministic preparation, Assessment, Implement, Verify, fresh correction Runs, durable results and controlled Publication. Operation includes a narrow Apply entry point and the retained model tools Check, Context and Docs.

Also necessary are registry and ownership maintenance, a Harness that is usable in practice, normal CLI account authentication, Run-local containers and Git working states, persistent Shared Notes and relevant technical and domain evidence.

### 3.2 Deliberately not commissioned

Extract and other Artifacts→Model operations, the Cockpit or a graphical UI, interactive model authoring and the migration of these old consumers lie outside the narrow V1. Their previous interfaces must not create new requirements for the execution core.

The later retirement of Setup was also accepted in the conversation, provided that tested explicit configuration makes an actual Apply call possible. This does not mean that usability is meaningless; it means that no separate onboarding product is built for it for now.

Ordinary reading of existing artifacts remains necessary. What is excluded is unilaterally making a new canonical truth out of them during Apply.

### 3.3 Extensions without a premature platform

Further Commands and user-defined Workflows should be able to combine Runs in the future. This requires an independently usable Run boundary, but no universal Workflow DSL in V1.

Longer-term Manager memory, semantic search, automated knowledge condensation, a graphical Workflow designer, dynamic organization, long-running agent containers and a custom code-mode runtime are not current requirements.

The approach remains provider-neutral. Codex and Claude are intended native mappings; additional providers need suitable adapters and their own evidence. The provider scope actually accepted may be narrower than the complete target picture, but must be named explicitly.

## 4. Quality principles

### 4.1 Architectural quality before reuse

The target architecture determines the implementation. Old types, package boundaries and runtime paths are not requirements. Historical work supplies insights and relevant regression expectations; unsuitable implementations may be replaced.

Nor is a complete rewrite an end in itself. Suitable, coherent foundations are kept. A newly written but over-abstracted system would miss the goal as well.

### 4.2 Pragmatic determinism

Facts that can be established unambiguously by technical means and are relevant in practice should be determined deterministically. Examples are identities, references, fixed Git states, file accounting, actual check results and resource closure.

This creates no obligation to classify or approve every work step or to accompany it with additional evidence protocols. The benefit of a control must justify its complexity.

### 4.3 Manager autonomy with clear responsibility

Managers work independently in their area, plan locally, coordinate their children and assess their results. The host supports this organization. It makes no domain architecture decisions of its own and does not replace the parent with a growing repair or approval machine.

### 4.4 Simplicity and cohesion

Few clear responsibilities, fitting dependency directions and readable code are explicit acceptance criteria. More packages, interfaces or status values do not automatically mean more quality. Conversely, a single large orchestrator is not an appropriate simplification.

### 4.5 Focus and preservation

An assignment comprises fulfilling the valid model, actual Findings and necessary consequences. Artifacts that already conform are preserved. Optional improvements are noted, not implemented unasked. An unchanged, conforming candidate is a valid work result.

### 4.6 Honest results

Domain approval, technical success, stored results, working provider integration and formal owner acceptance are different statements. Uncertain or incomplete states are not reinterpreted as successes. Later successful attempts do not change historical failures.

## 6. Canonical model and deterministic preparation

### 6.1 Meaning of the model

The model can describe domain concepts, use cases, architecture boundaries, rules, relationships and development obligations. Identities, Kinds, fields, Imports and references follow the existing language. Free prose complements the typed structure where meaning cannot sensibly be reduced to machine-decidable fields.

This concept defines no additional model grammar and no new mandatory set of Core primitives. For example, a project architecture can explicitly model a use case with exactly one handler; it does not follow that every such project convention must be built into the Markitect core.

### 6.2 Model authority and binding

An Apply works against a fixed, successfully checked model basis and the associated controlled inputs. Realization agents do not silently change requirements, ownership rules or ignore exceptions in order to remove a conflict.

A necessary material model decision is made visible as a blocker. It is settled outside this Apply. Only the model basis that is checked anew afterwards can carry a new realization attempt.

### 6.3 Initial compile and structure gate

Before the agentic Workflow begins, the model basis and the relevant project structures are checked deterministically. With an invalid or incompletely captured starting state, no Managers start. The actual diagnostics are returned; the agents should not be used to repair an uncompilable starting basis.

Project preparation connects the existing compiler with registry, accounting, organization derivation and context selection. No second compiler arises within the agent runtime.

### 6.4 What the check does not claim

Structural validity does not mean semantic completeness. A file that is already correctly registered is not automatically right in domain terms. A valid Definition does not prove that its behavior has been implemented.

Conversely, artifacts not yet produced are not automatically a model error in a fresh realization. Assessment must distinguish between missing realization and a missing necessary model decision. Existing unexplained files, by contrast, remain an accounting problem of the starting state.

### 6.5 Preserved foundation and self-model

The established semantics of the canonical language, the compiler, the snapshot values, the organization derivation and the realization mapping remain protected. Structural improvements must not change these guarantees in passing.

Separately from this, Markitect's own canonical self-model must describe the new architecture actually chosen. Updating this self-model is not a reinvention of the model language.

## 7. Registry, ownership and complete file accounting

### 7.1 Local shards and global view

Each responsible Manager, or each local Package, maintains its registry shard. It maps its own artifacts to the relevant model Definitions and gives a reason for the mapping. An artifact can realize several Definitions, but has one unambiguous responsibility.

The global registry is derived deterministically from these shards. It is not introduced as a second, independently maintained truth. When a child result is merged, its registration stays assigned to the responsible child.

### 7.2 Complete accounting instead of silent exceptions

For every relevant observed file it must be unambiguously established which permitted category it belongs to.

| Category | Treatment |
|---|---|
| Realization artifact | Valid registration and responsibility required. |
| Canonical model input | Authoritative project intent, protected during Apply. |
| Markitect control input | Controlled input, for example execution or ignore rules. |
| Operational state / administrative data | Deliberately separated from the product candidate and treated according to the existing convention. |
| Explicitly ignored file | Explicit permitted exception, not a hidden circumvention of a model obligation. |

The existing convention `.markitect/ignore.yaml` remains authoritative. `.gitignore` is no substitute for this mapping. The early picture “ignore everything under .markitect” was clarified: canonical model and registry files must not disappear from validation through a blanket directory exception. Git administration and operational data need a clear technical treatment, not an artificial registration as a domain artifact.

### 7.3 Changes to the registry and to project intent

Managers register newly created artifacts, update mappings when artifacts are moved and clean them up on permitted deletions. Registry maintenance is part of realization and is permitted within the responsibility.

This differs from changes to requirements, ownership policy or ignore rules. Such inputs must not be changed in order to get around a check. “Model unchanged” therefore does not mean “registry frozen”.

### 7.4 Assigned file and permitted actor are different

Accounting answers to whom a file is assigned and which Definitions it addresses. It does not on its own prove which Manager changed the file and whether it acted within its assignment in doing so.

The handoff therefore contains the actual task starting state, the fixed result state and the complete relevant diff. Parent review and Verify take accepted child integrations into account. These are not unauthorized own work of the parent Manager. At the same time, child files must not disappear wholesale from a parent diff in a way that would make later independent interventions invisible.

Existing Git bases and traceable diffs are used for this. A per-write ACL system or a global provenance and proof protocol is explicitly not intended.

## 8. Model-derived Manager organization

### 8.1 The model is the architecture

The organization is derived from the valid model. There is no second, manually maintained Manager hierarchy that enforces architecture decisions independently of the model. Ownership and Package responsibility become visible in the organization chart.

The organization comprises Root and the required local Package Managers, including empty and intermediate Packages. The existing rules for external model dependencies are not extended in passing into an additional executable Manager organization.

### 8.2 Complete participation in every mandate

Assessment, Implement and Verify use the same complete required model organization. The mandate changes the task, not the tree of responsibility at free discretion.

Root-only is correct when the modeled organization actually comprises only Root. It is not a permitted shortcut just because Root or the host considers a sole check sufficient. Participation must not be reduced to starting unused containers; the modeled responsibilities must actually be handled.

### 8.3 Responsibility of Root and local Managers

A local Manager realizes or checks its own obligations. A parent is additionally responsible for the delegation to its direct children, the alignment of their interfaces, their reviews and the integration upward.

Root forms the integrated overall result. It does not routinely do the domain work of all children, does not skip their responsibilities and must not simply replace required child decisions with its own approval.

### 8.4 No second delegation organization

Native provider sub-agents must not bypass the modeled product organization or replace it as an additional uncontrolled hierarchy. In the agreed V1 product path, delegation runs through Markitect's Manager structure.

To be distinguished from this are the chats that develop Markitect itself: these may use sub-agents within their bounded development assignments. Development organization and product runtime are two different levels.

## 9. Collaboration within a Run

### 9.1 Local planning and shared prerequisites

Each Manager plans within its assignment. Parents settle the needed shared interfaces and prerequisites before child assignments that depend on them start. There is no separate global planning Run and no host that takes over the domain project planning.

Independent children can work in parallel. If a child needs the integrated result of a sibling, the common parent coordinates the order. A private copy that has already started does not automatically receive later parent or sibling changes live; the technical update remains a traceable operation at clear handoff boundaries.

### 9.2 Communication along the hierarchy

Delegation, questions, answers, necessary alignment and escalation follow the defined hierarchy paths. Sibling dependencies run through the common parent's responsibility instead of introducing an arbitrary direct communication organization alongside the tree.

The permitted relationships are derived from the existing topology. No additional ACL language or separately maintained routing hierarchy is required for this. The exact technical enforcement and the handling of existing divergent paths remain the subject of the requested cross-check A1.

An answer can arrive asynchronously. A waiting Manager must be able to handle incoming questions instead of blocking its communication partner permanently. The host transports and correlates messages; it does not answer domain questions itself.

### 9.3 Child handoff, review and integration

A child delivers a fixed state and the information needed to assess it. The parent reviews the actual handoff, not merely a success story. It accepts, requests a correction or escalates a material model blocker.

Accepted results are integrated upward. It should be possible to review and integrate available results without first having to wait for all siblings. Necessary dependencies or conflicts can justify a different order; they are coordinated by the responsible Manager, not by a new global host planning framework.

### 9.4 Faulty handoffs remain the parent's responsibility

Deterministic diagnostics on child states must be available to the responsible parent. It must be able to recognize whether a local correction, a shared interface clarification or later integration is required.

Local self-correction by the child remains possible. However, it must not remove the relevant parent responsibility from the flow. Visibility of an invalid state does not mean approval of its unreviewed integration. The concrete design of the information flow is cross-checked under A2; it should manage without an additional review engine.

### 9.5 Correction within the Run and correction between Runs

A return by the parent during Implement stays within the same Run. The child keeps its conversation and working state and receives the necessary Findings or the updated shared basis.

A Reject by the independent Verify, by contrast, leads to a new Implement Run. Earlier Implement conversations are not continued. These two kinds of correction must not be mixed, either technically or in reports.

## 10. Universal Run mechanism and lifecycle

### 10.1 Independent call boundary

A Run executes exactly one mandate through the Manager organization. It can be executed and tested independently of Apply. In particular, Assessment or Verify may be examined in isolation without building separate orchestration paths.

Its necessary inputs are a checked model and project binding, the derived organization, a fixed starting candidate, the mandate, optional mandatory Findings, execution and Harness configuration and finite resources.

### 10.2 Responsibility of the Run

The Run is responsible for building the environment, session and Workspace lifetime, hierarchical collaboration, handoffs, integration, required checkpoints, fixing the result, securing the candidate, cleanup and storing its actual final result.

It does not decide which Run follows next and publishes nothing into the user repository. A regular successful return must not depend, even in a standalone call, on Apply subsequently still doing essential completion work.

### 10.3 Lifecycle

```text
Valid bound Run inputs
    → prepare the Run's own environment and the Manager Harnesses
    → start the Run-local Git Workspace Service and the Managers
    → work the assignment through the complete organization
    → fix the actual handoffs and the overall result
    → secure the required candidate durably and be able to reopen it
    → close all Run resources under control
    → store the final technical and domain outcome
    → deliver the closed result to the caller
```

This is a host responsibility, not an evidence protocol to be filled in by the agent. The concrete internal division may stay small. One executor with clear helper responsibilities is sufficient; an additional cascade of lifecycle services is not prescribed.

### 10.4 Continued availability within the Run

The end of a single provider response does not automatically end the Manager session. A Manager that has already submitted remains reachable for necessary questions and corrections within the same Run. Its fixed handoff and its later communicative activities are distinguishable.

Only the completion of the Run ends the shared execution environment. Subsequent Runs receive new conversations and new working environments.

## 11. Command, Workflow and Apply

### 11.1 Command responsibility

The Command provides the named product operation. It binds inputs, triggers the initial check, owns the overall budget, calls the Workflow and handles the final Publication or the overall result.

The CLI and other later interfaces use the same application operation. The CLI parser contains no domain logic of its own. The Command implements neither Manager communication nor Git merge algorithms.

### 11.2 Workflow responsibility

A Workflow describes the order of Runs, their inputs and result handovers, branches, repetitions, success and abort. It must remain understandable and easy to compose later.

It knows no concrete containers, provider processes or Git working copies. It may validate closed Run results, but should not depend on incidental internal resource names of the runtime. The technical validity of the Run completion belongs at the authoritative Run contract boundary.

### 11.3 Apply flow

```text
Initial model and structure check
    ├─ invalid / incomplete → end without starting agents
    └─ valid
         → Assessment
             ├─ Reject / model blocker → end without Publication
             └─ Approve
                  → Implement
                      ├─ not completed / model blocker → end
                      └─ valid finished candidate
                           → Verify
                               ├─ realization Reject
                               │    → new Implement with Findings
                               │    → new Verify
                               ├─ model blocker / technical abort → end
                               └─ Approve
                                    → final checks and guards
                                    → controlled Publication
```

All iterations share the original Command budget. A new Run ID resets neither time nor message resources. The domain loop is therefore “until approval or honest abort within finite limits”, not an unbounded search for success.

### 11.4 Extensibility

The shared Run call boundary can also be used for other Commands. V1 needs neither a DSL nor a graphical Workflow system. If new mandates later have additional result or capability requirements, these are derived from an actual use case, not modeled in advance as a universal platform.

## 12. Mandates: Assessment, Implement and Verify

### 12.1 Model Assessment

Assessment checks the semantic readiness of the model, which is already structurally valid. Each Manager looks at its area and relevant interfaces. Material contradictions, necessary open decisions and ambiguities that cannot be resolved are returned with Findings.

Investigations, suitable commands and, for example, a reasoned build attempt may help. Assessment, however, implements no domain realization and does not change the canonical project intent. Helper files that arise in private checking copies are not adopted as a product change.

Missing or outdated artifacts are, in the first instance, an implementation need. An Approve means “sufficient model basis for the realization”, not “the existing product is already correct”. Such an approval does not automatically skip Implement.

### 12.2 Implement

Implement reconciles the existing realization with the model, required checks and actual Findings. Managers change the artifacts necessary for this within their responsibility, maintain their registry, delegate and integrate reviewed child results.

Necessary follow-up changes are part of fulfilling the assignment. Additional test ideas, cosmetic changes or refactorings without relation to applicable obligations are not made merely because an agent wants to produce a diff.

Implement delivers a fixed integrated candidate. It does not approve its Publication itself. If no necessary changes exist, the unchanged submission is permitted after complete division of labor, checking and review.

### 12.3 Verify

Verify is a fresh Run over exactly the candidate to be checked. The complete organization independently assesses model conformance, domain correctness, interfaces, integration, relevant tests and realization mapping.

Verify does not repair the authoritative candidate. Its own investigations and check files stay local. The result is Approve, Reject with necessary realization Findings, or a material model blocker. A Reject is a regular domain verification result and not automatically a technical failure.

### 12.4 Corrections after Verify

A realization Reject hands the model binding, the last candidate and the actual Findings to a new Implement Run. A new Verify then follows again. Neither is the old Implement organization continued, nor is its earlier self-assessment handed to the new verifier as authority.

A material model contradiction that is discovered only later, by contrast, does not lead to endless implementing against the same insufficient specification. The Command ends without Publication; the model question is settled outside.

## 13. Checking strategy and four checkpoints

### 13.1 Shared checking mechanisms

The same authoritative compiler, registry and accounting mechanisms are applied at different points to suitable fixed states. Four validators that differ slightly from each other are not built.

Cheap structural checks should take place often. This does not mean that every isolated child copy must always run the complete project test suite. The origin of a checking obligation and the sensible place to run a test are different properties.

### 13.2 The four binding checkpoints

| Checkpoint | Check and consequence |
|---|---|
| **Before the Workflow begins** | Valid model basis and applicable project structure. On error, abort before the agentic Workflow and before Run resources. |
| **At child handoffs** | Fixed handoff state, accounting and suitable change context. Diagnostic to the parent; local correction or organizational alignment within the Run. |
| **Before successful Root completion** | Integrated overall state, relevant checks and bindings. No successful Implement or unjustified Approve with unresolved technical invalidity. |
| **Before Publication** | Exactly the accepted candidate, required checks and actual source/target guards. No impermissible transfer. |

### 13.3 Intermediate states and checking mandates

Intermediate states can be incomplete as long as other children are still working. Diagnostics must make this context visible. The host should not turn every temporary incompleteness into a final Command abort.

Verify may reject a faulty candidate as a regular result. It does not have to change it to get its own completion check green. For an approval, the corresponding validity conditions remain binding.

### 13.4 No check rituals

The host establishes the required technical results and makes them available to the Managers. Managers need neither retype known identities nor produce check receipts, disputes or extensive evidence matrices in order to be allowed to continue ordinary work.

## 14. Domain assignment, message and completion

### 14.1 The basic separation

A Manager has a domain assignment. Messages, questions and answers serve to fulfill it; they are not automatically new assignments. Likewise, the end of a provider response is not automatically the domain completion of the Manager or of its Run.

A small explicit decision interface is permitted. It should make actual semantic judgments unambiguous, not steer ordinary communication through a “report first, then continue working” ritual. Free closing prose alone is no technical proof of success.

### 14.2 Validity of a judgment

A judgment must match the assignment actually worked on, its model binding and the assessed state. A new candidate, a materially changed task or new mandatory Findings must not inherit an approval that has become stale unnoticed.

A purely communicative answer, by contrast, is not in itself a new domain approval task. The concrete mechanism for invalidation and renewed decision remains to be designed technically. It must neither reuse old approvals blindly nor force an identical new decision across the board at the end of every message.

### 14.3 Decisive counterexamples

| Situation | Distinction necessary in domain terms |
|---|---|
| A question is answered | Communication is not automatically a new implementation or checking assignment. |
| An answer is still pending | Incoming questions can still be handled; no unnecessary deadlock. |
| New mandatory Findings arrive | Their effect on the assignment and on the existing judgment must become visible. |
| The assessed candidate changes | An approval of the old state does not tacitly apply to the new one. |
| A fixed handoff has taken place | Later communication must not covertly change the state already reviewed. |
| A late finding refutes an assumption | The responsible parent or Root must be able to take the consequence into account. |

### 14.4 State of elaboration

The most recently requested cross-check A3 is to clarify these cases against the actual code and tests. This document therefore prescribes neither the removal of an existing `judge` tool nor a particular new state machine. What counts is that the agent needs less technical protocol knowledge while the domain and technical results remain unambiguous.

## 15. Harness: five sources and native working environment

### 15.1 Purpose

The Harness prepares the Manager for its responsibility as one would prepare an employee: role, organization chart, area of responsibility, model context, working rules and the tools needed are reliably available. The actual assignment message stays as clear and short as possible and focused on the current work.

A Harness is not just an assembled text with a hash. It must be possible for the provider actually started to load it and use it in the container.

### 15.2 Five controlled sources

| Source | Content and responsibility |
|---|---|
| **Markitect Core** | Versioned general rules for delegation, collaboration, ownership, registry, reviews, Findings and Notes. Not to be redefined by every project. |
| **Project** | Canonical domain content, architecture, policies, quality obligations and explicitly bound project conventions. |
| **Manager** | Own role, parent, direct children, relevant colleagues, responsibilities, registry shard, interfaces and project navigation. |
| **Run** | Mandate, fixed inputs, relevant Findings, permitted effects and expected results. |
| **Provider** | Implementation through actually supported native instructions, files, skills, hooks, tools and configuration. |

Markitect defines how its organization works. The project model defines which domain and architectural world this organization is to realize. Provider adaptations do not change this meaning.

### 15.3 Reproducibility and identity

The same relevant bound inputs should produce the same effective Harness configuration. These include the product rule version, model state, Manager, mandate, provider profile and the templates or tool definitions used.

A traceable Harness identity makes it possible to establish which instructions and capabilities were actually provided. Fresh operational names, container identifiers or secrets are not an independently maintained domain truth. Deterministic generation does not mean deterministic language model behavior.

### 15.4 Context access instead of an unfiltered encyclopedia

The Manager receives a compact orientation and the context necessary for its responsibility. Binding information must be neither silently truncated nor hidden because of a token target. At the same time, not all historical notes and process descriptions should be copied into every start instruction.

Statically selected context is permitted. Content, skills or scripts that can be loaded on demand are sensible when a concrete usage or size case shows their benefit. A new general context platform is not automatically necessary for this.

### 15.5 Native forms and fallback

AGENTS.md, CLAUDE.md, native skills, hooks, tools and scripts were intended as possible provider mechanisms. Not every provider has to use every one of these forms. The most recently formulated clarification explicitly also permits native base/developer instruction parameters if they meet the requirements cleanly.

Automatically loaded repository instructions and their priority must be handled deliberately. Neither such a file nor a provider profile may override the canonical intent or the basic Markitect rules uncontrolled. Conflicts are to be detected early as far as sensible; semantically unclear conflicts must stay visible instead of being hidden by a new universal policy framework.

For unknown compatible providers, a generic AGENTS.md Harness is intended as a best-effort representation of the instructions. It replaces no executable adapter, no Manager communication and no necessary technical capabilities. An unknown agent is not supported merely because this file exists.

### 15.6 Technical boundaries stay outside mere instructions

Important invariants are checked independently of the agent's obedience: model binding, registry, fixed Git states, actual checks, resource closure and Publication preconditions. This does not justify a return to per-write file approvals or extensive evidence protocols.

## 16. Tools, providers and authentication

### 16.1 Capabilities instead of transport binding

The domain capabilities concern delegation, questions and answers, receiving child results, review decisions, relevant context information and Shared Notes. Their authoritative semantics should have one implementation each.

MCP, CLI, shell scripts or typed APIs are possible technical means of access. MCP is not a domain architecture principle. Code Mode remains a possible later optimization; V1 needs no universal execution platform of its own for it.

### 16.2 Small, understandable tools

Tools should make the work possible and not drive the host through manually produced receipts. Information that the host knows unambiguously, such as the actual Manager, the Run binding or existing commit references, should not be reconstructed unnecessarily by the language model.

An unambiguous reference to the state actually checked can be necessary for reviews. It does not follow that the agent must guess or redundantly confirm technical identities. Likewise, two similar tools for the same domain purpose should not exist side by side.

### 16.3 Provider boundary

The provider adapter starts and ends the native runtime, transfers messages, mediates tools and observes actual response and process states. It decides neither on the next Workflow stage nor, in domain terms, on model conformance.

Native protocol terms such as `turn/start` may exist within the adapter. The domain core must not derive from them productive or communicative Turns, empty-Turn classifiers or an old Pass machine.

### 16.4 Normal account login and protection of secrets

The V1 product path uses normal CLI account authentication. A Codex API-key product variant and corresponding product examples should not be carried along.

Credentials do not belong in candidates, Harness texts, Shared Notes or unprotected logs. Preparation and removal take place under control in the Manager's own environment. A fleet of short-lived auth containers for individual file operations is not adopted as the standard solution.

Supported provider, login, expiry and refresh properties each need their own evidence. A successful Codex run proves neither Claude execution nor long-term token renewal. Missing capabilities must be recognizable before support is claimed.

## 17. Containers, Git working states and durable candidates

### 17.1 Lifetime per Run

Each Manager has, per Run, its own container, its own conversation, its own Harness and its own Git working state. Within the Run these persist across delegation, questions and corrections. They are not reused between Runs.

The Git Workspace Service, too, lives exactly one Run. Future Verify or correction Runs need no volumes or working copies reserved in advance. Run resources that are no longer needed are closed under control.

### 17.2 Clear role of the Git Workspace Service

The service prepares working states, provides starting commits, fixes handoffs, supports parent-child integration and the update of child states and reports technical Git conflicts.

It is not an agent, not a general helper and not a place for domain decisions. Provider login, project checks and Workflow control are other responsibilities. A logical service responsibility does not require additional large server infrastructure.

### 17.3 Isolation and collaboration

Manager copies are independent. Parents can integrate results into their own copy after review; changes are not propagated through a shared, freely writable working directory.

The technical isolation should enable the agreed collaboration. It is no substitute for the ownership review and no assumption that every Manager works correctly in domain terms merely because of a container.

### 17.4 Workspace and candidate are different states

A Workspace is mutable and bound to the active execution. A candidate is a fixed Git state with durably available objects. Model identity, commit identity and Git tree content are different quantities and must stay appropriately bound.

Persistence must not depend on running containers, leftover temporary volumes or live Assignment objects. A verifiable reference does not replace the Git objects actually present.

### 17.5 Intended small storage solution

Self-contained Git bundles with bound metadata are the V1 approach that was discussed concretely. The normative guarantee is their independent reopening, not the bundle format as an end in itself. An equivalent simpler form would be justifiable; an additional Git server platform is not intended.

A persistence proof removes the earlier temporary working states and opens exactly the candidate in a new environment exclusively from the stored data. Subsequent Verify and Publication must not need a live reference to the producing Run.

### 17.6 Checks and remaining resources

Separate short-lived check executions are permitted if they have an isolation that is actually necessary. Final project checks before Publication can also need their own clearly owned resources; they do not continue the old Manager containers.

Uncertainty about leftover resources is reported and not concealed. An unknown leftover container is not simply deleted as a blanket measure. The exact safe treatment after a hard host abort remains a technical limit; a general recovery system is not part of V1.

## 18. Binding results and cross-Run handovers

### 18.1 Two separate kinds of result

Binding Run results determine further Workflow execution. Shared Notes preserve optional information. Both are persistent, but have different authority.

A Run result contains only the bound information actually needed: Run identity and mandate, model/project binding, input candidate, technical completion, relevant domain judgment, result candidate, mandatory Findings and necessary technical observations including actual cleanup problems.

### 18.2 No live state in the result contract

Session objects, active Manager trees and temporary Workspace handles must not be the precondition for reading or publishing a completed result. The new Run builds its working environment itself from the durable inputs.

A successful Run return requires the required storage and confirmed readability. A result that is not reliably stored does not count as successfully handed over. Failed or incomplete Runs may retain diagnosable data without feigning a successful candidate.

### 18.3 Findings as an actionable handover

A Finding should make it recognizable which obligation is affected, what was observed, what is expected and which place or reference makes the correction possible. A small understandable structure is enough; a proof matrix per Definition is not required.

The origin is determined by the actual Manager or checking mechanism. The next organization receives the necessary Findings explicitly and not hidden in an earlier chat history.

### 18.4 Consistency across Run boundaries

A new Run must not accidentally work on a candidate other than the referenced one. Approval and candidate must match. A new model basis does not automatically make earlier bindings valid.

Fresh conversations do not mean that the product loses its memory: the continuity that is necessary in domain terms arises through model, candidates, results and Notes. That continuity specifically does not mean replaying the entire old conversation context.

## 19. Shared Notes, focus and independent verification

### 19.1 Shared Notes are part of V1

Managers can durably record side findings, improvement suggestions, test gaps and helpful insights. Notes survive Runs and Commands within the respective project. A new personal long-term memory for each Manager is not necessary for this.

Every Note has understandable content as well as traceable origin and context, such as Run, Manager, affected area and suitable references. Storage must not overwrite notes of competing writers unnoticed.

### 19.2 No automatic authority

A Note is not a delegation, not a new model obligation and not a ticket to be executed automatically. It bypasses neither the Manager hierarchy nor a review. A Manager should be able to file an optional observation and then return to the actual task.

Conversely, mandatory problems must not be moved into Notes merely to make an approval possible. What is decisive is their meaning for the current mandate, not the place of filing chosen by the agent.

### 19.3 Bounded and usable access

Notes are not copied wholesale into every start prompt. They must remain readable when needed, even if their number grows over many Commands. Storage and transport limits must fit together.

The most recently formulated cross-check R2 therefore concerns bounded retrieval without silent truncation or data loss. Pagination, context filters or references are possible means, but not yet a fixed new API. A vector database, semantic search or automatic prioritization is not required for this guarantee.

### 19.4 Verify independence

Verify receives the valid model, the exact candidate and the required technical information. It takes over neither the implementation conversations nor their self-assessment as domain authority. Notes marked with their origin may provide hints, but must not determine the truth about the candidate in advance.

Independent external oracles and their hidden expectations are not delivered to implementers. Agent-produced tests can be useful, but do not on their own replace the independent proof of domain quality.

## 20. Errors, budgets and controlled termination

### 20.1 Domain and technical results

| Outcome | Meaning and consequence |
|---|---|
| **Domain-accepted** | The mandate was judged positively within the appropriate scope. Usable only together with a valid technical completion. |
| **Realization Reject** | The realization violates requirements; actual Findings make a correction possible. |
| **Model blocker** | The firmly bound intent is materially insufficient or contradictory; no endless repair attempt in the code. |
| **Failed** | An actual error prevents the required execution. Not an ordinary domain Reject. |
| **Incomplete** | A complete or reliable completion cannot be established, for example on timeout, abort or uncertain cleanup. |

The exact naming of status values is an implementation detail. Their meanings must not be mixed. A completed verification Run can reject as a regular result; a positive agent claim cannot heal a transport or storage error.

### 20.2 Shared finite resources

The Command sets a finite overall budget. New Runs and Verify corrections create no new budget. The Run receives the bounded resource it needs for this and consumes it without knowing the overarching composition.

Per-message limits can bound technical calls, but do not replace the domain completion contract. Message or time budgets should not be raised across the board to cover up a deadlock or protocol error that is not understood.

### 20.3 Deadline down to the operation that actually blocks

Cancellation and deadlines must reach the controlled subprocesses, in particular in Git, guard and Publication paths. An outer deadline check is not sufficient if an inner process keeps running without bound.

Cleanup and final persistence can receive a separate small finite grace bound in order to secure diagnosable results even after an abort. This grace period permits no new domain work and no hidden extension of the actual assignment resources.

### 20.4 Honest cleanup

It must be possible to return and close partially started resources as far as technically available. An unclear completion is stored as unclear. A later empty container list must not retroactively turn an individual closure proof that failed earlier into success.

Ordinary error paths should clean up resources reliably. This does not claim a guarantee of being able to end everything immediately on any kernel, file system or host failure. Unqualified limits stay explicitly visible.

## 21. Controlled Publication

### 21.1 Approval of the exact candidate

Publication consumes a durably stored candidate and its stored, bound Verify approval. Implement must not approve its result for publication itself. An approval of candidate A does not automatically apply to a candidate B that differs from it.

Before the transfer, the stored bindings and required checks are checked again. All previous Run resources are closed; the publisher starts no domain Manager coordination.

### 21.2 User changes and conflicts

The actual target state must match the bound starting situation. User changes made in the meantime must not be overwritten blindly. For V1, a clear conflict outcome is the accepted simplification compared with an automatically invented semantic merge.

If a later function produces a merge that differs from the checked candidate, it needs explicit renewed checking semantics. The last deterministic check does not replace independent domain approval of new content.

### 21.3 Partial transfer and readback

A multi-file transfer is not automatically a completely atomic transaction merely because it is called Publication. The actual extent of changes already completed must remain recognizable on error or abort. Changes still pending must not appear as transferred.

The final readback confirms the content actually published. An error at this boundary must be reported neither as a successful transfer nor as a supposedly unchanged state. Blind rollback under possible user drift is not an automatically safe substitute.

### 21.4 No automatic user commit

Publication creates no automatic commit, push, release or deployment in the user project. Private Git commits that freeze candidates and internal development PRs while building Markitect are separate operations.

No-change, too, goes through the necessary binding and target checks. The correct result then contains no unjustified published changes.

## 22. Logical target architecture and dependencies

### 22.1 Responsibilities instead of mandatory packages

| Responsibility | Task | Explicitly not part of it |
|---|---|---|
| **Model / Project State** | Model compilation, registry, accounting, snapshots, organization and context. | Provider start, Workflow or publication. |
| **Project preparation** | Capture explicit inputs and combine them into a checked, fixed execution basis. | A second compiler or the old runtime as a precondition. |
| **Command application** | Initial check, budget, Workflow and final overall result. | Own Manager communication or Git merge logic. |
| **Workflow** | Coordinate Runs and their domain transitions. | Containers, provider protocols or concrete resource management. |
| **Run execution** | One mandate through the organization, including the complete lifecycle and the result. | Choosing the next Run or publishing into the user repository. |
| **Harness** | Compose controlled rules, context and working tools. | Git integration or domain Workflow decisions. |
| **Workspace / Candidate Storage** | Mutable private copies and independent durable candidates. | Domain review decisions or a general helper. |
| **Run Information** | Store and provide binding results and separate Notes. | Creating tasks automatically from Notes. |
| **Publication** | Transfer the exact accepted state under control. | Domain repair or starting agents. |
| **Infrastructure adapters** | Providers, containers, Git, checks, file system and technical interfaces. | Definition of the project domain. |

A logical area of responsibility is not automatically a Go package, interface, service or container. The concrete cut follows cohesion, real consumers and reasoned infrastructure boundaries.

### 22.2 Dependency direction

```text
CLI / other entry point
    → Command application
         → project preparation and deterministic foundation
         → Workflow
              → Run contract and Run execution
                   → model organization and Harness
                   → required Workspace, session, check and storage contracts
         → Publication

Concrete infrastructure adapters implement the required boundaries.
Composition lies at the outer application edge.
```

The compiler knows neither Docker nor Codex or Claude. The Run does not know the Apply correction loop. The Workflow implements no Manager coordination. Provider details stay out of the domain organization. The shared check of durable Run results belongs at one unambiguous authoritative boundary, not in several competing validators.

### 22.3 Domain, application and infrastructure

The distinction between Domain, Application and Infrastructure is a logical orientation, not an obligation to break every small feature down into three artificial file groups. Narrow interfaces arise where a dependency actually has to be separated.

A universal repository, event, policy or Workflow framework is not introduced merely to comply with a pattern. Likewise, old package names are neither preserved automatically nor replaced merely for cosmetic reasons.

## 23. Architectural quality and handling of existing code

### 23.1 Protected knowledge, replaceable implementation

Model language, compiler semantics and relevant deterministic guarantees are the foundation worth preserving. The historical agentic execution architecture has no protection as existing code.

For affected components, the classification Keep, Refactor, Replace or Remove applies. What is decisive is responsibility, coupling, understandability, testability and required behavior, not working time already invested.

### 23.2 No forced reuse

Additional adapters only for old internal APIs, permanent compatibility layers, competing runtime paths and special cases for preserving excluded consumers are not an acceptable default strategy.

The guiding question remains: **Would we also design this building block in this form if the earlier runtime did not exist?** A clean Git helper function can pass the question; an unsuitable old orchestration cannot pass it merely through existing tests.

### 23.3 No rewrite as a reflex

The original D8 decision permitted a selective rebuild. Once the new core has been built, this creates no obligation to discard everything again with every new Finding. The current need for correction is assessed on the basis of demonstrated contract and reliability problems.

A large file is a possible hint of overloaded responsibility, but not an automatic defect. Distributing state complexity that is not understood across additional files would not be a substantial improvement. First the semantics must become clear.

### 23.4 Active documentation

The canonical self-model, registry shards, generated documentation and the actual responsibilities are kept consistent together. Active entry documents contain applicable rules instead of a confusing sequence of contradictory historical work orders.

Historical insights and failed attempts remain traceably archived. They are not deleted, but neither do they become binding again merely through their proximity to the current plan.

## 24. Development organization and change process

### 24.1 Coordinator and separate implementation chats

The implementation of Markitect is organized by a Coordinator. It is responsible for architecture, dependencies, assignments, integration order and quality control. It is not an additional competing writer in the files of other chats.

Implementation chats work in their own worktrees and branches with an exact starting commit, unambiguous write responsibility and verifiable acceptance criteria. Shared contracts, registry shards and generated files have one responsible writer at any one time. Sub-agents must not bypass this boundary.

### 24.2 Parallelism according to actual decoupling

Few writing workstreams at first, at most two at the same time in the clarified planning, keep integration manageable. Read-only analysis and independent reviews can take place in parallel. The number of chats is not a productivity goal.

Dependent implementation starts only when the shared contracts needed are sufficiently clear. No large interface hierarchy without consumers is produced in advance. Early complete vertical proofs should test central assumptions before many further components build on them.

### 24.3 Review and integration

Substantial changes need an independent complete diff review. Checks and approval refer to the commit that can actually be integrated. Changes after the review need an appropriate renewed check; tests of a different state are not a current approval.

After larger integration steps, the overall architecture is checked as well. Clean individual PRs do not yet guarantee a coherent composition. Historical work or the work of others is neither silently discarded nor overwritten by a reset.

### 24.4 Decision and execution authority

Routine decisions within approved limits can be delegated. Changes to product semantics, significant architecture conflicts and final owner acceptance must be handled explicitly.

Real proofs need valid, bounded execution authority. In the conversation, a standing approval was granted for useful proofs; it does not replace source binding, resource limits, abort conditions and honest results. This concept extends no existing authorization. Release and deployment remain separate decisions.

### 24.5 Fresh Coordinator generations

Long development chats can be archived after a controlled handoff. The new Coordinator takes over the actual repository and evidence state, not the entire old conversation history.

A handoff names Main, open local work, confirmed evidence, limitations and the next bounded tasks. Worktrees, branches and historical results are handled deliberately; archiving a chat is not deleting the technical project state.

## 25. Acceptance and validation concept

### 25.1 Separate kinds of evidence

| Kind of evidence | What it shows | What it does not automatically show |
|---|---|---|
| Static code/architecture check | Actual responsibilities and recognizable contract violations. | Real runtime behavior, freedom from races or provider obedience. |
| Deterministic unit/integration tests | Behavior of the tested cases on the fixed code. | Complete native integration or freedom from errors of any kind. |
| Controlled sessions with real Git | Interplay of executor, candidates, reviews and error paths. | That a real provider serves the same flow reliably. |
| Native component check | A concrete provider capability or Run chain. | Public Workflow selection and Publication outside the checked path. |
| Public native Apply | The actual product path on the named model, candidate and runtime profile. | Universal reliability, other providers or arbitrary project sizes. |
| Independent domain oracle | Behavior of the candidate actually produced against independent expectations. | Untested properties or operational migrations. |
| Owner acceptance | Deliberate acceptance of a clearly bounded product scope. | Automatic release or deployment approval. |

### 25.2 Architectural acceptance criteria

| ID | Required evidence |
|---|---|
| **V01** | An invalid model or initial structure prevents the agentic Workflow. |
| **V02** | The complete required hierarchy works in Assessment, Implement and Verify, including grandchild, intermediate and empty Package. |
| **V03** | Parallel child work and communication along permitted hierarchy paths work, including crossed questions and abort. |
| **V04** | Review and integration concern exactly the actual task basis and the fixed handoff. |
| **V05** | Child diagnostics are usable at the parent; Root cannot complete unresolved technical invalidity as success. |
| **V06** | A Verify Reject produces new Implement and Verify Runs without old conversations or a reset overall budget. |
| **V07** | Material model blockers recognized late end without Publication and without endless code repair. |
| **V08** | Candidates can be reopened exactly after the old temporary environments have been removed. |
| **V09** | Standalone Runs deliver persisted actual final results; storage and cleanup errors stay visible. |
| **V10** | A reproducible Harness is used natively; short tasks, mandatory context, normal account authentication and no API-key product variant. |
| **V11** | Notes survive Runs/Commands, lose no entries under parallel access and do not extend the assignment automatically. |
| **V12** | Fresh Library, M1→M2 with limit value 5→3, preservation, strict no-change and independent oracle. |
| **V13** | A seeded defect is detected and, after correction, checked again independently; an ordinary Implement fix and a genuine Verify-Reject branch stay distinguishable. |
| **V14** | Own changes, the responsibility of others and accepted child integration are reviewed appropriately. |
| **V15** | Publication binds stored approval and candidate, handles drift and reports partial transfer and readback errors correctly. |
| **V16** | Timeout, provider error, budget exhaustion, start error and uncertain cleanup produce no false successes. |

The most recent audit test cases refine V03, V05, V10, V11 and V16. Their technical implementation is determined only after the requested cross-check; they are not a new general governance system.

### 25.3 Final state and repeatability

Relevant complete local tests, architecture and dependency gates, Linux/Windows compatibility, race checks and approved hosted CI are evidenced on the cleaned final state. Native evidence names provider, version, runtime, candidate and concrete limits.

The number of independent repetitions is set with a reason. Neither an arbitrary number of green runs nor uncontrolled repetition until the first success replaces a sensible reliability assessment. Earlier successes remain valuable, but do not qualify changed contracts without a check of their impact.

### 25.4 Quality is more than a green example

A Library demonstration should test the idea concretely, not replace the entire product definition. Acceptance additionally assesses understandability, cohesion, state complexity, extensibility within the target picture and the honest support boundary.

A bounded first Codex V1 can be assessed differently from a fully cross-provider product version. Capabilities that do not exist or are unqualified, such as further providers, login renewal, hard host aborts or live data migration, must not be implicitly promised by a general V1 label.

## 26. Reference scenarios

### 26.1 Fresh realization

The valid Library model contains domain obligations, responsibilities and necessary checks, but no complete realization yet. The initial check establishes structural validity. Assessment checks feasibility. Implement produces and registers the necessary artifacts. Verify checks independently, and only then does Publication take place. The external oracle assesses the actual candidate outside the Manager context.

### 26.2 Targeted change from five to three loans

The starting point is an already valid realization A1. In the canonical model M2, only the loan limit is changed from five to three. Markitect produces a correspondingly adjusted realization A2 and preserves the other obligations.

Which concrete files must change is not arbitrarily limited to a fixed number. What is decisive is that every change is justified by the model, required checks or necessary consequences. A migration of existing runtime data that may be necessary is a separate requirement and is not proven by new behavior tests alone.

### 26.3 No-change

An unchanged model that is applied again meets a conforming realization. All required mandates and reviews remain in effect. Optional improvement ideas end up in Notes. The result contains no unjustified artifact change and no artificially produced work merely to deliver a visible diff.

### 26.4 Faulty child handoff

A child delivers a new artifact without a valid registry entry or with an interface problem. The deterministic check delivers the actual diagnostic. The parent can recognize whether local registry maintenance, a shared decision or a different integration order is needed.

The child may repair locally; the parent remains responsible for the coordination. The system does not publish merely because an agent writes “done”, nor does it start an additional global repair Workflow for an ordinary local error.

### 26.5 Genuine Verify correction loop

Verify discovers a necessary realization defect in the fixed Implement candidate and returns Reject with Findings. The public Workflow selects a new Implement Run with fresh conversations and then a new Verify. Only that Verify's approval can carry the Publication of the corrected candidate.

A repair that already takes place in the first Implement is a different scenario. Likewise, a manually chained component check does not by itself prove that the public Workflow selects the right branch.

### 26.6 User change during Apply

While the Managers work in isolation, the user changes the target repository. The final guards detect relevant divergences. V1 ends with a recognizable conflict instead of overwriting blindly or presenting an unchecked merge as the candidate accepted earlier.

### 26.7 Abort during Publication

A controlled Git call blocks while the available execution deadline expires. The deadline reaches the subprocess. No further domain work is started; completed file paths are reported correctly, incomplete readbacks are not counted as success. The test must actually reach the blocking call and observe its outcome.

## 28. Open elaborations and audit limits

### 28.1 No automatic adoption of audit demands

The concept conformance audit [Q3] is a static check of a fixed source state. The request [Q4] formulated from it demands an independent cross-check before domain contract changes are implemented. The existing target concept remains authoritative; the exact solution proposal is not decided by this audit alone.

| Topic | Fixed goal | Still to be elaborated or confirmed |
|---|---|---|
| **A1 – Communication structure** | Coordination along the defined model hierarchy. | Reconcile the actual permission rules and a possible later owner clarification with the code; smallest consistent enforcement. |
| **A2 – Child diagnostics** | The parent can assess and coordinate faulty handoffs. | Combine visibility with possible local self-correction, without invalid integration or a new review engine. |
| **A3 – Completion semantics** | Message, active assignment and valid judgment are distinguishable. | Check counterexamples and eliminate unnecessary per-message rituals without using stale approval. |
| **A4 – Harness** | Five sources, real native use, sensible context and available working tools. | Assess instruction injection deliberately; add on-demand loading or skills only on demonstrated need. |
| **A5 – Workflow/Run boundary** | The Workflow coordinates closed Runs without technical resource management. | Assign the shared result validation coherently; no cosmetic restructuring. |
| **A6 – Further mandates** | The same mechanism remains reusable. | Extension only on the basis of an actual later Command; no current DSL commission. |

| **R2 – Notes/transport limits** | Stored Notes remain retrievable in bounded form and without silent truncation. | Reproduce the size conflict under control, then choose the smallest read interface. |
| **R3 – State complexity** | Understandable, coherent execution without unnecessary host micromanagement. | Check synchronization and completion states on the basis of concrete risks, not declare them defective across the board. |

### 28.2 Current direction of work

The most recent direction of work is cross-checking and targeted stabilization, not designing a large agent platform anew. Corrections already under way are taken into account so that no competing implementations arise.

After confirmed necessary changes, appropriate regressions, an independent complete diff review, integration and evidence on the final state actually affected follow. The remaining public native correction chain is to be distinguished from component results that have already succeeded.

### 28.3 Open acceptance decisions

Before formal acceptance, the actual provider scope, relevant runtime limits, necessary repetition evidence and remaining known limitations must be recorded explicitly. A clean final state can be accepted with limits without promising universal reliability or capabilities that are not implemented.

This chapter is a separate working state. It does not secretly change the target in sections 2–25 and must not, after later code changes, be reproduced unchecked as the current error status.
