# Claude projection workstream

## Context

Start from the full verified preparation integration SHA supplied in the assignment, as defined by [Baseline](../development/baseline.md). PR 59's `e9550f5` is the source audit base only; it omits these preparation contracts and is not the dispatch baseline.

At the PR 59 integrated baseline (`e9550f5c91430c6a65cbbd4ffcdbb49b48272537`), Claude files are generated by Markitect's built-in provider renderer. They consume the validated graph and captured files directly, not the external command `SemanticModel` DTO. Shared assumptions are owned by [the shared adapter contracts](../development/shared-contracts.md).

## Objective

Maintain or prepare bounded changes to the built-in Claude projection with explicit target selection, canonical ownership, deterministic output, and honest limits on what generated instructions establish.

## Scope

Claude-native Skill, Agent and mapped Rule outputs, shared Claude entrypoints/settings, strict inventory, and focused tests. A separate integration with an external Claude-related service must be treated as a command adapter workstream with its own target and lifecycle design.

## Current implementation

`internal/render/render.go` selects the `claude` target and dispatches resource types. Claude Agent, Skill and Rule files are generated in provider-specific helpers. `Project.spec.providerAdapters` configures shared entrypoints, `ruleSources`, retired names and strict inventory; validation occurs in `internal/app/outputs_provider.go`. The built-in renderer uses graph/file inputs and shares output ownership, path collision and local reconciliation code with other targets.

## Owned subsystem

Claude-specific templates, format helpers and isolated tests may be separately owned. `render.go`, common path/ownership helpers, shared Agent text/navigation behavior, `provider_adapters.go`, `rules.go`, output inventory and reconciliation are shared hotspots owned jointly with the renderer coordinator and Docs/Codex workstreams.

## Allowed changes

- Change Claude-only templates/settings and add focused output/inventory tests in owned files.
- Add explicit Claude fixtures to verify direct links to canonical resources or declared source files.
- Propose new Claude paths only with explicit owner, collision, retirement and inventory behavior.
- Explore remote Claude integration via a separate command adapter, initially read-only with an explicitly disjoint target.

## Forbidden changes

- Do not treat generated Codex or Markdown files as canonical policy or dependencies.
- Do not add provider-specific Core fields solely for a Claude projection.
- Do not change shared Agent behavior, Rule aggregation, dispatch, output ownership or inventory without coordinator review.
- Do not silently remove retired files, publish remotely, or add writes to observation/plan/verify commands.

## Dependencies

Depends on existing Agent/Skill/Rule Domain data, `Project.spec.targets`, `spec.ruleAdapters`, `spec.providerAdapters`, and shared output/inventory contracts. Shared changes require coordination with other native renderer workstreams and [shared adapter contracts](../development/shared-contracts.md).

## Design questions

- Is this a built-in local projection or a distinct remote command adapter?
- Who owns each aggregate Rule output: its explicit Project mapping and source list, or a single resource?
- Does strict inventory include all generated paths and retired names for the selected target?
- Are inline text and navigation changes source-relative and preserving canonical typed links?
- Does evidence describe configured output only, without claiming runtime behavior or authorization?

## Required tests

Test target gating, deterministic Claude output, explicit rule mappings/source requirements, role/shared-entrypoint selection, source-relative navigation, output collisions, strict inventory, and retired-file diagnostics as applicable. Remote command integrations need independent observe/plan/verify and target-scope tests; write behavior requires separate design.

## Required evidence

Record source revision, selected Claude target and mappings, canonical resource/source digests, generated path/hash inventory, collision/retired/unregistered findings, and tests. Remote work also records exact target identity, executable hash and declared version, observation scope, and limitations; the hash alone does not authenticate provenance.

## Exit criteria

Claude outputs remain direct projections from canonical resources or explicitly declared original files, with explicit ownership and deterministic inventory. Shared renderer changes are coordinator-reviewed and tests do not overstate runtime behavior.

## Completion questions

- Are all outputs covered by explicit mappings or resource ownership?
- Are changes isolated to Claude behavior where claimed?
- Were shared render, Rule aggregation, navigation, or inventory hotspots coordinated?
