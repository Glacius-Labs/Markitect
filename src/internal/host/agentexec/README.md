# External agent execution boundary

agentexec is a provider-neutral Host subprocess boundary for one Executor, Verifier, or inference proposal. It accepts an explicit Request, computes a deterministic request digest, adds a separate random run ID and nonce, sends one versioned JSON invocation over stdin, closes stdin, and accepts only a response that echoes the role, run ID, nonce, and request digest.

Run accepts optional audited input roots and requires a private log directory. It creates a new empty directory with os.MkdirTemp outside any selected roots, runs a literal executable and argv without shell interpretation, and removes the temporary directory after one invocation. On Windows, new private log directories are created with a protected DACL granting full control only to the current user SID; the directory and each produced log file are checked before private output is read. Existing Windows log directories must already have a protected owner-only DACL or Run refuses them without changing their ACL. POSIX keeps the existing 0700 directory mode behavior. These controls do not protect against other processes running as the same user, local administrators, or SYSTEM. When roots are supplied, it hashes regular files, entry names, modes, timestamps, and symlink targets before and after the process. A changed or unreadable selected root invalidates the result. An empty root list causes no repository or adopter-root acquisition and makes no input-tree mutation claim; the runner never discovers a repository root itself. This audit detects observed changes; it does not claim operating-system isolation or prevent access through the process's local authority.

Linux cleanup terminates the runner's original process group. A descendant that deliberately starts a new session or moves to another process group can escape that cleanup. This process-group lifecycle control is not full descendant containment; Windows uses a Job Object for its process cleanup.

The request bounds context to 8 MiB, scopes and policies to 128 IDs each, artifacts to 128 files and 16 MiB total, and serialized JSON to 32 MiB. The response protocol rejects duplicate JSON keys and case-colliding protocol field names, unknown fields, response-role reuse, digest mismatch, invalid outcomes, duplicate or non-portable candidate paths, invalid UTF-8, and candidate data beyond 8 MiB. Opaque `candidateJson` property names retain their exact case. Candidate file allowlists and protected source paths remain the caller's responsibility.

Configuration records the selected command, argv, model, JSON model options, provider version, timeout, output limits, and explicit absolute runtime-file paths, digests, and modes. `EnvironmentAllowlist == nil` preserves historical inheritance of the caller environment. A non-nil pointer selects only the listed caller environment names, and a non-nil empty list selects none; new Project execution flows must pass a non-nil list. agentexec then adds its two private protocol variables. The effective inherited values are bound into a SHA-256 environment digest in the receipt and configuration fingerprint; values are never copied into the receipt or public diagnostics. Allowlisting controls which environment values the child inherits; it does not prevent same-user access to OS-managed credentials or network resources.

The receipt binds the recorded configuration and hashes the actual command executable and declared runtime files. Runtime files have a 512 MiB combined limit and are fingerprinted with bounded streaming reads so a native Codex executable can be bound alongside its wrapper; runtime bytes are identity inputs, not project evidence or agent context. The command executable is rechecked after execution, so a persistent change or removal invalidates the result. This pre/post check does not prove which bytes the operating system loaded if the executable path is replaced and restored between checks. The caller supplies the provider-version claim; a wrapper may check it against the external CLI. Every receipt has retry count zero. Usage is included only when supplied as provider-reported telemetry.

`Fingerprint` returns the same normalized configuration digest recorded in a run receipt without starting the configured process. It binds normalized command and arguments, explicit model/provider options, the resolved executable bytes, and every declared runtime file's path, mode, and digest. A Host can compare this identity while preparing a saved plan and again before a later operation without invoking another agent.

Executor responses can propose candidate files or an optional typed task report in `reportJson`; a proposed response must contain at least one of those. `reportJson` must be one bounded canonical JSON object and is rejected for Verifier and inference roles. A caller that declares a task-specific `context.responseSchema` remains responsible for checking that object against its exact task contract. `candidateJson` remains inference-only. Verifier responses cannot include candidate files or inference JSON and must provide observations for a pass or failure. A verifier call is a separate process with a separate request; callers must construct its context explicitly and supply any candidate bytes as artifacts. The package performs no automatic live writes.

Both bundled provider adapters constrain the response identity fields to the exact invocation. For provider-facing `evidenceRefs`, they derive a sorted, unique set of request-supplied scopes, policies and artifact paths and publish a deterministic, collision-free mapping to short aliases. The provider schema permits those aliases; the adapter decodes only that outer field back to the original canonical references, preserving order and count. Unknown, duplicate, malformed or raw canonical selections are rejected. Empty mappings require `[]`. Because a Verifier must return the complete reference union and Host responses permit at most 128 evidence references, adapters reject Verifier requests exceeding that combined unique limit before starting the provider. Model identities, report groundings and verifier observation subjects retain their original representation. This transport encoding does not add evidence or repair an invalid selection; the Host still validates the canonical response.

## Codex adapter

The standalone adapter under internal/tooling/codexrunner adapts this protocol to codex exec. The caller provides the Python executable and absolute wrapper script as Config.Command and Config.Args, and lists the script in Config.RuntimeFiles with its selected digest and mode. The Codex CLI executable and optional Node entrypoint are explicit adapter arguments; no shell launcher or implicit shim discovery is used. The configured version is checked by running the selected executable with --version.

The adapter invokes Codex with --ignore-user-config, --sandbox read-only, --ephemeral, --json, --skip-git-repo-check, and --disable plugins, an output schema, an output-last-message file, the fresh working directory, and stdin prompt -. It does not change global Codex settings or authentication. Model output is candidate evidence, not acceptance. The adapter writes Codex JSONL events and stderr into the caller-selected private sidecar path with restrictive file mode, parses tool events and usage fields, and returns only the validated final response plus provider-reported counts.

The Codex CLI runs under the caller's local authority. --sandbox read-only is a Codex policy setting, not an operating-system sandbox assertion made by Markitect. No model is given executor conversation history during verification.

## Claude Code adapter

The standalone adapter under internal/tooling/clauderunner accepts the same closed invocation and returns schema-validated Claude `structured_output`. It uses a direct absolute Claude CLI path and exact configured version, requires Claude Code v2.1.248 or newer, passes the explicit model and supported `effort` option as literal argv, and does not edit global provider configuration. The CLI starts in restricted, no-built-in-tools, no-MCP, no-session-persistence print mode. Provider stdout and stderr are written only to the private sidecar. Provider CLI controls are not OS isolation; a strict isolated run must remain blocked until a host-managed launcher verifies isolation.
